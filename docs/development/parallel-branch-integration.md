# 并行开发与主线整合

本仓库采用“独立工作树并行开发、单一整合者串行更新主线”。线程中的 Git
操作共享同一个仓库和分支引用；工作树隔离不能阻止其他线程改写 `master`。

## 分支与整合职责

- 每条开发线程使用自己的工作树和 `codex/*` 分支，只在自己的工作树提交。
- 开发线程不更新、切换、重置或推送其他工作树的 `master`，包括快进合并。
- 同一时间只有一条由用户指定的整合线程可以更新和发布 `master`。
- 其他线程继续开发或等待交接；涉及同一源码、清单的修改先明确分工。
- 单头文件、features 和 API 索引按规范源码重新生成，不手工拼接生成结果。

## 开发线程交接

先将本线程已经完成的工作提交到自己的分支。未完成的修改保留在该工作树，
并在交接中明确列出；不替其他线程暂存、提交、stash、清理或切换分支。

```powershell
git fetch github
git merge github/master
# 解决冲突，重新生成受影响的派生文件，并运行对应检查。
git push github HEAD:refs/heads/codex/<本线程分支>
```

通过 PR 或明确的分支 tip 交给整合者。交接必须带上已验证的完整提交 SHA、
测试结果和仍未提交的范围。代码冲突需要按双方行为解决，不能用整文件覆盖
或空合并冒充功能整合。

## 整合线程发布

1. 获取两个远端的最新引用，并确认本地主线工作树干净。
2. 从最新主线建立临时整合分支，合入交接的提交，保留已有主线历史。
3. 重新生成受影响的派生文件，运行有意义的回归；区分新增失败和可复现的
   原主线失败，并如实记录，不能用跳过检查制造全绿结果。
4. 发布前再次获取主线，确认待发布提交包含最新远端主线和所有交接 tip。
5. 只使用普通推送或 GitHub 的合并操作。推送遭到非快进拒绝时，重新获取、
   合并、验证后再发布；禁止 `--force`、`--force-with-lease`、`+master`
   refspec，以及通过 API 把主线直接改到另一条历史。
6. 发布后核对远端 SHA 与祖先关系。本地 `master` 只通过快进同步已发布结果。
7. 分支清理前验证其 tip 仍可达主线；未提交工作所在的分支和工作树继续保留。

`git merge --ff-only` 只作用于所执行仓库的本地引用，不会自行更新远端。
本地与远端状态需要分别核对。

## 当前远端约定

- `github`：`https://github.com/xywhsoft/xrt.git`，用于 PR 和 GitHub Actions。
- `origin`：`https://gitee.com/xywhsoft/xrt`，主线镜像。
- 每次主线整合完成后，两个远端的 `master` 与本地 `master` 应指向同一提交。
- 两个远端暂时分叉时，整合双方历史后以普通推送同步；不能以其中一个远端
  的旧 tip 强制覆盖另一个远端。
- GitHub `master` 禁止强制推送和删除，保护规则也适用于管理员。

根目录 `AGENTS.md` 按本仓库现有忽略规则作为本地代理说明；在各工作树中
读取本文件执行上述约定。本文件是版本化的共同规则来源。
