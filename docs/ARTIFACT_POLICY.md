# 仓库资产策略

本策略区分发布契约、可再生发布资产、临时构建产物和历史归档。CI 只把前两类视为仓库完整性的硬条件；Git 历史承担长期追溯职责。

## 发布契约资产

公共头文件、内部构建头、正式源码、模块清单、活动测试、示例和发布文档属于发布契约。它们必须登记在产品模块清单中，路径必须存在；有意删除时必须在同一变更中更新模块依赖、测试、文档和发布状态。

`tools/check_release_maturity.py` 是这类资产的统一门禁。核心产品和每个扩展产品都必须独立通过检查。

## 可再生发布资产

`single/xrt.h`、`single/xrt_decl.h`、扩展单头与声明头、特性头、API reference 和示例索引虽然可以生成，但属于直接交付给使用方的 checkout-ready 产物，因此继续纳入版本控制。

修改其输入后必须运行相应生成器并提交结果。CI 使用 `--check` 做逐字节一致性验证，不自动提交生成结果。生成或校验命令见[构建与发布](BUILD.md)。

## 临时构建产物

对象文件、可执行文件、缓存、`out/`、`release/` 中的本机构建结果和诊断日志不属于发布契约。它们不得被 Metadata 门禁要求存在，也不得用来代替从干净 checkout 重建的证据。

## 历史归档

`archive/` 下的旧实现可以为人工研究保留，但不得登记进正式模块清单，也不得成为构建、测试、单头或发布成熟度的前置条件。删除归档内容不应导致 Metadata 失败。

需要长期记录重大移除时，优先保留简短的 tombstone，而不是复制完整历史源码。tombstone 至少应记录组件名、删除提交、原因、替代接口和最后可用 tag；完整内容由 Git 历史保存。

## 有意删除流程

1. 从模块清单和依赖闭包删除或替换正式资产。
2. 更新受影响的测试、示例、文档和发布状态。
3. 重新生成所有受影响的单头、声明头、特性头和参考文档。
4. 运行核心与扩展 Metadata 检查，并审阅生成 diff。
5. 若删除的是归档，只需确认它未被正式模块清单引用。
