# X.509 解析

`x509_parse` 是证书体系的零分配底层。它严格解析一张完整 DER 证书，同时公开 AlgorithmIdentifier、时间、Name、Extension 和 SubjectPublicKeyInfo 的借用视图。身份匹配、用途扩展、签名、路径、信任库和 CRL 由独立裁剪层建立在这些视图之上。

## 裁剪

```c
#define XRT_FEATURE_X509_PARSE
#define XRT_FEATURE_ASN1_DER
#define XRT_FEATURE_TIME
```

模块只依赖严格 DER 和 UTC 日历时间，不依赖加密、PEM、文件或网络。解析有效证书时不分配内存；输入必须在所有证书及其子视图使用完之前保持有效。

## 证书视图

```c
xx509cert cert;

if ( xrtX509Parse(der, der_size, &cert) ) {
	/* cert.Raw、Tbs、Issuer、Subject、SPKI 等都借用 der。 */
}
```

`xx509cert` 保留：

- 完整证书和 TBSCertificate；
- 自然编号的 v1、v2、v3 版本和规范 DER INTEGER 的完整序列号内容；
- TBS 与外层 AlgorithmIdentifier；
- Issuer、Subject 与 SubjectPublicKeyInfo 的完整 DER；
- 转换为 `xtime` 的 NotBefore 和 NotAfter；
- 可选唯一标识、扩展序列和不含 unused-bit 字节的签名。

解析器要求输入恰好是一张完整规范 DER 证书。它检查字段数量和顺序、显式默认版本、序列号 INTEGER 的规范编码、Issuer 非空、时间编码与真实日历、NotAfter 顺序、SPKI 结构、可选字段版本约束、扩展正文 DER、重复扩展 OID、TBS/外层签名算法一致和签名 BIT STRING。空 Subject 只允许与非空且 critical 的 SAN 同时出现。

`Serial` 借用 INTEGER 的完整内容八位组，不去掉正数符号补零，也不把负数转换为无符号幅值。RFC 5280 要求符合规范的 CA 使用正数且不超过 20 个内容八位组，但同时要求证书使用方妥善处理负数或零；现实系统根库中也存在零序列号信任锚。因此消费侧解析器接受所有规范 DER INTEGER，包括零、负数和历史超长值，并使证书与 AKI 能按相同字节语义精确匹配。签发器或合规检查器应单独执行 CA 侧约束。

```c
bool valid = xrtX509ValidAt(&cert, xrtNow());
```

有效期使用闭区间。参数合法时，过期或尚未生效只是 `false`，不伪装成运行错误。

## AlgorithmIdentifier

```c
xx509algorithm algorithm;
xrtX509AlgorithmParse(der_view, &algorithm);
```

`Oid` 是 OBJECT IDENTIFIER 的内容八位组；`Parameters` 在存在时保存完整参数 TLV，因而未知算法和未来参数不会丢失。结构层接受未知算法，实际验签层再决定支持范围和策略。

RFC 5280 时间也有独立入口，供证书、CRL、OCSP 和用户协议复用：

```c
xtime time;
xrtX509TimeParse(time_der, &time);
```

入口只接受恰好一项规范 DER `UTCTime` 或 `GeneralizedTime`，要求秒和结尾 `Z`，拒绝时区偏移、分数秒、无效日历以及 2050 年之前的 GeneralizedTime。失败时输出保持不变。

## Name

```c
xx509namecursor cursor;
xx509nameattr attribute;

xrtX509NameInit(cert.Subject, &cursor);
while ( xrtX509NameRead(&cursor, &attribute) == X509_VALUE ) {
	/* attribute.Rdn 保留属性所属的 RDN 编号。 */
}
```

Name 游标按 DER 顺序展平 RDN 中的 AttributeTypeAndValue，但保留 `Rdn` 编号、值标签和原始内容。模块不擅自把 DirectoryString 转成 UTF-8，也不丢弃未知属性。`xrtX509NameFind` 提供精确 OID 的常用查找路径。

`x509_name` 是独立可裁剪的规范比较层：

```c
xx509result equal = xrtX509NameEqual(cert.Issuer, issuer.Subject);
xx509result within = xrtX509NameWithin(cert.Subject, permitted_subtree);
```

两个入口都返回 `X509_VALUE`、`X509_DONE` 或 `X509_ERROR`，不会把无效编码误报为普通不匹配。比较遵循 RFC 5280 7.1 和 RFC 4518：支持 UTF8String、PrintableString、ASCII TeletexString、BMPString 与 UniversalString，使用 Unicode 3.2 case-fold、NFKC 和 insignificant-space 规则；空格后的 Unicode `Mn`、`Mc`、`Me` 标记按 RFC 4518 保持该空格的显著性；同一 RDN 内的属性按无序集合处理，RDN 序列保持有序。`domainComponent` 与 `emailAddress` 使用 caseIgnoreIA5Match，并分别检查 RFC 4519 单标签语法与 1..63、1..255 八位组边界。非 ASCII TeletexString 的字符映射由规范留给本地实现，xrt 明确返回 `XERR_UNSUPPORTED`，不进行不可靠猜测。

常见值在 64 个 Unicode 标量、常见名称在 16 个属性以内时不分配堆内存；异常长输入按需扩展。Unicode 表和 194 组 oracle 向量都由 `tools/gen_x509_name_data.py` 基于固定 Unicode 3.2 数据生成并可重复检查。

## Extension

```c
xx509extcursor cursor;
xx509ext extension;

xrtX509ExtensionInit(&cert, &cursor);
while ( xrtX509ExtensionRead(&cursor, &extension) == X509_VALUE ) {
	/* extension.Value 是 extnValue 内部的一项完整 DER。 */
}
```

扩展游标保留 OID、critical 和正文。`critical DEFAULT FALSE` 被显式编码为 false、空扩展序列、重复 OID、非 OCTET STRING 或正文不是一项完整 DER 都会在对象入口被拒绝。未知扩展仍公开给调用方；后续策略层负责拒绝未处理的未知 critical 扩展。

`xrtX509ExtensionFind` 是精确 OID 便捷入口。没有扩展时，初始化成功并由第一次读取返回 `X509_DONE`。

CRL、CRL 条目和其他 X.509 协议对象不需要伪造证书即可复用同一实现：

```c
xx509extcursor cursor;
xx509ext extension;

xrtX509ExtensionListInit(extensions_der, &cursor);
xrtX509ExtensionListFind(extensions_der, oid, oid_size, &extension);
```

空视图统一表示没有扩展；非空视图必须是一项非空、无重复 OID 的完整 `Extensions` DER。证书便捷入口只是这一通用层之上的薄封装。

## NameConstraints

`x509_name_constraints` 是 profile 与 Name 比较之上的独立可裁剪层，公开协议解析、子树遍历、单名称匹配和整张证书检查四级入口：

```c
#define XRT_FEATURE_X509_NAME_CONSTRAINTS
#define XRT_FEATURE_X509_PROFILE
#define XRT_FEATURE_X509_NAME

xx509nameconstraints constraints;
xx509subtreecursor cursor;
xx509subtree subtree;

if ( xrtX509NameConstraints(&ca, &constraints) == X509_VALUE ) {
	cursor = constraints.Permitted;
	while ( xrtX509SubtreeRead(&cursor, &subtree) == X509_VALUE ) {
		/* subtree 的全部视图借用 CA 证书 DER。 */
	}
	xrtX509NameConstraintsCheck(&constraints, &certificate);
}
```

`xrtX509NameConstraintsParse` 可直接解析一项独立 DER，供离线 PKI、信任锚元数据和自定义协议复用；`xrtX509NameConstraints` 是证书便利入口，并强制扩展为 critical。解析拒绝空 permitted/excluded 集合、重复或乱序字段、非规范非负 BaseDistance、显式编码的默认 `minimum=0`、错误 GeneralName 形式和非法 DNS/email/URI 约束。全部结果和游标都借用输入 DER，失败或游标结束不修改输出。

`xrtX509GeneralNameWithin` 支持 RFC 5280 要求的 `directoryName`、`dNSName`、`rfc822Name`、URI 与 IP：DNS 比较大小写不敏感，并允许向左增加标签；邮箱按 SMTP Mailbox 校验 Dot-string 或 Quoted-string，local-part 精确且大小写敏感，host 大小写不敏感；邮箱和 URI 的前导点表示仅下级域，URI 只比较绝对 URI authority 中的 DNS host；IP 使用地址与掩码逐位比较；目录名称复用 `xrtX509NameWithin`。其他 GeneralName 类型不会被猜测，相关名称出现时返回 `XERR_UNSUPPORTED`。

`xrtX509NameConstraintsCheck` 同时检查非空 Subject、全部 SAN，以及没有 SAN 时历史 Subject `emailAddress`。excluded 子树优先拒绝，同类型 permitted 子树按并集匹配，不同 CA 的约束由路径层形成交集。RFC profile 不使用非默认 `minimum` 且不使用 `maximum`；解析层为诊断保留这些任意精度值，匹配层只在证书实际出现相同名称类型时返回 `XERR_UNSUPPORTED`，不会静默忽略。

## CRL 结构层

`x509_crl` 是独立可裁剪的 RFC 5280 CRL 协议层：

```c
#define XRT_FEATURE_X509_CRL
#define XRT_FEATURE_X509_PARSE
#define XRT_FEATURE_ASN1_DER
#define XRT_FEATURE_TIME
```

它不依赖摘要、密码算法、路径、文件、网络或 TLS。解析和遍历成功路径零分配，全部视图借用调用方 DER。

```c
xx509crl crl;
xx509crlcursor cursor;
xx509crlentry entry;

if ( xrtX509CrlParse(der, der_size, &crl) &&
	 xrtX509CrlEntryInit(&crl, &cursor) ) {
	while ( xrtX509CrlEntryRead(&cursor, &entry) == X509_VALUE ) {
		/* entry.Serial、RevokedAt 和 Extensions 均借用 der。 */
	}
}
```

解析器同时支持省略 `version` 的 v1 和值为 1 的 v2 CRL，并严格检查：

- 顶层 `CertificateList` 恰好包含 TBSCertList、签名算法和签名；
- TBS 与外层 AlgorithmIdentifier 完整 DER 一致；
- Issuer 是非空 Name，时间是严格 RFC 5280 时间，`nextUpdate` 不早于 `thisUpdate`；
- 编码存在的 `revokedCertificates` 非空，每项恰好包含序列号、撤销时间和可选扩展；
- CRL 与条目扩展只允许出现在 v2，并复用通用扩展层拒绝空列表和重复 OID；
- 签名是非空、八位组对齐的 BIT STRING，未知签名算法仍完整保留给后续扩展。

`xx509crlentry.Serial` 和证书 `Serial` 使用相同语义：保留规范 DER INTEGER 的完整有符号内容，包括正数符号补零、零、负数和历史超长值。`xrtX509CrlFind` 做精确内容匹配，命中返回 `X509_VALUE`，未命中返回 `X509_DONE`，结构错误返回 `X509_ERROR`；`xrtX509CrlRevokes` 是直接接受证书的常用入口。

```c
xx509result revoked = xrtX509CrlRevokes(&crl, &certificate, &entry);
bool current = xrtX509CrlValidAt(&crl, xrtNow());
```

时间窗口使用闭区间。没有 `nextUpdate` 时，结构层只检查时间不早于 `thisUpdate`，不会擅自制定最大寿命；要求 `nextUpdate`、限制 CRL 年龄或处理离线缓存属于调用方策略。解析器不会因未知 critical 扩展直接丢失 CRL，因为扩展处理能力取决于上层。

## CRL 分发点

`x509_distribution` 是证书 profile 之上的独立零分配层，统一实现证书 `CRLDistributionPoints`、证书 `FreshestCRL` 与 CRL profile 共用的 `DistributionPointName` 和 `ReasonFlags`：

```c
#define XRT_FEATURE_X509_DISTRIBUTION
#define XRT_FEATURE_X509_PROFILE

xx509distributioncursor points;
xx509distributionpoint point;

if ( xrtX509CrlPoints(&certificate, &points) == X509_VALUE ) {
	while ( xrtX509DistributionRead(&points, &point) == X509_VALUE ) {
		/* point 的名称、原因和 CRL 发行者均借用证书 DER。 */
	}
}
```

`xrtX509DistributionPointParse` 解析一项独立 `DistributionPoint`；`xrtX509DistributionInit` 和 `xrtX509DistributionRead` 处理完整的 `SEQUENCE OF`。这些底层入口不要求输入来自证书，OCSP、缓存、诊断工具和用户协议可以直接复用。`xrtX509CrlPoints` 与 `xrtX509FreshestCrl` 是常见证书路径的便利入口，扩展不存在返回 `X509_DONE`。

`xx509distributionpoint` 明确区分可选名称、原因掩码和 `cRLIssuer`。`fullName` 直接提供 `GeneralNames` 游标；`nameRelativeToCRLIssuer` 保留上下文 TLV 与单个 RDN 内容。解析层拒绝空列表、空点、reasons-only、重复或乱序字段、非规范 named-bit 和畸形相对名称，同时不擅自把 `cRLIssuer` 限死为某一种 GeneralName；严格的发行者名称和作用域对应关系由 CRL policy 判断。

RFC 5280 只建议证书 `CRLDistributionPoints` 为 non-critical，因此便利入口能处理 critical 形式，最终是否接受由调用方路径策略决定。证书和 CRL 的 `FreshestCRL` 则必须 non-critical。CRL 内的 `FreshestCRL` 还有更窄的 profile：不能出现在 delta CRL 中，且每个点只能出现 `distributionPoint` 名称；`xrtX509CrlFreshest` 会执行这些约束。

## CRL Profile

`x509_crl_profile` 在结构层之上实现 [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280.html) 标准扩展的零分配类型化读取，并保持 CRL 结构、证书 profile 与策略验证可分别裁剪：

```c
#define XRT_FEATURE_X509_CRL_PROFILE
#define XRT_FEATURE_X509_CRL
#define XRT_FEATURE_X509_DISTRIBUTION

xbytesview number;
xx509issuingpoint point;
xx509crlreason reason;

xrtX509CrlNumber(&crl, &number);
xrtX509CrlIssuingPoint(&crl, &point);
xrtX509CrlEntryReason(&entry, &reason);
```

CRL 级入口包括 `xrtX509CrlNumber`、`xrtX509CrlDeltaBase`、`xrtX509CrlAuthorityKeyId`、`xrtX509CrlIssuingPoint` 和 `xrtX509CrlFreshest`；条目级入口包括 `xrtX509CrlEntryReason`、`xrtX509CrlEntryInvalidityDate` 和 `xrtX509CrlEntryIssuer`。扩展不存在返回 `X509_DONE`，成功返回 `X509_VALUE`，critical 口径或正文错误返回 `X509_ERROR`，失败和缺省都不修改输出。

`CRLNumber` 与 `BaseCRLNumber` 是 `INTEGER (0..MAX)`。`xrtX509CrlNumberParse` 返回去除可选正数符号零后的任意精度大端视图，不把协议范围错误缩成 64 位。CRL Number 与 AKI 必须 non-critical；Delta CRL Indicator 与 Issuing Distribution Point 必须 critical；Certificate Issuer 必须 critical。Reason Code 和 Invalidity Date 按 profile 约束读取为 non-critical。

`xx509issuingpoint` 明确区分所有 DEFAULT 和 OPTIONAL 字段。完整分发点名称直接提供 `GeneralNames` 游标，相对名称保留完整上下文 TLV 与 RDN 内容，调用方仍可使用 ASN.1 底层继续解释。三个证书类别作用域不能同时出现；ReasonFlags 使用独立位枚举，不能与不连续的 CRLReason 数值混用。

`xrtX509CrlInvalidityDateParse` 严格要求 `GeneralizedTime`。这个字段不使用证书有效期的“2050 年前 UTCTime、以后 GeneralizedTime”选择规则，因此 2026 年的合法 InvalidityDate 仍必须使用四位年份。`xrtX509CrlReasonParse` 接受规范定义的 0 到 6、8、9、10，并拒绝未分配值 7；`removeFromCRL` 是否只出现在 delta CRL 由策略层判断。

profile 层不会验证签名、CRL Issuer、签发者 `cRLSign`、AKI/SKI 对应、时间新鲜度、分发点匹配、unknown critical 扩展或间接 CRL 的发行者继承，也不会合并 complete/delta CRL。它只把原始扩展可靠地转换为公开协议模型，后续 `x509_crl_policy` 可以复用这些模型，而 OCSP、离线检查器和自定义 PKI 仍可直接选择低层入口。

同理，`x509_crl` 不验证密码签名，不比较 CRL Issuer 与签发者 Subject，不检查签发者 `cRLSign`，也不把“出现在列表中”直接解释成最终证书状态。独立的 `x509_crl_verify` 层只负责密码签名：

```c
#define XRT_FEATURE_X509_CRL_VERIFY
#define XRT_FEATURE_X509_CRL
#define XRT_FEATURE_X509_VERIFY

bool signature_ok = xrtX509CrlVerify(&crl, &issuer_certificate);
bool key_signature_ok = xrtX509CrlVerifyKey(&crl, &issuer_public_key);
```

两个入口解析 CRL 的公开 AlgorithmIdentifier，并把 TBSCertList、签名和公钥直接交给 `xrtX509SignatureVerify`。基础层不强制拉入密码后端；RSA、ECDSA、Ed25519 仍按现有 `XRT_FEATURE_X509_VERIFY_*` 宏独立启用，未知算法或缺少后端返回明确的 `XERR_UNSUPPORTED`。Issuer、作用域、`cRLSign`、removeFromCRL、delta/indirect 合并和软/硬失败策略属于更高层。这样 TLS 可以按需组合，而 OCSP、离线检查器和用户自定义 PKI 不会被 TLS 私有策略限制。

## CRL 策略

`x509_crl_policy` 把 CRL 结构、profile、签名和名称比较组合为可独立裁剪的 [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280.html) 策略层。它验证 CRL Issuer、签名、时间窗口、签发证书 `cRLSign`、AKI、CRL Number、unknown critical 扩展、Issuing Distribution Point、间接 CRL 条目和证书分发点作用域，但不负责建立或验证 CRL 签发者的证书路径。调用方必须先在同一信任上下文中验证 `pIssuer`。

```c
#define XRT_FEATURE_X509_CRL_POLICY

xx509crlconfig config;
xx509crlvalid valid;
xx509revocation status;

xrtX509CrlConfigInit(&config);
if ( xrtX509CrlValidate(&crl, &issuer, &config, &valid) ) {
	xx509result result = xrtX509CrlCheck(&valid, &certificate, &status);
}
```

`xrtX509CrlConfigInit` 使用当前墙上时钟和严格默认项：要求 `nextUpdate`、CRL Number、Authority Key Identifier、AKI `keyIdentifier` 和签发者 KeyUsage。需要可复现测试、缓存快照或外部可信时间时，调用方可以显式设置 `Time` 和 `Skew`；传入 `NULL` config 等同于当前时间严格策略。未知 critical CRL 或条目扩展默认拒绝，`Critical` 回调只有返回 `X509_VALUE` 才表示调用方已经完整处理该扩展。

`xrtX509CrlValidate` 成功后发布 `xx509crlvalid` 借用视图。视图、内部 profile 子视图和后续查询结果都不拥有 DER；原 CRL 与签发证书必须保持存活且内容不变。这个类型应只由验证入口产生，`xrtX509CrlCheck` 与 `xrtX509CrlSetInit` 依赖其验证不变量。常见一次性路径可用 `xrtX509CrlStatus`，复用同一 CRL 查询多张证书时应先验证一次再反复检查。

查询返回值具有明确作用域：`X509_ERROR` 表示输入或协议错误，`X509_DONE` 表示这份 CRL 不适用于证书或 delta CRL 没有该证书的新记录，`X509_VALUE` 才发布 `xx509revocation`。`X509_REVOCATION_GOOD` 只证明 `CoveredReasons` 中的原因未撤销，不能把一份原因分段 CRL 的 GOOD 当成全局 GOOD。多份分段 CRL 应依次交给 `xrtX509RevocationUpdate`；只有原因全集覆盖或任一分片确认撤销时，`xrtX509RevocationResult` 才返回最终 `X509_VALUE`。

complete/delta 组合使用 `xrtX509CrlSetInit` 和 `xrtX509CrlSetCheck`。两份已验证 CRL 必须具有相同标准化 Issuer、实际公钥、AKI、Issuing Distribution Point 与作用域；complete CRL Number 必须不小于 delta 的 BaseCRLNumber，并严格小于 delta CRL Number。查询先处理 delta 更新，再回退 complete CRL；`removeFromCRL` 只有经过这条组合路径才会变成 GOOD，未组合的移除记录不能直接进入多 CRL 聚合器。

该层全程零分配，失败和 `X509_DONE` 不修改输出。相对分发点名称在缺少足够可比较上下文时保守返回 `X509_DONE`，不会猜测适用性。网络获取、缓存、FreshestCRL 下载、软失败/硬失败和 OCSP 组合属于更高层，策略 API 保留明确结果，使 TLS、离线检查器和用户 PKI 可以选择自己的获取与失败规则。

旧版 `lib/nettls.h` 中的 CRL 私有结构、解析、签名与线性查找，以及 `test_tls_anchor_verify.h` 的签发者、撤销、空列表和过期真实 RSA 向量均作为资产保留。新实现复用真实 DER，并实际验证三份历史 CRL 的原始 RSA 签名，同时重新建立严格字段、失败原子性、零分配、v1/v2、扩展、损坏签名原因链、单头文件、32 位 TinyCC 和全字节变异证据；旧 TLS 测试不会被冒充为新协议层的覆盖。

## 公钥

```c
xx509pubkey key;
xrtX509PublicKey(&cert, &key);
```

公钥视图识别 RSA、RSA-PSS、EC P-256/P-384/P-521、Ed25519、Ed448、X25519 和 X448。RSA 额外公开去除符号零的模数与指数；EC 保留点编码；RFC 8410 公钥要求省略参数并使用固定长度。未知算法返回 `X509_KEY_UNKNOWN`，但 AlgorithmIdentifier 和原始 key bits 保持可用，为用户扩展和未来算法留出路径。

## 签名算法

`x509_signature` 把证书签名 AlgorithmIdentifier 转换为独立、零分配的协议数据模型。它只解释算法与参数，不拉入任何密码学验证后端，因此可以单独用于证书检查、策略过滤和上层自定义实现。

```c
#define XRT_FEATURE_X509_SIGNATURE
#define XRT_FEATURE_X509_PARSE

xx509signature signature;
xx509result result = xrtX509SignatureParse(
	&cert.SignatureAlgorithm, &signature
);
```

`X509_VALUE` 表示已知且参数合法，`X509_DONE` 表示结构合法但 OID 未知，`X509_ERROR` 表示已知算法使用了错误参数。后两种结果都不修改输出。调用方可在 `X509_DONE` 时直接使用 `xx509algorithm` 的 OID 和完整参数 TLV 接入自定义算法。

支持的协议标识包括 RSA PKCS#1 v1.5、RSA-PSS、ECDSA 的 SHA-1/SHA-224/SHA-256/SHA-384/SHA-512 形式以及 Ed25519、Ed448。摘要枚举只表达证书协议，不承诺当前裁剪构建包含对应验签实现。

RSA PKCS#1 按 RFC 4055 同时接受 NULL 和缺省参数。RSA-PSS 要求参数序列存在，完整公开主摘要、MGF1 摘要、盐长和 trailer；默认值是 SHA-1、MGF1-SHA-1、20 字节盐和 trailer 1。解析器接受 RFC 4055 要求兼容的显式默认值，同时拒绝重复、乱序、未知上下文字段、非 MGF1、溢出盐长和非 1 trailer。ECDSA、Ed25519 与 Ed448 参数必须缺省。

## 签名验证

签名验证按协议分派、摘要和密码后端分层裁剪。基础 `x509_verify` 不强制拉入任何密码算法；需要哪类证书就启用对应后端：

```c
#define XRT_FEATURE_X509_VERIFY
#define XRT_FEATURE_X509_VERIFY_RSA
#define XRT_FEATURE_X509_VERIFY_ECDSA
#define XRT_FEATURE_X509_VERIFY_ED25519
```

底层入口接受公开协议模型，可用于证书、CRL、OCSP 或调用方自己的签名对象：

```c
bool xrtX509SignatureVerify(
	const xx509signature* pScheme,
	xbytesview Content,
	xbytesview Signature,
	const xx509pubkey* pPublicKey
);
```

`xrtX509CertificateVerify(certificate, issuer)` 是常见路径的便利入口：它解析证书签名方案与签发者 SPKI，再复用同一底层分派。`xrtX509CertificateVerifyKey(certificate, public_key)` 接受已经提取或由信任配置直接提供的公钥，避免为了验证独立信任锚而伪造证书对象。这两个函数只验证 `TBSCertificate` 的密码签名，不比较 issuer/subject Name，也不检查时间、BasicConstraints、KeyUsage、未知 critical 扩展、撤销或信任锚；这些职责属于路径验证层。

RSA 后端支持 PKCS#1 v1.5 与 PSS 的 SHA-1/SHA-224/SHA-256/SHA-384/SHA-512。`id-RSASSA-PSS` 公钥只能验证 PSS；公钥参数存在时，主摘要、MGF1 摘要和 trailer 必须与签名参数一致，签名盐长必须不小于公钥声明的下限。参数缺省的 PSS 公钥不附加参数限制。该规则补齐了旧版只记录 PSS 密钥类型、未执行 RFC 4055 公钥限制的缺口。

ECDSA 后端严格解码 DER `r,s`，根据 SPKI 命名曲线选择 P-256 或 P-384，并允许协议 OID 指定的任意受支持摘要组合。摘要按 ECDSA `bits2int` 规则进入曲线底座，不再错误地把 P-256 固定为 SHA-256、P-384 固定为 SHA-384。已解析但当前没有后端的 P-521 和 Ed448 返回 `XERR_UNSUPPORTED`，不会伪装成签名不匹配。

所有失败都返回 `false` 并设置 `xrt.x509` / `X509_ERROR_SIGNATURE` 或参数错误；密码验证失败通过 `xrtErrorCause` 保留 `xrt.crypto` 原因。有效路径使用栈摘要和借用视图，不分配堆内存。调用方可以直接启用 `x509_verify` 做协议分派，并自行接管未启用或未来算法。

## 错误

X.509 错误使用 `xrt.x509` 域和 `X509_ERROR_*` 稳定代码。底层 DER、时间转换或扩展正文失败会尽可能通过 `xrtErrorCause` 保留原始原因；错误数据在适用时包含 `offset=<字节偏移>`。所有解析器和游标只在成功时发布输出。

## 服务身份

`x509_identity` 按 [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html) 匹配 TLS 服务身份。它依赖 `x509_profile` 和网络地址基础层，但不执行签名或证书路径验证。匹配只检查 SubjectAltName 中的 DNS-ID 与 IP-ID，不读取 Common Name。

```c
xx509genname presented;
xx509result result = xrtX509MatchHost(
	&cert, XRT_STR_LITERAL("api.example.test"), &presented
);
```

返回 `X509_VALUE` 表示匹配并可选发布实际 SAN，`X509_DONE` 表示引用身份有效但没有匹配，`X509_ERROR` 表示引用身份或 SAN 结构无效。TLS 层应把 `X509_DONE` 转换为握手身份错误，而协议工具可以继续自行决定策略。

DNS 比较使用大小写不敏感 ASCII 标签。引用身份必须是 ASCII preferred-name/A-label 形式；U-label 应由 URL/IDNA 层先转换。证书通配符只能是唯一且完整的最左标签，并且只匹配一个标签；无效的 presented DNS-ID 会被忽略。一个结尾根点在比较时被规范化。公共后缀策略不属于证书匹配层，因而 `*.com` 的语法有效性不会依赖内置后缀表。

```c
xx509result result = xrtX509MatchDns(
	XRT_STR_LITERAL("*.example.test"),
	XRT_STR_LITERAL("api.example.test")
);
```

IPv4 和 IPv6 引用身份复用 `xrtNetAddrParse` 的严格文本解析，并与 iPAddress SAN 做 4 或 16 字节精确比较。高层入口接受裸 IPv6 和 URL 常见的方括号 IPv6；Scope ID 被拒绝。只由 DNS 解析得到的连接地址仍应使用原 DNS-ID，而不是间接改用 IP-ID。

## Profile 扩展

`x509_profile` 在通用 Extension 视图之上提供常用证书 profile 的严格类型化读取。它依赖 `x509_parse`，不依赖签名算法、信任库、文件或网络，并保持有效路径零分配。未出现的扩展返回 `X509_DONE`，畸形扩展返回 `X509_ERROR`，成功结果返回 `X509_VALUE`。

```c
#define XRT_FEATURE_X509_PROFILE
#define XRT_FEATURE_X509_PARSE
#define XRT_FEATURE_ASN1_DER
#define XRT_FEATURE_TIME
```

SubjectAltName 和 IssuerAltName 分别通过 `xrtX509SubjectAltName` 与 `xrtX509IssuerAltName` 返回同一种借用游标，公开所有九种 `GeneralName`。DNS、邮件和 URI 保留 IA5 内容；IP 地址严格限制为 4 或 16 字节；directoryName 继续由 Name 游标解释。profile 层只验证结构和基本内容，主机名语法、通配符与服务身份匹配由独立身份层负责。

```c
xx509gencursor names;
xx509genname name;

if ( xrtX509SubjectAltName(&cert, &names) == X509_VALUE ) {
	while ( xrtX509GeneralNameRead(&names, &name) == X509_VALUE ) {
		/* name.Type、name.Raw 和 name.Value 都借用证书 DER。 */
	}
}
```

`xrtX509KeyUsage` 返回 `X509_USAGE_*` 位值，并拒绝空值、非最小 named-bit 编码以及缺少 keyAgreement 的 encipherOnly/decipherOnly。`xrtX509BasicConstraints` 区分 CA、pathLenConstraint 不存在和数值为零，拒绝显式默认 false 以及非 CA 的路径限制。

```c
uint16 usage;
xx509basicconstraints constraints;

xrtX509KeyUsage(&cert, &usage);
xrtX509BasicConstraints(&cert, &constraints);
```

ExtendedKeyUsage 使用公开 OID 序列游标，保留未知用途并拒绝空序列和重复 OID。SubjectKeyIdentifier 返回非空 OCTET STRING 的借用内容。`xrtX509GeneralNameInit` 与 `xrtX509OidInit` 也可脱离证书直接解析协议层 DER，避免上层再次实现相同游标。通用 OID 游标使用 `X509_ERROR_OID_LIST`；EKU 入口使用 `X509_ERROR_EXTENDED_KEY_USAGE` 并把前者保留为 cause。

```c
xx509oidcursor purposes;
xbytesview oid;
xbytesview key_id;

if ( xrtX509ExtendedKeyUsage(&cert, &purposes) == X509_VALUE ) {
	while ( xrtX509OidRead(&purposes, &oid) == X509_VALUE ) {
		/* 精确比较 OID 内容八位组。 */
	}
}
xrtX509SubjectKeyId(&cert, &key_id);
```

`xrtX509SubjectKeyIdParse` 和 `xrtX509AuthorityKeyIdParse` 可以直接解析扩展正文，证书便利入口则负责查找扩展并执行 profile 约束。AKI 公开 keyIdentifier、authorityCertIssuer 游标和规范 DER INTEGER 的完整序列号内容；issuer 与 serial 必须同时出现或同时缺省。SKI、AKI 在证书中必须是 non-critical，所有结果都借用输入 DER，并且只在成功时发布。

```c
xx509authoritykeyid authority;

if ( xrtX509AuthorityKeyId(&cert, &authority) == X509_VALUE &&
	authority.HasKeyId ) {
	/* authority.KeyId 可用于缩小候选发行者集合。 */
}
```

## 认证路径

`x509_path` 验证调用方已经按“目标证书在前、中间 CA 依次靠近信任锚”排列的路径。信任锚是验证输入，不属于候选认证路径；`xrtX509Anchor` 从受信任证书提取 Subject、公钥、证书身份和可选 NameConstraints，路径中再次出现同一锚证书会被拒绝。调用方也可以直接构造裸锚，此时 `Certificate` 留空，并可通过 `HasNameConstraints` 和 `NameConstraints` 提供独立的锚约束元数据。

```c
xx509anchor anchor;
xx509pathconfig config = { 0 };
const xx509cert* path[] = { &leaf, &intermediate };

xrtX509Anchor(&root, &anchor);
config.Time = validation_time;
xrtX509PathValidate(path, 2u, &anchor, &config);
```

验证在调用方给定的精确时间检查每张路径证书，并拒绝重复证书、发行者链断裂、签名失败和未处理的 critical 扩展。中间 CA 必须具有 nonempty Subject 和 critical `BasicConstraints(cA=TRUE)`；存在 KeyUsage 时必须允许 `keyCertSign`，出现 `pathLenConstraint` 时则必须显式具有该 KeyUsage。路径长度只计算当前 CA 下方的非 self-issued 中间 CA，不计算目标证书。中间 CA 的 ExtendedKeyUsage 若存在，也必须允许请求的应用用途或 `anyExtendedKeyUsage`，不能只约束目标证书。

每张 CA 证书和信任锚的 NameConstraints 都应用到目标及其下方全部非 self-issued 中间证书；self-issued 中间证书按 RFC 5280 跳过，但目标即使 self-issued 也必须检查。多个约束层自然形成交集，目标证书自身携带 NameConstraints 会被拒绝。路径错误使用 `X509_ERROR_NAME_CONSTRAINTS` 包装底层具体名称失败，并保留原因链。

`X509_PATH_REQUIRE_KEY_USAGE` 和 `X509_PATH_REQUIRE_PURPOSE` 可要求目标证书显式包含指定 KeyUsage 与 ExtendedKeyUsage；自定义 critical 扩展可由 `xx509criticalproc` 明确接管。`xx509pathconfig` 不保存系统当前时间，调用方必须显式提供验证时间，使测试、缓存和重放检查具有确定语义。

`xrtX509IssuerMatch` 是路径构建器可复用的候选筛选层：先比较 Issuer/Subject，再使用可用的 AKI/SKI 或 authority issuer/serial 排除确定不匹配的候选，最终签名仍由路径验证器决定。它不会因为候选缺少 SKI 就误判为不匹配。

`x509_path_build` 在已解析的候选发行者和独立信任锚中自动搜索。每一层先尝试直接终止到调用方顺序中的信任锚，再按候选顺序执行 Issuer/Subject、AKI/SKI 筛选和确定性深度优先回溯；完整候选路径始终交给同一个 `xrtX509PathValidate` 验证，不另设宽松验证路径。调用方可以通过候选和锚顺序表达稳定偏好，返回路径永远不包含信任锚证书。

```c
const xx509cert* issuers[] = { &presented_root, &intermediate };
const xx509cert* path[4];
xx509pathsource source = {
	issuers, 2u, &anchor, 1u
};
xx509pathresult result;

if ( xrtX509PathBuild(
	&leaf, &source, &config, path, 4u, &result
) ) {
	/* path[0..result.Count) 有效，result.Anchor 是命中的借用信任锚。 */
}
```

`ppPath` 是调用方提供的搜索与输出缓冲，容量同时限制最大路径深度；它不得与 `source.Issuers` 数组重叠。失败时 `ppPath` 可包含搜索暂存值，但 `xx509pathresult` 保持原值；成功时发布目标在前的完整路径长度和命中的借用锚。容量不够返回 `XERR_RANGE`，没有路径返回 `XERR_NOT_FOUND`，完整分支的首个验证错误保留在 `X509_ERROR_PATH_BUILD` 原因链中。容量不超过 16 时搜索帧不使用堆内存，更深路径只为搜索帧分配一次内存。证书对象、候选数组、锚和所有 DER 必须在调用期间保持有效。

## 信任库

`x509_store` 是拥有式信任锚集合。`xrtX509StoreAdd` 复制并严格解析一张 DER 证书，成功返回 `X509_VALUE`，字节完全相同的重复证书返回 `X509_DONE`；调用方可在返回后立即释放或复用原缓冲。每项只保存一份 DER，已解析证书和独立锚都借用这份副本。

```c
xx509store* store = xrtX509StoreCreate();
xx509pathsource source;

if ( (xrtX509StoreAdd(store, root_der, root_size) == X509_VALUE) &&
	xrtX509StoreSource(store, issuers, issuer_count, &source) ) {
	xrtX509PathBuild(
		&leaf, &source, &config, path, path_capacity, &result
	);
}
xrtX509StoreFree(store);
```

`xrtX509StoreAddPem` 遍历说明文本中的全部 PEM 块，只导入标签精确为 `CERTIFICATE` 的块，并忽略其他合法标签。整个调用是事务：任何边界、Base64、DER、证书或内存失败都会释放本次已经加入的证书，保持调用前数量，并且不修改 `pAdded`；成功时可选的 `pAdded` 只计算新增锚，重复块计为零。没有任何证书块返回 `XERR_NOT_FOUND`。底层 PEM 或证书错误保留在 `X509_ERROR_TRUST_STORE` 原因链中。

独立裁剪的 `x509_store_file` 提供 `xrtX509StoreAddFile`，整文件读取后自动识别一张 DER 证书或包含多张证书的 PEM 文本。有效 DER 以顶层 `SEQUENCE` 为优先，其他内容按行首 `BEGIN` 边界识别 PEM；空文件和不合法内容明确失败。导入仍保持事务性，可选的 `pAdded` 只在成功时发布。文件、PEM 与证书错误由 `X509_ERROR_TRUST_STORE_FILE` 包装，并保留原始原因链；若 OOM 已使错误对象也无法分配，则按统一错误模型退化为静态 `XERR_MEMORY`。读入缓冲在返回前释放，信任库继续只拥有每张证书的一份 DER。

`x509_store_system` 提供 `xrtX509StoreAddSystem` 和拥有式便捷入口 `xrtX509StoreSystem`。前者把当前系统锚事务式追加到既有库，可选的 `pAdded` 只统计去重后的新增项；后者返回一份可继续修改、最终由 `xrtX509StoreFree` 释放的独立快照，不使用全局缓存，也不会修改平台信任设置。Windows 动态枚举当前用户和本机的 `ROOT` 逻辑库，不增加 Crypt32 静态链接；macOS 动态读取 Security.framework 为调用方提供的默认锚；其他 Unix 首先使用 `SSL_CERT_FILE` 和冒号分隔的 `SSL_CERT_DIR`，未设置时读取主流系统 bundle 与 OpenSSL 哈希目录。Unix 环境变量分别覆盖同类默认位置，证书目录项必须采用 `xxxxxxxx.n` 哈希名称，空路径片段被忽略。

系统装载不会静默接受部分结果：平台枚举、显式环境路径、文件解析或内存失败都会回滚本次全部新增项。`X509_ERROR_TRUST_STORE_SYSTEM` 保存平台错误码或底层文件/证书原因链；完全 OOM 时仍允许退化为静态 `XERR_MEMORY`。系统信任快照只表达锚集合，不复制 Windows/macOS 原生验证器的吊销、策略、企业限制或按用途动态决策；这些策略仍由 XRT 路径层显式执行。

`xrtX509StoreCertificate` 与 `xrtX509StoreAnchor` 公开按索引借用的底层视图，`xrtX509StoreSource` 则把外部中间证书指针和库内连续锚数组组合成建链源。向信任库继续写入可能移动证书和锚结构，因此会使既有结构指针和 `xx509pathsource` 失效；DER 内容只在对应项仍存在时有效。完成构建后可从多个线程并发只读，任何写入或释放都不得与读取并发。信任库不替调用方判断某张证书是否应受信任，显式加入即表示调用方授予信任锚地位。

建链器本身不会读取文件、系统信任库、网络或 AIA，也不替调用方无限扩张候选集合；处理不可信证书集合时应限制候选数量和路径容量。文件与系统信任装载分别由可选的 `x509_store_file` 和 `x509_store_system` 提供；NameConstraints 已由路径层处理，证书策略、CRL 与 OCSP 仍作为后续独立可裁剪层补充。未知 critical 扩展一律拒绝，不能静默绕过。常见有效验证与建链路径不分配堆内存，签名算法后端继续按 RSA、ECDSA、Ed25519 独立裁剪。
