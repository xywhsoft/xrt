# XID 设计

## 旧版资产

旧版 XID 已经形成一套有用的产品形态：192 位固定值、32 字符 URL-safe 编码、无中心生成、生成/编解码/比较以及直接生成字符串的 helper。新版继续保留这些成熟能力和对应测试边界。

不能保留的是旧实现的隐含契约：它把 C 结构体内存直接编码，文本随主机端序变化；IP 字段强迫基础 ID 依赖网络，并泄露机器信息；高精度时钟低位和普通 PRNG 没有建立可证明的分布式唯一模型；每个 24 字节值还要单独堆分配。旧文档声称“时间有序”，原始字段顺序与字母表实际上也没有保证字符串排序。

## 新布局

新版把 `xid` 定义为单纯的 `uint8 Data[24]`。前八字节是偏置后的有符号 Unix 微秒大端值，后十六字节是系统安全随机数据。布局不受结构填充、端序、指针宽度和网络状态影响。

对负时间使用 `INT64_MIN` 起点偏置，对非负时间使用高位区间，完整 `xtime` 域都能往返并保持排序。实现使用算术映射，不依赖把超出 `INT64_MAX` 的 `uint64` 强制转换为有符号整数。

128 位随机后缀使同一微秒、不同线程、不同进程和不同主机之间无需共享机器号或中心计数器。它不承诺同一微秒内严格按调用先后递增；需要稳定业务顺序时应同时保存业务序号，而不是让全局锁进入每次 ID 生成热路径。

## 编码复用

文本层不再维护 XID 专用 Base64 算法，而是调用 `codec_base64` 的自定义字母表入口。24 字节正好编码为 32 个 Base64 字符，不需要填充，也不存在末尾未使用位。

字母表按 ASCII 排序，使每个六位编码值的字符顺序与数值顺序相同。由于输入长度固定，`memcmp(xid)`、`xrtXidCompare` 和 `strcmp(formatted)` 的顺序完全一致。解析先检查精确长度和字母表，以建立 `xrt.xid` 的位置错误，再交给统一 codec 完成字节还原。

## 性能与并发

单个生成只有一次安全随机调用、一次时钟读取和八次前缀写入，没有堆分配、全局锁或网络查询。批量入口直接让随机源填充整个 `xid[]`，随后覆盖每项前八字节，一次系统调用即可取得整批熵；额外取得但被时间前缀覆盖的随机字节是有意的简单性成本，不引入临时缓冲。

模块没有可变全局状态，线程安全由系统随机源和时间底座提供。批量输出由调用方拥有，不同线程写入不同区间即可并发生成。

## 失败语义

随机底座保证失败时清零整个请求缓冲，XID 在随机成功后才写时间，因此生成失败不会留下部分可用 ID。解析先写局部 24 字节值，全部校验和解码成功后才提交输出。格式化写入要求完整 33 字节容量，避免调用方误用被截断的标识。

随机错误保持 `xrt.random` 域，内存分配错误保持 `XERR_MEMORY`，只有文本格式失败使用 `xrt.xid`。上层宿主可以把格式位置和 Cause 映射到自己的错误模型，C 调用方仍可用布尔返回完成常见检查。

## API 形态

`xid` 是值类型，不需要 Ref/Release、create/destroy 或隐藏句柄。基础路径由 `Make`、`Write`、`Parse`、`Time`、`Compare` 组成；`Format` 和 `MakeString` 只为常见字符串路径提供所有权 helper；`MakeMany` 是高负载专用入口。没有兼容别名、版本后缀或把相同功能拆成对象式与过程式两套实现。
