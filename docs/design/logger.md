# Logger 设计

Logger 按能力分层，避免控制台、文件、JSON 和异步队列进入最小核心：

1. `logger_core`：记录、字段、Logger、通用 Sink、同步分发、默认对象、统计。
2. `logger_printf`：格式化字符串 Helper。
3. `logger_format_text`：稳定文本行格式化。
4. `logger_format_json`：复用公开 JSON 转义底座的无分配 JSON Lines 格式化。
5. `logger_console`：终端输出和显式颜色策略。
6. `logger_file`：通用格式回调、文件写入、动态记录缓冲、精确大小滚动、reopen 和持久化策略。
7. `logger_file_text` / `logger_file_json`：分别适配文本和 JSON 格式器，不让通用文件层强依赖两套格式。
8. `logger_async`：包装任意 Sink 的有界异步队列、背压和排空语义。

## 快照模型

Logger 保存不可变 Sink 数组。附加和移除在短临界区内发布新快照，提交只取得快照引用，然后在锁外调用 Sink。该模型没有每条记录的 Sink 数组分配，同时解决递归回调、自移除、共享 Sink 和并发销毁的数据生命周期问题。

## 依赖边界

核心依赖 `atomic`、`mutex` 和 `time`。线程标识是记录中的可选字段，不使核心依赖完整 `thread`。JSON 格式化只依赖 `json_escape` 和数值格式化；未选择 JSONL 时不会拉入任何 JSON 能力，选择流式 JSONL 时也不会拉入 `value_container`、JSON DOM、完整 JSON Writer 或 Buffer。

JSON 字符串转义只有 `json_escape` 一处实现，JSON Writer、XSON Writer、Logger JSONL 和公开 `xrtJsonQuoteWrite` 共同复用。Logger 使用内部无错误域核心，以避免每个字段反复保存线程错误上下文；对外仍暴露同一套严格 UTF-8 和转义语义。

字段对象面向常规检索，字段数组面向无损传输。两种形式共用一个字段值写出器，不复制类型处理。结构化错误完整保留原因链，并在写出前检查配置深度，使过深或循环链不会产生半条结构错误。

Console Sink 复用 `logger_format_text`，不复制时间、字段或转义实现。每个 Sink 用一把锁覆盖颜色前缀、全部格式器分段、颜色复位和可选刷新，保证一条记录在标准流上的原子可读性。自动颜色在创建时结合 `NO_COLOR`、TTY 和 Windows ANSI 能力确定，重定向输出不会夹带控制序列。Windows 每条记录从 CRT 流解析当前句柄：真实控制台无分配地把严格 UTF-8 分块写成 UTF-16，重定向目标保留原始字节；写控制台前先刷新 stdio，避免与调用方已有缓冲输出倒序。

错误构造会触发进程错误处理器，因此 Console 和 File Sink 使用原子记录的当前锁拥有线程保护同一 Sink 的错误递归：其他线程仍正常等待串行锁，同线程由错误处理器发起的嵌套记录直接丢弃。该方案不依赖 TinyCC 不支持的编译器线程局部存储，同时保持 Logger 核心允许普通递归回调的契约。

## 文件记录事务

文件格式器仍使用 `xlogwriteproc` 流式接口，但输出目标是每个 Sink 独占的动态 `xbuffer`，不是直接文件句柄。这一层必要的聚合同时解决四个问题：

1. 滚动判断使用完整编码后字节数，不再沿用旧版“消息长度加固定常量”的估算。
2. 一条文本或 JSON 记录只进入一次完整文件写，避免每个标点、字段和转义片段触发系统调用。
3. 格式化、UTF-8、记录上限和内存失败发生在文件修改前，不会留下格式化阶段的半条记录。
4. Sink 锁覆盖格式化、滚动、写入和可选持久化，并发提交不会交错。

缓冲不是固定预留。默认单条硬上限 16 MiB，常驻复用高水位 64 KiB；超过高水位的偶发容量在记录结束后释放。这样常见记录只在第一次增长时分配，同时避免高并发场景把固定 8K 或偶发超大记录乘以对象数量。

通用 `logger_file` 只依赖 `logger_core`、`buffer` 和 `file`。文本和 JSON 适配器各自复制不可变配置，并通过相同格式回调进入唯一文件实现。滚动只使用基础 `xrtPathRename`，没有引入 `file_whole`；跨进程滚动协调也不强制拉入 `file_lock`，需要该能力的应用可在更高层统一管理滚动时机。

所有内置目标最终都实现同一个 `xlogsink` 契约。异步能力通过包装 Sink 组合，不在 Logger 内复制一套输出目标和格式逻辑。

## 异步记录事务

Async Sink 把每条借用记录压成一次精确分配：固定记录、字段数组、Logger、消息、源位置、字段名和字符串值连续存放，错误字段只增加不可变引用。这样复制成功后的节点具有单一释放路径，也避免固定 8K 缓冲乘以连接或 Sink 数量。工作线程取走节点后才解除记录数和字节预算，生产者可立即继续，目标耗时不再占用队列额度。

记录数和字节数先在锁内预留，再在锁外分配和复制，最后回到锁内提交链表。这个两阶段事务解决了 `BLOCK` 策略的隐藏内存问题：没有预留时，每个阻塞生产者都可能持有一条队列外副本，使表面 `ByteLimit` 失效；预留后，高水位覆盖“正在复制”和“已经入链”的完整集合。复制 OOM 会回滚预留并唤醒等待者，不留下半记录。

FIFO 链同时承载记录与 Flush 控制节点。Flush 节点由调用线程和工作线程双引用持有，即使平台等待失败也不会让工作线程访问已经返回的栈对象。满载覆盖只允许移除队首记录，不允许跨过 Flush 栅栏；并发提交尚未完成时，Flush 只保证在调用前已经返回成功的记录，符合普通并发操作的线性化边界。

一个包装器固定一个工作线程，保持目标调用顺序和目标内部状态简单。多线程生产者只争用短队列临界区，目标写入、错误构造、记录释放和最终 Flush 都在锁外执行。目标递归写回同一包装器会被工作线程标识拒绝，既阻止无限日志循环，也消除满队列 `BLOCK` 的自锁路径。

状态由 Sink 与工作线程各持有一个引用。普通析构关闭队列并等待线程，工作线程内触发最后一个 Sink 引用释放时则只关闭和交接引用，不等待自身。`DRAIN` 让工作线程消费队列，`DISCARD` 在锁内摘除队列后于锁外释放；两条路径最终都 Flush 目标并由最后一个状态引用统一销毁同步对象、错误快照和目标引用。
