# I18N_SPEC v1.0 — 官网多语言翻译规范与质量门禁

官网多语言版本（中文 / English / Русский）的翻译源格式与质量门禁规范。
译文网页（wwwroot/en/、wwwroot/ru/）由生成器从本目录体系的 markdown 源生成，
**手工编辑 wwwroot 下的译文页面是禁止的**——源与产物分离是防漂移的第一原则。

**翻译主体**：由 ZCode 会话执行全部翻译，不依赖任何外部在线翻译服务。
本规范同时是 `tools/check_i18n.py` 的判定依据：门禁红线全部可机器判定，
FAIL 的章节不算完成，**禁止调低 check_i18n.py 红线来"通过"**。

---

## 1. 文件与目录

- 中文事实源：`docs/book/NN-slug.md`（唯一事实源，多语言工作不回改中文源）。
- 译文源：`docs/book/en/NN-slug.md`、`docs/book/ru/NN-slug.md`——与中文源**同名镜像**，
  进仓库、可 review、可重生成。译文是受管内容资产，不是临时文件。
- 术语表：`tools/i18n/glossary.json`（zh→en/ru 单文件双语，见第 4 节）。
- 生成物：`wwwroot/en/`、`wwwroot/ru/` 整站镜像，由生成器 `--lang` 产出，禁止手编。
- 章节清单以 `docs/book/order.json` 为准（144 章；ch09 无中文 md 源，译文同样跳过，
  有效翻译总量 143 章 × 2 语言 + 门面页）。
- 门面页（手维护页 index/start/guide/benchmarks/reliability/api/book 目录）：
  以 `wwwroot/en/`、`wwwroot/ru/` 独立拷贝翻译，不走 markdown 管线（数量少、更新频率低）。

## 2. 翻译红线（机器门禁 G1–G8）

| 编号 | 红线 | 说明 |
| --- | --- | --- |
| G1 | 代码块逐字节保留 | fenced 代码围栏（c/bad/good/embed/term）内容与中文源完全一致；embed 路径、term 真实输出（含程序输出的中文）原样保留 |
| G2 | 行内代码一致 | 反引号 `` `...` `` 的 token 集合与中文源一致 |
| G3 | API 符号集合一致 | 正文（代码块外）的标识符（xrt*/xXXX 函数、XRT_* 等宏）出现集合与中文源一致——API 名错译比不译更糟 |
| G4 | 结构一致 | h2 节名按语义对应且数量一致（八节骨架不增减）；h3 数量一致（内容组织不重排） |
| G5 | 无中文残留 | 译文正文（代码块、行内码、URL、品牌白名单之外）不得残留 CJK 字符——防漏翻 |
| G6 | 体量合理 | 译文词数 / 中文汉字数 ∈ [0.30, 1.60]——防漏段（过低）与注水（过高） |
| G7 | frontmatter 对齐 | num/slug/type/api 与中文源一致；title/lead 已翻译 |
| G8 | 术语登记 | 中文源出现 glossary 已登记术语而译文未用对应译法 → WARN（连续两批命中率 <90% 升级为 FAIL）；白名单品牌词按表保留 |

G1–G5、G7 为硬门禁（FAIL 即阻断）；G6 阈值为护栏；G8 以命中率监控逐步收紧。

## 3. 语言风格

- **English**：技术写作直接清晰；术语以微软/谷歌技术文档惯用译法为准；
  不逐字直译中文习语（"避坑"→ "pitfalls"，"速查"→ "cheat sheet"）；
  中文长句拆分为英文短句；祈使语气用于操作指引。
- **Русский**：技术文档规范语体（научно-технический стиль）；
  术语以微软俄语文档与 ГОСТ 惯用为准；避免口语化；
  缩写词（API、TLS、HTTP 等）保留拉丁字母不转写。
- 共同：品牌词不译（XRT、xhttp、xws、xlang、xge、xserver、XUI、xywhsoft）；
  "第 N 章" 译为 "Chapter N" / "Глава N"；中文书名号内容转直译或斜体。

## 4. 术语表协议

- 术语表 `tools/i18n/glossary.json`：`{"terms": [{"zh": "...", "en": "...", "ru": "...", "note": "..."}]}`。
- **先入表，再使用**：遇到表外新术语，先登记术语表（一个 zh 术语在每种语言内只允许一种译法），
  再在译文中使用；同一阶段内保持一致。
- 冲突时以术语表为准；修订译法必须同步改表并复核同卷已译章节。
- 术语表只增不改语义；删除条目需在 PROGRESS 记录原因。

## 5. frontmatter 与内链处理

- frontmatter 各字段翻译规则：`title`/`lead` 翻译；`num`/`slug`/`volume`(结构值)/`type`/`api` 保留。
- 行内 ref 链接 `ref-xxx.html` 目标不改（en/ru 站点共用中文 ref 页面，
  待 ref 页多语言化阶段再单独处理——见 PHASES 收尾阶段）。
- 章间交叉引用文字（"见第 66 章"）译为 "see Chapter 66" / "см. главу 66"，章号以 order.json 为准。
- 外链 URL 原样保留。

## 6. 批次纪律与执行护栏

1. **翻译前必读原文全文**：禁止凭记忆或章节标题臆译；每章开译前通读 zh 源。
2. **批次推进**：每批 3–5 章，批内全部过 `check_i18n.py check` 才算完成；
   FAIL 章节修复后重跑，不带病推进。
3. **禁止跳章**：按 order.json 章号顺序推进；阶段内时间不够宁可少完成一批。
4. **双语顺序**：同卷先 en 后 ru（术语表按卷沉淀复用）；en 卷全绿后开 ru。
5. **中文源变更同步协议**：zh 章节修订（git log 可查）后，对应 en/ru 章节标记"待同步"，
   在 PROGRESS 遗留项登记，下一批次优先补译。
6. **生成物同步**：批次全绿后运行生成器刷新 wwwroot/en|ru 并双仓库提交
   （D:/GIT/xrt 源 + D:/GIT/home/host/xrt 产物），commit message 注明阶段与章号范围。
7. **禁止降红线**：check_i18n.py 的阈值与规则只允许收紧，不允许放宽来"通过"。

## 7. 防漂移说明（为什么有这些规则）

- 教程重写工程的最大教训：**产物与源分离 + 机器门禁**是长任务不漂移的根基。
  译文工程直接继承：所有红线可机器判定，人的自觉不作为质量依据。
- G1/G3 存在的原因：这本书的价值在代码契约。翻译过程中最危险的失败模式
  不是语言质量差，而是"顺手改了代码"或"凭记忆写了不存在的 API"——
  教程重写期间门禁拦下过数十次此类事故，翻译期同样会犯。
- G5 存在的原因：漏翻整段是最常见且最难肉眼发现的翻译缺陷。
- 术语表存在的原因：跨 143 章的长任务，同一术语前后译法不一致
  （例如 coroutine 一处译"корутина"另一处译"сопрограмма"）会让读者怀疑专业性；
  唯一事实源 + 先入表再使用是唯一低成本的约束方式。
- 批次纪律存在的原因：长任务以"小步全绿"推进，每次 commit 都是可回退的干净状态；
  任何一次大范围带病推进都会让回退成本指数级上升。

## 8. 收尾检查

**阶段收尾**（每阶段结束执行）：
1. `python tools/check_i18n.py check --lang <lang>` 全绿（0 FAIL）；
2. `python tools/check_i18n.py report --lang <lang>` 贴出度量表；
3. en/ru 站内链接校验 0 断链；
4. 更新 `docs/i18n/I18N_PROGRESS.md`（状态表 + 阶段记录）；
5. 双仓库提交并输出阶段总结（完成章数、批次、术语增量、遗留项）。

**全项目收尾**（所有阶段完成后执行）：
1. 三语言全站链接校验 + hreflang/sitemap 互指校验；
2. `check_i18n.py report` 全量漂移总报告（比例分布、术语命中率、同步状态）；
3. CI 接线（ci.yml 增加 check_i18n 步骤）；
4. PROGRESS/PHASES 终态更新，双仓库最终提交。

每阶段由固定格式提示词开启（模板与阶段表见 `docs/i18n/I18N_PHASES.md` 文末）。
