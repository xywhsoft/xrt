# Crypto 组合指南

密码原语必须按职责组合，不能因为都与安全相关就互相替代。完整函数、长度、重叠、错误和裁剪契约见 [Crypto API](../api/crypto.md)；本文只说明常见系统如何选择和连接这些原语。

## 先区分职责

| 需求 | 原语 | 典型入口 |
| --- | --- | --- |
| 内容摘要和指纹 | Hash | `xrtSha256`、`xrtSha384`、`xrtSha512` |
| 共享密钥消息认证 | HMAC | `xrtHmacSha256`、`xrtHmacSha512` |
| 从根秘密派生用途密钥 | HKDF | `xrtHkdfSha256`、`xrtHkdfSha512` |
| 加密并验证完整性 | AEAD | `xrtChaCha20Poly1305Seal`、`xrtAesGcmSeal` |
| 协商共享秘密 | ECDH | `xrtX25519Shared`、`xrtP256Shared` |
| 公钥签名与验证 | Ed25519、ECDSA、RSA | 对应 `Sign` / `Verify` 入口 |

普通 Hash 不证明消息来自谁；HMAC 要求双方预先共享密钥；HKDF 不加密数据；ECDH 只产生密钥材料；AEAD 不自动认证握手对端。协议必须把这些边界补齐。

## 会话组合

常见临时会话按下面的顺序建立：

1. 双方生成临时 X25519 密钥对。
2. 双方验证并计算共享秘密。
3. 把协议版本、双方公钥和握手 transcript 放入 HKDF 的 salt 或 info。
4. 从 HKDF 输出中派生独立的发送密钥、接收密钥和 nonce base。
5. 每条记录使用唯一且可验证递增的 nonce 执行 AEAD。
6. 握手结束和连接关闭时清除私钥、共享秘密和派生密钥。

[会话组合示例](../../examples/crypto/session/main.c) 使用 `X25519 -> HKDF-SHA256 -> ChaCha20-Poly1305` 完成一条记录的原位封装与打开。示例中的零 nonce 只表示新临时密钥下的首条序号；同一密钥下的后续记录必须递增，不能重新从零开始。

X25519 本身不认证对端。真实协议必须用证书签名、预共享密钥或其他身份机制绑定握手 transcript，否则仍可能遭遇中间人替换公钥。

## 摘要与认证

`xrtSha*` 适合文件摘要、内容寻址和协议要求的 transcript hash。任何人都能重算公开消息的 Hash，因此 webhook、内部消息和令牌完整性应使用 HMAC 或公钥签名。

验证固定长度 MAC、摘要或 AEAD tag 时使用 `xrtConstTimeEqual`，不要用遇到首个差异就返回的普通字符串比较。口令派生应使用 PBKDF2 等专用方案并保存独立 salt；HKDF 不是口令哈希。

## AEAD 与 nonce

ChaCha20-Poly1305 和 AES-GCM 都要求同一密钥下 nonce 唯一。无状态随机抽取不能为长期密钥提供绝对不重复保证；长连接通常使用随机连接前缀加单调记录序号。

解密必须在认证成功后才发布明文。xrt 的 `Open` 和 detached `Decrypt` 都保证认证失败不修改调用方输出。裸 ChaCha20 和裸 AES 块不提供认证，只应用于已有协议或更高层原语实现。

## 签名选择

Ed25519 的常见入口直接接收原始消息，并额外支持 context 和 prehash 模式。ECDSA 和 RSA 的当前入口显式接收摘要或摘要算法，不猜测曲线、编码和散列方式。签名和验签是对称公开能力：

- ECDSA 提供 P-256/P-384 的 raw 与严格 DER 签名、验签。
- RSA 提供 PSS 与 PKCS#1 v1.5 签名、验签；新协议优先选择 PSS。
- Ed25519 提供种子、可复用展开密钥、纯模式、context 和 prehash。

旧 SHA-1 和 MD5 只为 WebSocket、HTTP Digest 等历史协议互操作保留，不应用于新签名、口令或内容可信性设计。

## 签名文本包

需要导入人工可编辑的规则或配置时，先明确认证域，不能同时宣称“允许任意转码”和“验证原始文件未发生任何变化”：

- 原始字节认证覆盖磁盘上的逐字节表示。签名应放在独立文件或固定二进制封套中，并在转码、换行处理和字段解析前验证。
- 规范文本认证覆盖解码后的语义表示。发布端与导入端必须共同规定 UTF-8、BOM、换行、字段顺序、尾随空白和签名行格式；只有规范化结果进入 HMAC 或签名计算。

内嵌 `hmac-sha256=` 行且允许 UTF-8/UTF-16 输入时，应采用第二种模型。推荐的导入顺序是：

1. 使用 `xrtFileReadAllLimit` 限制源文件字节数，拒绝读取过程中继续增长并越过上限的文件。
2. 使用 `xrtEncodingGuess` 与 `xrtTranscode` 按 `XUTF_STRICT` 生成唯一 UTF-8 表示；无法可靠判断编码或存在非法码元时直接失败。
3. 只做一次最小扫描，要求签名行具有唯一、固定的 ASCII 名称，是最后一条物理记录，并且值恰好是 64 个十六进制字符。
4. 使用固定 32 字节缓冲和 `xrtHexDecode` 解码期望值，对签名行之前的精确 UTF-8 字节调用 `xrtHmacSha256`，再用 `xrtConstTimeEqual` 比较。
5. 认证成功后才解析正文。简单的 `key=value` 应使用长度视图和分隔符解析；正则表达式只负责规则本身，不应替代整份配置的语法分析器。
6. 对文件大小、行长度、字段数量、规则数量和单条模式长度分别设置上限；未知字段、重复单值字段、空标识和零条规则都应明确拒绝。
7. 把字符串、规则数组和 `xregexset` 构建到临时对象中，全部解析和编译成功后一次发布。失败路径释放临时状态，不改变当前生效规则。

密钥应以显式长度字节视图传入，不能依赖 `strlen`，并在不再使用时清除。错误上下文至少保留读取、转码、封套、认证、字段解析或规则编译阶段，以及可用的行号和字段名；不能把所有失败压成一个无信息的布尔值。

HMAC 适用于彼此信任且共享密钥的发布者和导入者，但每个验证者也同时具有伪造能力。规则包需要向不受信任的节点分发时，应改用 Ed25519、ECDSA 或 RSA 签名，让节点只持有公钥。无论采用哪一种算法，都应先认证再编译未受信任的正则规则，避免让非法输入消耗无界编译资源。

## 所有权与清理

摘要状态、AEAD 状态和曲线值由调用方持有，不隐式分配。返回 `str` 的便利函数由 `xrtFree` 释放；固定缓冲入口不转移所有权。私钥、共享秘密、会话密钥、口令和不再使用的中间状态应调用 `xrtSecureZero` 清理。
