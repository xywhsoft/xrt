# 重构执行规则

## 范围边界

本次重构只处理 XRT 自身。XLang 标准库、编译器宿主、运行时绑定、生成代码、仓库同步
和独立扩展库均不属于当前实现范围，不作为 XRT 模块、重构资产、发布门禁或完成度分母。
XRT 稳定后再以独立任务设计语言适配；当前阶段只保证公共 C 契约具有通用、稳定、可绑定
的性质，不读取外部仓库状态来决定 XRT 功能是否完成。

XRT 不是互不相关功能的合集。新增或保留能力必须符合 [产品边界](SCOPE.md) 的体系准入
规则；仅因某个外部项目可能使用、已有历史实现或实现成本已经发生，不能成为进入 XRT
发布面的理由。

## 基线检查

```text
python tools/refactor_audit.py check --require-verified
python tools/refactor_audit.py summary
python tools/refactor_audit.py assets --module file
```

当前基线包含 `dev/ver1` 下的全部文件。`pending` 表示尚未完成逐文件审计，不表示文件可以忽略。
当前固定基线共 `669` 个源资产、`475893` 行可审计文本，已经全部达到 `verified`；上述
严格检查必须持续保持通过。后续修改当前实现不会改变只读基线总量，但如果承接文件、
模块或验证证据被删除，检查仍会失败，不能把这项完成状态当作永久豁免。

旧版不是待删除目录，而是重构资产库。每个模块开始前必须先建立旧实现、公共 API、测试、文档、范例、基准和历史缺陷的完整清单；不能只读主实现文件，也不能因新版已有同名能力就跳过旧版已经压实的边界。重构进度按已闭合的能力和证据计算，不按新写代码量或删除旧文件数量计算。

重构的目标不是把旧文件换成新文件。旧版中已经证明质量良好的算法、平台分支、体系化功能和测试应优先复用或修订；只有满足后文替换约束时才重新实现。新版存在一个近义 API、单个正常用例通过或代码结构看起来更新，都不能证明旧资产已经被继承。

`check` 同时验证旧树哈希、模块清单、当前承接文件和 `verified` 证据。已经删除、改名或拆分的当前文件不能继续充当证据；模块、目标和证据必须分别使用重复参数记录，不能把多个值拼入一个参数。模块整体迁入扩展库时，在 `dev/refactor/relocations.json` 登记扩展清单和产品根目录；审计器只接受唯一存在的同相对路径资产，特殊改名必须逐项登记，不能用忽略规则绕过失效证据。

完整读完旧文件后，使用台账命令记录结论、承接模块和证据：

```text
python tools/refactor_audit.py mark --path lib/example.h --audit reviewed --decision refine --module example --target src/example/example.c
```

`mark` 只用于未分段资产或已经按整文件记录的资产。文本资产一旦存在细分区间，必须使用 `revise-range` 更新，避免整文件操作覆盖既有逐行结论。

旧文件同时承载多个模块时，必须按稳定行区间分别记录，不能因迁移其中一项能力而提前完成整文件：

```text
python tools/refactor_audit.py mark-range --path lib/base.h --start 166 --end 209 --audit verified --decision refine --module core --target src/core/core.c --evidence tests/core/test_ref.c
```

`reviewed` 只表示已经逐行审计并确定去向；`migrated` 表示新版已经承接；`verified` 还要求测试、文档和裁剪证据齐全，并且必须记录有效决策、已知模块、当前承接文件、验证证据和结论说明。跨模块旧文件在所有区间完成前保持文件级 `pending`，台账单独统计已经闭合的历史代码行。

## 单模块工作流

1. 枚举旧实现、公共声明、调用点、测试、文档、范例、基准和问题记录。
2. 逐行阅读资产，整理功能、边界、缺陷、性能特征和依赖关系。
3. 建立旧能力到新能力的映射，决定保留、修订、替换、合并或退役并记录理由。
4. 先设计公共契约和文件边界，再迁移已经证明合适的实现，不为重构而重写。
5. 迁移每一项旧测试，或用更严格测试取代；退役测试必须说明旧契约为何不再成立。
6. 对旧版已压实的边界做等价或更强的故障、平台、压力和性能验证。
7. 运行当前模块的 GCC、TinyCC、32 位、裁剪和单头文件门禁；裁剪依赖使用 `--trim-only` 独立快速验证。
8. 编写完整 API 文档和可运行范例，并修正旧文档中已经发现的漂移。
9. 核对功能没有倒退、重复实现没有增加、代码量和依赖代价合理后，才能标记稳定。

每个模块的审计记录还必须能回答四个问题：旧版哪些代码被直接复用，哪些能力被
修订承接，哪些测试或边界被更强证据替代，哪些内容被退役以及原因。无法回答时，
模块最多处于 `reviewed`，不能因为新版实现已经编译而标记 `migrated` 或
`verified`。

## 资产闭环

模块进入 `stable` 前，`config/modules.json` 的 `legacy` 清单必须覆盖所有直接相关旧资产，并满足以下条件：

- 旧实现中的每项有效能力都有新 API、内部承接点或明确退役理由。
- 每个旧测试都已迁移、增强替代或有证据地退役。
- 旧文档和范例已用于核对使用手感、遗漏能力和历史语义，不能仅作为文字参考。
- 历史基准、故障记录和平台分支已转化为当前门禁；无法在本机执行的平台必须保留可复现验证方案。
- `verified` 证据同时指向实现、测试、文档和裁剪结果；只完成代码迁移最多标记为 `migrated`。

同一旧资产可服务多个新模块。公共大文件按行区间记录，各模块分别闭环，禁止用另一个模块的验证结论代替当前模块的审计。

模块申请稳定前执行：

```text
python tools/refactor_audit.py assets --module file --require-verified
```

该门禁只接受当前模块名下已经达到 `verified` 的资产结论；共享旧文件仍需按当前模块记录对应区间和证据。

## 替换约束

只有满足以下至少一项时才替换旧实现：

- 存在可复现的正确性或安全缺陷。
- 旧结构造成循环依赖、重复实现或无法有效裁剪。
- 新方案有经过基准验证的显著性能或内存收益。
- 旧实现无法形成清晰、稳定且可扩展的公共契约。

替换方案必须说明额外代码量、运行时成本、平台成本和维护成本。无法证明综合收益时，优先修订旧实现。

## 兼容边界

本次重构不提供旧 C API 的迁移期、别名、版本后缀或 `Ex`/`Ex2` 双轨入口。当前公共
头和 API 文档是唯一契约；旧名称只存在于 `dev/ver1` 审计记录中，不能因为旧迁移
指南仍有示例就重新进入声明、链接符号或单头文件。

不保留源码兼容不等于拒绝协议和数据兼容。HTTP 历史语法、Cookie 日期、TLS 线路
兼容字段、字符集和文件格式等互操作能力，应由相应协议文档明确接受边界，并通过同一
套当前 API 表达。协议必须接收的历史形式不能变成第二套函数，旧 API 也不能借“协议
兼容”名义继续存在。

重构期间可以按模块逐步替换内部调用点，但任一发布候选只能包含最终名称和最终对象
模型。用于开发过程的临时适配器必须在对应模块标记 `verified` 前删除，并由搜索、
导出符号、单头和独立消费者门禁证明没有遗留。
