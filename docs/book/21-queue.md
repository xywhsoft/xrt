## 导读

队列是卷三唯一**线程安全**的容器——它本来就是为跨线程传数据而生的，也因此是卷三与卷六（并发）之间的桥：本章教容器的用法与纪律，卷六把它接进线程、协程与 Channel 的完整体系——先在这里把单件武器用熟，到卷六才谈阵型。XRT 提供三种拓扑：**SPSC**（单生产者单消费者，最快）、**MPSC**（多生产者单消费者，事件聚合的标准形）、**MPMC**（任意多对多，最通用也最贵）。三者共享一套使用语言：**绑定外部槽位**（零内部分配）、**批量收发**（PushBatch/PopBatch）、**关闭停机协议**（Close 后生产者停、消费者取尽）。本章把这三件事讲透，并给出"拓扑优先"的选型纪律——通用性是有价格的，能确定拓扑就不要为它付钱。

## 引入

一个日志线程要接收全部工作线程的日志事件——这是 MPSC：多个生产者、一个消费者。一个渲染线程与一个解码线程一对一传帧——这是 SPSC。一个任务分发器让任意线程投递、任意线程领取——这是 MPMC。三个场景如果都用"一把互斥锁包一条普通队列"解决，能跑，但每秒百万次收发的路径上，锁的争用会把多核并行的优势磨平——十核机器八个核在等锁是常见惨案；而锁方案与无锁方案的差异，在本章练习的对照测量里会给出你机器上的具体数字。

无锁队列用原子操作替代锁：生产者与消费者各自推进自己的指针、以原子发布让对方可见——SPSC 甚至只需要两个原子的头尾指针，单条中位数百万级每秒；MPMC 要为每个槽位做发布同步，单条最贵、但批量接口把摊还成本压下来（仓库基准：批量 32 条时 1.34 亿条每秒）。**拓扑越确定，同步越少**——这就是"拓扑优先"：日志聚合确定是 MPSC 就用 MPSC，不要"以防万一"上 MPMC。

## 概念

### 三种拓扑一张表

| 队列 | 拓扑 | 单条开销 | 典型场景 |
| --- | --- | --- | --- |
| SPSC | 一对一 | 最小 | 两线程流水线（解码→渲染） |
| MPSC | 多对一 | 小 | 事件聚合（全线程→日志/监控线程） |
| MPMC | 任意 | 最大 | 任务分发、工作窃取 |

### 三个共享语言

```diagram flow
- 绑定槽位：InitBuffer 绑调用方数组——队列本身零内部分配，容量即数组长度
- 批量收发：PushBatch/PopBatch 一次过一批，摊还同步成本
- 关闭停机：Close 一次性宣布"不再有生产者"；消费者把余量取尽后自然终止
```

**绑定槽位**意味着队列的存储由调用方提供（栈数组、静态区、池都行）——队列只提供同步与索引逻辑，这也是 `_noalloc` 契约测试覆盖的形态之一。**批量接口**的返回值是"实际完成数"（`xqueuebatchresult` 的 `Count`）——队列可能未满但你请求的部分成功，返回值告诉你推进到了哪里。**关闭停机**是并发程序的终止协议核心：Close 必须在"确认全部生产者结束"后调用；已入队的数据不丢，消费者继续取尽。

### FIFO 与饥饿

三条队列都是 FIFO：先入先出、跨批保序。MPMC 的多个消费者并发 PopBatch 时，队列内部保证**每条消息恰好被领取一次**——不会重复投递，也不需要消费者协调。"公平性"则不做承诺：高频消费者可能长期领得多——需要加权公平就在业务层做（配额计数），不指望队列。

### 与卷六的关系

本章只教"单机多线程之间传指针"——跨进程的传输属于卷七网络与序列化的领地。卷六会把队列放进完整的并发体系：与协程调度器的配合（阻塞等待变成可等待的 Pop）、Channel 的"带关闭语义的队列"封装、以及什么时候该用 Future 代替队列。现在只需要记住：**队列传的是 `ptr`**——消息对象的生命周期归发送方分配、接收方处理，跨过队列边界后不要再由发送方释放。

### 容量与背压的第一次相遇

队列容量（槽数组长度）不是越大越好，它是**背压**的第一道阀门：队列满时 PushBatch 部分成功，生产端感知到推不动就该减速或缓冲——这正是第 59 章网络背压的微缩版。容量规划的两个极端都有代价：容量太小，突发流量瞬间打满，生产者频繁空转重试；容量太大，内存驻留上涨，而且消费者故障时积压的消息更多、恢复更久。经验起点：容量取消费者一个调度周期处理量的 2 到 4 倍，再用第 6 章统计与队列水位实测校准。队列的 Count 是公开字段——生产端的快满检查零成本。

### 无锁的纪律边界

无锁指内部不用互斥锁，不等于随便并发——两条纪律仍然成立。其一，SPSC 的两端各自独占：一个生产者线程、一个消费者线程；多线程 Push 同一条 SPSC 是未定义行为，那是 MPSC 的场景。其二，槽内数据的发布时序由队列保证，但你自己的消息对象必须入队前写好、出队后才写——跨过队列边界的写竞争不是队列的责任。把这两条纪律记牢，无锁队列的快才真正属于你。

## 契约

- **绑定存储**：槽位数组由调用方提供；容量 = 槽数组长度；队列零内部分配。
- **批量核对**：Push/Pop 的返回 `Count` 是实际完成数，满载与空载都可能部分成功。
- **停机协议**：`Close` 在全部生产者结束后调用一次；已入队数据可继续取尽；关闭后 Push 失败。
- **恰好一次**：多消费者并发 Pop，每条消息恰好被领取一次，无需外部去重。
- **消息归属**：队列传 `ptr`；对象由发送方创建、接收方处理，归属纪律同第 5 章；入队前写好、出队后才写。
- **拓扑优先**：能确定一对一/多对一就选 SPSC/MPSC；MPMC 为通用性付最高单价。

### 选型速断：三问定队列

实际选型时三个问题按序问自己。第一问：**几条流水线？** 两条线程一对一，SPSC 到手，结束。第二问：**谁聚合？** 多个源汇到一个处理者（日志、监控、事件循环），MPSC。第三问：**真的任意对任意吗？** 大量写着 MPMC 的场景，细看其实是"多个生产者 + 若干消费者池"——消费者数量固定且任务等价时，MPSC 到分发器、分发器 SPSC 到各消费者，两级专用队列常常比一级 MPMC 更快也更清晰。三问答完还剩 MPMC 的，才是真需要它的场景：动态工作窃取、无中心分发的任务图。把这三个问答写进设计文档的选型段落，评审时就有据可查。

## 避坑

### 坑 1：忽略批量返回值（压力测试下的计数对不上）

症状：偶发丢消息或消息滞留——压力测试下计数对不上，低负载时一切正常。

原因：`PushBatch` 请求 32 条、队列只剩 5 个空位时只进了 5 条；不核对 `Count` 就当 32 条全进了，后续消息全部错位。

```c bad
xrtMPMCQueuePushBatch(&Queue, pMessages, 32u);   /* 返回值被丢弃 */
/* 队列可能只收下前 N 条——剩下 32-N 条静默滞留在发送缓冲 */
```

```c good
xqueuebatchresult Sent = xrtMPMCQueuePushBatch(&Queue, pMessages, 32u);
if ( Sent.Count < 32u ) {
	RetryLater(pMessages + Sent.Count, 32u - Sent.Count);   /* 从断点续传 */
}
```

### 坑 2：生产者还没停就 Close（停机协议被打破）

症状：停机阶段偶发崩溃或"最后一批消息丢失"；复现依赖线程时序，越压测越难捉——这正是停机协议要按固定顺序执行的原因。

原因：`Close` 的前提是**全部生产者结束**——还有线程在 Push 时关闭，关闭后到达的 Push 行为未定义（或按失败处理但你的代码没当回事）。

```c bad
/* 主线程：不等工作线程 */
xrtMPMCQueueClose(&Queue);
/* 某工作线程此刻还在 Push——停机协议被破坏 */
```

```c good
for ( i = 0; i < WorkerCount; ++i ) {
	xrtThreadWait(Workers[i], NULL);   /* 先等全部生产者结束（第 48 章线程 API） */
}
xrtMPMCQueueClose(&Queue);            /* 再关闭 */
DrainAndShutdown(&Queue);             /* 消费者取尽后自然终止 */
```

## 练习

### 基础：FIFO 与批量核对

复现 MPMC 示例：容量设 4、分三批 Push 共 6 条（中间一批会部分成功），按返回值断言实际推进，最后一次性取尽输出顺序——先在纸上算出哪一批会部分成功、推进到第几条，再与程序对拍。

### 进阶：双线程流水线（停机协议实战）

SPSC 队列连接两个线程：生产者发 100 万个递增序号指针（指向静态数组的槽），消费者核对严格递增后结束；用停机协议收尾。提示：序号取模映射到固定槽数组，避免一百万次分配。

### 挑战：日志聚合器（MPSC 的完全体练习）

MPSC 队列实现最小日志线程：4 个工作线程各产生十万条 `{线程号, 序号}` 事件（批量 64 发送），日志线程聚合计数并验证"每线程内部序号连续"。验收标准：总计数零丢失零重复；每线程序号连续无空洞；停机干净（日志线程自然退出而非被杀）。

## 速查

| 知识点 | 速查 |
| --- | --- |
| 三拓扑 | SPSC 一对一最快 / MPSC 多对一 / MPMC 任意最通用，接口三件套完全同构 |
| 绑定存储 | `InitBuffer(队列, 槽位数组, 容量)`；零内部分配，容量即数组长度 |
| 批量纪律 | 返回 `Count` 必核对；部分成功从断点续传 |
| 停机协议 | 全生产者结束（join）→ `Close` → 消费者取尽 → 自然终止，四步顺序不可乱 |
| 恰好一次 | 多消费者并发 Pop 不重不漏，无需外部去重 |
| 消息归属 | 传 `ptr`；发送方创建、接收方处理 |
| 拓扑优先 | 能确定拓扑就不用 MPMC——通用性按单条开销计价 |
| 选型三问 | 一对一？谁聚合？真任意对任意？——答完再定 |
| 容量起点 | 消费者单周期处理量 × 2~4；快满检查读公开 Count |
