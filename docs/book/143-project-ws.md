## 导读

卷十三项目五：**实时推送服务**（pushd）——WebSocket 长连接网关：客户端连上后订阅频道（`{"op":"sub","ch":"metrics"}`），服务端把后端产生的消息推给频道全体成员（广播）；支持踢出（kick）、频道成员查询、优雅停机（先 Seal 再清场的完整流程）。它是 xws 四章（第 109-112 章）的综合运用：**路由端点**（第 112 章 `xrtWsServerRoute`——Origin 策略与授权回调的安全入口）、**连接组**（第 111 章 `xwsgroup`——成员管理/快照广播/Seal 半关闭）、**发送路径**（第 110 章 writer/引用/压缩——广播的组播原语）、**连接生命周期**（第 109 章 pause/resume/关闭协议）。新加的系统约束是**长连接并发**：数百条连接同时活着的生命周期管理、广播的扇出放大、慢客户端对整体的影响——项目一二四的经验加上这条后在静态服务器（第 144 章）汇成全栈。

## 引入

需求场景：监控仪表盘要实时显示服务指标——轮询（1 秒一拉）延迟高且浪费；SSE（第 106 章）单向够用但要客户端分频道的**订阅语义**与双向控制（sub/unsub/kick）——WebSocket 的双向长连接是自然形态。pushd 的接口设计：**连接协议**（升级到 `/ws`，子协议 `push.v1`）；**订阅消息**（JSON：sub/unsub 频道名）；**推送消息**（JSON：频道+载荷+序号——客户端按序号检漏）；**管理动作**（kick 指定连接、列出频道成员——运维接口）。**验收标准**：① 100 并发连接三频道广播全达（无漏发——序号对账）；② 慢客户端（收但不读）不拖快客户端（隔离验证）；③ kick 立即生效（后续消息不到达被踢者）；④ 优雅停机：Seal 后新连接拒绝、在途消息送达、全部连接关闭后才退出（终态计数对账）；⑤ 广播内存与连接数×消息大小解耦（引用发送——stats 验证）；⑥ 背压下服务稳定（广播不因单连接满而阻塞）。

## 概念

### 架构：三层组装

```diagram flow
- 入口层：HTTP Router + xrtWsServerRoute("/ws")——Origin 三档默认（SAME_HOST_OR_ABSENT）
  + Authorize（可选令牌校验）；Open 回调 Ref+GroupAdd
- 会话层：每连接状态（订阅频道集/最后序号/身份）挂在组外的 Map
  ——组管成员关系、Map 管业务状态（职责分离）
- 广播层：快照（GroupSnapshotCreate）→ 逐成员 GroupTextAsync
  ——引用载荷（一份内存 N 连接共享）；慢连接按策略（跳过/记慢）
```

**订阅集的存放决策**：连接组只管"连接的集合"（第 111 章边界——不管消息编码不关业务）；**频道→连接集**的映射是业务状态——独立的多组结构（每频道一个 `xwsgroup`）或 Map<频道, 组>。决策：**每频道一组**——组的并发语义（唯一成员/引用/快照）正是频道成员管理需要的，免费获得；备选 Map<频道, 连接数组>要自己实现全部并发语义——否决。

### 模块选型与理由

| 步骤 | 选型 | 理由 |
| --- | --- | --- |
| WS 入口 | `xrtWsServerRoute` 固定端点 | 自动响应五类（405/403/400/426/500）+ Origin 默认——安全默认免费 |
| 成员管理 | 每频道一个 `xwsgroup` | 唯一成员/容量/快照并发语义现成 |
| 广播 | 快照 + 逐成员引用发送 | 一份载荷 N 连接（内存解耦——验收 ⑤）；快照保稳定遍历（第 111 章坑 1 的正面形态） |
| 载荷构造 | JSON（第 32 章） | 订阅/推送消息的序列化；序号字段支撑对账 |
| 慢客户端 | 跳过+记慢（策略可换） | 单连接 AGAIN 不拖整体（验收 ②⑥）——组播"每连接独立受理"语义 |
| 停机 | Seal→排空→逐频道关闭→销毁 | 第 111 章停机模板的直接运用 |
| 业务状态 | Map<连接, 订阅集> | 连接的业务上下文（组外的应用层结构） |

### 广播管线：从后端消息到 N 个客户端

```diagram flow
- 后端消息到达（生产者：定时器/上游订阅）
- 构造载荷：JSON 编码（频道+载荷+全局序号递增）
- 查频道组：GroupSnapshotCreate（稳定成员快照——加引用）
- 逐成员：GroupTextAsync（引用载荷）
  ——AGAIN/失败：慢连接策略（跳过+计数；可选踢出）
- 快照销毁（归还成员引用）
```

**序号的作用**：每频道单调递增——客户端检测漏收（收到 3 和 5——4 丢了：主动 re-sync）。**引用发送的组播升级**（第 110 章）：载荷一份、N 连接的队列各持引用——释放回调计数（最后一个写完才真释放）；`GroupTextAsync` 内部正是这个形态。**慢连接策略的三档**：跳过+记慢（默认——丢一帧可接受，客户端 re-sync）；踢出（配置阈值——慢性劣化连接清理）；无界等待（**不提供**——单连接拖死全体违反验收 ②⑥）。

### 订阅协议与消息处理

收到消息（第 109 章事件）→ JSON 解析（第 32 章）→ 按字段 `op` 分派：**sub**（校验频道名合法→加入对应组 `GroupAdd`——首建组则创建）；**unsub**（`GroupRemove`+引用归还）；**心跳**（客户端 ping——连接层自动 Pong 已处理（第 109 章），应用层可选回显在线状态）。**非法消息**：解析失败回错误帧（JSON 错误码）不断连（协议宽容——损坏一帧不代表连接坏）；频道名非法回错误——**每个错误可定位**（第 4 章错误模型的应用消息版）。

### 优雅停机全流程

第 111 章停机模板在 pushd 的完整展开：**第一步**停止接受（监听层 Drain——新 HTTP 升级不再受理）；**第二步** Sealing 全部频道组（`GroupSeal`——幂等；新订阅进不来、已有成员照常收发）；**第三步**终末广播（"server shutting down"帧——给客户端明确信号而非静默断）；**第四步**逐连接关闭（`ConnClose` NORMAL 码——协议化告别）；**第五步**等 Close 回调计数归零（全部连接终态）；**第六步**销毁组与路由（`Release` 的 Data 生命周期在此收尾——第 112 章"Router 与全部连接退出后恰好一次"）；**第七步**停 Engine。**验收 ④ 的对账点**：关闭帧送达（客户端收到了 shutting down）+ 无泄漏（组的成员计数归零）+ 退出码 0。

### 与前面项目经验的对位

十二条经验（第 142 章清点）在长连接形态的重放与新增：**验收先行**（六条——并发与时序条目占比上升）；**形态决定容器**（频道=组、订阅集=Map、消息=JSON——三形态三容器）；**视图即取即弃**（消息事件的视图即解析即分派——不留缓冲）；**分层换件**（换传输层 TLS/换序列化 XSON 是单层）；**平台事实进设计**（Origin 策略与子协议协商是 WS 的"平台事实"）；**预算先算**（广播扇出 = 消息率×连接数——背压与慢策略的预算依据）；**测试四象限**（并发测试成为主战场：100 连接×三频道×序号对账）。**新增两条**：**扇出是放大器**（1 条后端消息 × 1000 连接 = 1000 次发送——广播路径的每纳秒都被放大，引用发送不是优化而是必需）；**长连接的状态清理是最终考验**（短连接的清理在每次请求后自然发生；长连接的清理只在停机与踢出——泄漏更隐蔽，终态计数对账是唯一可靠的验收）。

### 实现走查：广播与订阅的核心源码

pushd 的两个核心循环——订阅处理与频道广播——的源码形态（在教学示例之上给出关键段走查）：

```c
/* 消息事件：JSON 协议分派（sub/unsub） */
static void on_message(xwsconn* Conn, const uint8_t* Data,
	size_t Size, ptr Ctx)
{
	pushd* S = Ctx;
	xvalue Msg;
	xstrview Op, Ch;

	/* 解析失败：错误帧回复，连接保持（宽容契约） */
	xvalue* V;
	if ( !xrtJsonParse(Data, Size, &Msg) ||
		((V = xrtValueObjectGet(Msg,
			XRT_STR_LITERAL("op"))) == NULL) ||
		!xrtValueGetString(V, &Op) ) {
		send_error(Conn, "bad message");
		return;
	}
	if ( ((V = xrtValueObjectGet(Msg,
			XRT_STR_LITERAL("ch"))) == NULL) ||
		!xrtValueGetString(V, &Ch) ||
		!channel_name_valid(Ch) ) {
		send_error(Conn, "bad channel");
		return;
	}

	if ( xrtStrEqual(Op, XRT_STR_LITERAL("sub")) ) {
		xwsgroup* Gr = pushd_channel(S, Ch);  /* 取或建 */
		xrtWsGroupAdd(Gr, Conn);               /* 幂等 */
		send_ok(Conn, "subscribed");
	} else if ( xrtStrEqual(Op, XRT_STR_LITERAL("unsub")) ) {
		xwsgroup* Gr = pushd_find(S, Ch);
		if ( Gr != NULL ) { xrtWsGroupRemove(Gr, Conn); }
		send_ok(Conn, "unsubscribed");
	}
}

/* 频道广播：快照 + 引用发送 + 慢连接跳过 */
static void pushd_broadcast(pushd* S, xstrview Ch, str Payload)
{
	xwsgroupsnapshot* Snap;
	size_t i;

	xwsgroup* Gr = pushd_find(S, Ch);
	if ( (Gr == NULL) || xrtWsGroupSealed(Gr) ) { return; }
	Snap = xrtWsGroupSnapshotCreate(Gr);   /* 稳定快照 */
	for ( i = 0; i < xrtWsGroupSnapshotCount(Snap); i++ ) {
		xwsconn* C = xrtWsGroupSnapshotGet(Snap, i);
		xwsgroupop* Op = xrtWsGroupTextAsync(Gr, view(Payload));
		if ( Op == NULL ) { S->SlowCount++; }  /* 跳过+记慢 */
		else { xrtWsGroupOpDestroy(Op); }
	}
	xrtWsGroupSnapshotDestroy(Snap);       /* 归还成员引用 */
}
```

**走查要点。** ① `on_message` 的分派顺序：先整帧解析（坏帧回错误不断连）、再字段校验、后操作执行——**每级错误独立可定位**（bad message/bad channel/成功回执）。② `pushd_channel` 取或建组——首订阅创建组、`GroupAdd` 幂等（重复 sub 同频道安全——第 111 章唯一成员语义的兑现）。③ `pushd_broadcast` 的快照循环是坑 1/2 的正面形态：快照稳定遍历、组级异步操作、失败跳过计数——三件契约一次到位。④ 停机路径的 `GroupSealed` 检查：Seal 后广播自然静默（终末广播在 Seal **前**发——顺序即语义）。

### 验收矩阵与并发测试设计

六条验收的测试矩阵（第 132 章四象限的长连接版）：**正向**——100 连接三频道×1000 帧广播序号对账（验收 ①）；**并发竞态**——广播与订阅/退订并发（快照语义的实测）、广播与 kick 并发（Remove 后不触达——验收 ③）；**慢客户端**——1 慢（收不读）+99 快（验收 ②：快的序号不受影响）；**背压**——注入生产率 > 消费率（验收 ⑥：服务稳定、慢计数上升）；**停机**——停机时 50 活跃连接（验收 ④：shutting down 帧全达、计数归零、退出码 0）；**资源**——OOM 逐点（广播路径分配失败——跳过该帧不崩）。**测试的客户端侧**也要并发框架——第 58 章 executor 驱动 100 个虚拟客户端（连/订/收/对账）——**测试代码本身是并发的**，它的正确性靠序号对账（不靠时序假设）。

## 契约

- **端点安全**：`xrtWsServerRoute` 固定端点——Origin 三档默认（SAME_HOST_OR_ABSENT）+ Authorize 可选令牌校验；Open 借用连接、长期持有须 Ref 后存（第 112 章契约）。
- **频道即组**：每频道一个 `xwsgroup`——成员语义（幂等 Add/容量拒绝/稳定快照）由组提供；订阅集与成员管理分离（业务归应用层）。
- **广播管线**：快照（稳定遍历+加引用）→ 逐成员引用发送 → 快照销毁归还引用；载荷一份内存 N 连接共享（内存与扇出解耦）。
- **慢客户端三档**：跳过+记慢（默认）/踢出（阈值）/不提供无界等待——单连接不拖全体。
- **序号协议**：每频道单调递增——客户端按序号检漏并主动 re-sync（重启不丢语义的运维红利）。
- **消息宽容**：单帧解析失败回错误帧不断连；每个错误可定位。
- **停机七步**：停接→Seal（幂等）→终末广播→逐连接 Close→计数归零→销毁组与路由→停 Engine——终态对账。
- **Data 生命周期**：路由 Release 在 Router 与全部连接退出后恰好一次（第 112 章契约）。
- **踢出语义**：GroupRemove 先出组、再 ConnClose——出组后的广播不再触达被踢者（验收 ③ 的机制基础）。

### 交付形态与运维接口

pushd 的交付与运维设计：**部署形态**——独立进程（单头或静态库链接——第 131 章选型）；监听地址/频道容量/慢阈值从命令行或环境（第 42 章）读入——**工具的配置面**保持最小（三个参数够部署；复杂配置是 configd 的领域）。**运维接口**——管理端点（HTTP：列频道/成员数/慢计数/踢出）挂在同一 Router 的另一路径（第 104 章 HTTP 路由与 WS 端点共存——第 112 章"一个 Router 两类端点"的形态）；输出 JSON（第 32 章）供脚本消费。**可观测性**——连接计数/频道计数/广播速率/慢计数周期打点（第 37 章 logger 或直接 stdout JSON Lines——第 138 章 file_json 形态）；stats（第 6 章）监控内存水位。**优雅重启**——停机七步 + systemd 式监督：重启窗口客户端重连（第 109 章重连是客户端责任）+ 序号 re-sync 补齐丢失帧——**重启不丢语义**是序号协议的运维红利。

### 与 SSE 推送服务的边界复查

pushd 完成后值得复查第 106 章的选型判断：什么时候 SSE 够、什么时候必须 WebSocket？pushd 的三个需求里，**频道订阅**（客户端告诉服务端要什么）与 **kick 管理**（双向控制）是 SSE 做不了的——SSE 只能服务端推、客户端没有上行通道（订阅要靠 URL 参数——频道多了不现实）；**序号推送**本身 SSE 也能做（SSE 也有 id 字段与 Last-Event-ID 续传——第 106 章的机制）。所以分界线精确化：**纯下行推送用 SSE**（更简单——走 80 端口、自动重连浏览器内建）；**需要客户端上行控制（订阅/确认/心跳定制）用 WebSocket**。pushd 的订阅语义使它站在 WS 一侧——但如果需求退化为"全员广播同一流"（如全站公告），SSE 是更轻的答案。**选型复查**（每次实现完一个方案后回头看替代方案）是设计能力的组成部分——它让下一次选型更快更准。

### 压测方法与容量规划

第 135 章方法在长连接服务的落地：**压测问题**（"1000 连接×3 频道×100 帧/秒的广播下，P99 帧延迟与内存水位是多少？"——先写问题再搭实验）；**负载模型**——虚拟客户端（executor 驱动：连接/订阅/收帧/对账四阶段）+ 生产者（定时器定速率）——**两端都是确定性脚本**（无真网络依赖，本地回环——第 103 章 mock 思想的压测版）；**度量**——帧延迟分布（发送到接收的延时直方图——第 41 章时间戳打点）、内存水位（stats 周期采样）、慢计数轨迹；**扫描**——连接数梯度（100/500/1000）× 速率梯度（10/100/1000 帧每秒）的 sweep——拐点（哪个维度先饱和：内存？扇出 CPU？Engine Worker？）指认扩容方向。**容量规划产出**——单实例的推荐负载带（如"≤800 连接且 ≤200 帧/秒时 P99 < 50ms"）+ 超出时的动作（加实例/降帧率/频道分片）。

### 复盘：项目五的新增经验

pushd 在十二条之上新增的经验：**扇出设计先于优化**（广播路径的引用发送/快照/跳过是设计决策不是性能补丁——架构期就要定）；**长连接的终态对账**（连接/组/订阅集三类状态的清理验证只能靠计数归零——第 109-111 章各层的"恰好一次"在项目层汇成一个对账表）；**序号是廉价的自愈协议**（一个单调整数换来漏检+re-sync——比确认重传机制便宜两个数量级，够用就是好协议）；**测试客户端也是被测系统**（并发测试框架的正确性不能靠时序假设——序号对账同样适用于测试代码自身）；**运维接口是产品的一部分**（列频道/踢出/慢计数不是"以后加"而是交付定义的一部分——第 103 章五段超时同理：可运维性在设计期决定）。五条累计十七条——最后一个项目（静态服务器收官）将检验它们在**全栈组合**下的韧性。

## 避坑

### 坑 1：遍历组时直接发（无快照）

症状：广播循环中成员增删——迭代错乱或漏发（新连入的没收到本帧、刚退的在快照外被发）。

原因：组的 Count/成员是瞬时态——遍历期间集合在变。**快照是稳定遍历的唯一正解**（第 111 章坑 1）：锁外分配+保序增持——遍历期间的增删不影响本快照。

```c bad
n = xrtWsGroupCount(pGroup);
for ( i = 0; i < n; i++ ) { 发(第 i 个成员); }   /* 期间增删：错乱 */
```

```c good
xwsgroupsnapshot* Snap = xrtWsGroupSnapshotCreate(pGroup);
for ( i = 0; i < xrtWsGroupSnapshotCount(Snap); i++ ) {
	发送(xrtWsGroupSnapshotGet(Snap, i));
}
xrtWsGroupSnapshotDestroy(Snap);
```

### 坑 2：广播循环里等慢连接

症状：一个客户端 TCP 窗口满——整个广播循环卡住——全体频道成员的后续消息全部延迟。

原因：把"发"当同步语义。组的异步操作对象不等单个连接；循环里自己同步等 = 把扇出串行化。**跳过+记慢**是默认；慢性劣化连接由踢出策略处理。

```c bad
for ( each member ) {
	while ( send(conn, msg) == AGAIN ) { wait(); }  /* 慢者拖全体 */
}
```

```c good
/* 组操作对象：全体受理即返回；慢者的 AGAIN 归其连接背压 */
xwsgroupop* Op = xrtWsGroupTextAsync(pGroup, msg);
xrtWsGroupOpDestroy(Op);   /* 发起即走（或按需等待聚合） */
```

### 坑 3：停机直接销毁组（没 Seal 没关连接）

症状：停机瞬间在途升级/在途广播——销毁后访问悬空；或连接没关就 Engine Destroy 卡住。

原因：停机是**有序流程**不是一次调用。第 111 章模板七步缺一不可——Seal 挡新成员、终末广播给信号、逐连接 Close 走协议、计数归零才销毁。

```c bad
stop_listener();
xrtWsGroupDestroy(pGroup);   /* 在途升级/连接未关：悬空与卡死 */
```

```c good
stop_listener();
xrtWsGroupSeal(pGroup);          /* 1.挡新 */
broadcast("shutting down");       /* 2.信号 */
close_all_members(pGroup);       /* 3.协议化关闭 */
wait_close_count_zero();         /* 4.终态计数 */
xrtWsGroupDestroy(pGroup);       /* 5.销毁 */
xrtNetEngineDestroy(pEngine);    /* 6.最后停 Engine */
```

### 频道容量的设计权衡

`xrtWsGroupCreate(Limit)` 的容量参数在 pushd 语境的权衡：**限多少**——热门频道（全体广播）容量=最大并发连接数（防的是异常风暴不是正常峰值）；细分频道容量小（防单频道被灌爆）；**满了怎么办**——`GroupAdd` 返回容量错误（AGAIN 类可重试）：订阅回执报"channel full"（客户端退避重试或降级订阅汇总频道）；**与授权的关系**——容量是无差别的硬闸，授权（Authorize）是身份闸——两层先后（先授权后容量）语义不重叠。这个设计点是第 111 章"容量是过载防线不是协议错误"的项目化思考：**每类资源都要有明确的拒绝路径**，拒绝的语义（可重试/不可重试）要与错误类别绑定——第 4 章错误模型的资源版。

## 练习

### 基础：单频道广播闭环

固定端点 + 单组：客户端连上自动入组，服务端定时广播序号帧。验收标准：三个客户端序号连续（无漏）；断开重连重新入组。

### 进阶：完整订阅协议

sub/unsub/ping 三操作 + 频道名校验 + 错误帧回复。多客户端多频道交叉订阅。验收标准：交叉订阅的广播互不串频道；非法频道名回错误帧且连接保持；订阅集与组成员一致（对账）。

### 挑战：pushd 全功能 + 压测

kick/成员查询/优雅停机七步全部实现；100 连接×3 频道压测（序号对账+漏发统计）；慢客户端注入（收不读）验证隔离。验收标准：六条验收全过；停机终态计数对账；全程 stats 零泄漏。

### 全书倒数第二章的小结

pushd 完成后，全书只剩最后一章——项目六（综合静态文件服务器，第 144 章）。六个项目的递进回顾：**logstat**（流式处理——数据规模约束）、**configd**（长期状态——生命周期约束）、**xdl**（远程资源——网络不确定性约束）、**pushd**（长连接并发——扇出与终态约束）。每个项目的验收清单都在加长、每条经验都在多个形态间重放——这是螺旋式课程的收官节奏。最后一章将把这些约束**全部叠加**（静态服务器 = 长连接生命周期 × 磁盘 IO × 协议正确性 × 缓存策略 × 安全边界——五个维度的交集），并承担全书收官的双重使命：技术上的全栈综合、叙事上的知识地图总收拢。读完第 144 章，你手里应该有一个**能跑、能测、能运维、能扩展**的完整作品——以及对"这本书到底教了什么"的自己的答案。
