## 导读

本章把事件时间、耗时测量和业务日历放在同一张地图上。`xtime` 保存从公元 1 年元旦开始的 UTC 整数毫秒，`xrtTimer` 读取单调时钟的 double 秒；两种表示分别服务于可持久化的时刻和本次进程中的测量。不能把计时器读数写成日历日期，也不能拿墙钟跳变后的差值判断网络超时。

读完本章，你应能用 `xrtTimeSplitAt` 把同一时刻展示成固定偏移的日期，用 `xrtTimeAdd` 正确处理月末，并在协议边界明确转换 Unix 纪元。时间代码的可靠性来自明确的单位、纪元和时钟来源，而不是一个看起来合理的整数。两个完整示例先演示日历主线，再演示计时主线；后面的契约和测试方法解释这两条线如何进入日志、重试和账单逻辑。

## 引入

假设一个服务升级后，数据库里的时间戳仍是毫秒，但读取端把它当成 Unix 毫秒：数字位数看起来正常，显示出来却相差近两千年。这是纪元错配。第二个服务把服务器本地日期写成不带偏移的文本，跨时区部署后，同一事件在各节点相差数小时。这是时区信息丢失。第三个服务把“续费一个月”实现成增加三十天，非闰年一月三十一日的账单落到了三月二日。这是把业务日历当成固定时长。

三个问题都发生在值的解释层。存储格式应写清公元 UTC 毫秒，外部系统要求 Unix 时用转换函数，展示时再加偏移。业务周期选择日历单位，物理等待选择相对毫秒，耗时测量选择单调秒数。为每个接口参数命名时写出这些含义，评审者才能发现混用。整数本身不记录单位，更不记录它来自哪一种时钟；直接强制转换类型也不会转换纪元。

这套纪律同样适用于缓存和网络：缓存过期时刻需要可解释的日历时间，连接等待预算需要单调经过时间。管理员改钟不应延长一次握手，时区切换不应改变已保存事件的绝对顺序。先确定你处理的是时刻、时长还是周期，再选择工具，通常比事后修正显示格式更有效。

## 概念

### 表示：整数毫秒

`xtime` 是有符号 int64 毫秒，零点是公元 1 年 1 月 1 日 00:00:00.000 UTC。零点前一毫秒属于公元前 1 年的最后一天，日历没有零年。完整整数范围对应零点前后各约 2.92 亿年，采用外推 Gregorian 日历。这个范围描述表示能力；系统本地时区和文本协议的范围往往更小，不能据此假定操作系统能处理任意远古日期。

`xrtNow()` 返回墙钟时刻，可用于日志和数据库索引。Unix 起点为 1970 年，常量 `XRT_TIME_UNIX_EPOCH` 表示这个时刻在公元毫秒轴上的位置。使用 `xrtTimeFromUnixMs` 和 `xrtTimeToUnixMs` 在边界转换，并检查结果；整数类型相同不代表纪元相同。两个时刻的原始减法只有在差值可表示时才安全。需要处理极端范围时，使用带溢出检查的 `xrtDateDiff`，并明确结果单位。

`xrtTimer()` 返回高精度单调 double 秒。其原点没有日历意义，也不适合跨机器或跨进程持久化比较。两次读数相减得到经过秒数，乘以一千才是毫秒；整数等待参数和计时器读数不能直接互换。单调钟免受日历校时影响，读取失败返回 NaN，所以可靠的测量代码还需要检查读数有效性，而不是把失败误当成零耗时。

### 分解：UTC 与固定偏移

```diagram flow
- 存储：公元 UTC 毫秒，记录纪元和单位
- 运算：业务周期走日历加法，耗时走单调秒数
- 分解：xrtTimeSplit 按 UTC，xrtTimeSplitAt 按显式偏移
- 展示：最后转换日期字段，不把本地文本回写成时间轴
```

固定偏移以 UTC 以东为正，单位是秒，范围为负 86399 到正 86399。东八区传入八乘三千六百；它表示固定偏移，不会自动判断某地区的夏令时。分解得到的毫秒字段范围为零到九百九十九。要重建同一时刻，应保留日期字段和偏移，不能把已偏移的字段再次当成 UTC 构造。

需要系统本地规则时，启用本地时间模块并使用 `xrtTimeLocal` 与 `xrtTimeFromLocal`。春季跳时可能产生不存在的日期，秋季回拨可能产生两个候选时刻；后者要选择拒绝、较早或较晚的策略。固定偏移与本地时区是两种明确的选择，不能以固定偏移替代历史时区规则。测试固定偏移无需依赖部署机器；测试本地规则则要控制时区环境和操作系统支持范围。

### 日历运算：进位语义

`xrtTimeAdd` 按单位选择运算：毫秒到周使用固定时长；月、季度、年使用日历语义。月末会钳制到目标月份最后一天，因此一月三十一日加一个月在闰年落到二月二十九日，在非闰年落到二月二十八日。二月二十八日加一年仍是次年的二月二十八日；只有原日期的日超出目标月时才截断，不会因为目标是闰年就凭空增加一天。

续费政策还要区分“从上次实际账单日继续加月”和“始终使用最初约定的日”。前者在二月截断后，三月可能继续落在二十八日；后者要在业务层保留原始锚点。库提供单次加法，不能替产品决定周期规则。同样，固定一天是二十四小时；跨本地夏令时后，下一天的当地钟点未必相同。

`xrtDateDiff` 返回指定单位的 int64 差值。固定单位向零截断，二十三小时按天计算为零；月差计算连续月份序号，月末到下月一日也可能为一；年差跨公元前后时跳过零年。它不代表两个日期之间已经完成多少个订阅周期。所有可失败的构造和计算都应检查 bool 结果，溢出失败保留输出，不要读未初始化的输出参数。

### 格式化与解析（展示层的最后一站）

文本转换位于协议与展示边界。通用格式的 `%f` 对应三位毫秒，`%F` 与 `%T` 分别输出日期和钟点。RFC 3339 解析能接受更多小数位，但丢弃毫秒以下尾数；HTTP-date 只有秒精度且使用 GMT。落入不同协议后，精度和年份范围可能变化，因此不要把格式化后再解析当成任意值的无损编码。

通用公元纪年拒绝零年，协议中的四位年份零却可能有专门映射，阅读协议函数的契约比猜测数字规则更安全。日期解析要检查整段输入与函数结果；输出字符串的拥有型版本需要调用 `xrtFree`。日期结构和整数值没有动态所有权，格式化产生的拥有字符串却有释放责任。把释放放在失败分支和成功分支都能到达的清理路径，避免长期运行的日志或报表任务积累泄漏。

## 契约

- **时刻**：`xtime` 是公元 UTC 毫秒，纪元写进存储与接口契约；本地偏移用于展示。
- **计时**：`xrtTimer` 返回单调 double 秒，检查 NaN；`xrtNow` 返回可受校时影响的墙钟时刻。
- **等待**：公开等待接口接收相对 int64 毫秒，零表示不阻塞，`XRT_WAIT_FOREVER` 表示无限等待，其余负值非法。睡眠函数不接受无限等待标志。
- **日历**：`xrtTimeAdd` 的月、季度、年按日历计算，其他单位为固定时长；可失败操作检查返回值。
- **所有权**：数值和日期结构按值保存，拥有型格式化字符串需要释放；线程并发共享可写输出时由调用方同步。

### 从示例到工程：时间的三个宿主

**日志时间戳**：`xrtNow()` 的公元毫秒可以持久化，查看者按自身偏移展示。如果发送给已有 Unix 协议，要在出口转换，避免接收端猜测。日志中的单位标签、纪元说明和时区文本互相补充：标签帮助程序解释数值，偏移帮助人核对现场，原始绝对值方便排序。不要仅因某份 JSON 里字段名叫 time，就假定双方采用同一格式。

**超时与截止**：公开等待接口传相对毫秒，具体操作在内部使用单调预算。多步重试应共享总体预算，不能每一步重新获得完整等待时间。应用确需维护自己的总预算时，以单调读数计算剩余时间，向上取整成毫秒，并处理无限等待、NaN、范围和耗尽情况。不要使用曾经存在的旧截止类型来调用当前接口。

**业务周期**：`xrtTimeAdd` 负责一次日历进位；账单日的原始锚点、节假日顺延和本地钟点政策归业务层。把一月三十一日怎样续费写进产品规则，之后围绕这些规则测试，而不是让实现偶然决定用户看到的日期。三种宿主分别对应事件时刻、经过时间与日历周期；每一种都应有自己的变量含义和边界测试。

### 一个心智模型：时间的三层视图

存储层保存公元 UTC 毫秒，负责版本、单位和纪元说明；运算层选择固定时长或日历单位，并检查溢出；展示层选择 UTC、固定偏移或系统本地规则，再格式化成人读文本。把这三层分开，才能在更改报表时区时保持数据库稳定，在改变账单政策时保持日志时间不变，在升级外部协议时集中审查纪元转换。

例如一个“每天当地九点执行”的任务，不能简单每隔二十四小时累加绝对值。它先在展示与日历规则中确定下一次当地日期与钟点，再用本地规则构造绝对时刻，遇到跳时或重复时按产品政策处理。随后等待执行时使用单调预算，不让系统校时把已经开始的短期等待任意延长。这种流程同时用到了三层，但每个值的职责都保持清楚。

### 时间测试的诀窍

时间测试首先隔离不确定源。业务函数接受明确的 `xtime` 参数，测试传入固定边界日期，生产调用方才读取 `xrtNow`。不要只测当前月份：加入闰年二月、月末、公元前后、Unix 零点前一毫秒和目标范围边界。时区测试既要验证同一绝对值的不同展示，也要验证带偏移结构能重建原值；本地规则测试要覆盖不存在和重复的钟点。

重试、节流和超时的测试注入单调 double 秒读数，推进虚拟时钟，而不是把日历毫秒塞进同一个回调。真实睡眠验证只断言下界与有限容差，调度繁忙时允许更长等待。异步操作还要区分“提交成功”“发送完成”和“接收完成”：等待时间单位修正后，错误的完成条件仍可能留下未消费数据，后续解析因此失败。用状态与接收字节数定义完成，而不是用固定睡眠假装完成。

## 避坑

### 坑 1：本地时区存日志时间（存储层混入展示参数）

症状：多节点日志时间对不上；跨时区部署后"同一事件"的时间差几小时；夏令时切换日日志出现"重复的一小时"。

原因：存储层混入了展示层的时区——每台机器的"本地时间"是不同的展示参数。

```c bad
xtime Now = xrtNow();
xdatetime T;
xrtTimeSplitAt(Now, LocalOffset(), &T);   /* 按本地偏移分解后存字符串 */
SaveLog("%lld-%02d-%02d ...", (long long)T.Year, ...); /* 存的是"本地时间文本"——时区信息丢失 */
```

```c good
xtime Now = xrtNow();
SaveLog("%lld", (long long)Now);          /* 存 UTC 毫秒整数 */
/* 展示时才分解：xrtTimeSplitAt(偏移按查看者)——时区是查看参数 */
```

### 坑 2：用秒数近似日历运算（两轨混用）

症状：订阅/账单周期在月末漂移——1 月 31 日 +30 天 = 3 月 2 日；用户侧显示"多扣两天"。

原因：日历月不是固定秒数——用 30×86400 近似"一个月"在 31 天月与 2 月都会错。

```c bad
xtime Next = Now + 30LL * 86400 * 1000;   /* "加一个月" = 30 天近似 */
```

```c good
xtime Next;
xrtTimeAdd(Now, 1, XTIME_UNIT_MONTH, &Next);   /* 日历进位：1/31 + 1月 = 2/28 */
```

## 练习

### 基础：双时区对照（同一时刻两种展示）

取当前时刻，按 UTC 与 +8 偏移分别分解打印——两个时刻的毫秒值相同、展示不同；再算两个展示的小时差验证偏移正确。

### 进阶：订阅续费计算器（日历语义的可视化）

实现 `next_billing(当前, 周期月数)`：日历加法进位；对 1 月 31 日开通的月付用户连续计算 12 个月的账单日，观察月末截断行为并输出说明。

### 挑战：耗时基准工具（单调钟 + 中位数）

用单调钟实现 `measure(函数, 次数)`：预热 N 次后正式计时、取中位数（第 10 章 Near 的容差思想用于判断两次测量是否"实质相同"）、输出毫秒与人类可读两种格式。用它测第 23 章的数组 vs 链表遍历，数字应与该章对照实验同量级。

## 速查

| 知识点 | 速查 |
| --- | --- |
| 表示 | `xtime` 是从公元 1 年元旦开始的 int64 UTC 毫秒，无零年 |
| 双钟 | `xrtNow` 记录事件；`xrtTimer` 读单调 double 秒，差值测耗时 |
| Unix 边界 | `XRT_TIME_UNIX_EPOCH` 标识 1970 年；用转换函数检查范围 |
| 分解 | `xrtTimeSplit` 按 UTC；`xrtTimeSplitAt` 按以东为正的秒偏移 |
| 日历加法 | `xrtTimeAdd` 月末钳制；固定一天不等于每个地区的当地下一天 |
| 差值 | `xrtDateDiff` 返回指定单位的整数，不计完成的订阅周期 |
| 等待 | 相对毫秒；`XRT_WAIT_FOREVER` 为无限等待，零为不阻塞 |
| 文本 | 三位毫秒，协议可能降低精度；拥有字符串要释放 |
| 测试 | 固定日历边界、虚拟单调钟、显式异步完成条件 |
