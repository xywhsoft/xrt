## Ориентация

Модуль UDP вписывает датаграммы в модель движка: **двойственная форма** — безсвязный конец (recvfrom несёт адрес источника — любой источник, фильтруете вы) и соединённая (после connect принимается только тот пир — клиентская форма); **событийный приём/передача** (колбэки движка — та же грань колбэков, что у TCP); **семейство батчинга** (пример udp_batch — амортизация нескольких датаграмм за один приём/передачу); **мультикаст** (вступление/выход из группы — пример multicast); **PMTU и асинхронные ошибки** (примеры udp_introspect/udp_errors — ICMP unreachable и прочие возможности платформы). У UDP нет управления потоком и машины состояний — но колбэки движка, подсчёт ссылок и протокол остановки — все те же.

## Введение

Существенное различие UDP и TCP не «надёжный против ненадёжного», а **граница данных**: TCP — байтовый поток (границы сообщений — ваша забота; цепочка буферов главы 64 и кадрирование главы 71 существуют ради этого); UDP — датаграммы (один send — одно сообщение, один recv — одно полное сообщение — границу хранит ядро). Это различие делает форму API UDP совершенно иной: без бюджета отправки (датаграмма либо входит в очередь, либо нет), без цепочки приёма (одно сообщение — один буфер), без управления потоком (ненадёжность — свойство: аудио/видео реального времени скорее потеряет, чем накопит).

Выбор из двух форм: **безсвязный конец** (серверная форма) — после bind принимает от любого источника (recvfrom прикладывает адрес источника; ответ sendto указывает адресата); **соединённая форма** (клиентская) — после connect «запирает» пира и принимает только от него (фильтр делает ядро), send шлёт напрямую (без указания каждый раз). UDP connect не делает рукопожатия (это просто фильтр + адрес по умолчанию) — семантически совершенно не то, что TCP connect (реальное установление соединения).

## Понятия

### Двойственная форма и жизненный цикл

```diagram flow
- Создание: объект xnetudp -> bind (безсвязный) или connect (соединённая)
- Состояния: машина состояний UDP (BINDING/BOUND/CONNECTING/CONNECTED — переходные состояния асинхронного bind/connect)
- Приём/передача: безсвязный recvfrom (с источником) / sendto (с адресатом); соединённый recv/send (фиксированный пир)
- Закрытие: Close -> CLOSED -> Destroy — подсчёт ссылок как у Stream (контракт главы 66 продолжается)
```

**Асинхронные bind/connect**: привязка и соединение UDP — тоже операции движка (переходы машины состояний — опрос `xrtNetUdpState` или ожидание событий; помощник `WaitState` примера udp демонстрирует опрос с дедлайном).

### Грань событийных колбэков

Таблица событий UDP (та же форма, что у Stream): Read (датаграмма пришла — recvfrom/recv в колбэке), Write (можно отправлять), Close (уведомление о финале). **Приём/передача в колбэке**: прибытие датаграммы запускает колбэк, колбэк подтягивает (вытягивающий recv — датаграммы в очереди, колбэк — уведомление); пакетное подтягивание (несколько за один колбэк — эффективная форма разгона завалов). Ограничения Worker те же, что у Stream (колбэки на Worker, межпоточно Post — контракт главы 67 в UDP-версии).

### Семейство батчинга и структура датаграммы

`xnetudppacket` (носитель датаграммы + адреса источника); пакетные варианты оперируют несколькими датаграммами сразу (подача/приём массивом) — амортизирующий вход сценариев высокого PPS (DNS-серверы, мониторинговые репорты). **Семейство Msg** (SendMsg/RecvMsg — родня портового слоя главы 63): векторная отправка с адресатом — многобуферный вариант UDP.

### Мультикаст и PMTU

**Мультикаст** (пример multicast): вступление/выход из групп (адрес группы + локальный интерфейс), управление TTL (прыжки между сегментами); приём/передача тем же API, что юникаст (адрес группы как адресат). **Зонд PMTU и асинхронные ошибки**: oversized send отбрасывается по пути (при запрещённой фрагментации) — ICMP «frag needed» возвращается асинхронно (RecvError по возможностям платформы — применение гейта возможностей главы 63 к UDP); пример udp_errors демонстрирует приём ошибок, udp_introspect — запросы PMTU/статистики.

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/network/udp/main.c -lws2_32 -liphlpapi

```

**Что только что произошло.** (1) Безсвязный конец сервера делает bind (порт 0 — динамическое назначение; Local извлекает и печатает `127.0.0.1:NNNNN`); ожидание состояния (помощник `WaitState` опрашивает BOUND в пределах дедлайна — управление переходным состоянием асинхронного bind). (2) Клиент в соединённой форме connect к серверу — принимает только от него (ответ сервера). (3) Клиент send `hello UDP` — без параметра адресата (connect уже запер); (4) событие Read сервера срабатывает, recvfrom подтягивает (источник — клиент) → печать `received: hello UDP` — каждая форма на своём месте. (5) Ответ sendto на адрес клиента — ответ безсвязного конца обязан указывать адресата.

Из `examples/network/udp_batch/main.c` и `examples/network/udp_multicast/main.c` (читать вместе):

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/network/udp_batch/main.c -lws2_32 -liphlpapi
batch: truncated prefix=16 of 64
pull batches: 3 packets in 1 batch

```

**Что только что произошло.** (1) `truncated prefix=16 of 64` — семантика усечённого префикса (малый буфер принимает большую датаграмму: усечение до вместимого, размер датаграммы запрашиваем — форма усечения внутри границы UDP). (2) `pull batches: 3 packets in 1 batch` — пакетное подтягивание: три датаграммы одним вызовом (доказательство амортизации разгрома завала за один колбэк). (3) Строки wait/future: блокирующее ожидание и форма Future делают по одному пакетному приёму (borrow=take=ok — оба вида владения при извлечении буферов датаграмм проверены). (4) Строка error queue: пустое вытягивание и асинхронные финалы очереди ошибок — семейство RecvError, протестированное на UDP. (5) Строка writable: синхронный и асинхронный пробы отправляемости. Пример multicast добавляет мультикаст-позицию (join → send на адрес группы → приём → leave); примеры sync/future — сестринские блокирующая/Future формы — четыре формы выровнены с семейством TCP.

## Контракты

- **Границы данных**: одна датаграмма — один буфер, без цепочки и бюджета — фундаментальное отличие от TCP; границы не теряются, и порядок тоже (порядок и не обещался).
- **Двойственная форма**: безсвязный конец (любой источник + sendto ответ) / соединённая (connect-фильтр + фиксированный адресат) — по роли.
- **Асинхронный жизненный цикл**: управление переходными состояниями bind/connect (опрос State или ожидание событий + deadline).
- **Та же грань колбэков**: события Read/Write/Close; вытягивающий приём/передача; ограничения Worker и Post как у Stream.
- **Мультикаст**: join/leave + TTL; приём/передача как юникаст. Семейство батчинга амортизирует высокий PPS.
- **Асинхронные ошибки**: ошибки класса ICMP/PMTU гейтятся по возможностям платформы (RecvError) — обратная связь «недостижимо» ненадёжных датаграмм.

### От примеров к инженерии: три хозяина UDP

**Класс обнаружения и регистрации** (дом мультикаста): обнаружение сервисов (испытательная версия примера multicast), раздача конфигурации, широковещательные сердцебиения — малые датаграммы + мультикаст + безсвязная дешевизна; TTL мультикаста управляет охватом (TTL=1 ограничивает локальным сегментом).**Класс потоков реального времени** (ненадёжность как свойство): аудио/видео, игры, телеметрия — отправка фиксированным ритмом, без ретрансляции потерь (перепосылка устаревших данных бессмысленна), seq-номера для обнаружения переупорядочивания. **Класс запрос-ответ** (надёжность строится прикладным слоем): DNS-запросы, простой RPC — тайм-аут + повтор + спаривание ID запроса (стандартный слой продвинутого упражнения). Общий водораздел трёх хозяев — **цена потери пакета**: обнаружению всё равно, реальному времени ретрансляция запрещена, запрос-ответ обязан повторять — стройте прикладной слой по цене, а не по умолчанию «всё через TCP» или голый UDP наугад.

### Место UDP в эпоху QUIC

Место UDP в современном сетевом стеке заслуживает главо-уровневого обновления картины: **QUIC/HTTP3 полностью работают на UDP** — надёжный транспорт, управление потоком и шифрование перестроены на прикладном слое (над UDP). Почему: окостенение TCP в ядре (переделки посредниками-миддлбоксами, медленные апгрейды, блокировка головы строки) вытолкнула инновации вниз, на носитель UDP. Модуль UDP XRT поставляет для этого engine-форму фундамента (грань колбэков/батчинг/мультикаст/PMTU) — сырьё для протоколов класса QUIC. Он дополняет собственный стек TCP XRT (engine-обёртку над TCP ядра): стандартный веб — TCP (глава-золотой стандарт), собственные протоколы и малые задержки стартуют с сырья UDP. **Современный ответ на «TCP или UDP»**: потребность в стандартных протоколах — TCP; управляемая эволюция протокола — сырьё UDP; уже не старая дихотомия «надёжный против быстрого».

### Наблюдение и безопасность: два слабых места UDP

Слабые места наблюдения UDP-сервиса надо укреплять проактивно (конвейер главы 49). **Потери невидимы**: у UDP нет ретрансляции — сколько потеряно, знает только прикладной слой (анализ пробелов seq — статистика непрерывности seq в журнал); **плоскость безопасности**: UDP легко подделывает адрес источника (нет рукопожатия) — точки обороны против усилительных отражающих атак (классика — усиление DNS): ограничение размера ответа (на запрос 64 байта не возвращать 4000), проверка адресата (фильтр соединённой формы), ограничение скорости. Пройдите оба слабых места до выхода сервиса в свет — «простота» UDP — простота API; эксплуатационная и безопасностная работа только прибавляется.

## Ловушки

### Ловушка 1: читать UDP connect как TCP connect

Симптомы: вера «connect успешен = пир достижим» — на деле connect успешен, даже когда пира нет (UDP connect ставит только фильтр); или вера в надёжность после connect — потери как были, так и есть.

Причина: UDP connect — локальная настройка фильтра — без рукопожатия, без подтверждений, без изменения ненадёжной природы.

```c bad
if ( xrtNetUdpConnect(Udp, &Peer) ) {
	AssumeReachable(Peer);   /* неверно — UDP connect не проверяет существование пира */
}
```

```c good
xrtNetUdpConnect(Udp, &Peer);   /* ставит фильтр + адресата по умолчанию — локальная операция */
SendRequest(Udp);
if ( !WaitResponse(Udp, Deadline) ) {   /* достижимость проверяется прикладным запрос-ответом */
	RetryOrFail();
}
```

### Ловушка 2: размер датаграммы сверх MTU пути

Симптомы: на локальной петле нормально, между сегментами теряется — большие датаграммы отбрасываются (фрагментация запрещена или у промежуточного маршрута MTU меньше); редкие частичные приходы (частичная потеря фрагментов).

Причина: датаграмма UDP превышает MTU пути — фрагментация ядром (частичная потеря = потеря всей) или PMTU-дыра (бит DF + ICMP отфильтрован).

```c bad
char Big[65000];
Fill(Big);
xrtNetUdpSend(Udp, Big, sizeof(Big));   /* сверх MTU — между сегментами почти наверняка потеря целиком */
```

```c good
/* прикладное ограничение в безопасном размере (обычно ниже 1200-1400 байт); большие сообщения — TCP или прикладная нарезка */
char Packet[1200];
xrtNetUdpSend(Udp, Packet, sizeof(Packet));
```

## Упражнения

### Базовое: воспроизведение двойственного контура

Воспроизведите главный пример; затем добавьте «второго клиента», шлющего на сервер — убедитесь: безсвязный конец принимает от любого источника, соединённая форма — только от запертого пира (пакеты второго клиента фильтруются).

### Продвинутое: тайм-аут-повтор запрос-ответ

Стандартный слой надёжности UDP-клиента: отправить запрос → ждать с дедлайном → по тайм-ауту повторить (экспоненциальный откат) → после N неудач доложить; сервер имитирует потери (случайно отбрасывая 50%) для проверки сходимости повторов. Подсказка: семейство deadline + отмена главы 53.

### Вызов: служба обнаружения через мультикаст

Обнаружение сервисов в локальной сети: серверы вступают в группу и периодически вещают о себе; клиенты вступают в группу и принимают сообщения обнаружения; подтверждение — юникастное соединение. Критерий приёмки: при конкурентном вещании многих серверов клиент перечисляет всех; join/leave чисто (без утечек); контроль вещательного шторма (интервал + TTL); вся цепочка от обнаружения до соединения в журнале и аудируема.
