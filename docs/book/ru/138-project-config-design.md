## Ориентация

Второй проект — **центр конфигурации** (configd): централизованное управление конфигурацией группы сервисов — JSON-конфигурация поставляется файлом или по HTTP, поддерживается послойное переопределение по окружениям (трёхслойное слияние: умолчания/разработка/продакшен), валидация (типы и ограничения), опциональное раскрытие переменных шаблона (`{$env}` — внедрение фактов окружения) и горячая замена (перечитывание по изменению файла). Отличие формы от Проекта 1 (глава 137, одноразовый инструмент) принципиально: **конфигурация — долгоживущее состояние** — её загружают, кэшируют, по ней спрашивают, она может обновляться — управление жизненным циклом и конкурентный доступ впервые становятся главной темой. Эта глава — **глава проектирования**: требования и приёмка, выбор модели данных, слоистость и выбор модулей, семантика горячей замены и конкурентности, политика валидации и безопасность шаблона — всё фиксируется до написания реализации (глава 139). Методологическая позиция проектной главы: **код — исполнение проекта, а переделки чаще всего растут из проектной нечёткости**.

## Введение

Проблема конфигурации выглядит тривиально — «прочитать JSON, чего там». В реальной системе сложность конфигурации приходит из четырёх измерений: **разнообразие источников** (файл / HTTP-интерфейс / переменные окружения / командная строка — должно уметь комбинироваться); **послойное переопределение** (умолчания перекрываются слоем окружения, слой окружения — слоем инстанса — семантика слияния должна быть явной); **запаздывающая валидация** (ошибочная конфигурация взрывается лишь при первом использовании — перехватывать надо уже на старте); **распространение обновлений** (какие компоненты перечитают изменившуюся конфигурацию, что делать с операциями, которые используют старые значения). Нечёткость в любом измерении превращается в продакшен-инцидент: перепутан порядок слияния — продакшен работает на значениях разработки; валидации нет — порт 0 «успешно стартует»; гонка горячей замены даёт двум потокам несогласованную половину конфигурации.

Эта глава превращает каждое из четырёх измерений в **явное проектное решение** — у каждого решения есть отвергнутые альтернативы и обоснование (методология таблицы выбора главы 137, поднятая на архитектурный уровень). Реализация следующей главы исполнит эти решения построчно — в этом **приёмочность проектной главы**: когда реализация закончена, сверка возвращается к каждой строке — каждое решение либо соблюдено, либо явно пересмотрено.

## Понятия

### Требования и критерии приёмки

Пользовательские сценарии configd (форма user story): **UC1 загрузка** — при старте сервиса конфигурация вытягивается из `config.json` (или HTTP-эндпойнта); при отказе — явная ошибка (молчаливо работать с пустой конфигурацией не разрешается). **UC2 слоистость** — глубокое слияние двух слоёв `default.json` → `config.{env}.json` (вложенные объекты рекурсивно, массивы заменяются целиком — семантика замены объявлена явно); **UC3 запрос** — взятие значения по пути (`server.port`, `db.pool.max`) с ожиданием типа (запросили целое — получили целое, несовпадение типа — ошибка); **UC4 валидация** — полная проверка на этапе загрузки (обязательные существуют / типы верны / значения разумны), ошибка несёт **путь в конфигурации** (`db.pool.max: must be > 0` — применение модели ошибок главы 4); **UC5 шаблон** — строковые значения поддерживают раскрытие `{$ENV_HOME}` (внедрение фактов окружения в конфигурацию); **UC6 горячая замена** — при изменении файла перезагрузка, **атомарная передача** старой и новой конфигурации (в любой момент запрос видит либо всё старое, либо всё новое — смеси не существует).

**Критерии приёмки** (в главе реализации сверяются построчно): (1) у каждого из шести UC есть позитивные и негативные случаи; (2) у семантики слияния есть тестовые векторы (вложенное переопределение / замена массива / конфликт типов); (3) тест гонки горячей замены (согласованность конкурентных запросов во время обновления — threads-форма главы 132); (4) все ошибки валидации несут путь; (5) OOM по каждой точке (загрузка конфигурации содержит выделения памяти — дисциплина главы 133); (6) ноль следов при неудачной загрузке (половинная конфигурация не просачивается наружу — атомарность).

### Выбор модели данных: динамический value или специальная структура

Первое и самое важное решение — **что такое конфигурация в памяти**:

| Вариант | Форма | Преимущества | Недостатки |
| --- | --- | --- | --- |
| A: динамический value (глава 31, xvalue) | весь JSON загружается в дерево value | совместим с любой схемой (эволюция конфигурации — ноль правок кода); запросы идут общими путями; JSON-десериализация за один шаг | медленные запросы (поиск по строковому пути); нет проверки на этапе компиляции |
| B: специальная структура | `struct config { int Port; struct db Db; }` | самый быстрый доступ, типобезопасность | изменение схемы требует править структуру и код загрузки; слияние многих источников пишется вручную |
| C: загрузка в value + снимок в структуру | загрузка/слияние/валидация в домене value, после загрузки — разовое извлечение в структуру | оба мира: гибкость на этапе загрузки + скорость на этапе использования | код извлечения требует сопровождения (зеркало схемы) |

**Решение: C**. Обоснование: у конфигурации разные **частота эволюции** (схема меняется часто — в домене value это бесплатно) и **частота чтения** (горячий путь — возможен запрос на каждый запрос — структура даёт O(1)) — **сопоставление по этапам**. B отвергнуто: слияние и шаблон в домене структур писать вручную слишком тяжело; A отвергнуто: строковый поиск запросов попадает в горячий путь. Зеркальная цена C держится под контролем **макросов извлечения** (одна строка объявления на поле — реализация в главе 139).

### Слоистость и выбор модулей

```diagram flow
- Слой источников: файл (чтение xfile, глава 44) / HTTP (клиент xhttp, главы 97-99)
  — единый интерфейс «дай поток байтов»: источник заменяем
- Слой разбора: JSON (глава 32) -> дерево xvalue; XSON (глава 33) зарезервирован для расширения
- Слой слияния: глубокое слияние двух деревьев value (объекты рекурсивно / массивы заменой — семантика явная)
- Слой шаблона: раскрытие переменных окружения в строковых значениях (строки главы 25 + окружение главы 42)
- Слой валидации: набор правил (обязательные/типы/диапазоны) -> ошибки с путём (глава 4)
- Слой снимка: value -> структура, разовое извлечение (точка атомарной передачи)
- Слой запросов: прямой доступ к структуре (O(1))
```

Каждый из семи слоёв — главная тема какой-то предыдущей главы — **выбор модулей целиком из существующих глав** (без новых зависимостей): очередное подтверждение тезиса «проект = рекомбинация существующих слоёв». Контракты между слоями: поток байтов → дерево value → слитое дерево value → прошедшее валидацию дерево value → снимок в структуре — **каждая стрелка — чистое преобразование данных** (без побочных эффектов, отказ атомарен).

### Горячая замена и конкурентность: семантика атомарной передачи

Ядро проектирования горячей замены — **протокол передачи старой и новой конфигурации**. Выбор configd: **неизменяемый снимок + атомарная замена указателя**. Продукт загрузки — неизменяемая структура (после загрузки её никто не меняет — потокобезопасность даром, конфигурационная версия неизменяемого разделения главы 114); сторона запросов держит **указатель с подсчётом ссылок** (общая ссылка главы 5 — `Ref` взял одну, после использования `Destroy`); обновление = построить новый снимок → атомарно заменить глобальный указатель (атомарная операция главы 9) → старый снимок освобождается сам, когда счёт ссылок доходит до нуля. **Гарантия семантики**: в любой момент любой спрашивающий видит **целиком согласованную** конфигурацию (либо старую, либо новую — смеси не бывает); спрашивающий внутри долгой операции продолжает пользоваться старым снимком до её конца (graceful-передача — без принудительного выдёргивания). **Отвергнутые альтернативы**: глобальная блокировка чтения-записи (блокировка входит в горячий путь запросов — отвергнуто); обновление изменяемой структуры на месте (конкурентный ад — отвергнуто).

### Слои валидации: семантическая правильность за пределами синтаксической законности

JSON-парсер гарантирует **синтаксис** (глава 32); слой валидации отвечает за **семантику**: **существование** (обязательные ключи — нет ключа, есть ошибка); **тип** (значение ожидаемого типа — `server.port` обязан быть целым); **диапазон** (port 1..65535, `pool.max > 0` — бизнес-ограничения). Все три выполняются один раз на этапе загрузки (**перехват на старте** — «работать с ошибочной конфигурацией» не разрешается); формат ошибки `路径: 消息` (путь: сообщение) (`db.pool.max: must be > 0`) — **ошибки с путём** избавляют разборщика от листания всего JSON. Выражение правил валидации: небольшой декларативный массив (путь ключа + тип + обратный вызов ограничения) — **правила как данные**: новое поле — одна строка правила (та же экономика сопровождения, что у макросов извлечения).

### Момент раскрытия шаблона и граница безопасности внедрения

Раскрытие `{$VAR}` происходит **после слияния, до валидации** — обоснование: продукт шаблона может влиять на валидацию (валидировать надо порт уже после раскрытия); а слияние происходит в исходном домене (`{$BASE}` слоя умолчаний не раскрывается до перекрытия слоем окружения — переопределение приоритетнее внедрения). **Границы безопасности**: раскрывать только **переменные окружения** (источник из белого списка — глава 42); не раскрывать рекурсивно (если в значении `{$A}` снова `{$B}` — не раскрывается; защита от цепочки внедрения); неопределённая переменная — ошибка (не молчаливая пустая строка — конфигурация ссылается на несуществующее окружение, это ошибка развёртывания). Эти три правила — контракт безопасности слоя шаблона, конфигурационная версия дисциплины паролей главы 76: **плоскость внедрения защищается на каждой границе «строка становится конфигурацией»**.

**Что только что произошло.** (1) JSON-текст → дерево value → запрос поля → сериализационный круговорот — **полный поток данных слоя разбора** проходит в десятке строк. (2) Представление value, возвращаемое запросом, — ровно вход слоя валидации configd (проверка типов делается по нему). (3) Этот замкнутый контур — стартовая точка реализации главы 139: снаружи надеть «слой источников (файл/HTTP) → слой слияния → слой шаблона» — и получится полный конвейер загрузки — **у каждого слоя, выбранного в проектной главе, есть такой исполняемый атом** (архитектурная версия «образец как шлюз» главы 137: **проектирование не бумажное занятие — у каждого выбора есть проверенная деталь**).

### Форма проектного документа: эта глава как шаблон

В какой форме писать проектную главу? Не большая UML-диаграмма, а **список решений** — у каждого решения пять элементов: **проблема** (что решаем), **варианты** (минимум две альтернативы), **решение** (что выбрали), **обоснование** (почему победило), **проверка** (как узнать, что решение исполнено). Демонстрация этой главы: модель данных (выбор из трёх, обоснование — сопоставление частот по этапам, проверка — число строк макросов извлечения); протокол передачи (выбор из трёх, обоснование — структура уничтожает состояние гонки, проверка — threads-тест без смешанных состояний); семантика слияния (явное объявление, проверка — тестовые векторы); безопасность шаблона (три границы, проверка — случаи внедрения). **Почему не UML**: у диаграмм большое пространство двусмысленностей (из двух диаграмм каждый читает своё), а у списка решений каждая строка сверяема — та же философия, что у шлюзов BOOK_SPEC (**машинная проверяемость важнее человеческой интерпретации**). Этот проект Проекта 2 будет построчно цитироваться в начале главы реализации (глава 139) — читатель увидит, что отображение «решение → код» и есть настоящая поставка этой главы: **не документ, а сверяемый набор ограничений**. Проектная глава чат-сервиса (глава 140) наследует тот же шаблон — переиспользование проектной методологии опережает переиспользование кода.

### От инструмента к сервису: повторный проход уроков Проекта 1

Семь уроков ретроспективы главы 137 проходятся заново в контексте configd — **форма другая, уроки те же**: **приёмка прежде** (шесть UC и шесть критериев против пяти — приёмка сервиса обязана покрывать конкурентность и жизненный цикл, инструмента — нет); **форма решает контейнер** (дерево value против массива счётчиков — «эволюционность» данных становится новым измерением: форма данных инструмента фиксирована, у сервиса может эволюционировать); **представления живут одним кадром** (слой валидации работает по представлению value, извлечение — только в слое снимка — без раннего закрепления); **слоистая заменяемость** (слой источников файл/HTTP заменяем против семейства Reader — та же дисциплина, поднятая до семи слоёв); **факты платформы входят в проект** (факты платформы сервиса — модель конкурентности и соглашения о расположении файлов конфигурации); **бюджет прежде** (загрузка один раз + горячий путь запросов — бюджет указывает необходимость слоя снимка); **тестирование в четырёх квадрантах** (сервис добавляет квадранты threads и гонки горячей замены). **Все семь пройдены заново, два усилены** — таков учебный замысел последовательности проектов: не разные проекты, а **углубление одной методологии в разных ограничениях**.

## Контракты

- **Приёмка прежде**: шесть пользовательских сценариев и шесть критериев приёмки — глава реализации сверяет построчно; без сверки нет завершения.
- **Решение о модели**: домен загрузки в value + домен снимка в структуре — сопоставление по этапам частоты эволюции и частоты чтения.
- **Семантика слияния**: объекты сливаются рекурсивно, массивы заменяются целиком — семантика объявлена явно и закреплена тестовыми векторами.
- **Атомарная передача**: неизменяемый снимок + подсчёт ссылок + атомарная замена указателя — целиком согласованно в любой момент.
- **Graceful-передача**: долгая операция держит старый снимок до конца — без принудительного выдёргивания.
- **Три слоя валидации**: существование / тип / диапазон — одна полная проверка на этапе загрузки, перехват на старте.
- **Ошибки с путём**: `db.pool.max: must be > 0` — ошибка локализована путём в конфигурации.
- **Безопасность шаблона**: только переменные окружения, без рекурсии, неопределённая — ошибка; плоскость внедрения защищена.
- **Момент раскрытия**: после слияния, до валидации — переопределение приоритетнее внедрения, валидация смотрит на финальные значения.
- **Детали проверены**: у выбора каждого слоя есть исполняемый атом (два образца этой главы) — проектирование не бумажное занятие.

### Дополнительный проект HTTP-источника (сетевая расширенная форма UC1)

Помимо файлового источника, UC1 допускает HTTP-эндпойнт — три пункта дополнительного проекта: **сборка клиента** (easy-слой главы 97 или конструктор главы 98: вытягивание конфигурации — редкая операция, easy достаточно; верификатор обязателен — «не проверять — не вариант» главы 84 в конфигурационной сцене ещё строже: **захваченный источник конфигурации равен захваченным всем нисходящим потребителям**); **семантика отказа** (неудача вытягивания — ошибка по UC1 — но **можно** спроектировать «при отказе жить с прошлым снимком + тревога» — стратегия деградации есть решение развёртывания: первый старт (нет старого снимка) обязан закончиться отказом, отказ обновления на ходу терпим со старой конфигурацией — два момента, две стратегии); **граница кэша** (семантика кэширования HTTP-ответа — режим `only-if-cached` автокэша главы 100 — ровно «в оффлайне работать с кэшированной конфигурацией» — точное отображение четырёх режимов на конфигурационную сцену). HTTP-источник поднимает configd с «локального файлового инструмента» до «сетевого клиента конфигурации» — но в семислойном конвейере меняется только слой источников (третье исполнение дисциплины слоистой замены главы 137).

## Ловушки

### Ловушка 1: двусмысленная семантика слияния (массивы и глубокие объекты)

Симптом: слой окружения хотел «переопределить только db.pool.max», а заменил весь объект pool (min вернулся к умолчанию — число продакшен-соединений резко меняется); или наоборот, хотели заменить весь массив, а он слился поэлементно со слоем умолчаний.

Причина: семантика слияния не **объявлена явно** — поведение «глубокого слияния» для объектов и массивов по умолчанию различается от библиотеки к библиотеке. Решение проектного этапа должно быть записано тестовыми векторами: вложенные объекты рекурсивно, массивы заменяются целиком — у каждого слияния есть файл ожиданий на вход и выход.

```c bad
/* поведение слияния не вписано в контракт: слияние массивов — как вздумается реализации */
merge(a, b);   /* массивы поэлементно? целиком заменить? — никто не знает */
```
```c good
/* контракт прямо: объекты рекурсивно, массивы заменой + закреплено тройкой тестовых векторов */
merge_objects_recursive(); replace_arrays_whole();
```

### Ловушка 2: валидация в «первом использовании» вместо этапа загрузки

Симптом: ошибочная конфигурация успешно стартует — взрывается в три часа ночи при первом обращении к той функции (худшее время отказа).

Причина: ленивая валидация откладывает отказ до момента, когда разбор труднее всего. Полная проверка на этапе загрузки = **перехват на старте** — отказ вскрывается ещё при развёртывании (основа критерия (3)).

```c bad
int get_port(void) {
	return cfg_get_int("server.port");  /* взрыв при первом использовании: три часа ночи */
}
```
```c good
/* полная валидация в конце загрузки: существование/тип/диапазон — отказ старта с путём */
if ( !cfg_validate(&tree, rules) ) { fail_with_path(); }
```

### Ловушка 3: горячая замена правкой изменяемой структуры на месте

Симптом: в момент обновления конкурентные читатели видят наполовину новую конфигурацию — `server.port` уже новый, а `server.tls` ещё старый (новый порт со старым TLS — рукопожатие падает).

Причина: изменяемая структура + запись на месте без синхронизации = состояние гонки. Протокол атомарной передачи (неизменяемый снимок + замена указателя) уничтожает «смешанное состояние» структурно — не дисциплиной блокировок, а **невозможностью**.

```c bad
struct config g_cfg;            /* глобально изменяемая */
void hot_update(struct config* n) {
	g_cfg.port = n->port;        /* окно наполовину нового: конкурентный читатель видит смесь */
	g_cfg.tls = n->tls;
}
```
```c good
cfg_snapshot* fresh = build_snapshot(&tree);  /* новый снимок (неизменяемый) */
atomic_swap(&g_current, fresh);               /* атомарная замена указателя */
/* читатель: Ref одну -> читать -> Destroy — целиком согласованно */
```

### Сопоставление с реальными системами конфигурации

Сопоставление проекта configd с индустриальными формами проясняет границы компромиссов. **etcd/Consul**: распределённое KV-хранилище + watch-пуш — у односнимочной модели configd нет watch и протокола согласованности (это главная тема распределённых систем — за пределами книги, но интерфейс зарезервирован: атомарная замена указателя снимка и есть упрощённая форма «локального watch»). **Spring profiles**: активация и комбинация многих профилей — гибче и сложнее фиксированного двухслойного слияния configd; двухслойное переопределение закрывает 90% сценариев (умолчания + окружение), больше слоёв — делу расширения. **Производные переменных окружения** (12-factor): вся конфигурация внедряется из окружения — слой шаблона configd ровно мост к файловой конфигурации (гибрид: скелет файла + внедрение окружения — практический компромисс двух мировоззрений). Вывод сопоставления: **configd — «минимальная полнота, которой достаточно»** — каждый сложный признак реальной системы отображается в какую-то точку расширения этого проекта (слой источников / число слоёв слияния / глубина шаблона), и это ещё одна приёмка полноты проекта.

## Упражнения

### Базовое: вывод векторов слияния вручную

Напишите три группы тестовых векторов слияния (слой умолчаний + слой окружения → ожидание): частичное переопределение вложенных объектов, замена массива целиком, конфликт типов (умолчание int, окружение даёт string — ожидается ошибка с путём). Критерий приёмки: вручную выведенный результат становится файлом ожиданий тестов главы реализации.

### Продвинутое: диаграмма последовательности протокола передачи

Нарисуйте последовательность горячей замены: поток загрузки (построить новый снимок → атомарная замена) и два потока запросов (Ref → чтение → Destroy) в трёх переплетениях — что каждый видит до / во время / после замены. Критерий приёмки: видимость каждого случая выводится из «неизменяемость + атомарный указатель» — смешанных состояний нет.

### Вызов: проектирование набора правил

Для правдоподобной конфигурации (три секции server/db/log) напишите полный набор правил валидации (путь + тип + ограничение диапазона) и три намеренно нарушающих входа. Критерии приёмки: нарушающие входы все перехвачены на старте, ошибки содержат путь; число строк правил того же порядка, что число полей конфигурации (проверка экономики сопровождения).
