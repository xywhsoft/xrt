## Ориентация

После шести клиентских глав (97–102) перспектива переворачивается: теперь вы сервер. `xrtHttpServerStart` одним шагом собирает Engine, агрегированный TCP Server, Stream и протокольные машины состояний без ввода-вывода в открытый текстовый HTTP/1-сервис — зависимости не прячутся за таблицей функций (честная обрезка). В главе три темы: **конфигурационная грань** — пять тайм-аутов (Header/Body/Request/Idle/Write — каждый независимо защищает свою стадию, ноль отключает); **цепочка событий** — `Open → Headers → Body → Request → Error/Close`, где `Headers` принимает стратегическое решение до чтения тела (буферизовать/стримить/отбросить/отвергнуть/ответить напрямую), `Body` принимает только потоковые фрагменты, возврат false из обратного вызова — 500; **три пути ответа** — `Reply` (прямой ответ фиксированными байтами, ноль временных контейнеров), `ReplyBody` (версия с источником тела), `Respond` (полный построитель динамических полей и trailer). Маршрутизация и middleware — глава 104; SSE и потоковость — главы 106/107. Вход разбора заголовков запроса у протокольного автомата в основе — ровно сетевая привязка парсера главы 89 (http1_net: цепочка буферов идёт в парсер напрямую, без ручной сшивки).

## Введение

Крупнейшая парадигменная разница сервера и клиента — **инверсия управления**: клиент «инициирует и ждёт», сервер «управляется событиями» — когда придёт запрос, сколько их, с телом или без, и не вредоносно-ли-медленный, всё решает противоположная сторона. Дизайн среды выполнения разворачивается вокруг этой инверсии: пять тайм-аутов, каждый против своего вида «медленной атаки» (медленные заголовки — HeaderTimeout, медленное тело — BodyTimeout, зависшее приложение — RequestTimeout, висит без дела — IdleTimeout, ответ не движется — WriteTimeout); стратегия тела решается на стадии Headers — прежде чем дойдёт маршрутизация, вы обязаны сказать, «что делать с телом этого запроса»; прикладное противодавление (`PauseRequestBody`) позволяет **не читать тело противоположной стороны**, пока асинхронный потребитель не догонит, — TCP-окно естественно сжимается, память не растёт.

Путь прямого ответа `Reply` заслуживает отдельной фразы: фиксированные JSON/текстовые ответы **не создают временных контейнеров Reply или Header**, не требуют строить словари или JSON-объекты — один вызов прямо в замороженное ядро. Health-проверки, короткие ошибки, фиксированные ответы между микросервисами — эти «есть у каждого сервиса» пути получают форму с нулевой стоимостью.

## Понятия

### Запуск и конфигурация

`xrtHttpServerStart(Engine, 配置, 事件表)` (движок, конфигурация, таблица событий) создаёт и немедленно стартует; **провал запуска не оставляет частично работающего Server** — все логические конечные точки либо связались все, либо общий провал (конфигурация нескольких конечных точек — в разделе Network). Ключевые пункты конфигурации:

- **Пять тайм-аутов** (микросекунды): `HeaderTimeout` (стадия чтения заголовков), `BodyTimeout` (чтение тела), `RequestTimeout` (длительность прикладной обработки), `IdleTimeout` (простой keep-alive), `WriteTimeout` (нет прогресса ответа) — ноль отключает соответствующую защиту. У каждого отрезка медленной атаки свой шлюз.
- **Соединения и потолки**: `MaxConnections` (ноль = без прикладного лимита), `MaxInformations` (число информационных ответов в очереди на запрос), `WriteSize` (лизинг одной zero-copy отправки — **фиксированный буфер отправки на каждое соединение не резервируется**); приёмная память управляется предоставляемым по надобности `xnetbuf` TCP и жёсткими потолками.
- **Network**: полностью открыты несколько конечных точек TCP Server, общие динамические порты, accept-очередь, reuse-port — `xrtHttpServerLocal` возвращает реальные конечные точки (стандартная поза «порт прослушивания 0», как в главе 66); `xrtHttpServerNetwork` одалживает ссылку на нижележащий `xnetserver` (низкоуровневая статистика для особых сценариев; после использования `xrtNetServerDestroy`).

### Цепочка событий и стратегия тела

```diagram flow
- Open: адрес, Worker, факты нижележащего TCP-соединения
- Headers: точка решения до чтения тела - буферизовать / стримить / отбросить / отвергнуть / ответить直接
  (запрос без тела идёт дальше; запрос с телом стоит на границе заголовков, ожидая стратегию)
- Body: срабатывает только в потоковом режиме - одалживает фрагменты тела; возврат false = ошибка обратного вызова + 500
  (при уже отправленном ответе ответ главнее; PauseRequestBody приостанавливает доставку)
- Request: полный запрос прибыл - синхронный ответ или удержание Connection для поздней доставки
- Error -> Close: на соединение максимум один стабильный финал-ошибка и ровно один финал; Shutdown = всё освобождено и завершено
```

Три ключевые семантики. (1) **Право стратегии у Headers**: по маршруту вызывается `xrtHttpConnSetRequestBodyLimit` (единственный жёсткий потолок текущего Exchange) — лимит загрузки есть решение уровня маршрута, а не глобальная константа. (2) **Противодавление Body**: `PauseRequestBody` можно вызывать только внутри обратного вызова Body — по возврату обратного вызова текущего фрагмента оно теряет силу (нужно оставить — копируйте сами); после завершения асинхронного потребителя **из любого потока** `ResumeRequestBody` (встроенная в Connection команда восстановления, без выделения узлов задач); во время паузы BodyTimeout продолжает отсчёт — потерянный потребитель не может бесконечно занимать соединение. (3) **Единственность ответа**: на запрос — ровно одна финальная фиксация (Respond/Reply/ReplyBody, одно из трёх); `xrtHttpConnInform` может заранее отправить информационный ответ 1xx (кроме 101).

### Три пути ответа и замороженное ядро

- `xrtHttpConnReply(连接, 状态, 类型, 字节)` (соединение, статус, тип, байты) — прямой ответ фиксированными байтами: копируется в компактное Body и сразу в замороженное ядро HTTP/1, ноль временных контейнеров. Стандартная форма health-проверки.
- `xrtHttpConnReplyBody(连接, ..., 可选 xhttpbody 引用)` (соединение, ..., опциональная ссылка xhttpbody) — версия того же прямого пути с источником тела: Borrow/Take/Reference/файл/производитель избавляют от копирования; неизвестная длина — chunked (1.1) или закрытие (1.0). После возврата вызова вызывающий может уничтожать свою ссылку body.
- `xrtHttpConnRespond` — полный путь построителя для динамических полей и trailer (зеркало построителя запросов главы 98).

### Жизненный цикл: Drain и Shutdown

`xrtHttpServerDrain` — грациозное осушение: новые соединения не принимаются, идущие запросы завершаются, соединения закрываются одно за другим; событие `Shutdown` публикуется после выхода **всех** протокольных объектов, передачи прав транспорта, завершения среды выполнения и возврата принятых обратных вызовов Upgrade-передачи — «ничего не бегает» гарантировано событием, а не догадкой. Шаблон финала «цикл ожидания `XHTTP_SERVER_CLOSED`» тот же, что у TCP главы 66.

## Контракты

- **Атомарность запуска**: все логические конечные точки связываются одновременно, провал не оставляет частичного Server; диапазоны адресов валидируются до открытия; потолки валидируются статически без выделения.
- **Пять тайм-аутов**: Header/Body/Request/Idle/Write каждый защищает свой отрезок, микросекунды, ноль отключает; у каждого отрезка медленной атаки свой шлюз.
- **Последовательность событий**: все прикладные события исполняются последовательно на Worker-владельце соединения; Error максимум один (стабильная ошибка + цепочка причин), Close ровно один; сбой транспорта — фиксированный порядок Error→Close.
- **Стратегия Headers**: выбор из пяти буферизация/поток/отброс/отказ/прямой ответ; лимит тела уровня маршрута (SetRequestBodyLimit меняет единственный жёсткий потолок текущего Exchange).
- **Противодавление Body**: Pause только внутри обратного вызова Body; по возврату обратного вызова фрагмент недействителен; Resume из любого потока (встроенная команда, ноль выделений); во время паузы BodyTimeout отсчитывается.
- **Единственность ответа**: одна финальная фиксация; Inform шлёт 1xx (кроме 101); информационные и финальный ответ на одной линии противодавления.
- **Путь прямого ответа**: Reply/ReplyBody входят в замороженное ядро без временных контейнеров; ссылку body после фиксации можно уничтожать; неизвестная длина — chunked/закрытие.
- **Жизненный цикл**: Drain — грациозное осушение; Shutdown публикуется после полного освобождения ресурсов (включая Upgrade-передачу); финал Closed ждётся циклом.
- **Обрезка**: `XHTTP_FEATURE_HTTP_SERVER` зависит от Exchange/Response/TCP Server; потоковый исходящий, файлы, TLS, Upgrade — независимые комбинируемые слои; в ядре нет второй машины состояний.

## Ловушки

### Ловушка 1: сохранить представление фрагмента из обратного вызова Body для асинхронной обработки

Симптом: асинхронный потребитель читает перемешанные данные фрагментов или падает — то же висячее представление, что в главе 95.

Причина: фрагменты Body — **заимствование** — по возврату обратного вызова недействительны. Асинхронное потребление — либо копия, либо Pause/Resume, чтобы среда выполнения ждала вас.

```c bad
static bool onBody(..., xbytesview Chunk, ...) {
	queue_push(g_Queue, Chunk);      /* сохранили представление: по возврату повисло */
}
```

```c good
static bool onBody(xhttpconn* pConn, ..., xbytesview Chunk, ...) {
	if ( !consumer_ready() ) {
		copy_and_queue(Chunk);                 /* оставить - копируем */
		xrtHttpConnPauseRequestBody(pConn);    /* приостановить дальнейшую доставку */
		return true;
	}
	consume_now(Chunk);                          /* синхронное потребление, ноль копий */
	return true;
}
/* после завершения асинхронного потребителя из любого потока: xrtHttpConnResumeRequestBody(pConn) */
```

### Ловушка 2: медленному клиенту не выставили WriteTimeout

Симптом: клиент, оборвавший сеть посреди загрузки (без RST), занимает соединение и буферы часами — лимит соединений съедают такие зомби.

Причина: дефолт WriteTimeout может не покрывать вашу форму развёртывания (ноль = защита выключена). У «нет прогресса» стадии ответа обязан быть срок.

```c bad
xrtHttpServerConfigInit(&Config);
/* WriteTimeout остался дефолтным/нулём - зомби-соединения занимают место вечно */
```

```c good
xrtHttpServerConfigInit(&Config);
Config.WriteTimeout = UINT64_C(30000000);   /* 30s без прогресса ответа - бросаем */
Config.IdleTimeout = UINT64_C(75000000);    /* keep-alive 75s */
/* все пять явно - защита это контракт развёртывания, не везение */
```

### Ловушка 3: длительная блокирующая операция в обратном вызове Request

Симптом: Worker заблокирован — остальные соединения того же Worker все встали (серверная цена экономики Worker главы 63).

Причина: события исполняются на Worker последовательно; блокировка в обратном вызове (синхронный файловый IO, внешний вызов) закладывает в залог целый Worker. RequestTimeout лишь ограничивает урон, не лечит.

```c bad
static void onRequest(..., const xhttpserverrequest* pReq, ...) {
	char* p = blocking_external_call(...);   /* блок 2s: Worker весь встал */
	reply(...);
}
```

```c good
static void onRequest(xhttpserver* pS, xhttpconn* pC,
		const xhttpserverrequest* pReq, ptr pD) {
	submit_to_pool(pC, pReq);   /* перепоручить пулу исполнения (глава 58), удержав Connection */
	/* по завершении в пуле - доставка обратно на Worker-владелец и Respond; RequestTimeout страхует */
}
```

## Упражнения

### Базовое: эксперимент с пятью тайм-аутами

На базе образца server проверяйте по одному: медленные заголовки (по байту заголовка в секунду), медленное тело, клиент не читает ответ — наблюдайте срабатывание соответствующего тайм-аута и закрытие соединения. Критерии приёмки: время отказа каждого из трёх отрезков соответствует конфигурации; обратный вызов ошибки получает структурированную ошибку и информацию о стадии.

### Продвинутое: маршрутизация и параметры

Router-ом реализуйте двухуровневые параметры пути `/items/{id}` и `/items/{id}/parts/{part}`; Request печатает значения параметров; добавьте обработчик PUT. Критерии приёмки: параметры пути извлекаются по порядку; несовпадение 404; несовпадение метода 405.

### Вызов: шлюз с лимитом загрузки

Обратный вызов Headers ставит лимит тела по маршруту (`/avatar` 2 MB, `/video` 200 MB, прочее 1 MB); Body принимает потоково и считает байты; запрос сверх лимита отвергается на стадии тела (413), соединение закрывается чисто. Критерии приёмки: три лимита действуют каждый; соединение сверх лимита не занимает память (лимит перехватывает до расхода); нормальная загрузка принимается целиком.
