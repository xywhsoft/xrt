## Ориентация

В TLS две стороны «доказывают себя»: клиент доказывает «кому я доверяю» (верификатор, глава 84), сервер доказывает «кто я» (**идентичность**, эта глава). `xtlsidentity` упаковывает одну DER-цепочку сертификатов и один приватный ключ в **неизменяемый разделяемый объект**: при создании глубоко копирует весь материал и выполняет перекрёстную проверку (действительно ли приватный ключ соответствует публичному в сертификате? какие схемы TLS эта цепочка может подписывать?), после чего объект конкурентно разделяется потоками и конфигурациями серверов, а рукопожатие пользуется им для производства подписи CertificateVerify. Четыре строго типизированных конструктора (RSA/P-256/P-384/Ed25519) покрывают магистральные серверы; расширительный интерфейс `xrtTlsIdentityCreate` отдаёт подписную способность на аутсорс HSM, системному хранилищу ключей или удалённому подписчику. Аутентификация клиентскими сертификатами сейчас не реализована (контракт главы 81), поэтому идентичность сегодня — понятие **серверное**; сам объект от роли отвязан.

## Введение

Что готовят для развёртывания TLS-сервера? Цепочку сертификатов (листовой + промежуточные CA, PEM-файл) и приватный ключ. Неприятности начинаются с загрузки: DER-форматов приватного ключа несколько (PKCS#1, PKCS#8, голый скаляр SEC1, семя Ed25519); алгоритм публичного ключа сертификата должен совпасть с приватным; у RSA-PSS-сертификатов ещё и параметрические ограничения (дайджест, MGF1, нижний предел соли) — при любом несовпадении подпись провалится только в рукопожатии, и встречать вы будете тревогу трёх часов ночи, а не ясную ошибку при старте.

Ответ `xtlsidentity` — **полная проверка на этапе создания**: конструктор разбирает приватный ключ, сверяет SPKI сертификата, проверяет общие подписные схемы для версий TLS — «у идентичности нет ни одной общей TLS-схемы — отказ прямо при конструировании». Упасть при старте в десять тысяч раз лучше, чем в рукопожатии: опыт развёртывания и опыт безопасности — одно и то же. Прошедшая проверку идентичность неизменяема: цепочка сертификатов глубоко копируется в один компактный блок (перед освобождением безопасно обнуляется), заимствованные представления действуют до освобождения последней ссылки — много Worker-ов разделяют один объект, ноль блокировок.

## Понятия

### Четыре конструктора и их диалекты приватных ключей

| Конструктор | Входная форма приватного ключа | Проверка на этапе создания |
| --- | --- | --- |
| `xrtTlsIdentityRsa` | PKCS#1 или незашифрованный PKCS#8 DER | модуль, экспонента, все CRT-параметры, листовой SPKI, ограничения RSA-PSS |
| `xrtTlsIdentityP256` | 32-байтовый скаляр / SEC1 / незашифрованный PKCS#8 | диапазон скаляра, OID кривой, опциональный публичный ключ SEC1, листовой P-256 SPKI |
| `xrtTlsIdentityP384` | 48-байтовый скаляр / SEC1 / незашифрованный PKCS#8 | то же (P-384) |
| `xrtTlsIdentityEd25519` | 32-байтовое семя / одно-двухслойный DER OCTET / RFC 8410 PKCS#8 | умолчания параметров алгоритма, производный публичный ключ, листовой Ed25519 SPKI |

Три общности: **первый сертификат цепочки обязан быть листовым**; **приватный ключ не заимствуется** (глубоко копируется в идентичность; буфер вызывающего можно переиспользовать немедленно); **RSA сохраняет полную CRT-вид, Ed25519 — однократно развёрнутый подписной ключ** — путь рукопожатия не повторяет деривацию. PEM/файл/системное хранилище не входят в ядро идентичности: сперва возьмите DER через PEM-декодирование главы 77, затем отдайте конструктору — между слоями ходит только DER.

### CanSign: тройной запрос способности

`xrtTlsIdentityCanSign(身份, 版本, 方案)` отвечает «может ли эта идентичность подписать этой схемой» — проверяя одновременно ограничения версии TLS, тип идентичности сертификата, стандартные схемы и влитые бэкенды. Суть правил: TLS 1.3 не принимает RSA-PKCS#1 в CertificateVerify (жёсткое правило современного протокола); схемы ECDSA обязаны совпадать с кривой сертификата; сертификаты `rsaEncryption` и `RSASSA-PSS` входят только в пути `rsa_pss_rsae_*` и `rsa_pss_pss_*` соответственно; у ограниченного PSS-ключа параметры обязаны одновременно удовлетворять обеим сторонам — сертификату и приватному ключу. Белый список подписей политики (глава 84) пересекается с `CanSign` — это и есть фактическая схема рукопожатия; `exampleSignature` образца главы демонстрирует выбор ходовой схемы по типу идентичности.

### Sign: двухшаговая подпись и определённость

`xrtTlsIdentitySign(身份, 版本, 方案, 内容, 输出, 容量, &长度)` принимает **полное TLS-содержимое под подпись** (протокольный контекстный заголовок строит вызывающий — 64-пробельный ролевой префикс TLS 1.3 обрабатывается на уровне открытого примитива `xrtTls13CertificateVerifySignature`). Двухшаговость по обычаю всей библиотеки: пустой выход запрашивает точную длину, нехватка ёмкости не зовёт подписчика, неудача не публикует частичной подписи. Стратегии случайности трёх бэкендов: RSA-PSS берёт криптографически безопасную случайную соль; ECDSA — детерминированная подпись RFC 6979 low-S (глава 75 объясняла, почему определённость — достоинство); чистый режим Ed25519 определён сам по себе.

### Create: аппаратура и удалённые подписчики

В реальной корпоративной среде приватный ключ часто живёт в HSM или системном хранилище ключей и не экспортируется в DER. `xrtTlsIdentityCreate` — расширительный интерфейс: цепочка сертификатов всё так же глубоко копируется XRT, подписная способность отдаётся на аутсорс колбэкам `Supports`/`Sign` — оба обязаны допускать конкурентные вызовы; `Supports` — предикат способности без ошибки, `Sign` при неудаче не меняет выход. Без аппаратных потребностей берите встроенные строго типизированные конструкторы — колбэчный порт приготовлен для втыкаемости, это не ежедневный путь.

### Жизненный цикл: от загрузки к разделению

```diagram flow
- Загрузка: PEM/файл -> DER (глава 77), цепочка сертификатов + приватный ключ уходят конструктору
- Проверка: разбор приватного ключа + перекрёстная сверка SPKI + проверка общих схем (неудача - отказ)
- 共享：不可变对象被服务端配置/多 Worker 并发引用（Retain/Release）
- Уничтожение: последнийссылка освобождён -> весь ключевой материал безопасно обнулено -> колбэк Release ровно один раз
```

`Retain`/`Release` — подсчёт ссылок; при освобождении последней весь ключевой материал безопасно обнуляется и вызывается колбэк `Release` (форма Create). Неизменяемость идентичности значит: разделяемость конфигурациями многих серверов, конкурентная подпись многими Worker-ами, комбинирование с политиками/контекстами — **собрали раз, разделяем везде**; та же философия «разделяемое только-чтение дешевле всего», что у пула объектов главы 22, но здесь разделяется неизменяемое значение, а не переиспользуемый слот.

`Retain`/`Release` — тот же подсчёт ссылок; последнее освобождение обнуляет материал и зовёт колбэк `Release` — см. диаграмму выше.

(2) Каждая конструкция и есть полная проверка: разбор приватного ключа, перекрёстная сверка SPKI, проверка общих схем — встроенный материал весь законен, конструкция проходит; подсуньте пару с несовпадающими сертификатом и ключом — конструкция падает сразу со структурной ошибкой (код ошибки identity + цепочка причин DER/X.509/crypto). (3) `CertificateCount` подтверждает длину цепи (здесь по одному листу на форму); реальное развёртывание передаёт полный массив промежуточных CA. (4) С параметрами программа переключается на полный путь «прочитать DER-файлы → построить → двухшаговый Sign» — `exampleSignature` выбирает схему по типу (RSA через PSS, Ed25519 напрямую), пустой выход запрашивает длину, затем выделение и подпись, печать числа байтов подписи (у Ed25519 всегда 64, у RSA — длина модуля). (5) Каждая идентичность после использования — `Release`: управлением жизненным циклом неизменяемого разделяемого объекта ведает только эта пара вызовов.

**Что только что произошло.** (1) **Три домена Ed25519 взаимно несовместимы**: PURE (подпись сообщения напрямую), CONTEXT (со контекстной строкой — именно эта идея разделения доменов работает в CertificateVerify TLS 1.3), PREHASH (подпись 64-байтового предхеша SHA-512). Подпись междоменно непроверяема — это криптомеханизм «один алгоритм, разные назначения не смешиваются»; ролевой префикс TLS («TLS 1.3, server CertificateVerify») и защищает от переноса TLS-подписи сайта в другой протокол. (2) ECDSA работает по интерфейсу «принимает дайджест, а не сообщение» (алгоритм дайджеста объявляет перечисление `Hash`); raw `r||s` фиксированной ширины и проволочный DER взаимоконвертируемы — круговорот двойного представления ECDSA из главы 75. (3) Сверьте со слоем идентичности: внутри `IdentitySign` ровно эти нижние примитивы плюс TLS-контекстная обёртка — понимание нижнего слоя помогает диагностировать межслойные вопросы вида «CanSign разрешил, а рукопожатие падает» (обычно белый список политики не открыл схему).

## Контракты

- **Неизменяемое разделение**: после создания неизменяем; разделение подсчётом ссылок; заимствованные представления (сертификаты/публичные ключи) действуют до освобождения последней ссылки; многопоточная подпись без блокировок.
- **Проверка на этапе создания**: разбор приватного ключа + перекрёстная сверка листового SPKI + проверка общих схем TLS; нет общей схемы — прямой отказ; первый сертификат цепи обязан быть листовым.
- **Глубокая копия приватного ключа**: конструкторы не заимствуют вход; один компактный блок, безопасное обнуление перед освобождением; RSA хранит CRT-вид, Ed25519 — развёрнутый ключ.
- **Семантика CanSign**: четырёхкратная проверка версия + тип + схема + бэкенд; 1.3 отвергает PKCS#1; схема ECDSA следует кривой сертификата; ограниченный PSS-ключ — двусторонние параметрические ограничения.
- **Контракт Sign**: двухшаговость (пустой выход запрашивает длину); нехватка ёмкости не зовёт подписчика; неудача не публикует частичную подпись; случайная соль PSS / детерминированный low-S у ECDSA / чистый режим Ed25519.
- **Расширение Create**: предикат `Supports` без ошибки; `Sign` конкурентен, при неудаче выход неизменен; `Release` ровно один раз; цепочка сертификатов всё равно глубоко копируется.
- **Модель ошибок**: коды ошибок identity в `xrt.tls`; провалы DER/X.509/crypto сохраняются как Cause — верхний слой может отображать по фазам TLS, C-вызывающий читает нижнюю причину.
- **Обрезка**: ядро `TLS_IDENTITY` + `_RSA/_EC/_P256/_P384/_ED25519` независимо — сервер только на Ed25519 не втягивает код RSA.

## Ловушки

### Ловушка 1: сертификат и ключ не совпали — выяснилось вечером релиза

Симптом: сервис стартует нормально, клиентские соединения падают на этапе CertificateVerify — в журнале лишь «signature invalid», не видно, что перепутан материал.

Причина: многие пути загрузки впервые пользуются приватным ключом только в рукопожатии; перепутанный сертификат (скажем, после продления сменили сертификат, а ключ остался старым) вскрылся первым же реальным соединением.

```c bad
/* только читать файлы, не строить идентичность: ошибка отложена до рукопожатия */
load_file("cert.pem", &Cert, &CertSize);
load_file("key.pem", &Key, &KeySize);
/* сохранить, при рукопожатии использовать напрямую - несовпадение никто не заметит */
```
```c good
/* строить идентичность при старте: несовпадение падает на месте */
xtlsidentity* pIdentity = xrtTlsIdentityP256(
	&(xbytesview){ Cert, CertSize }, 1u,
	(xbytesview){ Key, KeySize }
);
if ( pIdentity == NULL ) {
	fprintf(stderr, "identity: %s\n",
		xrtErrorMessage(xrtGetError()));
	return EXIT_FAILURE;   /* вскрытие на этапе старта, с цепочкой причин */
}
```

### Ловушка 2: самодельные комбинации подписных схем (CanSign не прошёл — упорствуем)

Симптом: идентичности Ed25519 назначили схему RSA-PSS или P-256-сертификату — схему P-384: `IdentitySign` возвращает неудачу, рукопожатие висит.

Причина: схемы TLS жёстко связаны с типом ключа (RFC): у схем ECDSA есть имя кривой, RSA делится на семейства rsae/pss, у Ed25519 только чистая схема. Это не «попробовать посмотреть» пункт конфигурации.

```c bad
/* идентичность Ed25519 + схема RSA: неизбежная неудача */
xrtTlsIdentitySign(pIdentity, XTLS_VERSION_13,
	XTLS_SIGNATURE_RSA_PSS_RSAE_SHA256, ...);
```
```c good
/* схема следует типу идентичности: спросить CanSign заранее */
xtlssignature Scheme = pick_scheme_for(xrtTlsIdentityType(pIdentity));
if ( !xrtTlsIdentityCanSign(pIdentity, XTLS_VERSION_13, Scheme) ) {
	/* ошибка конфигурации: доложить на старте, не в рукопожатии */
}
```

### Ловушка 3: разделяемое изменяемое состояние в Sign-колбэке HSM-расширения

Симптом: при конкурентных рукопожатиях перемежающиеся неудачи подписи либо перепутанный выход — документация `Create` прямым текстом требует конкурентоспособности Supports/Sign, но реализация колбэка воспользовалась нереентерабельным дескриптором.

Причина: объект идентичности конкурентно разделяется многими Worker-ами; подписные колбэки одновременно бегут в нескольких рукопожатиях. Колбэк — контракт без блокировок; выстроить очередь или погресионные сессии для доступа к устройству с состоянием — ваша ответственность.

```c bad
static bool hsmSign(..., void* pOutput, size_t* pSize) {
	hsm_begin(pHsmSession);   /* разделяемая сессия: конкурентные рукопожатия топчут друг друга */
	hsm_op(...);
	hsm_end(pHsmSession);
}
```
```c good
/* на каждый вызов своя сессия (или пул сессий); неудача не меняет выход и длину */
static bool hsmSign(const void* pContent, size_t iSize,
		void* pOutput, size_t iCapacity, size_t* pSize) {
	hsmsession* pS = hsm_session_acquire();   /* через пул */
	bool bOk = hsm_sign(pS, pContent, iSize, pOutput, iCapacity, pSize);
	hsm_session_release(pS);
	return bOk;
}
```

## Упражнения

### Базовое: самопроверка четырёх форм на встроенном материале

Прогоните без параметров образец identity и сверьте значения перечисления в четырёх строках с `xtlsidentitytype`. Затем сгенерируйте OpenSSL самоподписанную пару Ed25519 (сертификат и ключ, экспорт DER) и пройдите параметрический путь с проверкой 64-байтовой подписи. Критерии приёмки: самопроверка четырёх форм вся зелёная; путь на собственном материале выводит `identity=5 certificates=1 signature=64 bytes`.

### Продвинутое: перехват несовпадающего материала на старте

Намеренно перепутайте две пары (сертификат RSA + ключ EC; сертификат P-256 + ключ P-384), постройте каждую идентичность и напечатайте цепочку причин ошибки (`xrtErrorMessage` + `xrtErrorCause`). Критерии приёмки: обе пары валятся на конструировании, не на подписи; цепочка ошибок различает «провал DER-разбора» и «несовпадение SPKI».

### Вызов: имитатор подписи HSM

Реализуйте через `xrtTlsIdentityCreate` «имитируемый HSM»: `Supports` признаёт только Ed25519; `Sign` внутри — настоящая реализация (семя хранится в «аппаратной» структуре, имитируя неэкспортируемость) плюс атомарный счётчик вызовов. Подключите его к серверу главы 85 (или протестируйте единично), конкурентно подписывая из 8 потоков. Критерии приёмки: все подписи успешны и проверяемы; счётчик равен числу подписей (доказательство конкурентности); «аппаратное» семя ни разу не покидает имитируемую структуру (подтверждение код-ревью).

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Объект идентичности | упаковка цепочки + ключа; неизменяем, подсчёт ссылок, многопоточное разделение без блокировок |
| Четыре конструктора | Rsa/P256/P384/Ed25519; диалекты ключей различны (PKCS#1/#8/SEC1/семя) |
| Проверка на создании | разбор ключа + перекрёстная сверка SPKI + проверка общих схем; нет схем — отказ |
| Обработка ключа | глубокая копия без заимствования; один блок с обнулением перед освобождением; CRT/развёрнутый ключ остаются |
| CanSign | версия + тип + схема + бэкенд; 1.3 отвергает PKCS#1; ECDSA следует кривой; PSS — двусторонние ограничения |
| Sign | двухшаговый запрос/подпись; неудача не публикует частичное; случайная соль PSS / low-S у ECDSA / чистый Ed25519 |
| Привязка схем | схема следует типу ключа; белый список политики ∩ CanSign — схема рукопожатия |
| Расширение Create | HSM/системное хранилище/удалённый подписчик; предикат Supports + конкурентный Sign + ровно один Release |
| Входная граница | PEM/файл/системное хранилище вне ядра идентичности — сперва DER, потом конструкция |
| Обрезка | _RSA/_EC/_P256/_P384/_ED25519 независимо; одноалгоритмный сервер не несёт остальных |
