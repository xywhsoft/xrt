## Ориентация

Заключительная глава xmail. Предыдущие четыре дали слой данных (115) и три протокола (116–118); эта глава сливает их: **`mail_compose`** (высокоуровневая композиция — `xmailmessage`/`xmailattachment` заимствуют все данные вызывающего; `xrtMailCompose` одной строкой даёт полное сообщение: **трёхслойный автоматический выбор multipart** (mixed/alternative/related комбинируются по содержимому, границы взаимно различны), автоматическое кодирование QP/Base64, **Bcc идёт только слою отправки, в сообщение не попадает**); **`smtp_submit`** (высшая отправка — одна структурная отправка, конверт выводится из сообщения; соединение держит вызывающий); **слой синтаксиса адресов** (`mail_address`: валидация addr-spec, ASCII по умолчанию с явным SMTPUTF8); **замкнутый цикл** (Compose → статическая проверка Valid → сессия Submit → вложения кодируются потоково, ноль копий целого сообщения на всём пути). Карта слоёв: от `xrtSmtpSubmit` (одна строка) до `CommandWrite` (байты) — каждый уровень свободен для спуска.

## Введение

«Отправить HTML-письмо с вложением» в эпоху ручного MIME — двадцать строк клея: выбрать структуру multipart (mixed оборачивает related оборачивает alternative?), сгенерировать не сталкивающиеся границы, QP-кодировать тело, Base64-кодировать вложения с переносами, обработать кодированные слова китайского Subject, посчитать Content-Type… глава 116 дала примитивы для всего — но неужели распространённые комбинации каждый раз склеивать руками? Ответ `mail_compose` — **структурированный ввод + автоматический выбор технологии**: вы объявляете «вот тело, вот HTML-версия, вот две встроенные картинки, вот три вложения» — структура **выводится из содержимого автоматически** (трёхслойная вложенность собирается сама, границы генерируются взаимно различными), кодирование автоматично по типу (текст QP / вложения Base64 кусками), а Date/Message-ID/boundary вы вставляете, только когда нужен **детерминированный вывод** (тесты/архивы).

Обработка Bcc — образец проектирования безопасности: **адрес скрытой копии входит только в получателей конверта SMTP-слоя отправки** (в RCPT TO он есть), **в RFC-сообщение — никогда** (в заголовках To/Cc его нет) — протокольно корректная реализация «скрытой копии»; пропустить этот слой (вписать Bcc в заголовки) — превратить её в открытую копию, приватную аварию, где получатели видят друг друга.

## Понятия

### Compose: описание, валидация и два выхода

```diagram flow
- Описание: xmailmessage (From/Reply-To/To/Cc/Bcc/UTF-8 Subject/Text/Html/
  встроенные ресурсы/вложения/свои поля) - всё заимствует данные вызывающего
- Валидация: xrtMailMessageValid - проверяет только описание (не генерирует случайных значений, не выделяет, sink не зовёт)
  - "все статические ошибки ввода до первой записи в сеть"
- Выход первый: xrtMailComposeWrite(описание, sink, ...) - прямая запись в поток (вложения кодируются кусками в sink)
- Выход второй: xrtMailCompose(описание, &длина) - полное сообщение (освобождается xrtFree)
```

**Ключ детерминированного вывода**: Date/Message-ID/три границы могут предоставляться вызывающим — пустыми остаются текущий UTC / криптостойкая случайность / криптостойкая случайность (домен Message-ID пуст — выводится из From). Тесты и архивы вставляют фиксированные значения → вывод воспроизводим байт-в-байт; продакшн оставляет пустыми → криптостойкая случайность. **Свои поля не могут перекрыть структурные поля, управляемые Compose** — владение структурными полями (Content-Type/boundary/объявления кодировок) принадлежит слою композиции; добавленные поля структуру не ломают.

### Трёхслойный автоматический выбор multipart

| Комбинация содержимого | Структура |
| --- | --- |
| обычные вложения есть | `multipart/mixed` |
| чистый текст + HTML сосуществуют | `multipart/alternative` |
| HTML со встроенными ресурсами | `multipart/related` |
| все три вместе | трёхслойная вложенность — **границы обязаны различаться** (гарантия слоя композиции) |

Политика кодирования: текст QP (MIME-форма ширины строк главы 116); вложения **Base64 фиксированными малыми кусками** — «без кодированной копии, растущей с размером вложения» (пик кодирования вложения 10 МБ = кусок, а не 13 МБ). Это приземление философии потоковых тел главы 108 на слое кодирования.

### Синтаксис адресов и граница интернационализации

`xrtMailAddressValid` валидирует addr-spec и отдаёт взаймы local-part/domain: **по умолчанию принимает только ASCII** local-part и DNS-стиль домена (поддерживаются цитируемые local-part и domain-literal); **только с явно установленным `XMAIL_ADDRESS_SMTPUTF8`** принимаются интернационализированные local-part / UTF-8-домены — и SMTP-клиент всё равно решает отправку по возможностям сервера (синтаксис прошёл ≠ противоположная сторона примет). **Граница слоёв**: этот слой ведает только синтаксисом сообщения — длины пути, DNS, IDNA, лимиты конверта принадлежат верхним слоям (расслоение главы 89 в почтовой редакции: синтаксический слой без транспортной политики).

### Submit: замкнутая отправка высшего уровня

`xrtSmtpSubmit(客户端, 消息, 截止, 取消)` (клиент, сообщение, дедлайн, отмена): внутри собирается MIME (через Compose) → выводится конверт (From→MAIL FROM; To+Cc+**Bcc**→RCPT TO) → отправка через DATA/BDAT — одной строкой от «структурированного описания» до «линии». Против трёх слоёв главы 117: `CommandWrite` (байты) ← `smtp_client` (сессия) ← `submit` (бизнес) — **каждый уровень вниз — строка спуска, каждый вверх — поколение делегирования**.

### Панорама замкнутого цикла отправки-приёма

```diagram flow
- Отправка: описание -> Valid (статическая проверка) -> Compose (структура + кодирование) -> Submit (конверт + сессия + потоковая отправка)
- Приём: потоковый забор POP3/IMAP -> MailMessageParse (представления) -> курсор multipart -> декодирование кодированных слов -> бизнес
- Инженерия накопленного: архивировать при приёме (конвейер главы 118) + собирать при отправке (эта глава) - ноль резиденции целых сообщений на обоих концах
```

(2) `xrtMailCompose` одной строкой даёт полное сообщение: китайский Subject автоматически в кодированные слова (`=?utf-8?B?...?=`), чистый текст QP-кодируется, Date/Message-ID криптостойко-случайны — **все решения двадцати строк ручного MIME исполняются здесь автоматически**. (3) После fwrite вывода — `xrtFree`; этот выход есть форма «полного сообщения» (нужен поток — переключитесь на `ComposeWrite`+sink: вложения идут в sink кусками). (4) Разберите этот вывод обратно `MailMessageParse` главы 116 — **отправка и приём пользуются одним словарём разбора**, цикл самосогласован.

## Контракты

- **Заимствованное описание**: message/attachment целиком заимствованы — ноль скрытых связей / ноль словарей / ноль рекурсивных owned-деревьев.
- **Valid — чистая проверка**: случайных значений не генерирует, не выделяет, sink не зовёт — все статические ошибки до первой записи в сеть.
- **Два выхода**: ComposeWrite пишет прямо в sink (вложения кодируются кусками) / Compose даёт полное сообщение (xrtFree).
- **Структура автоматична**: три слоя mixed/alternative/related комбинируются по содержимому; взаимная различность границ гарантирует слой.
- **Ключи детерминизма**: Date/Message-ID/границы вставляемы (пусто = криптостойкая случайность); домен Message-ID выводится из From.
- **Граница полей**: свои поля не перекрывают структурные — владение структурой у слоя композиции.
- **Политика кодирования**: текст QP; вложения Base64 фиксированными кусками — ноль кодированных копий, растущих с размером.
- **Семантика Bcc**: только в конверт слоя отправки, никогда в RFC-сообщение — протокольно корректная скрытая копия.
- **Адреса ASCII по умолчанию**: SMTPUTF8 явно; синтаксис прошёл ≠ доставляемо (суждение возможностей — протокольному слою).
- **Слой Submit**: описание → сборка → конверт → сессия одной строкой; дедлайн/отмена насквозь.

## Ловушки

### Ловушка 1: получатель Bcc вписан в собственное поле

Симптом: «скрытая копия» становится открытой — все получатели видят друг друга в заголовках; приватная авария.

Причина: семантика Bcc реализуется **потреблением слоя отправки** (получатели конверта) — его отсутствие в заголовках сообщения и есть свойство. Добавить адрес Bcc как своё поле = вписать открытую копию руками.

```c bad
message.Bcc = &Secret;
add_custom_field(&message, "Bcc", "secret@x.com");  /* в сообщение: открытая копия */
```

```c good
message.Bcc = &Secret;   /* только структурное поле */
/* Submit выводит конверт: RCPT TO содержит secret; в заголовках Bcc нет - настоящая скрытая копия */
```

### Ловушка 2: вложения через Compose (не Write) — и жалобы на память

Симптом: вложение 50 МБ через выход полного сообщения `Compose` — в памяти одновременно оригинал и полное сообщение.

Причина: у двух выходов разная семантика: `Compose` — «дай мне полное сообщение» (агрегация неизбежна); для потоковой передачи — `ComposeWrite`: вложения кодируются фиксированными малыми кусками прямо в sink (сетевой поток/файл), пик = кусок.

```c bad
str raw = xrtMailCompose(&Msg, &n);   /* 50МБ агрегировано: пик удвоен */
send_all(raw);
```

```c good
/* ComposeWrite + потоковый sink: куски выходят напрямую */
xrtMailComposeWrite(&Msg, stream_sink, pCtx, ...);  /* малые куски прямо в сеть */
```

### Ловушка 3: тестовые ассерты без вставки ключей детерминизма

Симптом: сравнение двух выводов Compose проваливается — Date/Message-ID/границы каждый раз случайны.

Причина: пусто = криптостойкая случайность (правильное продакшн-умолчание); тестам для детерминизма нужно **вставить** фиксированные значения — это спроектированный ключ, а не дефект.

```c bad
raw1 = xrtMailCompose(&Msg, NULL);
raw2 = xrtMailCompose(&Msg, NULL);
assert(equal(raw1, raw2));   /* случайные Date/ID: никогда не равны */
```

```c good
Msg.Date = FixedDate; Msg.MessageId = FixedId;
provide_boundaries(&Msg, "t1", "t2", "t3");
raw1 = Compose(&Msg); raw2 = Compose(&Msg);
assert(equal(raw1, raw2));   /* детерминизм: байт-в-байт */
```

## Упражнения

### Базовое: проверка трёхслойной структуры

Постройте три описания (чистый текст + HTML + вложения; + встроенная картинка) — вывод Compose разберите по слоям курсором главы 116, проверьте структуру и взаимную различность границ. Критерии приёмки: подбор структуры сходится с таблицей; порядок трёхслойной вложенности верен.

### Продвинутое: эксперимент с замкнутым Bcc

Сообщение с Bcc отправить Submit на локальный тестовый сервер (или самосбор главы 104) — снять линию: RCPT TO содержит скрытую копию, в заголовках сообщения DATA поля Bcc нет. Критерии приёмки: оба доказательства на месте; адрес скрытой копии никогда не появляется и в пересылаемых получателями сообщениях.

### Вызов: инструмент полной цепочки отправка-приём

Композиция: ComposeWrite потоково отправляет вложение 10 МБ (DATA-поток главы 117) → потоковый приём POP3 (глава 118) → инкрементальный разбор восстанавливает (глава 116) → вложение пишется на диск с проверкой хеша. Критерии приёмки: память постоянна по всей цепочке (уровня МБ); хеши вложения совпадают; тема с кодированными словами проходит круг без потерь.
