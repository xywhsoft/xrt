## Ориентация

POP3 — простейший из трёх протоколов приёма (POP3/IMAP/глава 119): **загрузочная** модель — подключиться, аутентифицироваться, перечислить письма, забрать по одному, (опционально) удалить, попрощаться. Просто не значит небрежно: **dot transparency многострочных ответов** (экранирование точек в начале строк тела и завершение одиночной точкой у RETR/TOP — симметричная противоположность DATA SMTP); **потоковый приём** (`Begin/Next` выдаёт построчно, **не выделяя целое письмо** — каждая строка заимствует внутренний буфер, стабильна лишь до следующего чтения: три выхода — прямая запись в файл / инкрементальный MIME / собственное хранилище); **семантика идентичности UIDL** (уникальные ID поддерживают клиентскую логику «забирать только новое»); **семейство аутентификации SASL** (USER/PASS открытым текстом отвергается по умолчанию, SASL PLAIN плюс механизмы OAuth); **апгрейд STLS** (CAPA объявляет → +OK → апгрейд на месте → **повторный CAPA**). Расслоение xpop3: протокольные примитивы (офлайн) + клиент (синхронная машина состояний: AUTHORIZATION→TRANSACTION→MULTILINE→UPDATE) + опциональный слой message (ограниченная агрегация).

## Введение

Разница моделей POP3 и IMAP решает выбор: POP3 предполагает «забрал — значит локально» — сервер есть транзитная точка доставки, клиент — авторитетное хранилище; IMAP (глава 119) предполагает «сервер — авторитет» — почта остаётся на сервере, папки/флаги/поиск серверные. Простота POP3 даёт низкие ресурсы и офлайн-дружественность; богатство IMAP — синхронизацию многих устройств. Сегодня большинство сценариев — «принял и заархивировал» (вытащить в локальную базу) — потоковый приём POP3 подходит точно.

**Построчное заимствование** `Begin/Next` заслуживает внимания: RETR письма на 20 МБ — в любой момент в памяти только текущая строка; представление строки, которое выдаёт `Next`, **стабильно лишь до следующего чтения линии** (приход следующей строки затирает её). Это радикальнее «буферизации целого письма» — «принять почту» превращается в форму «читать файл» (изоморфизм IO-потоков главы 41).

## Понятия

### Протокольные примитивы: ответы, факты и команды

- **Ответы**: `xrtPop3ReplyParse` различает `+OK`/`-ERR` и заимствует текст статуса; `StatParse` (**64-битные** счётчики и байты — большие ящики не переполняются), `ListParse`/`UidlParse` (многострочные элементы; **UIDL не копируется и не обрезается**).
- **Переиспользование семейства точек**: завершение многострочности и дезэкранирование точек напрямую используют `MailLineRead`/`MailDotLine`/`MailDotDecodeWrite` из `mail_net` — **POP3-специфичной копии не держится** (два направления одного семейства примитивов с DATA SMTP).
- **Возможности**: `CapabilityParse` возвращает имя и параметры даже для неизвестных расширений; `Capability` даёт стабильные биты только распространённым стандартам.
- **Команды**: `CommandWrite` как родовая подстраховка (ёмкость включает завершающий ноль; отвергает управляющие символы/инъекции CR/LF/512B — та же дисциплина, что у командного слоя SMTP).

### Клиент: машина состояний и многоуровневые входы

```diagram state
AUTHORIZATION -> TRANSACTION: аутентификация успешна (USER/PASS или SASL)
TRANSACTION -> MULTILINE: многострочная команда (RETR/TOP/LIST/UIDL полностью)
MULTILINE -> TRANSACTION: строка одиночной точки (Next восстанавливает автоматически)
TRANSACTION -> UPDATE: Quit (фиксирует отметки DELE)
любое -> FAILED: ошибка линии (не переиспользуется)
```

**Четыре уровня входов**: `Send/Line` (самый низкий уровень линии — лазейка для SASL-продолжений и неизвестных расширений) → `Receive` (разбор +OK/-ERR) → `Command` (сборка + статусный ответ) → `Begin/Next` (многострочно, построчно). **Все стандартные команды построены на публичных входах** — STAT/LIST×2/UIDL×2/RETR/TOP/DELE/RSET/NOOP/QUIT суть сборки, а не частные пути: пользовательские расширения стоят на равных с официальными командами.

### Потоковый приём и опциональная агрегация

`Begin/Next` у RETR/TOP: каждая строка дезэкранирована от dot transparency, **целое письмо не выделяется**, представление строки заимствует внутренний приёмный буфер (стабильно до следующего чтения). Три выхода: писать прямо в файл (глава 45), инкрементальный разбор MIME (модули главы 116 кормятся по шагам), собственное хранилище сообщений. Опциональный слой `pop3_message`: на той же машине состояний **ограниченные** `RetrWrite/TopWrite` (агрегация в owned-байты внутри потолка) плюс входы дерева MIME — берёте только построчный путь, код агрегации не приезжает (свобода обрезки).

### Аутентификация: открытый текст отвергается по умолчанию, семейство SASL

`pop3_auth`: традиционные USER/PASS плюс SASL RFC 5034 (PLAIN и два механизма OAuth). **Дисциплина учётных данных**: конфигурация только заимствует учётные данные; Base64- и открытотекстовые временные буферы **обнуляются до возврата вызова** (парольная инженерия главы 77, исполненная на протокольном слое). **Передача учётных данных открытым текстом отвергается по умолчанию** — `AllowPlaintext` существует только для явно контролируемых сред совместимости (та же позиция, что базовая линия TLS у Basic главы 106). Отказ сервера в учётных данных оставляет в AUTHORIZATION (можно повторить); ошибка линии вводит FAILED.

### TLS: неявный и STLS

Базовый клиент — открытый текст на 110; `pop3_client_tls` добавляет две формы: неявный TLS (рукопожатие при подключении); STLS (CAPA явно объявляет → отправить STLS → **только после полного потребления +OK** исполняется рукопожатие → **повторный CAPA после рукопожатия** — возможности до апгрейда не утекают в защищённую сессию; та же логика, что повторный EHLO у STARTTLS SMTP). Verifier обязателен.

Остальные границы ответов, UIDL и многострочных данных проверяются тестами того же набора; короткая программа показывает два входа.

Вторая программа из `extlibs/xpop3/examples/offline/main.c`.


**Что только что произошло.** (1) Программа создаёт локальный слушатель и серверный поток, направляя демонстрационное имя на loopback. Стенд не реализует CAPA, поэтому автоматическое чтение возможностей отключено; настройку для реального сервера выбирают по его поведению. (2) Клиент выполняет USER/PASS и RETR, построчно потребляя `xrtPop3ClientNext`. Программа побайтно проверяет тему, пустую строку и тело; требуются ровно три строки и полный признак завершения многострочного ответа. (3) После QUIT программа ждёт серверный поток и уничтожает соединение, слушатель, резолвер и движок. Строка успеха появляется только после проверки содержимого и завершения работы. Фиксированные открытые учётные данные разрешены лишь для этого loopback-стенда; реальный пример использует TLS и учётные данные времени выполнения. Программа не удаляет почту: получение и удаление на сервере являются отдельными операциями.

## Контракты

- **Расслоение протокол/клиент**: примитивы от сети не зависят; клиент — сборка машины состояний; стандартные команды построены на публичных входах.
- **64-битные факты**: счётчики и байты STAT 64-битные; UIDL не копируется и не обрезается.
- **Общее семейство точек**: завершение многострочности/дезэкранирование переиспользуют примитивы mail_net — без POP3-специфичной копии.
- **Дисциплина инъекций**: CommandWrite отвергает управляющие/CR/LF/512B — как SMTP.
- **Потоковый приём**: RETR/TOP заимствуют построчно (стабильно до следующего чтения); целое письмо не выделяется; три выхода (файл/инкрементальный MIME/своё хранилище).
- **Опциональная агрегация**: слой message с ограниченными RetrWrite/TopWrite — построчный путь кода агрегации не несёт.
- **Обнуление учётных данных**: конфигурация заимствуется; временные буферы обнуляются до возврата вызова; открытый текст по умолчанию отвергается.
- **Семантика аутентификации**: отказ в учётных данных оставляет AUTHORIZATION; ошибка линии — FAILED, не переиспользуется.
- **TLS**: неявный/STLS; рукопожатие только после полного потребления +OK; повторный CAPA после апгрейда; верификатор обязателен.
- **Семантика UPDATE**: отметки DELE вступают в силу на UPDATE у Quit — Abort бросает удаления.
- **Владение**: разделяемые объекты заимствуются, не уничтожаются; из обратных вызовов Worker не звать; один клиент без конкурентности.

## Ловушки

### Ловушка 1: сохранение представления строки и продолжение приёма

Симптом: после приёма обработка кешированных строк — содержимое уже байты следующей строки.

Причина: граница стабильности строки — «следующее чтение линии»; самое агрессивное заимствование клиента POP3. Хотите сохранить между строками — копируйте.

```c bad
while ( Next(&Line) ) {
	rows[n++] = Line;   /* сохранённые представления: все недействительны при следующем Next */
}
process(rows);   /* всё — последняя строка */
```

```c good
while ( xrtPop3ClientNext(pClient, &Line) == OK ) {
	process_now(Line);          /* потреблять немедленно */
	/* или копировать: append_own_store(Line); */
}
```

### Ловушка 2: USER/PASS по открытому соединению

Симптом: `AllowPlaintext` включили и забыли — записи прослушки интрасети полны учётных данных.

Причина: отказ по умолчанию — защита, а не помеха; правильный путь совместимости со старыми серверами — STLS (апгрейд, коль скоро CAPA объявляет), а не отказ от шифрования.

```c bad
Config.AllowPlaintext = true;   /* удобство: учётные данные открытым текстом */
Auth(pClient, User, Pass);
```

```c good
if ( capa_has_stls() ) {
	Stls(pClient, ...);   /* сперва апгрейд */
}
Auth(pClient, User, Pass);   /* внутри шифрованного туннеля */
```

### Ловушка 3: предположение, что DELE удаляет немедленно

Симптом: после DELE сервер упал / клиент прервался — после перезапуска письмо на месте; пользователь думает «удалилось и вернулось».

Причина: удаление в POP3 **двухфазное**: DELE лишь помечает, фиксирует UPDATE у Quit — протокольная защита от случайного удаления. Хотите «точно удалено» — завершите Quit; хотите «может быть удалено» (пробная обработка) — Abort откатывает.

```c bad
Dele(pClient, 1);
/* крах/Abort: письмо не удалено - выглядит как баг */
```

```c good
Dele(pClient, 1);          /* отметить */
...
xrtPop3ClientQuit(...);    /* UPDATE фиксирует - по-настоящему удалено */
/* при сбое обработки Abort: отметки откатываются - страховочная сетка */
```

## Упражнения

### Базовое: разбор ответов и фактов

Постройте многострочные образцы `+OK`/`-ERR`/STAT/List/Uidl и прогоните через примитивы. Критерии приёмки: 64-битные счётчики верны; UIDL сохраняется полной длиной; завершение многострочности распознаётся верно.

### Продвинутое: забирать только новое

Список UIDL сверяется с локально виденным набором (Map главы 18) → RETR только новых UID → запись после обработки → опционально DELE+Quit. Критерии приёмки: повторные прогоны без дублей; стабильность UIDL (одно письмо — один ID); перезапуск после прерывания ничего не теряет и не дублирует.

### Вызов: конвейер архивации почты

Потоковый приём POP3 → кормление построчно в представление сообщения / инкрементальный разбор MIME главы 116 → извлечение заголовков и тела → запись в локальное хранилище mbox/JSONL. Письмо 20 МБ. Критерии приёмки: память постоянна весь путь (уровня МБ); после архивации разбор главы 116 восстанавливает целиком; возобновляемый приём (сверка UIDL).
