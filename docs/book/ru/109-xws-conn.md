## Ориентация

Главы 94–96 тома 9 дали **протокольное ядро** WebSocket (кадры/сообщения/потоки); библиотека-расширение xws достраивает над ним **инженерный соединительный слой**: `xwsconn` принимает TCP- или TLS-поток с уже завершённым рукопожатием — она не ведает URL, DNS, HTTP-запросами, политикой сертификатов или перенаправлениями (это дело главы 93 и тома 8 TLS), а управляет только событиями сообщений соединения, противодавлением, закрытием и интроспекцией. В главе три блока: **события и дисциплина представлений** (начало сообщения/данные/конец, события Ping/Pong/Close; представления данных действительны только внутри обратных вызовов); **противодавление и контракт отправки** (приёмное управление pause/resume, верхняя/нижняя водяные отметки и результат AGAIN — наследование полного словаря сетевого потока); **полный обход цепочки** (семь строк самопроверки `connection_tour`, покрывающих офлайн-сборку, живую пару соединений, девять видов отправки, асинхронное семейство, авто-Pong, паузу-восстановление и чистое закрытие — исполнимая таблица контрактов этой главы). Мост Future/корутин и протокол закрытия завершают главу.

## Введение

Границы разделения труда xws стоит нарисовать сразу: **базовая библиотека** (том 9) даёт кадры, сообщения, рукопожатие, согласование расширений, permessage-deflate — комбинируемые протокольные детали; **слой расширения xws** (с этой главы) подключает эти детали к реальным соединениям и добавляет инженерные средства (события соединения, жизненный цикл ссылок, ожидание Future, группы соединений, серверную маршрутизацию). Контрактная документация прямо говорит: «HTTP-клиентские/серверные адаптеры, маршрутизация и каркасные объекты удобства вышли из ядра» — слой расширения позиционируется как **зона перестройки высокоуровневых возможностей** и не имеет права допускать, чтобы объектная модель обратно загрязняла путь кадров и прямой отправки/приёма. Это расслоение «тонкое ядро, толстое расширение» полностью изоморфно xhttp (протокольное ядро в томе 9, прикладной слой в томе 10).

Первое проектное решение соединительного слоя — **принять, а не создавать**: `xwsconn` получает «поток с уже завершённым рукопожатием» — кто завершил рукопожатие (процесс обновления главы 93, серверная маршрутизация xws (глава 112)) неважно; соединительный слой смотрит только на «готовый транспорт». Это позволяет ему одинаково стоять над TCP и TLS (путь перехвата TLS главы 96).

## Понятия

### Модель событий и дисциплина представлений

События соединения: начало сообщения, фрагмент данных, конец сообщения, Ping, Pong, Close, ошибка, финальное закрытие — больше, чем слой Stream главы 95: Ping/Pong получают **независимые события** (управляющие кадры не только автоотвечают — они ещё и видны). **Дисциплина представлений** едина со всей библиотекой: представления данных в обратном вызове действительны только во время обратного вызова; сохранение между обратными вызовами требует копирования или принятия владеющего буфера. Правила ролей наследуются от ядра: сервер требует маскирования клиентских кадров, клиент требует отсутствия маски у серверных — роль фиксируется при установке соединения и никогда не угадывается покадрово.

### Противодавление: pause/resume и водяные отметки

```diagram flow
- Приём: поток событий сообщений -> потребление приложением
- Медленное потребление: pause приостанавливает приём -> противоположная сторона чувствует TCP-противодавление -> память постоянна
- Возобновление: resume продолжает - никогда не решайте медленного потребителя бесконечно растущей прикладной очередью
- Отправка: наследует верхнюю/нижнюю отметки сетевого потока, потолок стоящих в очереди байтов и контракт результата AGAIN
```

Это соединительный слой дисциплины «не потребляем = не принимаем» (экономика Worker главы 61).AGAIN и словарь водяных отметок пути отправки идентичны главе 95 — кто прошёл слой Stream, здесь не встретит ни одного нового слова.

### Три состояния владения отправкой (анонс пути отправки)

copy (копия до возврата — короткие управляющие кадры/короткие сообщения), ref (release ровно один раз при выводе из очереди — статические или разделяемые большие блоки), take/buffer (передача уже выделенной памяти или цепочки сетевых буферов) — глава 110 разворачивает формы writer; здесь сначала утверждается атомарное правило «до приёма владение остаётся у вызывающего, после приёма освобождает только соединение».

### Мост Future и корутин

Future оборачивает только отправки, закрытия, drain и ожидание финалов **на уже установленном соединении** — скрытый HTTP-клиент не создаётся. Две дисциплины: **отмена ожидания ≠ уничтожение соединения** — вызывающий решает по контракту конкретной операции: продолжать пользоваться, закрыть нормально или прервать; корутины ждут через общую систему Future/Wait (глава 57) — **внутри WebSocket не ведётся второй планировщик**. Семья образцов `connection_future` демонстрирует формы ожидания.

### Протокол закрытия и домены ошибок

Порядок нормального закрытия: отправить или ответить Close → прекратить отправку новых данных → ждать Close противоположной стороны или дедлайна → закрыть направление записи → ждать завершения транспорта. Нарушение протокола, превышение лимитов, отказ нижнего слоя могут прерваться напрямую — но **все принятые ссылки обязаны освобождаться ровно один раз** (гарантия финального состояния владения ссылками). Модель ошибок: протокольные ошибки используют стабильные коды домена WebSocket и по возможности отображаются на RFC Close code; сетевые/TLS/ошибки прикладных обратных вызовов **сохраняют собственные домены** — никогда не сплющиваются в одну булеву причину (цепочка причин главы 4, исполненная на протокольном слое).

**Что только что произошло.** Семь строк — семь классов контрактов. (1) **Офлайн-сборка**: материалы запроса/ответа строятся без соединения (чисто функциональная грань слоя рукопожатия — глава 93). (2) **Живая пара соединений**: xhttp-сервер и клиент завершают обновление по кольцу; интроспекция (роль/протокол/состояние) исполняется **внутри обратного вызова Worker-владельца** — дисциплина принадлежности Worker у синхронных вызовов. (3) **Девять синхронных отправок + writer-take**: copy/ref/take × text/binary плюс путь writer (глава 110) доставляются целиком — release-обратный вызов нагрузки Take срабатывает **ровно один раз** (проверка финального состояния владения). (4) **Асинхронное семейство + барьер ожидания**: отправки Future и ожидание (отмена не уничтожает соединение). (5) **Авто-Pong**: Ping наблюдает автоматический ответ — автоматизация управляющих кадров. (6) **Пауза/восстановление**: главный обратный вызов приостанавливает приём, данные удерживаются, после восстановления доставка продолжается — семантика противодавления. (7) **Чистое закрытие**: обе стороны завершают рукопожатие Close. Строка — контракт; семь строк — всё зелено; контрактная таблица этой главы и есть этот вывод.

## Контракты

- **Граница приёма**: xwsconn принимает рукопожатые TCP/TLS-потоки; не ведает URL/DNS/HTTP/сертификатами/перенаправлениями — слои сверху и снизу каждый на своём месте.
- **Модель событий**: начало/данные/конец сообщения + Ping/Pong/Close/ошибка/финал; представления данных действительны только внутри обратных вызовов; роль фиксируется при установке.
- **Противодавление**: pause/resume; неограниченные прикладные очереди запрещены; отправка наследует контракты отметок и AGAIN.
- **Атомарность владения**: три состояния copy/ref/take; непринятое остаётся у вызывающего, после приёма соединение освобождает ровно один раз.
- **Мост Future**: оборачивает только операции установленных соединений; отмена ожидания ≠ уничтожение соединения; корутины идут через общую систему Future/Wait — второго планировщика нет.
- **Порядок закрытия**: Close → стоп новым данным → ждать противоположную сторону/дедлайн → закрыть направление записи → ждать транспорта; abort тоже гарантирует освобождение ссылок.
- **Домены ошибок**: протокольные ошибки отображаются на коды домена WS + RFC Close code; сетевые/TLS/прикладные сохраняют свои домены — без сплющивания.
- **Обрезка**: соединение/владение/асинхронность/TLS/группировка в независимых таблицах (кадровый слой не тянет сеть — продолжение таблицы обрезки ядра).

## Ловушки

### Ловушка 1: pause без resume (или противоположная сторона уходит по тайм-ауту)

Симптом: клиент «загадочно перестаёт получать сообщения» — сервер сделал pause, потребительская логика зависла, соединение полуживёт до тайм-аута.

Причина: pause означает «пока не принимаем» — оно обязано быть спарено с явным путём восстановления (асинхронный потребитель закончил, нижний уровень готов). Пока действует приостановка, для противоположной стороны соединение стоит.

```c bad
onMessage(...) {
	if ( busy() ) {
		xrtWsConnPause(pConn);   /* приостановили - никто не восстанавливает */
	}
}
```

```c good
onMessage(...) {
	if ( busy() ) {
		xrtWsConnPause(pConn);
		defer_resume_on_ready(pConn);   /* явная точка запуска восстановления */
	}
}
```

### Ловушка 2: отмена Future принята за закрытие соединения

Симптом: после тайм-аута ожидания Future соединение сразу Destroy — половина сообщения, принимаемого противоположной стороной, режется пополам; возможно и двойное освобождение.

Причина: отмена ожидания значит лишь «не ждём» — соединение и владение принятыми данными целы. Решайте по контракту операции: продолжать (ждать следующий Future), закрыть нормально или прервать.

```c bad
if ( wait_timeout(pSendFuture) ) {
	xrtWsConnDestroy(pConn);   /* отмена != уничтожение: возможно двойное освобождение / половина сообщения */
}
```

```c good
if ( wait_timeout(pSendFuture) ) {
	/* приняты ли данные? состояние соединения подскажет - потом выбирать способ закрытия */
	if ( !xrtWsConnClose(pConn, Code, Reason) ) {
		xrtWsConnAbort(pConn);   /* прерывать только когда close не удалось */
	}
}
```

### Ловушка 3: синхронная отправка из не-Worker потока

Симптом: перемежающиеся сбои машины состояний — синхронные отправки спроектированы для исполнения на Worker-владельце соединения (комментарий строки 2 обхода говорит это прямо).

Причина: объект соединения — не разделяемая между потоками изменяемая система; межпоточные операции идут через семейство Future/асинхронное (внутри они диспетчеризируют корректно). Тот же источник, что дисциплина последовательности Worker у слоя сессий главы 85 и событий сервера главы 103.

```c bad
/* синхронная отправка прямо из произвольного потока */
xrtWsConnText(pConn, Msg);   /* не Worker-владелец: гонка */
```

```c good
/* между потоками: через семейство Future/асинхронное (внутри диспетчеризация на Worker соединения) */
/* см. модуль websocket_http_future: семантика ожидания семейства ConnectAsync */
```

## Упражнения

### Базовое: аннотировать обход построчно

Прогоните connection_tour и напишите по одному предложению на строку вывода — «какой контракт проверен». Критерии приёмки: все семь контрактов указывают на соответствующие пункты раздела Контрактов этой главы.

### Продвинутое: стресс-пара пауза-восстановление

На кольцевом каркасе обхода: потребитель случайно держит паузу 0–50 мс, потом resume; отправитель гонит 1000 сообщений на полной скорости — посчитайте доставки и потери. Критерии приёмки: ноль потерь (пауза лишь задерживает); память постоянна (статистика главы 6); для противоположной стороны колеблется только пропускная способность.

### Вызов: двухканальный прокси

Сообщения, принятые соединением A, пересылаются соединению B (и наоборот) — со сцепкой пауз двух соединений: когда B занят, pause у A. Критерии приёмки: ноль потерь пересылки; при замедлении B приём A приостанавливается синхронно (память постоянна); при закрытии любой стороны другая завершает чисто (Close распространяется).
