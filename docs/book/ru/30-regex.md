## Ориентация

`xregex` — движок регулярных выражений XRT; три инженерных решения определяют его характер: **небэктрекинговый движок** — время сопоставления линейно по длине входа, катастрофический бэктрекинг (ReDoS) структурно невозможен, недоверенный текст сопоставляется безопасно; **разделение компиляции и сопоставления** — `xrtRegexCompile` порождает неизменяемый объект со счётом ссылок (скомпилировали один раз — разделяете везде), а `xregexmatcher` — кеш исполнения, эксклюзивный для каждого прохода (повторные сканы одного текста — ноль повторных распределений); **именованные захваты** — `(?<name>...)` читаются по имени группы, заменяя хрупкие числовые номера. Глава разъясняет употребление и выигрыш всех трёх решений; сам синтаксис регулярных выражений дан шпаргалкой стандартного подмножества.В финале глава приглашает его **ограниченного родича** — `xpattern`: когда форма матчинга — структура захвата `{name}` (маршруты, ключи конфигурации) и один текст диспетчеризируется против десятков образцов, он быстрее и проще regex.

## Введение

Две реальные аварии. Первая: служба журналов сопоставляла пользовательские выражения фильтрации бэктрекинговым движком; шаблон в духе `^(a+)+$` гонял одно сопоставление тридцать секунд — очередь росла, сервис впал в анабиоз; такой «катастрофический бэктрекинг» — структурный дефект бэктрекинговых движков: запись шаблона определяет худшую сложность. Вторая: в разборе конфигурации группы захвата `(\w+)=(\d+)` читались по номерам — мейнтейнер вставил группу в середину, все номера сдвинулись на единицу, все чтения ниже по течению разошлись, а компилятор не сказал ни слова.

`xregex` невосприимчив к обеим авариям: худший случай небэктрекингового движка линеен — «плохих шаблонов» не бывает, бывают «чуть более медленные»; именованные захваты `(?<key>\w+)=(?<value>\d+)` читаются по имени — добавление и изменение групп не тревожит существующий код чтения. Добавьте сюда дизайн жизненного цикла «скомпилированный объект неизменяем и разделяем, матчер — эксклюзивный кеш», и вы получите движок, подготовленный к долгой работе на сервере.

## Понятия

### Жизненный цикл: два слоя — компиляция и сопоставление

```diagram flow
- Компиляция: xrtRegexCompile(шаблон) -> неизменяемый объект (счёт ссылок, разделение через Retain/Release)
- Матчер: MatcherCreate(скомпилированный объект, текст) -> эксклюзивный кеш исполнения
- Скан: Find(смещение) находит первое / Next продвигает к следующему - цикл на весь текст
- Захват: CaptureNamed(имя группы) читает текст и диапазон
- Финал: MatcherFree возвращает кеш; Release возвращает скомпилированный объект
```

Слой компиляции неизменяем: один и тот же `xregex*` разделяется многими потоками и многими матчерами и никогда не модифицируется — жизнью и смертью его управляет подсчёт ссылок (тот же примитив, что и в главе 30). Слой матчера эксклюзивен: каждый проход держит собственный кеш (позиции, слоты захвата), и **повторные сканы одного текста переиспользуют кеш** — сто сканов инициализируются один раз. Разделение слоёв делает выполнимой модель стоимости «скомпилировали один раз — сопоставили миллион раз».

### Небэктрекинг: гарантия линейности

Бэктрекинговый движок при неудаче перебирает все пути — некоторые шаблоны взрывают число путей экспоненциально (корень ReDoS). Небэктрекинговый движок (линия NFA/DFA) **отслеживает все возможные состояния одновременно** и обрабатывает каждый входной символ ровно один раз — худшее время линейно по длине входа. Инженерное следствие: у времени сопоставления есть жёсткий верхний предел — его можно спокойно ставить на пути запросов и на недоверенный вход. Плата — чуть больший постоянный множитель на некоторых шаблонах: незаметно для подавляющего большинства, зато в обмен на определённость «плохих шаблонов нет».

### Именованные захваты и замена

`(?<name>[A-Za-z_]+)=(?<value>\d+)` определяет две именованные группы; `xrtRegexMatcherCaptureNamed(匹配器, "value", ...)` (матчер, "value", ...) вычитает по имени представление текста и диапазон. Замена `xrtRegexReplace(编译对象, 文本, 替换, ...)` (скомпилированный объект, текст, замена, ...) поддерживает номерные ссылки `$1`/`$2` (у именованных групп есть и неявные номера); `xrtRegexEscape` экранирует произвольный текст в форму «сопоставлять буквально» — обязательный шаг перед вклейкой пользовательского ввода в шаблон. `xrtRegexFullTest` решает «полное совпадение всей строки», дополняя семантику «найти подстроку» у Find.

### Когда regex избыточен: структурное сопоставление образцов (pattern)

regex отвечает на «**один текст против одного образца**»; pattern отвечает на «**один текст против набора образцов**» — стандартная форма таблиц маршрутизации, ключей конфигурации и диспетчеризации команд. Синтаксис имеет ровно три элемента: литеральные поля совпадают побайтово точно; `{name}` захватывает одно непустое поле (никогда не пересекая разделитель — по умолчанию `/`; `xpatternconfig.Separators` настраивает множество байтов); `{*name}` может стоять только в конце, захватывая остаток и допуская пустоту. `{{` и `}}` экранируют литеральные фигурные скобки. Никакого метаязыка, квантификаторов и ветвления — три прямых следствия: **небэктрекинг выполняется по построению** (взрываться нечему); **нет ловушек экранирования** (ввод пользователя — всегда сопоставляемый текст, никогда ингредиент образца — ловушка 2 здесь структурно исчезает); **сопоставление заякорено на полный ввод** (без нормализации пути, URL-декодирования или свёртки регистра — это работа глав 102/105; в этом и есть слоистость).

Исход использует трёхзначный `xpatternresult`: `XPATTERN_ERROR` / `XPATTERN_NONE` / `XPATTERN_MATCH` — **промах не ошибка** (та же философия, что у `xwaitresult` главы 9: поток управления отделён от ошибок). Жизненный цикл многих образцов зеркален regex: `xrtPatternBuilderCreate` регистрирует десятки образцов нарастающе, `xrtPatternBuilderCompile` компилирует их за один раз в единую детерминированную программу (неизменяемая, долгоживущая; строитель освобождается сразу после); при попадании `Match.Value` напрямую возвращает бизнес-идентичность, данную при регистрации (скажем `"user"`), а `Match.Index` — номер образца — **ключ диспетчеризации встроен**, не нужно заново разбирать семантику групп захвата. Разовые случаи обходятся `xrtPatternExtract` — извлечением по всей строке без компиляции. Четыре потолка бюджета (байты образцов / число образцов / захваты / скомпилированные байты) отсекают раздувание памяти недоверенными образцами; ошибки превышения несут байтовое смещение внутри образца (`xrtPatternErrorOffset`). Разделение одной строкой: **нужно «описание формы плюс квантификаторы и ветвление» — regex; нужно «нарезка полей плюс диспетчеризация многих образцов» — pattern** — таблица маршрутов главы 105 и классификация журналов главы 138 стоят на этой стороне.

### Шпаргалка подмножества синтаксиса

| Синтаксис | Значение |
| --- | --- |
| `.` `\d` `\w` `\s` | классы: любой/цифра/слово/пробельный |
| `[abc]` `[^abc]` | множество символов и его отрицание |
| `*` `+` `?` `{m,n}` | квантификаторы |
| `(...)` `(?<name>...)` | группировка и именованная группа |
| `^` `$` `\b` | начало/конец строки и граница слова |
| `a\|b` | альтернатива |

Синтаксис — общее подмножество мейнстримных движков: без обратных ссылок и заглядывания (формы, которые небэктрекинговый движок не поддерживает; документация говорит об этом прямо, а не молча игнорирует).

### Полная программа: компиляция, сопоставление и именованный захват

Из образца репозитория `examples/text/regex/main.c` — извлечение `width=128` и `height=72` из текста конфигурации:


```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/text/regex/main.c -lws2_32 -liphlpapi
width = 128
height = 72
```

**Что только что произошло.** (1) `xrtRegexCompile` компилирует один раз в неизменяемый объект — здесь он используется локально и в конце `Release`-ится; в долгоживущих сценариях он висит на глобальной переменной (компиляция на старте, освобождение на выходе), и каждое сопоставление лишь берёт ссылку. (2) После создания матчера `Find` находит первое совпадение от смещения 0 — группа `(?<key>...)` захватывает пару имён. (3) `CaptureNamed("key")` и `CaptureNamed("value")` вычитают представления по имени — это устойчивее к рефакторингу, чем номерное чтение `$1`/`$2`. (4) В цикле `Next` продвигает к следующему совпадению — `width` и `height` отсканированы и выведены каждый; кеш матчера переиспользуется между сопоставлениями. (5) Весь процесс несёт ноль риска «катастрофического бэктрекинга» — небэктрекинговый движок сканирует линейно на любом шаблоне.

(2) Продукт замены — владеющая строка (освобождение `xrtFree`). (3) В этом образце `Escape` не понадобился, но запишите: **перед вклейкой пользовательского ввода в шаблон обязателен `xrtRegexEscape`** — скобки во вводе вроде `a(b` суть синтаксические символы; без экранирования получится нелегальный шаблон или ложное сопоставление (герой ловушки 2).

### Полная программа: pattern — захват {name} в стиле маршрутов

Из репозиторного образца `examples/text/pattern/main.c` — один образец маршрута; попадание и есть диспетчеризация:

```embed path="examples/text/pattern/main.c" title="examples/text/pattern/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/text/pattern/main.c -lws2_32 -liphlpapi
kind=user group=admin id=42
```

**Что только что произошло.** (1) Четвёрка `xpatternspec`: шаблон, бизнес-идентичность (`"user"` — ключ диспетчеризации попадания), флаги бюджета; настоящая таблица маршрутов регистрирует десятки до одной компиляции. (2) Нарастающая регистрация строителем → `Compile` даёт неизменяемый объект → **строитель можно освободить немедленно** — та же дисциплина жизненного цикла, что у скомпилированного объекта regex. (3) `xrtPatternMatch` пишет захваты в массив вызывающего в порядке объявления шаблона (`group` первым, `id` вторым); захваты — **представления, заимствующие ввод** (дисциплина главы 3). (4) Одна строка вывода даёт все три элемента диспетчеризации: `Match.Value` (какой класс маршрута), два захваченных сегмента (параметры) — весь вход HTTP-обработчика маршрута умещается в этой строке.

## Контракты

- **Гарантия линейности**: небэктрекинговый движок; худшее время сопоставления линейно по длине входа — катастрофического бэктрекинга не существует.
- **Двухслойный жизненный цикл**: скомпилированный объект неизменяем и разделяется счётом ссылок; кеш матчера эксклюзивен, по одному на проход.
- **Именованные захваты**: определение `(?<name>...)`, чтение `CaptureNamed`; номерная ссылка `$1` тоже доступна.
- **Дисциплина экранирования**: динамическое содержимое обязано пройти `xrtRegexEscape` перед входом в шаблон.
- **Разграничение семантик**: `Find` ищет подстроку, `FullTest` решает всю строку — выбирайте по потребности, не имитируйте через `^...$`.
- **Подмножество синтаксиса**: общее ядро мейнстрима; обратные ссылки и заглядывание не поддерживаются — документировано явно, без умолчаний.
- **Границы pattern**: якорь на полную строку; захваты заимствуют входной текст; ошибки живут в домене `xrt.pattern`, `xrtPatternErrorOffset` даёт байтовое смещение в образце; промах — это NONE, не ошибка.

### От примеров к инженерии: три хозяина регулярных выражений

**Слой валидации**: проверка легальности ввода (правила имени пользователя, форматы SKU) — шаблоны статически компилируются в глобальные, на каждый запрос строится только матчер, `FullTest` решает всю строку. Три дисциплины валидационных шаблонов: якорить где можно (`^...$` или семантика FullTest), белый список множеств символов лучше чёрного, сообщение об отказе объясняет формат. **Слой извлечения**: добыча данных из полуструктурного текста (поля журналов, строки конфигурации) — именованные захваты плюс полный скан `Next`, результаты уходят в дерево значений или бизнес-структуры; это одна из промежуточных станций текстового конвейера главы 36. **Слой замены**: шаблонная перепись (конвертация форматов, маскирование данных) — ссылки на захваты `Replace` держат логику пересборки внутри строки замены. Всем трём слоям общая дисциплина производительности: **компиляция на старте, сопоставление на горячем пути** — хорошая форма ловушки 1 и есть общий каркас кода всех трёх.

### Разделение труда со строковым семейством и глобами

Когда три инструмента сопоставления текста из главы 25 уступают место регулярным выражениям? **Буквенный поиск** (найти фиксированный `ERROR`) — `xrtStrFind`, накладные расходы регулярных выражений не нужны; **простые глоб-шаблоны** (`*.log`) — `xrtStrGlob`, проще и быстрее; **структурные шаблоны« («три цифры в группе, соединены дефисами») — вотчина регулярных выражений. Мнемоника: **если шаблон формулируется одной фразой — хватит строкового инструмента; «описание формы» требует регулярного выражения**. Цена злоупотребления — не только производительность: читаемость, сопровождаемость и ловушки экранирования (ловушка 2) все ждут своего часа; код с правильно выбранным инструментом объясняет сам себя на ревью.

### Взгляд на тестирование: шаблон — тоже код

Регулярный шаблон — сгущённый код, и он заслуживает кодового обращения. Три привычки: **именовайте шаблоны** — `static const char* PATTERN_SKU = "..."` плюс комментарий о намерении, а не россыпь по точкам вызова; **наборы граничных случаев** — каждому шаблону тройка «должен совпасть/не должен/граница» (пересадка идеи граничных значений главы 26), регресс при каждом изменении шаблона; **выборочный замер производительности** — прогоняйте показательные входы через статистику главы 6 или простое таймирование, подтверждая отсутствие сюрпризов в константах. Воспроизводимая случайность главы 11 (генерация уродливых входов с фиксированным семенем) даёт фаззингу шаблонов готовый инструмент — эти дисциплины будут систематизированы вновь в главе 132.

## Ловушки

### Ловушка 1: перекомпиляция шаблона на каждый запрос

Симптом: аномальный CPU на горячем пути; профилировщик показывает горячую точку в `xrtRegexCompile` — каждый запрос компилирует один и тот же шаблон с нуля.

Причина: замысел разделения слоёв компиляции и сопоставления проигнорирован — компиляция тяжёлая (постройка автомата), сопоставление лёгкое; тяжёлая операция попала в цикл.

```c bad
bool handle(const char* sFilter)
{
	xregex* pRegex = xrtRegexCompile((xstrview){ sFilter, strlen(sFilter) });
	/* ... одно сопоставление ... */
	xrtRegexRelease(pRegex);   /* компиляция+освобождение на каждый запрос - автомат построен зря */
}
```

```c good
/* компиляция один раз на старте, глобальное разделение */
static xregex* gFilter;
void init(void) { gFilter = xrtRegexCompile(XRT_STR_LITERAL("...")); }
bool handle(const char* sText)
{
	/* строим только матчер (лёгкий); скомпилированный объект даёт ссылку */
	xregexmatcher* M = xrtRegexMatcherCreate(gFilter, Text);
	/* ... Find/Next ... */
	xrtRegexMatcherFree(M);
}
```

### Ловушка 2: пользовательский вклеен в шаблон напрямую

Симптом: ввод с `(`, `*` или `[` либо не компилируется, либо ведёт себя странно; хуже — тщательно сконструированный ввод уводит семантику шаблона в сторону (уязвимость класса инъекций).

Причина: синтаксические символы регулярных выражений не экранированы — текст пользователя истолкован как часть шаблона.

```c bad
xstrview UserInput = ...;
xstrbuf Pat;
xrtStrBufInit(&Pat);
xrtStrBufAppend(&Pat, XRT_STR_LITERAL("^"));
xrtStrBufAppend(&Pat, UserInput);          /* "(admin)" входит в шаблон - синтаксические символы! */
xrtStrBufAppend(&Pat, XRT_STR_LITERAL("$"));
str sPat = xrtStrBufTake(&Pat);
xregex* R = xrtRegexCompile((xstrview){ sPat, strlen(sPat) });   /* компиляция падает или инъекция */
```

## Упражнения

### Базовое: именованное извлечение (ощущение именованных захватов)

Воспроизведите главный пример: полным сканом `"width=128 height=72 depth=24"` выведите три пары ключ-значение; затем несуществующим ключом (например `color`) проверьте, что скан естественным образом его пропускает.

### Продвинутое: фильтр журнала

Сопоставьте `[WARN] 2026-04-02 disk 90%` именованными группами — уровень, дата, модуль, значение, каждая захвачена отдельно; подсчитайте разницу числа WARN и ERROR на отрезке журнала. Подсказка: после захвата группы даты прогоните её через разбор времени главы 40 (если он есть) или оставьте строкой.

### Вызов: подсветка поиска

Реализуйте `highlight(文本, 查询词)` (текст, слово запроса): запрос экранируется через `Escape`, компилируется в шаблон «сопоставление целого слова» (с границами `\b`), все позиции совпадений находятся по всему тексту, на выходе текст с метками `<<>>`. Критерии приёмки: слово запроса с синтаксическими символами регулярных выражений (`(`, `*`, `[`) по-прежнему сопоставляется буквально; подряд идущие совпадения не перекрываются; время на 1000 совпадений в тексте 100 КБ линейно и измеримо.

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Гарантия линейности | небэктрекинговый движок — худший случай линеен, ReDoS нет, недоверенный текст безопасен |
| Двухслойная модель | скомпилированный объект неизменяем и разделяем (Retain/Release) / кеш матчера эксклюзивен (Create/Free) |
| Дисциплина стоимости | компиляция один раз, глобальное разделение; в циклах строим только матчеры |
| Захват | `(?<name>...)` + `CaptureNamed`; `$1`/`$2` — номерные ссылки в заменах |
| Экранирование | динамическое содержимое проходит `xrtRegexEscape` (возвращает владеющую строку) перед входом в шаблон — единственный безопасный путь к буквальному сопоставлению |
| Семантики | Find подстрока / FullTest вся строка / Next продвижение / Replace перезапись |
| Три хозяина | валидация (якорь + белый список) / извлечение (именованные захваты, полный скан) / замена (пересборка ссылками на захваты) |
| Разделение инструментов | буквальный поиск — StrFind / простые глобы — StrGlob / описание формы — регулярные выражения |
| Дисциплина шаблонов | именованные шаблоны + наборы граничных случаев + замеры производительности — шаблон тоже код |
| Родич pattern | захват `{name}` + литеральные сегменты; Builder компилирует много образцов разом; три состояния без ошибки; Match.Value — ключ диспетчеризации |
