## Ориентация

Этой главой том 1 закрывается. Предыдущие восемь глав строили фундамент однопоточного мира: типы и представления (глава 3), модель ошибок (глава 4), управление памятью (главы 5–6), временные арены (глава 7), версии и обрезка (глава 8). Эта глава добавляет последний кусок: **что удерживает порядок, когда несколько потоков исполнения трогают одни данные на самом нижнем уровне**. Три ступени: **атомарные операции** (`xatomic32/64/ptr` — чтение, запись и чтение-изменение-запись одной переменной без чередования); **спин-блокировки** (`xspinlock` — защита критических секций длиной в несколько инструкций); **примитивы ожидания** (`xdeadline` и `xwaitresult` — математика тайм-аутов и единый словарь исходов ожидания).

Это классическая глава-фундамент. Глава 8 упоминала, что заголовок атомарных операций — один из первых потребителей компиляционного развилки возможностей: один и тот же заголовок на платформах без атомарных инструкций идёт по внутренней реализации, а где они есть — по инлайн-пути, благодаря замыканию возможностей прямо здесь. Смотря вперёд: синхронизация потоков главы 52, система отмены главы 53 и «атомарная замена глобального указателя» центра конфигурации (главы 138–139) всё стоит на примитивах этой главы; здесь преподаётся только **слой примитивов** — одна машина, одна переменная, осязаемые мелочи; системный конкурентный дизайн остаётся тому 6. Прочитав, вы должны уметь отвечать на три вопроса: когда **блокировка не нужна** (достаточно одной переменной); когда блокировка **не должна быть тяжёлой** (счёт порядков величин «спин против мьютекса»); и почему «ждать до тайм-аута» обязано использовать **абсолютный дедлайн**, а не относительный тайм-аут, сбрасываемый каждый круг.

## Введение

Три реальных инцидента открывают путь. **Первый: счётчик теряет обновления.** Сервис статистики копит число запросов через `count++`; восемь потоков добавляют по миллиону, сумма останавливается около 7,2 миллиона и при каждом запуске разная. `count++` — чтение-изменение-запись из трёх шагов; три шага двух потоков могут чередоваться — оба читают 41, каждый прибавляет единицу, оба пишут 42 — одно обновление бесследно исчезает. Мьютекс лечит, но платить «сном-пробуждением» за инкремент целого — из пушки по воробьям. **Второй: флаг лжёт.** Поток-производитель заполняет структуру, затем выставляет флаг «данные готовы»; потребитель изредка видит флаг истинным, а читает полуновые данные. Записи без ограничений порядка не дают межпеременных обещаний — видимость флага не влечёт видимость данных. Это не вероятностная мистика, это модель памяти. **Третий: суммарное время цикла повторов выходит из-под контроля.** Код «ждать 100 мс на каждую попытку, сдаться через десять секунд» реально работал двадцать восемь секунд — каждый круг ждал свежие 100 мс, бюджет ожидания сбрасывался десятки раз. Системе нужно не «сколько ждать каждый круг», а «**до какого момента**».

Три проблемы — три инструмента: атомарное чтение-изменение-запись делает `count++` одним шагом; порядок памяти делает пару «публикация-получение» надёжной; математика дедлайнов превращает тайм-аут из относительной величины в абсолютный момент времени. Вместе их меньше тридцати функций, но это общий фундамент всего в книге — от очередей (глава 21) до токенов отмены (глава 53).

## Понятия

### Три ширины и семейство чтения-изменения-записи

Атомарный модуль даёт три ширины: `xatomic32`, `xatomic64`, `xatomicptr` — целые 32/64 бита и ширина одного указателя. Семейная форма у всех одинакова: `Init` времени исполнения (статические объекты — макросами вроде `XRT_ATOMIC32_INIT(0u)`, стартовое состояние одинаково на всех платформах), `Load`, `Store`, `Exchange`, `FetchAdd/FetchSub/FetchAnd/FetchOr/FetchXor` и `CompareExchange`. Префикс «Fetch» единообразно значит **вернуть старое значение**: `xrtAtomic64FetchAdd(&Counter, 1u, ...)` возвращает значение до прибавления, а счётчик уже обновлён — нужно новое? Прибавьте единицу к старому; не возвращайтесь за ещё одним Load (лишняя атомарная операция и лишнее предположение о времени).

Полезное правило: **форму разделения выбирает инструмент**. Просто счётчик, флаг, указатель «на кого это сейчас указывает» — одна переменная; атомарных достаточно, без блокировок и дёшево. «Два поля должны меняться вместе» — инвариант, который атомарность не выразит (между двумя атомарными операциями всё ещё можно вклиниться); это территория блокировок (глава 52). Передача владения указателем между потоками — территория очередей (глава 21). Классические симптомы неверного слоя: мьютекс поверх очереди (очередь уже потокобезопасна), блокировка ради счётчика (атомарные дешевле на порядок).

### Сравнение с обменом: контракт переписи ожидаемого значения

`xrtAtomic64CompareExchange(&Counter, &iExpected, 10u, 成功序, 失败序)` (порядок успеха, порядок неудачи) заслуживает отдельного раздела больше всех в семействе: если текущее значение равно `*iExpected` — поменять на `10u` и вернуть истину; **если нет — вернуть ложь и переписать фактически наблюдённое текущее значение в `*iExpected`**. Эта перепись — намеренный контракт: стандартная форма CAS-цикла — «попробовать с ожидаемым; при неудаче поправиться переписанным фактическим значением и повторить», без дополнительного Load и без лишнего окна между чтением ожидания и новой попыткой. Порядок неудачи поэтому обязан нести семантику получения (переписанное значение должно читаться), не быть сильнее порядка успеха и не содержать RELEASE — проверка параметров это принуждает; незаконная комбинация ставит `XERR_ARGUMENT`, объект не тронут.

Классическое применение CAS — «изменить одно поле структуры, не блокируя всю структуру»: прочитать старое, вычислить новое локально, CAS-нуть обратно; неудача значит, кто-то опередил — повторить с переписанным значением. Каждый шаг цикла атомарен, всё «чтение-вычисление-запись» — нет: это и есть граница применимости: **при редких конфликтах почти всегда успех с первой попытки; при плотных конфликтах сам цикл становится горячей точкой**. Очередь без блокировок главы 21 — этот же паттерн, высоко инженеризованный.

### Порядок памяти: пять уровней и одно правило по умолчанию

Каждая атомарная операция принимает параметр `xmemoryorder`: `XMEMORY_RELAXED` (атомарна только эта операция; никакого межпеременного порядка — для чистого счёта достаточно); `XMEMORY_ACQUIRE` (сторона чтения — последующие обращения не переупорядочиваются до неё; «получить» опубликованные данные); `XMEMORY_RELEASE` (сторона записи — предыдущие обращения не переупорядочиваются после неё; «опубликовать» завершённые записи); `XMEMORY_ACQ_REL` (оба, для чтения-изменения-записи — стандартная поза CAS); `XMEMORY_SEQ_CST` (полная последовательная согласованность — самое наглядное и самое дорогое). Матрица законности проста: Load принимает только RELAXED/ACQUIRE/SEQ_CST, Store — только RELAXED/RELEASE/SEQ_CST; нарушение ставит `XERR_ARGUMENT`.

Инженерное правило — одна строка: **пока не доказано обратное, используйте SEQ_CST**. Ловушка порядка памяти в том, что ошибка по большей части работает — переупорядочивания и видимость всплывают лишь на конкретных CPU и уровнях оптимизации компилятора; зелёный тест не значит правильно. Верный рабочий процесс: сначала напишите правильно на SEQ_CST; когда профилирование (метод главы 135) укажет горячий счётчик или точку публикации — деградируйте **с обоснованием** до RELAXED или пары ACQUIRE/RELEASE и напишите в комментарии, почему это безопасно. Обещание платформы одностороннее: платформы только с полными барьерами реализуют более сильным порядком — публичный контракт никогда не ослабляется; опирайтесь на документированный нижний предел.

Пара «публикация-получение» — самая используемая: сторона записи `Store(标志, 1, RELEASE)` (флаг) (данные полностью готовы до объявления), сторона чтения `Load(标志, ACQUIRE)` (флаг) (данные, прочитанные после флага, неизбежно объявленной версии). Если любая сторона применила RELAXED — обещание испаряется; это герой ловушки 1 ниже.

### Барьеры, Pause и запрос свободы от блокировок

Три помощника дополняют семейство: `xrtAtomicThreadFence(序)` (порядок) — самостоятельный барьер (не привязан к переменной — подстраховка смешанных форм вроде «несколько обычных записей плюс один атомарный флаг»); `xrtAtomicSignalFence` ограничивает только переупорядочивание компилятором, не CPU (граница «обработчик сигнала против потока»); `xrtAtomicPause()` — подсказывающая инструкция в зазоре вращения (PAUSE на x86, YIELD на ARM) — говорит конвейеру «этот цикл ждёт другого; не вливайте ресурсы спекулятивного исполнения сюда». `xrtAtomicIsLockFree(sizeof(uint64))` отвечает «действительно ли эта ширина свободна от блокировок на вашей платформе» — один вопрос на этапе выбора закрывает большинство соображений порядка величины.

### Спин-блокировка: критическая секция в несколько инструкций

`xspinlock` построена на атомарном CAS и является **самой лёгкой блокировкой библиотеки**: не удалось взять — занято ждёт (вращается), не спит. Применимость — счёт порядков величины: для критической секции в несколько инструкций вращение стоит одного неудавшегося CAS плюс нескольких Pause; мьютекс потенциально стоит системного вызова и переключения потоков — обычно на порядок дороже. Наоборот: как только секция содержит IO, выделение памяти или больше нескольких десятков инструкций, вращение из дешёвого превращается в сжигание CPU — вращающийся поток не только не работает, он отбирает ядра у держателя. Критерий — **длина критической секции**, а не «спин звучит продвинуто».

Три формы жизненного цикла изоморфны четвёрке главы 52: стек `xrtSpinInit/xrtSpinUnit`, статическая `XRT_SPIN_INIT`, куча `xrtSpinCreate/xrtSpinDestroy`; `xrtSpinTryLock` — неблокирующий вариант (возвращает ложь при занятости). Одно жёсткое контрактное правило: **уничтожение удерживаемой блокировки завершается неудачей и ставит `XERR_STATE`** — это не совет по очистке, а принудительная проверка от утечек.

```diagram flow
- Разделение одной переменной (счётчик / флаг / указатель) -> атомарные операции: без блокировок, один шаг, чередование безопасно
- Инварианты многих переменных (поля меняются вместе) -> блокировки: спин (несколько инструкций) или мьютекс (дольше)
- Передача владения указателем между потоками -> очереди (глава 21): внутри уже без блокировок, снаружи не запирать
- Ожидание с бюджетом -> абсолютный дедлайн xdeadline + единый исход xwaitresult (систематизация в главах 52-53)
```

### Примитивы ожидания: математика дедлайнов и пятирезультатный исход

Модуль ожидания — три функции и одно перечисление, но это единый выход для всей семантики тайм-аутов библиотеки. `xdeadline` — абсолютный момент времени как `uint64` (микросекунды монотонных часов, глава 41): `xrtDeadlineAfter(相对微秒)` (относительные микросекунды) строит отсечку от текущего момента (переполнение возвращает `XRT_DEADLINE_NEVER`, то есть никогда не истекает); `xrtDeadlineExpired` — наступила ли; `xrtDeadlineRemaining` — сколько микросекунд осталось. Это решает третий инцидент: **сконструирован однажды, передаётся всюду, никогда не сбрасывается** — цикл повторов ждёт через `Remaining` каждый круг, а общий бюджет — то самое первое число.

`xwaitresult` раскладывает «исход ожидания» на пять взаимоисключающих значений: `XWAIT_ERROR` (настоящая неудача), `XWAIT_OK` (успех), `XWAIT_TIMEOUT` (время вышло), `XWAIT_CANCELLED` (отменено — токены отмены главы 53 кончаются здесь), `XWAIT_CLOSED` (ожидаемый объект закрыт). Замысел: **отделить нормальный поток управления от ошибок** — тайм-аут и отмена ожидаемы ветви, которые обрабатывает вызывающий, а не «исключения», запихнутые в цепочку ошибок. От `xrtThreadWait` главы 52 до ожиданий соединений сетевой библиотеки возвращается именно это перечисление — выучите семантику здесь; систематизированное ожидание и отмена разворачиваются в томе 6.

## Примеры

### Первая полная программа: атомарный счёт и однозначный CAS

```embed path="examples/core/atomic/main.c" title="examples/core/atomic/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/core/atomic/main.c -lws2_32 -liphlpapi
counter=10
```

**Что только что произошло.** (1) Макроинициализация `XRT_ATOMIC64_INIT(0u)` — статические и стековые объекты одинаково; стартовое состояние согласовано между платформами. (2) `FetchAdd(1, RELAXED)` показывает: слабейшего порядка достаточно для чистого счёта — не публикуем других данных, не нужны и обещания порядка. (3) Ожидание CAS равно 1 (совпадает с фактическим значением после FetchAdd); успех меняет на 10 — **при успехе `*iExpected` не тронут**. (4) Пара «успех ACQ_REL / неудача ACQUIRE» — стандартная поза CAS: порядок неудачи обязан позволять чтение переписанного значения и не быть сильнее порядка успеха. Поменяйте `iExpected` на 2 и перезапустите: CAS не удаётся, перепись возвращает 1 — это значение и есть стартовая точка повтора.

(2) Вторая строка вывода посвящена переписи при неудаче CAS: ожидание 0x99 не совпадает, фактическое 0x0A вписывается обратно. (4) Финальные `IsLockFree + ThreadFence + SignalFence + Pause` зажигают всех помощников. Программа вдвойне полезна как миграционная самопроверка: запустите её первой на новой платформе; пять верных строк — атомарный слой ведёт себя одинаково.

### Третья полная программа: два жизненных цикла спин-блокировки

```embed path="examples/concurrency/spin/main.c" title="examples/concurrency/spin/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/concurrency/spin/main.c -lws2_32 -liphlpapi

```

**Что только что произошло.** (1) Стековая форма проходит `Init → Lock → 临界区（一条自增）→ Unlock → Unit` (критическая секция: один инкремент) — секция ровно в одну инструкцию, законный диапазон вращения. (2) Кучная форма дополняет `Create/TryLock/Destroy`: `TryLock` обязан не удаться при удержании и удаться в свободном состоянии — оба состояния проверены. (3) Блокировка в примере защищает демонстрационную одиночную переменную — в реальном коде для голого счётчика ответ атомарный, не блокировка; пример запирает саму демонстрацию жизненного цикла. Глава 53 поставит спин-блокировку в трёхстороннее сравнение «спин против мьютекса против очереди без блокировок» с таймированием.



**Что только что произошло.** (1) `xrtDeadlineAfter(50000)` строит абсолютную отсечку через 50 мс; `Remaining` сразу читает около 50000 микросекунд (шкала монотонных часов). (3) Заметьте: `SleepUntil` ест ту же математику дедлайнов — параметры тайм-аутов всех ждущих API библиотеки пересчитываются через неё; сконструирован однажды — передаётся всюду.

## Контракты

- **Граница атомарности**: атомарная операция гарантирует одну переменную, один шаг, без чередования; две атомарные операции вместе **не** имеют целостной атомарности — межпеременные инварианты принадлежат блокировкам (глава 52), передача владения — очередям (глава 21).
- **Семантика Fetch**: всегда возвращать старое значение до операции; новое выводите сами — без рефлекторного «сходить ещё раз Load».
- **Перепись CAS**: успех не трогает `*pExpected`; неудача вписывает фактически наблюдённое значение в `*pExpected` — цикл повторов правится от него, без дочитывания.
- **Законность порядка памяти**: Load ∈ {RELAXED, ACQUIRE, SEQ_CST}; Store ∈ {RELAXED, RELEASE, SEQ_CST}; порядок неудачи CAS без RELEASE и не сильнее порядка успеха. Незаконные комбинации ставят `XERR_ARGUMENT`; объект не изменён.
- **Обещание нижнего предела порядка**: реализации могут быть только сильнее документированного порядка, никогда слабее — пишите против документации, не против конкретной платформы.
- **Правило по умолчанию**: SEQ_CST, пока не доказана возможность ослабления; деградация требует данных профилирования (глава 135) и письменного обоснования.
- **Жизненный цикл спин-блокировки**: стек Init/Unit, статическая `XRT_SPIN_INIT`, куча Create/Destroy; **уничтожение удерживаемой блокировки — неудача с `XERR_STATE`**; TryLock неблокирующий, при удержании возвращает ложь.
- **deadline — чистое значение**: без владения, передаётся по значению; переполнение `After` возвращает `XRT_DEADLINE_NEVER`; `NEVER` никогда не истекает, `Remaining` возвращает `UINT64_MAX`.
- **xwaitresult, пять исключающих состояний**: ERROR/OK/TIMEOUT/CANCELLED/CLOSED; тайм-аут и отмена — поток управления, не ошибки; они не входят в цепочку ошибок.
- **Правила потоков**: атомарные объекты не имеют частично обновлённых состояний (любое наблюдение видит либо старое, либо новое); барьеры и Pause переносимы на все платформы.

## Ловушки

### Ловушка 1: публикация данных без порядка памяти (флаг солгал)

Симптом: увидев флаг «данные готовы», потребитель всё равно читает устаревшие данные; проблема появляется вероятностно и меняет частоту с CPU или флагами компилятора.

Причина: запись данных и запись флага обе использовали RELAXED (или вовсе обычные записи) — между ними нет обещания порядка; флаг может стать видимым раньше данных. Пара «публикация-получение» без одной стороны — пара, которой не существует.

```c bad
Data = Compute();                                   /* обычная запись */
xrtAtomic32Store(&Ready, 1u, XMEMORY_RELAXED);      /* слабая публикация: данных может ещё не быть видно */
```

```c good
Data = Compute();                                   /* запись данных */
xrtAtomic32Store(&Ready, 1u, XMEMORY_RELEASE);      /* публикация: все предыдущие записи готовы */
/* пара на стороне потребителя: после xrtAtomic32Load(&Ready, XMEMORY_ACQUIRE) Data — опубликованная версия */
```

### Ловушка 2: длинная работа внутри спин-блокировки

Симптом: под нагрузкой CPU насыщаются и пропускная способность падает; профилирование показывает горячую точку в цикле занятого ожидания `xrtSpinLock`.

Причина: критическая секция содержит IO, выделение памяти или длинное вычисление — вращающийся поток не работает, но отбирает ядра, держатель замедляется, ожидания растут, порочный круг. Вращение предполагает «секция в несколько инструкций».

```c bad
xrtSpinLock(&Lock);
SaveToDisk(&Record);        /* IO в критической секции: миллисекунды — вращающиеся сжигают целое ядро */
xrtSpinUnlock(&Lock);
```

```c good
xrtSpinLock(&Lock);
iCount++;                   /* несколько инструкций: законный диапазон вращения */
xrtSpinUnlock(&Lock);
/* длинную работу — мьютексу (глава 52) — ждущий сон не жжёт CPU; или сперва вычислить, потом войти в короткую секцию для фиксации */
```

### Ловушка 3: относительный тайм-аут внутри цикла повторов

Симптом: цикл с надписью «повторять максимум десять секунд» реально работает двадцать с лишним; каждый круг сбрасывает бюджет ожидания, сумма расходится с числом кругов.

Причина: «сколько ждать каждый круг» приняли за «сколько ждать всего». Относительный тайм-аут ограничивает один круг; цикл умножает его на N; по-настоящему обещать система может **абсолютную отсечку**.

```c bad
for ( i = 0; i < 100; i++ ) {
	if ( TryOnce() ) { break; }
	Sleep(100000);        /* бюджет сбрасывается каждый круг: 100 кругов могут превысить 10 секунд */
}
```

```c good
xdeadline D = xrtDeadlineAfter(UINT64_C(10000000));   /* сконструировать один раз, вне цикла */
while ( !TryOnce() ) {
	if ( xrtDeadlineExpired(D) ) { return XWAIT_TIMEOUT; }
	WaitOnce(xrtDeadlineRemaining(D));                 /* остаток убывает, никогда не сбрасывается */
}
return XWAIT_OK;
```

## Упражнения

### Базовое: счёт без блокировок на четырёх потоках

Через `xrtAtomic64FetchAdd` (RELAXED) четыре потока прибавляют по миллиону; главный поток после объединения Load-ом сверяет сумму — ровно четыре миллиона. Критерий приёмки: сумма постоянна (одинакова при каждом запуске); замените атомарность на обычный `++` и пронаблюдайте потерянные обновления.

### Продвинутое: изменение поля через CAS-цикл

Структура содержит `Done` и `Value`; через `xrtAtomic32CompareExchange` реализуйте «выставить Done в 1 и записать Value только если Done равен 0» — при неудаче правьтесь и повторяйте, используя перепись ожидаемого значения. Критерии приёмки: при многопоточной конкуренции успеха добивается ровно один поток; всюду без блокировок.

### Вызов: спин против мьютекса — трёхстороннее таймирование

Одна задача счёта в трёх реализациях: атомарная, спин-блокировка и мьютекс (API главы 52); таймируйте каждую и сравните. Затем удлините критическую секцию (добавьте вычислений) и перемерьте; пронаблюдайте, где преимущество спина разворачивается. Критерий приёмки: квантованная точка перелома «в нескольких инструкциях побеждает спин, дальше мьютекс»; вывод перекрестно сверяется с разделом о разделении труда главы 52.
