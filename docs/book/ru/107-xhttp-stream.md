## Ориентация

Тело HTTP — поле боя «содержимого» и «памяти»: загрузка 2 GB, потоковое скачивание, ответ, генерируемый по надобности, — **размер тела не должен равняться занятой памяти** — отправная точка всего дизайна. `xhttpbody` объединяет пять источников тела: фиксированное семейство (`Empty/Copy/Borrow/Take/Reference` — переигрываемо, известная длина), **ограниченный поток-производитель** (`HttpBodyStreamCreate` — производство в потоке задачи, бюджетный потолок, фундамент SSE), **файловые тела** (`http_body_file` — асинхронный файловый IO в форме тела), собственные источники (обратный вызов производителя) и трансформированные тела. На стороне потребления `xhttpbodyreader` — однопотребительское потоковое чтение, а `xhttpbodychunk` — **независимый лизинг данных** (`ChunkRelease` возвращает, можно освободить позже Reader — идеальный напарник отправки по ссылке TCP). Серверные обратные вызовы Body главы 103 и конец-производитель SSE главы 106 получают здесь полный фундаментальный рассказ.

## Введение

Три сценария тела с требованиями к форме памяти. Загрузка 2 GB: сервер не может накопить всё и потом обрабатывать — потоковые обратные вызовы Body главы 103 уже закрыли принимающую сторону; но **отправляющая сторона клиента**? читать 2 GB в память и потом POST? Файловые тела дают «читаем и шлём по ходу». Потоковая генерация скачивания: длина ответа неизвестна, содержимое производится по надобности (курсор базы, живой транскодинг) — тело потока-производителя даёт «генерируем и шлём по ходу» под потолком бюджета. Потребность переигрывания: перенаправления 307/308 главы 99 требуют переигрываемого тела — фиксированное семейство переигрываемо по природе; а поток-производитель? Тело, которое даёт `HttpBodyStreamCreate`, **потребляется один раз** — сценариям повторной отправки при перенаправлении подходят фиксированное семейство или файловые тела.

Лизинг — важнейшее новое понятие главы: Chunk, выдаваемый `Next`, **владеет независимым лизингом данных** — данные не копируются, но вы обязаны вернуть `ChunkRelease`; Chunk может пережить Reader (стоять в очереди отправки по ссылке, когда объект тела уже уничтожен — управляет счётчиком ссылок). Это та же мысль, что отправка по ссылке WebSocket главы 95 (освобождение только по завершении записи), приземлившаяся на слой тела.

## Понятия

### Пять источников и семантика переигрывания

| Источник | Вход создания | Переигрываемо | Типичный сценарий |
| --- | --- | --- | --- |
| Фиксированное семейство Empty/Copy/Borrow/Take/Reference | `xrtHttpBodyCopy` и др. | да (известная длина = байты ввода) | JSON/короткие тела/переотправка 307 |
| Ограниченный поток-производитель | `xrtHttpBodyStreamCreate(配置, &流)` (конфигурация, &поток) | нет (одно потребление) | SSE/потоковая генерация/выдача прогресса |
| Файловое тело | семейство `http_body_file` | да (переоткрываемо) | загрузка больших файлов/статическое скачивание |
| Собственный источник | обратный вызов производителя | зависит от реализации | курсор базы/конвейер шифрования |
| Трансформированное тело | слой композиции | зависит от реализации | сжатые ответы |

Детали фиксированного семейства: `Copy` кладёт дескриптор и копию в **одно компактное выделение по фактической длине** (второго выделения под то же тело не строится); `Borrow` не продлевает жизненный цикл внешней памяти (исходный буфер обязан жить во время отправки); `Reference` обязан получить процедуру освобождения (если только заимствуете — берите Borrow). `xrtHttpBodyView` заимствует непрерывные байты фиксированного тела — источники, не гарантирующие непрерывность, возвращают `false` (файл/поток/трансформация могут быть разрывными).

### Reader: один потребитель и лизинги

```diagram flow
- Открытие: Reader открывает тело (один потребитель - конкурентные вызовы запрещены)
- Чтение: Next(потолок, &Chunk) -> DATA (лизинговый кусок) / AGAIN (пока нет, Wait на Future) / EOF
- Лизинг: Chunk - независимый лизинг данных - по использовании ChunkRelease; можно освободить позже Reader/Body
- Переигрывание: фиксированное семейство может открыть Reader заново и читать с начала
```

Дисциплина алиасинга (на уровне контракта): дескриптор/буфер/слоты длины выводимого Chunk **не должны перекрывать** нижележащие байты Reader, Body или фиксированного тела — ошибка алиасинга не двигает Reader вперёд и не очищает выходную длину, а фиксированное Body остаётся неизменным при переигрывании и конкурентных открытиях. Эта защита делает безопасным «объект тела, разделяемый несколькими Call» (ссылки тела с семантикой заморозки главы 98).

### Ограниченный поток-производитель: бюджет и финалы

`MaxBytes/MaxChunks` из `xhttpbodystreamconfig` — бюджет конца-производителя (резервирования + очередь + активные лизинги покрыты целиком) — порог AGAIN для SSE приходит именно отсюда. Три финала: разрушение последней ссылки потока = очередь содержимого затем **нормальный EOF**; `Close` идемпотентно предзакрывает ввод; `Fail` отбрасывает недоставленное содержимое и передаёт стабильную Cause потребляющей стороне. Три формы записи `Write/WriteRef/WriteTake` соответствуют копия/ссылка/принятие — то же семейство, что пять ступеней отправки главы 67.

### Файловые тела: асинхронный IO в форме тела

Семейство `http_body_file` оборачивает файловый IO портов завершения главы 71 в тело: `xrtHttpBodyFileConfigInit` + создание файлового тела — **чтение идёт асинхронным файловым путём** (двигают Worker среды выполнения), без блокировок и без чтения целиком; `xrtHttpBodyFileFuture`/`FileRangeFuture` дают форму Future «ждать готовности тела». Range-варианты естественно поддерживают докачку загрузки/скачивания. Файловые тела **переигрываемы** (переоткрыть файл, перечитать) — безопасная комбинация больших файлов + переотправка при перенаправлении.

### Полные формы загрузки и скачивания

- **Загрузка** (клиент): файловое тело + `SetBody` построителя главы 98 — память клиента при загрузке файла 2 GB ≈ один блок чтения; сервер принимает потоковыми обратными вызовами Body главы 103.
- **Скачивание** (клиент): `ResponseBodyLimit` главы 98 ведает бюджетом, потоковое потребление (обратные вызовы Body или Reader) — память развязана с объёмом скачивания; декодеры главы 92 цепляются на путь потребления.
- **Генерируемые ответы** (сервер): тело потока-производителя + `Respond` — курсор базы выдаёт шаг за шагом; при упоре в бюджет AGAIN оставляет производителя ждать потребителя. При запуске всего этого поверх TLS-сервиса (глава 85) разбор заголовков запроса идёт через TLS-привязку парсера главы 89 (http1_tls) — без буфера уровня соединения между записями; дисциплина потоковости проходит насквозь.

### Первая полная программа: выписывание потока-производителя и обратное чтение

Программа ниже из `examples/http/body_stream` — минимальный замкнутый цикл ограниченного потока-производителя:

```term
$ gcc -O1 -DXRT_MODULE_ALL -I extlibs/xhttp/single -include xhttp.h impl.c extlibs/xhttp/examples/http/body_stream/main.c -lws2_32 -liphlpapi
first chunk
second chunk
```

**Что только что произошло.** (1) `Config.MaxBytes=1024/MaxChunks=16` ставит бюджет, затем `HttpBodyStreamCreate` одним вызовом даёт **пару объектов**: `xhttpbody` (отдаётся запросу/ответу) и `xhttpbodystream` (держит конец-производитель). (2) Два отрезка `Write`, затем поток уничтожен — **разрушение последней ссылки = нормальный EOF**: поставленное в очередь содержимое доставляется сперва, EOF следом. (3) Цикл обратного чтения (тот же каркас, что у клиента главы 106): `Next(8, &Chunk)` режет малым потолком, DATA печатает + `ChunkRelease`, AGAIN ждёт на Future `xrtHttpBodyReaderWait`, EOF завершает. (4) Две строки вывода означают «поток байтов, записанный производителем, добирается до потребителя целиком» — **объект тела есть точка развязки производства и потребления**: концы могут жить в разных потоках в разные моменты. В реальном развёртывании конец-производитель — поток задачи (события SSE/выдача курсора), потребитель — транспорт HTTP.

## Контракты

- **Пять источников**: фиксированное семейство (переигрываемо, известная длина), поток-производитель (одно потребление, ограничен), файлы (переигрываемы, асинхронное чтение), собственные, трансформированные — единая форма `xhttpbody`.
- **Дисциплина фиксированного семейства**: Copy одно выделение (дескриптор + копия одним компактным блоком); Borrow не продлевает внешнюю жизнь; Reference обязан иметь процедуру освобождения; View успешен только для источников с гарантией непрерывности.
- **Поток-производитель**: бюджет MaxBytes/MaxChunks покрывает резервирования + очередь + лизинги; три финала EOF/Close/Fail; три формы Write (копия/ссылка/принятие).
- **Reader**: один потребитель; DATA (лизинг)/AGAIN (Wait Future)/EOF — три состояния; Chunk — независимый лизинг (ChunkRelease; освобождаем позже Reader/Body — дружественно отправке по ссылке).
- **Защита от алиасинга**: вывод не перекрывает нижележащие байты тела; ошибка алиасинга ничего не двигает и не ломает — фиксированные Body неизменны при переигрывании и конкурентных открытиях.
- **Файловые тела**: асинхронное чтение без блокировок и чтения целиком; переигрываемы; Range-варианты; форма готовности Future.
- **Матрица переигрывания**: переотправка 307/308 → фиксированное семейство/файлы; генерация один раз → поток-производитель.
- **Принадлежность бюджета**: клиентский ResponseBodyLimit (глава 98) ограничивает тело представления; бюджет потока-производителя ограничивает производителя — два слоя, каждый ограничен по-своему.
- **Обрезка**: `HTTP_BODY`/`HTTP_BODY_STREAM`/`HTTP_BODY_FILE` независимые макросы.

## Ловушки

### Ловушка 1: исходный буфер тела Borrow изменён/освобожден во время отправки

Симптом: изредка отправляется перемешанное содержимое — со стеком или с освобождённой до отправки кучей буфером скомбинировали Borrow.

Причина: контракт Borrow — «не продлевать жизненный цикл внешней памяти» — тело помнит только указатель; во время отправки (возможно асинхронной, возможно повторной) исходные данные обязаны жить как есть. Сомневаетесь — берите Copy или Reference.

```c bad
uint8 Buf[256];
fill(Buf);
xrtHttpRequestSetBody(pReq, xrtHttpBodyBorrow(view(Buf)));  /* стековый буфер */
send_async(pReq);   /* кадр стека умирает по возврату: отправка читает мусор */
```

```c good
/* либо Copy (малые тела), либо Reference + обратный вызов освобождения (свой кучный буфер) */
xrtHttpRequestSetBody(pReq, xrtHttpBodyCopy(view(Buf)));
/* или xrtHttpBodyReference(view(HeapBuf), release_cb, ctx) - освобождение автоматически по завершении отправки */
```

### Ловушка 2: после заполнения бюджета потока терять данные и производить дальше

Симптом: потоковый ответ теряет отрезки — после AGAIN производитель пропустил этот элемент и перешёл к следующему («чтобы не блокировать»).

Причина: AGAIN — противодавление, не ошибка — **ввод не удержан ни в каком виде**; элемент в ваших руках — единственная копия; пропуск = потеря данных. Правильное действие: ждать `WaitWritable` и отправить тот же элемент.

```c bad
for ( each_item ) {
	if ( send(stream, item) == AGAIN ) {
		continue;   /* выброшено - у клиента пробел в этом отрезке */
	}
}
```

```c good
for ( each_item ) {
	while ( send(stream, item) == AGAIN ) {
		wait_writable(stream);   /* шаблон ожидания из главы 106, ловушка 2 */
	}
}
```

### Ловушка 3: забыть Release у Chunk Reader (или держать его как представление вечно)

Симптом: лизинги в статистике выделений только растут — бюджет исчерпан, всё становится AGAIN.

Причина: Chunk — лизинг, а не представление — он занимает бюджет производителя; Release — действие возврата. Нужно держать долго — копируйте (кроме отправки по ссылке — это как раз проектный сценарий лизинга: освобождение по завершении отправки).

```c bad
while ( next(&Reader, &Chunk) == DATA ) {
	queue_push(g_Q, Chunk);   /* лизинг не возвращён: бюджет исчерпан */
}
```

```c good
while ( next(&Reader, &Chunk) == DATA ) {
	if ( want_keep(Chunk) ) {
		queue_push(g_Q, copy_chunk(Chunk));  /* храним копию */
	}
	xrtHttpBodyChunkRelease(&Chunk);          /* вернуть лизинг */
}
```

## Упражнения

### Базовое: сравнение пяти источников

Одним и тем же текстом создайте и отправьте тела Copy/Borrow/Take/Reference/потоком-производителем (на локальный сервис); сравните статистику выделений и переигрываемость (прочитать дважды). Критерии приёмки: числа выделений соответствуют контракту; второе чтение фиксированного семейства успешно, второе открытие потока-производителя проваливается (или ведёт себя по контракту).

### Продвинутое: конвейер загрузки большого файла

Клиент файловым телом шлёт POST файла 2 GB (сгенерируйте временный файл) → серверные потоковые обратные вызовы Body принимают и пишут на диск → сверьте хэши. Весь путь записывайте пики памяти обоих концов. Критерии приёмки: обе пики не зависят от размера файла (уровня MB); хэши совпадают; при ограничении скорости посередине (имитация медленного диска) конвейер стабилен.

### Вызов: трансформированное тело (конвейер шифрования)

Собственный тело-производитель: читать блоки файла → шифровать блоки AES-GCM (глава 74) → кодировать в тело — сервис «шифрованной загрузки файла». Клиент потребляет, расшифровывая в обратную сторону по схеме декодирования главы 92. Критерии приёмки: круг туда-обратно восстанавливает оригинал; ключ живёт только в памяти обеих сторон (SecureZero в финале — дисциплина главы 76); пик памяти постоянен.
