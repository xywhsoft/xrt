## Ориентация

Для одностороннего push от сервера к клиенту у Web-мира два варианта: WebSocket (главы 95–97, двунаправленный, отдельный протокол) и **SSE** (Server-Sent Events — протокол событий поверх потока HTTP-ответа). Философия реализации xhttp одной фразой: **никаких выделенных SSE-соединений, потоков, очередей или сетевых машин состояний** — `xrtHttpSseReplyCreate` создаёт обычный `xhttpreply` со статусом 200, `Content-Type: text/event-stream` и одноразовым телом неизвестной длины; фактическую отправку ведут **единственная** машина состояний ответа HTTP Server, противодавление TCP/TLS и срок записи; возвращённый `xhttpbodystream` — независимый конец-производитель, отдаваемый фоновой задаче или любому потоку на запись. Клиентская сторона — то же зеркало: слой соединения плюс парсер событий (инкрементальная машина синтаксиса `text/event-stream`), разрывное возобновление `Last-Event-ID` встроено. Правило выбора: когда push односторонний — берите SSE — протокол прост, едет по порту 80, автопереподключение встроено в браузер.

## Введение

Push прогресса, потоки котировок, хвост журнала, потоковая выдача LLM по токенам — «сервер говорит без остановки, клиент только слушает» покрывает большую часть потребностей push. Тащить сюда WebSocket — зенитка по комарам: одностороннее использование двунаправленного протокола плюс полный груз handshake-обновления, сердцебиений и протокола закрытия. Ответ SSE — «не меняйте протокол»: по-прежнему HTTP-ответ, просто **не заканчивающийся** — в chunked-потоке с `Content-Type: text/event-stream` события составляются из строк полей `event:/data:/id:/retry:`, разделённых пустыми строками.

Инженерная трудность на обоих концах. Сервер: поток ответа должен сотрудничать с фоновыми производителями — события приходят из потока задачи, соединение пишется на Worker — как путешествует противодавление? Клиент: синтаксис событий **инкрементальный** (одно поле data может быть разбито на несколько data:-строк; события пересекают границы chunk) — парсер обязан быть потоковым. xhttp даёт структурированные ответы на обоих концах: серверный `SseSendEvent` (одно полное событие за вызов, сперва валидация потом кодирование, половина события при провале не фиксируется) + конец-производитель `xhttpbodystream` (противодавление AGAIN + восстановление `WaitWritable`); клиентский парсер продвигается поле за полем под ограничениями потолков.

## Понятия

### Сервер: поезд на единственной машине состояний

```diagram flow
- Создание: SseReplyCreate(конфигурация, &поток) -> обычный Reply (200/text-event-stream/тело неизвестной длины)
- Настройка: до фиксации обычными Header-API добавить Cache-Control/CORS/X-Accel-Buffering (обязанность слоя развёртывания)
- Фиксация: после HttpConnRespond Server замораживает и удерживает источник тела - Reply можно уничтожать
- Производство: поток отдан потоку задачи -> пишут SseSendEvent/SendComment/Write-семейство
- Противодавление: AGAIN не удерживает ссылку на ввод -> ждать WaitWritable и повторять
- Финал: разрушение последней ссылки = очередь событий затем нормальный EOF; Close идемпотентно предзакрывает; Fail отбрасывает недоставленное + стабильная Cause
```

Три проектные дисциплины. (1) **Граница протокольно-необходимого и прикладного выбора**: `ReplyCreate` ставит только Content-Type; `Cache-Control: no-cache`, аутентификацию, CORS, политику буферизации прокси (`X-Accel-Buffering: no`) приложение ставит до фиксации обычными Header-API — слой SSE не гадает за вашу среду развёртывания. (2) **Атомарность**: каждый Send сперва полностью валидирует и измеряет, потом кодирует прямо в один узел Body Stream — **временная строка события не строится, половина события при провале не фиксируется**; жёсткие бюджеты байтов и Chunk покрывают конкурентные резервирования, очередь и активные лизинги. (3) **Раздельные жизненные циклы**: после фиксации Respond Reply можно уничтожить, Stream живёт дальше — «объект ответа» и «конец-производитель» — два жизненных цикла.

### Структура события и упаковка

Четыре элемента `xhttpsseevent`: `Type` (строка event: — имя типа события), `Data` (строки data: — может быть многострочной), `Id` (строка id: — курсор возобновления), `Retry` (строка retry: — миллисекунды переподключения, рекомендуемые клиенту); `Flags` объявляет, какие элементы присутствуют. `SseSendEvent` упаковывает полное событие одним вызовом; `SseSendComment` (строка комментария `: heartbeat` — поддержание жизни); `xrtHttpBodyStreamWrite/WriteRef/WriteTake` пишут сырые байты напрямую (предкодированные события, пересылка прокси, собственные расширения — структурированный Writer не обязательный путь).

### Противодавление и ожидание

Запись производителя, упёршаяся в полный бюджет, возвращает `AGAIN` — **ни одной ссылки на ввод не удержано**, вызывающий повторяет в точности; `xrtHttpBodyStreamWaitWritable` возвращает общий Future следующего поколения записываемости — **отмена одного ждущего влияет на остальных ждущих**, поэтому напрямую отменять нельзя (общая семантика Future главы 58). Это «AGAIN + WaitWritable» — тот же словарь, что у Stream WebSocket главы 96.

### Клиент: соединение и парсер

Клиентская сторона — два слоя: **слой соединения** (`http_sse_client` — инициирует GET, поддерживает переподключение и заголовок Last-Event-ID) и **парсер** (инкрементальная машина синтаксиса `text/event-stream` — строки полей, границы событий, склейка многострочных data). Конфигурация парсера ограничивает одиночную строку, данные события, тип и ID — **структурный потолок памяти** (SSE-версия «что ограничивать, решает структура содержимого» главы 99: тело представления выбрано безграничным, структурированная память ограничена). Разрывное возобновление: отправленный сервером `id:` записывается клиентом и при переподключении приносится обратно заголовком `Last-Event-ID` — сервер продолжает после курсора.

### Выбор SSE против WebSocket

| Измерение | SSE | WebSocket (главы 95–97) |
| --- | --- | --- |
| Направление | одностороннее (сервер → клиент) | двунаправленное |
| Протокол | чистый поток HTTP-ответа | отдельный протокол после обновления |
| Инфраструктура | прозрачен любым HTTP-посредникам | нужна поддержка Upgrade |
| Переподключение | встроено в браузер/клиент + возобновление по курсору | строит приложение |
| Подходит | push/потоковая выдача/прогресс | чат/коллаборация/двунаправленная телеметрия |

## Контракты

- **Нет выделенной машины состояний**: SSE Reply — обычный Reply (200/text-event-stream/неизвестная длина); отправка едет на единственной машине состояний ответа с существующими противодавлением и сроком записи.
- **Граница протокол/приложение**: ReplyCreate ставит только Content-Type; Cache-Control/CORS/политика буферизации — ставьте сами до фиксации.
- **Жизненный цикл**: после Respond Reply можно уничтожить, Stream независим (его держит поток задачи/издатель); разрушение последней ссылки = EOF после очереди событий; Close идемпотентен; Fail отбрасывает недоставленное + стабильная Cause.
- **Атомарность записи**: сперва валидация и измерение, потом кодирование в один узел; временная строка события не строится; половины события при провале нет; бюджет байтов/Chunk покрывает резервирования + очередь + лизинги.
- **Противодавление**: AGAIN не удерживает ввод; WaitWritable — общий Future (без односторонней отмены); прямые записи байтов Write/WriteRef/WriteTake опциональны.
- **Четыре элемента события**: event/data/id/retry + Flags; строка комментария поддерживает жизнь; id — курсор возобновления.
- **Клиентский разбор**: инкрементальная машина синтаксиса; четыре потолка строка/данные/тип/ID — структурированная память ограничена; возобновление Last-Event-ID.
- **Цикл потребления**: DATA (кусок + Release) / AGAIN (Wait Future) / EOF — каркас трёх состояний.
- **Обрезка**: `HTTP_SSE` сервер/клиент независимы; парсер можно использовать отдельно на собственном транспорте.

## Ловушки

### Ловушка 1: затолкать в SSE-событие data с голыми переводами строк

Симптом: «одно событие», полученное клиентом, разорвано на несколько или разбирается в кашу — переводы строк внутри data изменили границы событий.

Причина: SSE разделяет события пустыми строками, а многострочность data выражается несколькими строками `data:` — `SseSendEvent` при упаковке обрабатывает многострочное data корректно (разбивая на несколько data:-строк), но обход структурированного входа со склейкой строк руками легко пишет переводы строк голыми.

```c bad
xrtHttpBodyStreamWrite(pStream, XRT_BYTES_LITERAL(
	"data: line1\nline2\n\n"));   /* у line2 нет префикса data: - синтаксическая ошибка */
```

```c good
xhttpsseevent Event = { 0 };
Event.Data = XRT_STR_LITERAL("line1\nline2");   /* упаковщик разобьёт на многострочные data: */
Event.Flags = XHTTP_SSE_EVENT_DATA;
xrtHttpSseSendEvent(pStream, &Event);
```

### Ловушка 2: игнорировать AGAIN — крутить вплотную (жёг CPU) или выбрасывать

Симптом: задача-производитель пишет на полной скорости, после заполнения бюджета сжигает CPU в плотном цикле; или AGAIN принят за ошибку, события выброшены — у клиента пробелы.

Причина: AGAIN — сигнал противодавления (та же семантика, что в главе 95): правильное действие — дождаться записываемости и отправить **то же самое событие** — AGAIN ввод не удержал; данные в ваших руках — единственная копия.

```c bad
while ( xrtHttpSseSend(pStream, Data) == XHTTP_BODY_STREAM_AGAIN ) {
	/* плотный цикл: жжёт CPU и может никогда не протиснуться */
}
```

```c good
xhttpbodystreamresult R;
while ( (R = xrtHttpSseSend(pStream, Data)) ==
		XHTTP_BODY_STREAM_AGAIN ) {
	xfuture* pW = xrtHttpBodyStreamWaitWritable(pStream);
	if ( pW == NULL ) { break; }
	xrtFutureWaitFor(pW, Timeout);   /* ждём, общий Future не отменяем */
	xrtFutureDestroy(pW);
}
/* выход из цикла с R OK/CLOSED - обработать соответственно */
```

### Ловушка 3: не поставить X-Accel-Buffering — события копятся в прокси

Симптом: при прямом локальном соединении события приходят вживую, за nginx клиент «получает комок раз в вечность» — прокси считает поток ответа буферизуемой загрузкой и копит партиями.

Причина: живость SSE зависит от **небуферизации** промежуточными устройствами; `X-Accel-Buffering: no` — стандартный заголовок, сообщающий прокси; это знание среды развёртывания, потому xhttp не добавляет его автоматически (граница протокол/приложение); добавляете вы.

```c bad
pReply = xrtHttpSseReplyCreate(NULL, &pStream);
respond(pConn, pReply);   /* развёртывание за прокси: события копятся партиями */
```

```c good
pReply = xrtHttpSseReplyCreate(NULL, &pStream);
xrtHttpReplySetHeader(pReply,
	XRT_STR_LITERAL("X-Accel-Buffering"),
	XRT_STR_LITERAL("no"));
xrtHttpReplySetHeader(pReply,
	XRT_STR_LITERAL("Cache-Control"),
	XRT_STR_LITERAL("no-cache"));
respond(pConn, pReply);
```

## Упражнения

### Базовое: сверка обоих концов

Прогоните sse_server и sse_client; смените серверное событие на собственный тип + многострочные data, клиент после разбора печатает структуру. Критерии приёмки: многострочные data склеиваются верно; рост курсора id виден.

### Продвинутое: сервис push прогресса

Добавьте к серверу главы 104 маршрут `/progress`: после подачи задачи SSE толкает прогресс (событие percent каждые 100 мс, heartbeat каждые 15 с); задача-производитель — в отдельном потоке, пишет через Stream. Критерии приёмки: при медленном клиенте (потребление с ограничением скорости) память сервера постоянна (противодавление работает — наблюдайте путь AGAIN); завершение задачи шлёт событие done с id, затем EOF.

### Вызов: разрывное возобновление

Клиент потребляет N событий и разрывает; переподключение несёт `Last-Event-ID`; сервер продолжает после курсора (хранилище курсора на выбор: кольцо в памяти или Map главы 18). Критерии приёмки: поток событий клиента продолжается бесшовно (без повторов и пробелов); при рестарте сервера (курсор потерян) клиент принимает с начала (зафиксируйте это различие поведения); сердцебиение держит соединение в простой.
