## Ориентация

Хеш-отображение отвечает «где этот ключ»; AVL-дерево отвечает «что ещё рядом с этим ключом»: обход по порядку естественно сортирован, а диапазонные запросы («все сессии с ID от 20 до 30») проходят дерево один раз. XRT даёт ему два лица — **интрузивный `xavl`** (узел встраивается в бизнесовый объект, вставка-удаление без выделений, один клан со связным списком главы 17) и **владеющий `xavltree`** (дерево владеет объектами; изъятие есть передача). Логика выбора между лицами продолжает «массивы значений против массивы указателей» (глава 14): принадлежность объекта решает форму контейнера. Глава ведёт оба лица парой полных образцов и досконально разбирает «мультииндексность» (одно дерево по ID, другое по имени) — убийственное применение интрузивной формы.

## Введение

Менеджеру сессий нужны два представления: эксплуатационной стороне — «найти ровно эту по ID сессии» (хеширование умеет), аудитной — «экспортировать всё в порядке ID» или «выгрузить отрезок ID» — хеширование не умеет, сортированному массиву вставка стоит линейно, список вовсе неупорядочен. Ответ AVL-дерева — сбалансированное двоичное дерево поиска: вставка, удаление и поиск все O(log n), **обход по порядку и есть сортированная последовательность**, диапазонный запрос проходит дерево один раз.

Второе решение следует сразу: кто кем владеет — дерево объектами или наоборот? Объекты сессий уже живут в пуле (их жизненным циклом ведает пул); дереву нужно лишь «организовать их по ID» — интрузивный `xavl`, узел — поле объекта, ноль выделений. А самостоятельный сценарий («этой пачке конфигурационных записей и жить и умирать с деревом») берёт владеющий `xavltree`: вставка есть передача, изъятие есть возврат. Это решение зеркалит главу 14 в точности; с этой главой экзамен многовариантности тома 3 получает последний кусок.

## Понятия

### Два лица, одна таблица

| Измерение | Интрузивный `xavl` | Владеющий `xavltree` |
| --- | --- | --- |
| Владение объектами | вызывающий (стек/пул/массив — где угодно) | дерево |
| Вставка/удаление | **ноль выделений** (только связи) | вставка выделяет узел |
| Мультииндексность | один объект, несколько полей-узлов, несколько деревьев | одно дерево, одно владение |
| Функция сравнения | обратный поиск носителя из узла (`offsetof`) | сравнивает элементы напрямую |
| Типовые сценарии | многовидовые индексы над пуловыми объектами | упорядоченное владение самостоятельными конфигурациями/данными |

### Обход по порядку — и есть сортировка

```diagram flow
- Вставка: функция сравнения усаживает; дисбаланс ротируется сам - баланс частное дело дерева
- Поиск: O(log n), спуск по функции сравнения
- Обход по порядку: порядок лево-корень-право = последовательность возрастания ключей
- Диапазонный запрос: старт от нижней границы, стоп у верхней, проход только по поддеревьям интервала
```

«Самобалансирование» AVL для пользователя — чёрный ящик: вы поставляете только трёхзначную функцию сравнения; ротации, высоты и ребалансировку дерево ведает само. Подпись-сигнатуру сравнения стоит разглядеть — `(查找键, 树节点, 用户数据)` (ключ поиска, узел дерева, пользовательские данные): ключ и узел — **разные типы** (один — ключ, другой — узел, несущий ключ); в интрузивной форме сравнение сперва обратным поиском через `offsetof` берёт носителя, затем сравнивает ключи — та же идиома «обратного поиска», что и `XRT_CONTAINER_OF` главы 17.

### Интрузивный: индекс без выделений

Дескриптор `xavl` сам по себе без содержимого (`Init` лишь инициализирует дескриптор); вставка лишь перецепляет связи существующих объектов — ни одного кучевого выделения на всём пути. Где живут бизнесовые объекты — решаете вы: стековый массив (образец один), пул объектов (глава 22), даже slot_map — дереву всё равно, оно только связывает. Один объект с двумя полями-узлами висит на двух деревьях сразу: «одно по ID, другое по имени» — C-форма мультииндексности баз данных. Цена записана в функции сравнения: каждое сравнение делает обратный поиск носителя; эта индирекция — прирождённая стоимость интрузивной формы.

### Владеющий: владение и передача

`xavltree` распоряжается жизнью и смертью объектов: вставка есть передача (дерево выделяет узел, оборачивающий объект), итерация выдаёт указатели объектов, а изъятие (семейство `Take`) возвращает объект вам и отдаёт узел дереву. Оно годится сценам «данные прирождённо принадлежат этому дереву» — конфигурационные записи, статические словари. Когда не нужны ни мультииндексность, ни внешний пул, владеющая форма пишет вдвое меньше шаблонного кода.

### Разделение труда с хеш-отображением

AVL и отображения главы 18 — не конкуренты, а коллеги. Точный поиск по одному ключу — оба уровня O(1)/O(log n), у хеширования константа меньше; но как только вопрос становится «что ещё рядом с этим ключом» — упорядоченный обход, диапазонные запросы, предшественник/последователь, минимум/максимум — хеширование структурно не умеет, а AVL начинает всё с O(log n). На практике менеджер ресурсов часто держит обоих: `xmap` на горячем пути локации, `xavl` как упорядоченное представление для аудитов и экспорта — одна пачка объектов под двумя индексами (один объект на двух индексах — как раз форма интрузивного). Таблица выбора главы 23 записывает это разделение правилом: **только поиск → отображение; поиск + порядок → AVL; и то и другое → держать обоих; не заставляйте один контейнер тащить два вида вопросов**.

### Семантика повторных ключей

Если в дереве уже есть узел с тем же ключом, `Insert` возвращает **тот существующий узел** (не NULL) — повтор не ошибка и не перезапись; «что делать» возвращается вызывающему: заменить значение, отказать или переименовать. Семантику возврата надо запомнить твёрдо: **NULL — успешная вставка** (наоборот многим библиотекам); не-NULL — «столкновение ключей, вот старый узел».

## Примеры

### Первая полная программа: интрузивный индекс и упорядоченная итерация

Из репозиторного образца `examples/containers/avl/main.c`:


```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/containers/avl/main.c -lws2_32 -liphlpapi
id=10 name=alpha
id=20 name=beta
id=30 name=gamma
```

**Что только что произошло.** (1) Массив сессий лежит на стеке (30, 10, 20 вперемешку); поле `Index` встраивает `xavlnode` — перед подвешиванием `xrtAVLNodeInit` обнуляет связи, этот шаг не опционален. (2) Сравнение `(iID > pSession->ID) - (iID < pSession->ID)`: сперва обратный поиск носителя, затем ключ, трёхзначный возврат; вычитание предотвращает переполнение (старый знакомый главы 14). (3) `xrtAVLInsert` успешен ровно возвратом NULL — в цикле ветка `== NULL` и есть ветка успеха. (4) **Ноль кучевых выделений** на всём пути: дерево лишь связало три стековых объекта в упорядоченную структуру. (5) Обход по порядку всегда выводит 10, 20, 30 — порядок вставки 30,10,20 на вывод не влияет; ценность «индекса» — расцепление порядка вставки и упорядоченного представления. (6) `offsetof(examplesession, Index)` — обратный поиск: адрес узла минус смещение поля даёт адрес носителя — сопутствующая идиома интрузивности.

```term

```

**Что только что произошло.** (1) Вставка-передача: конфигурационные объекты, войдя в дерево, держатся деревом; итерация выдаёт указатели объектов. (2) Сперва точное попадание в id=20 — форма поиска и вывода попадания. (3) Диапазонная итерация идёт от нижней границы 20 до верхней 40, выводя 20, 30 — «интервальный экспорт» есть прямое применение диапазонной итерации; даже полного обхода дерева не нужно. (4) Дерево распоряжается жизнью и смертью: при `Unit`/`Destroy` объекты освобождаются вместе с ним — владеющая семантика экономит вам и заботу, и один слой контроля.

### От образцов к инженерии: трёхъярусная структура индексов

Настоящий менеджер ресурсов — обычно «трёхъярусная структура индексов»: внизу хранилище объектов (пул или slot_map, ведающие жизнью, смертью и стабильными адресами); в середине индекс локации (`xmap` или `xintmap`, ключ → дескриптор); наверху упорядоченное представление (интрузивный `xavl`, аудиторские экспорты и диапазонные запросы). Каждый ярус делает своё дело — хранилище гарантирует стабильные адреса, локация несёт горячий путь, представление несёт порядок — и интрузивный AVL существует именно потому, что ярус хранения гарантирует неизменность адресов объектов. Эта трёхъярусная структура появится в полной форме в таблице соединений главы 67; дойдя туда, вернитесь и сравните: два образца этой главы натренировали минимальное употребление среднего и верхнего ярусов.

## Контракты

- **Повторные ключи**: не-NULL от `Insert` = столкновение, возврат — существующий узел; NULL = успех. Ветку успеха пишите `== NULL`.
- **Интрузивный ноль выделений**: `NodeInit` до `Insert`; жизненный цикл объекта обязан покрывать период на дереве; снятие с дерева прежде уничтожения объекта (та же дисциплина, что у списка главы 17).
- **Владеющий**: вставка-передача; `Unit`/`Destroy` освобождают сами объекты.
- **Функция сравнения**: трёхзначный возврат; интрузивная форма сперва делает обратный поиск носителя; от переполнения — двухшаговое сравнение вычитанием.
- **Итерация**: по порядку = возрастание; диапазонная итерация идёт по поддеревьям интервала, никогда по всему дереву.

### Проверка функции сравнения

Вся поведенческая корректность AVL стоит на функции сравнения; она заслуживает тестирования как самостоятельная единица. Три вопроса проверки: **трёхзначная ли** — равенство обязано возвращать 0; сравнение, возвращающее -1 или 1 на равных, даёт «не могу найти только что вставленный ключ»; **переполненно-безопасная ли** — целочисленные сравнения двухшаговой формой вычитания; **согласованная ли** — одна и та же пара ключей обязана сравниваться взаимно-дополняюще с любого направления (a<b влечёт b>a); несогласованная функция сравнения полностью разрушает структурный баланс дерева. Закончив функцию сравнения, скормите ей ручные случаи (меньше/равно/больше/экстремумы) и лишь потом вешайте дерево — этот порядок избавляет от целого сеанса «дерево ведёт себя странно».

## Ловушки

### Ловушка 1: возврат Insert как булево

Симптом: вставка «всегда не удаётся» или «всегда удаётся» — в зависимости от того, как написан if; при столкновении объект молча теряется либо старые данные перетолковываются.

Причина: в обратность другим библиотекам, NULL у `xrtAVLInsert` — успех, не-NULL — старый узел, возвращённый при столкновении ключей; проверка, написанная на рефлексе «не-ноль есть истина», переворачивает логику целиком.

```c bad
if ( xrtAVLInsert(&tSessions, &pSessions[i].Index, &pSessions[i].ID,
		exampleCompare, NULL, NULL) ) {
	/* казалось, сюда = успех; на деле сюда = столкновение ключей */
}
```

```c good
if ( xrtAVLInsert(&tSessions, &pSessions[i].Index, &pSessions[i].ID,
		exampleCompare, NULL, NULL) == NULL ) {
	/* NULL — успешная вставка */
}
```

### Ловушка 2: забытый NodeInit либо уничтожение объекта, ещё висящего на дереве

Симптом: первое — падение на вставке (связи — мусорные значения); второе — то же семейство, что у списка: дерево указывает на освобождённую память, и падение приземляется далеко от места.

Причина: неинициализированные поля связей в интрузивной форме — неопределённое состояние; уничтожение объекта периода-на-дереве уносит вниз и указатели дерева.

```c bad
examplesession* pDead = find_expired(&tSessions);
xrtFree(pDead);                        /* Index всё ещё на дереве - дерево повисло */
```

```c good
examplesession* pDead = find_expired(&tSessions);
xrtAVLRemove(&tSessions, &pDead->Index);   /* сперва снять с дерева */
xrtFree(pDead);                             /* потом уничтожить */
```

## Упражнения

### Базовое: проверка беспорядочной вставки

Воспроизведите главный образец: вставьте 5 сессий вперемешку, утвердите, что обход по порядку всегда возрастающий; повторите с другим порядком вставки — вывод не меняется. Внутренняя форма дерева между прогонами может отличаться полностью, а вывод по порядку совпадает — наблюдаемое доказательство того, что «баланс — частное дело дерева».

### Продвинутое: двойной индекс (убийственное применение интрузивного)

Дайте объекту сессии второе поле-узел; постройте два дерева, «по ID» и «по лексикографии имени»; одна пачка объектов выводит обход каждого дерева отдельно. Подсказка: две функции сравнения + два раунда Insert; объекты существуют в одном экземпляре.

### Вызов: интервальный экспортёр (диапазонная итерация против грубой фильтрации)

Загрузите 1000 конфигураций со случайными ID во владеющее дерево; реализуйте `export(minId, maxId)`, выводя всё в интервале; сравните число посещённых узлов с «полной итерацией + ручной фильтрацией». Критерии приёмки: на 10 случайных интервалах внутри [0,1000] вывод построчно совпадает с грубым методом; зафиксируйте и доложите разницу счётчиков итераций двух методов.

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Две формы | интрузивный `xavl` — ноль выделений, мультииндексность / владеющий `xavltree` — владеет объектами |
| Возврат | `Insert` NULL = успех; не-NULL = существующий узел с тем же ключом |
| Обратный поиск | `offsetof(宿主, 节点字段)`; один корень с `XRT_CONTAINER_OF` |
| Упорядоченность | обход по порядку = возрастание ключей; диапазонная итерация только по поддеревьям интервала |
| Дисциплина подвешивания | `NodeInit` вперёд; снятие прежде уничтожения; жизненный цикл покрывает период на дереве (как у списка главы 17) |
| Трёхъярусная структура | хранилище (пул/slot_map) + локация (map) + упорядоченное представление (интрузивный AVL) — стандарт настоящего менеджера ресурсов |
| Баланс | авторотации; пользователь ставляет только трёхзначное сравнение; перед подвешиванием скормите сравнению ручные случаи |
| Разделение с map | только поиск → map; поиск + порядок → AVL; обе потребности → оба индекса рядом |
| Сложность | поиск/вставка/удаление O(log n); обход и диапазон — только по необходимым поддеревьям; рядом с map каждый несёт свою службу |
