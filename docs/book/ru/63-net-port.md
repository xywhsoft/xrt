## Ориентация

Событийный порт (`xnetport`) — **сердце** сетевого движка: пять платформенных бэкендов (IOCP/epoll/kqueue/io_uring/select) унифицированы в один интерфейс, `xrtNetPortBackend` запрашивает текущий бэкенд, `Capabilities` объявляет набор возможностей. Две формы программирования (анонс главы 62): **readiness** (уведомления Watch читаемо/записываемо — epoll/select/kqueue) и **completion** (Connect/Accept/Recv/Send отдают результат напрямую — IOCP/io_uring); плюс **управляющие события** (Post пользовательские события, Wake пробуждение, Cancel отмена операций в полёте — три двери, связывающие с планировщиками и каналами). Большинство бизнес-кода использует порт косвенно через слой Stream (глава 66) — эта глава — справочный слой для понимания внутренностей движка и прямого использования порта.

## Введение

У каждой из пяти платформ свой нативный событийный механизм: Windows IOCP (порты завершения — модель completion), Linux epoll (уведомления готовности — readiness) и io_uring (очереди завершения — completion), macOS kqueue (readiness), кроссплатформенная подстраховка select. Писать пять голых адаптеров — классическая нагрузка сетевой библиотеки, а различия возможностей (у IOCP нет readiness, у select нет completion) заставляют «один код на пять платформ» ветвиться по возможностям.

Ответ порта XRT: **единый интерфейс + объявление возможностей** — интерфейс покрывает все операции обеих форм (Watch/Unwatch — readiness; семейство Connect/Accept/Recv/Send — completion), `Capabilities` (возвращает битовые флаги) запрашивает, что поддерживает текущий бэкенд, а межплатформенный код ветвится по возможностям или поднимается на слой Stream (который уже проделал ветвление внутри). Вывод примера port_tour показывает напрямую: на Windows `iocp=completion select=readiness` — два порта, по одной форме; на Linux epoll и uring по разные стороны — платформенные различия из «ловушек» превращаются в «объявления».

## Понятия

### Полная панорама операций порта

| Семейство | Входы | Форма | Примечания |
| --- | --- | --- | --- |
| Самоописание | Backend/Capabilities/GetConfig | — | Запросы бэкенда и возможностей |
| readiness | Watch/Unwatch | уведомления читаемости/записываемости | Колбэк, когда fd готов |
| Завершение потоков | Connect/Accept/ReadProbe/Recv/RecvVec/Send/SendVec | completion | Результат доставляется напрямую |
| Завершение датаграмм | RecvFromVec/RecvMsg(Vec)/SendToVec/SendMsgVec | completion | UDP, ориентировано на сообщения |
| Управление | Post/Wake/Cancel/RecvError | — | пользовательские события / пробуждение / отмена / приём ошибок |

**Назначение трёх управляющих дверей**: `Post` доставляет события USER (внешняя логика внедряется в поток событий — истечение таймера, смена конфигурации); `Wake` пробуждает ожидающий порт (межпоточно безопасно — точка приземления Wake-канала скелета главы 60); `Cancel` отменяет операцию в полёте (завершается CANCELLED — портовый диалект дерева отмен главы 53).

### readiness против completion подробно

```diagram flow
- readiness (epoll/select/kqueue): зарегистрировать интерес -> уведомление о готовности -> вы читаете/пишете
  Ответственность на вызывающем: момент чтения/записи, управление буферами, неблокирующая обработка
- completion (IOCP/io_uring): подать операцию + буфер -> результат доставляется при завершении
  Ответственность на порту: очередь операций, закрепление буферов, доставка завершений
- Объявление возможностей: запрос Capabilities — не предполагайте у бэкенда обе формы
```

Самое примечательное различие форм — **принадлежность буферов**: при readiness буфер ваш (когда готово — вы заполняете/читаете); при completion буфер **заморожен** от подачи до завершения (та же дисциплина, что у асинхронных файлов главы 47 — портовая версия). На Windows IOCP только completion — Watch недоступен; select только readiness — подача операций недоступна; на Linux epoll и uring по разные стороны. **Паттерн прямого межплатформенного использования порта**: ветвление по возможностям (if Capabilities.completion → подача, else → Watch) или единый подъём на слой Stream.

### Типы событий и ожидание

Ожидания порта возвращают **события** (структуры с типом + ассоциированными данными): READABLE/WRITABLE (readiness), завершение CONNECT / приход ACCEPT / результаты чтения-записи (по операциям completion), USER (Post), WAKE (Wake), ERROR (платформенные ошибки вроде ICMP unreachable — RecvError гейтится по возможностям платформы). Формы ожидания: блокирующее ожидание (следующее событие) и ожидание с тайм-аутом (такт насоса движка — нижний слой PollFor главы 60). Цикл потребления событий — точно скелет главного цикла Worker движка.

### Порт и Stream

Stream главы 66 стоит над портом: колбэки Stream (Accept/Read/Close) управляются событиями порта; Stream внутри делает адаптацию двойственности (бэкенды completion подают напрямую; бэкенды readiness читают/пишут после готовности) + машина состояний (четыре состояния главы 66) + подсчёт ссылок. **Критерий выбора слоя**: нужен точный контроль (фундамент собственного протокола, пакетный приём/отправка UDP — пример udp_batch использует порт напрямую) → порт этой главы; стандартная обработка соединений → слой Stream. Пять примеров port_epoll/port_iocp/port_kqueue/port_select/port_uring демонстрируют по одному бэкенду в прямом использовании.

### Полная программа: двойственность и объявление возможностей

Из примера репозитория `examples/network/port_tour/main.c` — два порта демонстрируют по форме:


```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/network/port_tour/main.c -lws2_32 -liphlpapi
port: backends iocp=completion select=readiness ok
port: watch -> READY -> unwatch ok
port: tcp connect + accept + readprobe + recv/send ok
port: stream vec recv/send ok
port: dgram recvfromvec/recvmsg/recvmsgvec ok
port: dgram sendtovec/sendmsgvec ok
port: cancel in-flight recv -> CANCELLED ok
port: post USER + wake WAKE ok
port: recv-error gated by platform ok
```

**Что только что произошло.** (1) Прямое свидетельство `Backend/Capabilities`: `iocp=completion select=readiness` — на Windows по форме на порт (объявление возможностей предотвращает предположения). (2) Маршрут readiness: Watch регистрирует → событие READABLE → Unwatch снимает — три шага одного наблюдения готовности. (3) Маршрут completion, всё семейство: TCP Connect/Accept/ReadProbe/Recv/Send (с векторными вариантами Vec — несколько буферов одной подачей) и UDP-семейство RecvFrom/SendTo (датаграммы — одна датаграмма на операцию). (4) Три управляющие двери проверены: Cancel приёма в полёте завершается CANCELLED (диалект главы 53); события Post/Wake — пользовательское и пробуждение — приходят. (5) `recv-error gated by platform` — платформенный гейт возможностей RecvError (вызовы вне возможностей отвергаются, а не рушатся — принуждение декларативного дизайна).

(2) Ценность select — **подстраховка** (работает на любой платформе) — точка приземления отладки разработки (среды без выделенного бэкенда) и обучения; продакшн предпочитает IOCP/epoll/uring (автовыбор движка). (3) Пять примеров port_X (epoll/iocp/kqueue/select/uring) одинаковы по структуре — **одни и те же вызовы на пяти бэкендах** — живое доказательство ценности единого интерфейса: смена бэкенда стоит нулёвых правок кода (или только параметра создания).

## Контракты

- **Объявление возможностей**: перед прямым использованием порта запросите Capabilities — не предполагайте обе формы; вызовы вне возможностей отвергаются (декларативное принуждение).
- **Заморозка буферов**: от подачи до завершения при completion буфер неприкосновенен (портовая версия дисциплины главы 47).
- **Три управляющие двери**: Post внедряет USER / Wake пробуждает межпоточно / Cancel отменяет в полёте — взаимно однозначно тройке скелета (внедрение выноса / пробуждение насоса / дерево отмен).
- **Векторные варианты**: RecvVec/SendVec подают несколько буферов сразу — амортизирующий вход пакетного IO (IO-версия идеи батчинга главы 21).
- **Выбор слоя**: стандартные соединения поднимаются на Stream (глава 66); собственные фундаменты / пакетный UDP используют порт напрямую.
- **Событийный цикл**: ожидание порта — главный цикл Worker движка — потребление событий есть нижняя форма насоса скелета — а чтобы планировать мелкие задачи прямо на этот цикл, есть мост: сетевые группы задач (task_net) главы 60.

## Ловушки

### Ловушка 1: Watch на бэкенде completion

Симптомы: вызов отвергнут («no readiness capability») или на компиляции выглядит нормальным, а в рантайме падает — на Windows IOCP нет уведомлений готовности.

Причина: предположение двойственности у бэкенда — IOCP только completion, select только readiness; вызов без проверки возможностей.

```c bad
xnetport* Port = xrtNetPortCreate(...);   /* Windows по умолчанию IOCP */
xrtNetPortWatch(Port, Fd, EVENTS, Callback, Data);   /* отвергнуто — нет возможности readiness */
```

```c good
uint32 Caps = xrtNetPortCapabilities(Port);   /* битовые флаги */
if ( Caps & XNET_PORT_CAP_READINESS ) {
	xrtNetPortWatch(Port, Fd, EVENTS, Callback, Data);
} else if ( Caps & XNET_PORT_CAP_COMPLETION ) {
	xrtNetPortRecv(Port, Fd, Buffer, Size);   /* подача — ветвление по возможностям */
}
```

### Ловушка 2: трогать буфер после подачи

Симптомы: приходит грязь или редкие ошибки завершения — одно семейство с ловушкой 2 асинхронных файлов главы 47; зависит от таймингов, трудно воспроизвести.

Причина: при форме completion буфер закреплён портом от подачи до завершения — ранняя перезапись есть гонка данных.

```c bad
xrtNetPortRecv(Port, Fd, Buffer, Size);   /* подать приём */
memset(Buffer, 0, Size);                    /* сразу обнулить — порт в это время пишет внутрь */
```

```c good
xrtNetPortRecv(Port, Fd, Buffer, Size);
/* буфер заморожен до прибытия события завершения; чтобы переиспользовать раньше — пул буферов (глава 22), блок за одним IO */
```

## Упражнения

### Базовое: репортер возможностей

Создайте порт → напечатайте Backend/Capabilities/GetConfig — прогоните на каждой доступной платформе и зафиксируйте матрицу возможностей пяти бэкендов.

### Продвинутое: readiness-эхо

Порт select + Watch: слушайте UDP-сокет, после готовности recvfrom и отошлите обратно — минимальный полный контур модели readiness (сверьте с примером port_select).

### Вызов: TCP-клиент в двух формах

Одну и ту же логику TCP-соединения напишите дважды: версия completion (IOCP/uring — подача) и версия readiness (select/epoll — готовность) — сравните формы кода и принадлежность буферов, соберите отчёт. Критерий приёмки: обе версии работают на поддерживающих бэкендах; дисциплина заморозки буферов соблюдена в версии completion (пул буферов); отчёт сравнивает объём кода и сложность двух моделей.
