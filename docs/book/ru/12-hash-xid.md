## Ориентация

Завершающая глава тома 2 ставит рядом две темы «идентичности»: **хеширование** сворачивает произвольные байты в отпечаток фиксированной ширины, а **XID** генерирует для каждой записи временно-упорядоченный уникальный идентификатор. Их объединяет одно слово — **детерминированность**: детерминированность хеша делает проверку и распределение по корзинам воспроизводимыми; детерминированность XID даёт «словарный порядок = порядок времени генерации». Глава одновременно проводит границу безопасности: хеш без ключа не стойкое к атаке коллизий; ключевой SipHash — правильный выбор для внешне видимых ключей (вроде ключей хеш-таблиц); «хранение пользовательских паролей» не ответ ни тем ни другим — это территория криптомодуля тома 8. Прочитав главу, вы выберете верный инструмент для трёх частых задач: проверка целостности данных, внешние ключи хеш-таблиц, распределённые первичные ключи.

## Введение

Три сценария. Первый: ежедневная синхронизация гигабайт индексных файлов — нужно знать «изменилось ли» — пересылать весь файл для сравнения слишком дорого; посчитайте отпечаток и отправьте 8 байт. Второй: сервер делает ключи хеш-таблицы из полей заголовков запроса, и атакующий конструирует коллизионные входы, вырождая хеш-таблицу в связный список — это hash-collision DoS, и ответ — дать хешу ключ, известный только вам. Третий: выбор первичного ключа для распределённой системы — автоприращаемые целые требуют координационного центра, полностью случайный UUID v4 фрагментирует индексы базы, а идентификатор со «временем впереди» естественно кластеризуется по порядку создания.

Три сценария соответствуют `xrtHash32/64` (детерминированные отпечатки), `xrtSipHash` (ключевой, стойкий к коллизиям) и XID (временно-упорядоченный уникальный идентификатор). Никто из них — не криптографический примитив; граница применения пришпилена в контрактах. Глава также закрывает том 2: детерминированные числа главы 10, детерминированные случайные последовательности главы 11 и детерминированные отпечатки этой главы вместе — три краеугольных камня «инженерной определённости»: всё, что записано в ассерты тестов, обязано быть воспроизводимо кроссплатформенно и сквозь время.

## Понятия

### Детерминированное хеширование: один вход — всегда один выход

`xrtHash32(pData, iSize)` и `xrtHash64` используют фиксированное семя по умолчанию — **одни и те же байты дают одно и то же значение когда угодно и в любом процессе**. Это предпосылка контрольных сумм, распределения по корзинам и ключей кэша. Когда нужна межпроцессная согласованность, но «не дать противнику предвычислить», берите версии с явным семенем `xrtHash32Seed` / `xrtHash64Seed`: многомашинное шардирование держит одно семя ради согласованности; внешние сценарии меняют семя, перемешивая таблицы предвычислений. Заметьте другую сторону «детерминированности»: **бесплючевой хеш вычислим кем угодно** — он доказывает «данные таковы», но не «от кого данные».

### Ключевое хеширование: SipHash-2-4

`xrtSipHash(pData, iSize, Key)` использует `xsipkey` (128-битный ключ, конструируется `xrtSipKey(低64, 高64)` — дословные токены). Не зная ключа, коллизии не построить — ключи хеш-таблиц над недоверенным входом обязаны идти через него. Потоковый интерфейс `xrtSipHashInit` / `Update` / `Final` обрабатывает данные, приходящие кусками (сетевые потоки, большие файлы), и **равнозначен по результату** одноразовой версии — тот же ключ и те же данные дают то же 64-битное значение в обеих позах. Жизненный цикл ключа следует дисциплине чувствительных данных главы 5: по завершении `xrtSecureZero`.

### XID: 192-битный идентификатор со временем впереди

```diagram flow
- Структура: 64-битная микросекундная метка + случайные и последовательные биты, всего 24 байта
- Текстовая форма: фиксированные 32 символа (в духе base62), входит прямо в URL / журналы / первичные ключи
- Упорядоченность: время впереди => словарный порядок = порядок времени генерации; индексо-дружелюбно, журналы сортируемы
- Ноль распределений: двоичный путь — семантика значения; текстовый путь пишет в буфер вызывающего
```

XID разрешает трилемму «распределённого первичного ключа»: координационный центр не нужен (время + случайность + последовательность генерируются локально), фрагментации нет (временной префикс кластеризуется), читаемо (32-символьный текст). `xrtXidMake` генерирует, `xrtXidWrite` пишет в буфер вызывающего (ёмкость `XID_TEXT_CAPACITY`, каноническая длина `XID_TEXT_SIZE` без хвостового нуля), `xrtXidParse` строго разбирает обратно в двоичное (любое отклонение длины или набора символов отказывает целиком и сообщает **позицию первого нелегального байта** — `xrtXidErrorOffset`), а `xrtXidTime` извлекает момент генерации за O(1) битовых операций. Пакетная генерация — `xrtXidMakeMany` (берёт сразу партию случайных байт, снижая накладные расходы системных вызовов); `xrtXidCompare` даёт стабильный полный порядок — базовый примитив сортировки и дедупликации. Сверьте разделение труда с четырьмя слоями главы 11: XID внутри использует безопасный источник случайности ради уникальности, но сам XID — не «секрет»: его появление в URL, журналах и базах безвредно; когда нужен непредсказуемый идентификатор (скажем capability-токен), берите `SecureText` главы 11.

### Таблица выбора

| Потребность | Инструмент | Не использовать |
| --- | --- | --- |

| Межпроцессно согласованное шардирование | `Hash64Seed` с одним семенем | —— |
| Внешние ключи таблиц над недоверенным входом | `xrtSipHash` (ключ хранится в секрете) | бесплючевые хеши |

### Предварительное напоминание: отпечаток — не шифрование

Перед прогоном примеров пришпилим частое заблуждение: хеширование — это **отпечаток**, не **шифрование**. Шифрование обратимо (с ключом можно восстановить); отпечаток нет (из 8 байт не восстановить файл в 8 ГБ); шифрование прячет содержимое, отпечаток публикует существование содержимого. «Посчитать отпечаток файла и удалить оригинал» — неисправимая ошибка: отпечаток служит только **сравнению**, не **хранению**. С этой границей в голове три группы примеров получают правильное прочтение.

## Примеры

### Полная программа: детерминированное хеширование и явное семя

Из примера репозитория `examples/hash/hash32/main.c`:

```embed path="examples/hash/hash32/main.c" title="examples/hash/hash32/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/hash/hash32/main.c -lws2_32 -liphlpapi
default: 9590B597
seeded : 064A210B
```

**Что только что произошло.** (1) `sizeof(sKey)-1` явно исключает хвостовой ноль — вход хеша бинарно-безопасная байтовая строка, нулевое завершение — лишь конвенция C-строк; один лишний ноль — другие данные и другой отпечаток. (2) Семя по умолчанию выводит `9590B597` — стабильно кроссплатформенно и межверсионно: что вы посчитали сегодня, совпадает со вчерашним CI. (3) Те же данные с другим семенем дают совершенно иной отпечаток — семя участвует в той же детерминированной функции, и суть «защиты от предвычислений» в том, что противник не знает вашего варианта функции.

### Полная программа: сведение одноразового и потокового SipHash

Из `examples/hash/variants/main.c` — проверка равнозначности двух поз:

```embed path="examples/hash/variants/main.c" title="examples/hash/variants/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/hash/variants/main.c -lws2_32 -liphlpapi
seed64: 1E3C0D5C77AC4C64
sip:    21D9F0C356D09D0A
stream-equal=yes
```

**Что только что произошло.** (1) `xsipkey` строится из двух 64-битных слов — 128-битное пространство ключей, ключ из безопасной случайности (глава 11), не зашит в код. (2) Одноразовый `xrtSipHash` на восемнадцатибайтовом входе даёт `21D9F0C356D09D0A`. (3) Потоковая версия скармливает те же данные **двумя кусками** (`Update` дважды), и результат `Final` полностью совпадает с одноразовым — третья строка `stream-equal=yes` есть важнейший ассерт главы: нарезка на куски не влияет на отпечаток, сетевая потоковая обработка и цельноблочное вычисление взаимно сверяемы. (4) Строка `Hash64Seed` показывает типовое употребление сеяного детерминированного хеша: отпечаток `"user:42"` с семенем `0x1234` стабилен — многомашинное шардирование маршрутизирует по этому значению по модулю, и пока семя неизменно, маршрутизация не меняется при масштабировании.

### Полная программа: генерация XID, текстовизация, разбор, извлечение времени

Из `examples/id/xid/main.c`:

```embed path="examples/id/xid/main.c" title="examples/id/xid/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/id/xid/main.c -lws2_32 -liphlpapi
XID: V-OPfAm6...（32 字符定长文本，示例）
Unix microseconds: 17...(微秒时间戳)
```

**Что только что произошло.** (1) Одна линия: `Make` генерирует → `Write` текстовизирует → `Parse` разбирает обратно в двоичное → `Time` извлекает момент — четыре функции образуют цикл чтения-записи XID. (2) Длина входного представления `Parse` — `XID_TEXT_SIZE` (без хвостового нуля): любое отклонение длины или символа отказывает целиком, а `xrtXidErrorOffset` извлекает из ошибки позицию первого нелегального байта — ошибка несёт собственную локацию, разбирать сообщения не нужно. (3) Временная метка вывода меняется с моментом запуска, но свойство **префиксного возрастания** неизменно: напечатанный раньше XID словарно меньше напечатанного позже.

## Контракты

- **Детерминированность**: `Hash32/64` и SipHash с одним входом и ключом всегда дают один вывод, стабильно кроссплатформенно и межверсионно (нарезка на куски не влияет).
- **Граница безопасности**: беспключевые хеши не стойки к атаке коллизий; внешние ключи таблиц — SipHash с ключом в секрете; **хранение паролей не входит в главу** (хеширование паролей тома 8).
- **Дисциплина ключа**: `xsipkey` — чувствительные данные; генерация из безопасной случайности, по завершении `xrtSecureZero`.
- **Упорядоченность XID**: словарный порядок = порядок времени генерации; `Compare` даёт стабильный полный порядок; **направление единичного сравнения** при быстрых подряд идущих генерациях не является обещанием (микросекундные часы решают очерёдность).
- **Строгость разбора**: `Parse` принимает только канонический текст фиксированной длины; при неудаче вывод не пишется, смещение ошибки читается из ошибки потока.
- **Пакетная генерация**: `MakeMany` генерирует сразу партию в непрерывном хранилище, снижая число системных вызовов.

## Ловушки

### Ловушка 1: бесплючевой хеш как внешний ключ хеш-таблицы

Симптомы: серверная хеш-таблица рушится по производительности под специально сконструированными запросами (hash-collision DoS); чем длиннее таблица, тем заметнее деградация.

Причина: хеш-функция с семенем по умолчанию публична — атакующий может офлайн построить массу входов с одним отпечатком, вырождая вашу таблицу в связный список.

```c bad
uint64 iKey = xrtHash64(Header.Value, Header.Size);  /* публичная функция */
Bucket = TableFind(iKey);                             /* коллизии конструируемы */
```

```c good
uint64 iKey = xrtSipHash(Header.Value, Header.Size, gTableKey);  /* ключ в секрете */
Bucket = TableFind(iKey);
```

### Ловушка 2: разбор XID считает хвостовой ноль в длину

Симптомы: при чтении XID обратно из текста (файл, параметр URL) разбор падает, смещение ошибки указывает за последнюю ячейку; пошаговая отладка показывает «со строкой всё в порядке».

Причина: вход `Parse` — представление **ровно из 32 символов** (`XID_TEXT_SIZE`); передача `strlen+1` или использование `XID_TEXT_CAPACITY` как длины превращает хвостовой ноль в 33-й символ.

```c bad
char arrText[XID_TEXT_CAPACITY];
load(arrText);
if ( !xrtXidParse((xstrview){ arrText, XID_TEXT_CAPACITY }, &Value) ) {
	/* длина 33: верный отказ — хвостовой ноль не часть текста */
}
```

```c good
char arrText[XID_TEXT_CAPACITY];
load(arrText);
if ( !xrtXidParse((xstrview){ arrText, XID_TEXT_SIZE }, &Value) ) {
	size_t iOffset = 0;
	xrtXidErrorOffset(xrtGetError(), &iOffset);   /* позиция первого нелегального байта */
}
```

## Упражнения

### Базовое: сведение отпечатков

Посчитайте по одному и тому же куску текста `Hash32` и `Hash32Seed(…, 0x12345678)`, напечатайте оба значения; поменяйте один байт и пересчитайте, убедившись, что отпечаток меняется полностью (эффект лавины на ощупь). Посчитайте и разность двух изменённых значений — в среднем переворачивается около половины бит.

### Продвинутое: потоковый верификатор

Напишите `hash_stream(path)`: читайте файл кусками (по 4 КБ) в потоковый интерфейс SipHash и возвращайте отпечаток; тот же файл сверьте одноразовым интерфейсом при цельном чтении. Подсказка: обе позы обязаны совпасть — это источник уверенности для инкрементальной проверки.

### Вызов: связка и сортировка журналов

Напишите маленький инструмент: сгенерируйте 100 XID (партия `MakeMany`), сперва вперемешку сложите в массив, затем отсортируйте по `Compare` и напоследок извлеките времена, ассертя монотонную неубываемость; сымитируйте два журнала, связанных одним текстом XID (`Parse` обратно в двоичное, затем `Equal`). Критерий приёмки: все ассерты после сортировки проходят; два двоичных значения одного текста дают `Equal` истину, с другим XID — ложь.

## Шпаргалка

| Тема | Краткая справка |
| --- | --- |
| Детерминированные отпечатки | `Hash32` / `Hash64` с семенем по умолчанию; кроссплатформенно стабильно |
| Явное семя | `Hash32Seed` / `Hash64Seed`: согласованное шардирование или защита от предвычислений |
| Стойкость к коллизиям | `SipHash` + ключ в секрете; обязателен для внешних ключей таблиц |
| Потоковость | `SipHashInit/Update/Final` равнозначен одноразовому |
| Структура XID | 24 байта = время впереди; текст фиксированно в 32 символа |
| Цикл XID | `Make/Write/Parse/Time`; ошибка разбора несёт смещение |
| Упорядоченность | словарный порядок = порядок генерации; `Compare` стабильный полный порядок |
| Хранение паролей | ни одна функция главы — это территория криптохеширования паролей тома 8 |
