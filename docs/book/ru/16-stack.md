## Ориентация

Стек — мельчайший контейнер информатики, но XRT даёт ему четыре варианта — потому что потребность «стек» в разных ограничениях выглядит по-разному. Вывод вперёд: в подавляющем большинстве сцен берите динамический стек `xstack`; подтверждены «глубина известна + горячий путь» — фиксированный стек; нужна долгосрочная стабильность адресов элементов — блочный; храните ссылки на объекты — указательная разновидность. Задача главы — сделать этот выбор выводимым. **Динамический стек** `xstack` давит сколько угодно; **фиксированный стек** `xfixedstack` привязывается к буферу вызывающего с нулевым выделением на всём пути; **блочный стек** `xblockstack` при росте **не меняет адреса уже размещённых элементов**; указательная разновидность хранит `ptr`. Двумя полными программами глава разбирает два инженерных ограничения — «нулевое выделение» и «стабильный адрес», даёт таблицу выбора из четырёх и сводит механический приём «рекурсия → явный стек» в таблицу соответствий — это базовое движение безопасного парсера. Рекурсивно-нисходящие парсеры и обходы с возвратом — сквозной прикладной сценарий главы — они же главная структура данных главы 31 и второй половины тома 3. Читая, держите в голове конкретный вопрос: «что случится с моим стеком, если ввод вложится на десять тысяч уровней?» — у каждого варианта свой ответ, и в этом весь выбор.

## Введение

Рекурсивно-нисходящему парсеру нужно сохранять на каждом уровне рекурсии «текущую позицию сканирования» — этот сценарий снова возникнет в парсере JSON главы 31, где вы увидите, как реальные кадры соответствуют здешней имитации. Локальная переменная на стеке вызовов? Глубина рекурсии определяется вводом (глубина вложенности из границ ресурсов главы 3), переполнение стека — поверхность атаки. Заменить рекурсию рукописным циклом? Тогда нужен явный стек кадров. Как выбрать его ограничения: кадр разбора в десятки байтов, максимальная глубина ограничена границей ресурсов (скажем 128) — **глубина известна, путь горячий**: фиксированный стек на стековом массиве, нулевое кучное выделение на всём пути. А при обходе дерева, которое пользователь в любой момент меняет, не должны ли адреса узлов, удерживаемые в пути, инвалидироваться ростом стека? Нет — рост инвалидирует адреса **собственных элементов стека**, не узлов дерева; но если в стеке лежат «указатели на рабочие зоны внутри стека», стабильные адреса блочного стека становятся жёсткой потребностью.

Две сцены — два ответа: в этом смысл существования семейства — **ограничение ведёт выбор**, а не один универсальный стек на все случаи. Развернём «рекурсию в явный стек» ещё на шаг: любой рекурсивный алгоритм механически переписывается в «цикл + явный стек» — «уровень вызова функции» становится «push», «return» становится «pop». После переписывания потолок глубины переходит из системного стека вызовов (неуправляем) в ёмкость вашего стека (явно управляемая) — именно поэтому границы ресурсов главы 3 вообще осуществимы: парсер заявляет «максимальная глубина 128», ёмкость стека кадров готовится по 128, и сверхглубокий ввод получает отмену на 128-м уровне (отвергается), а не прорезает стек процесса.

## Понятия

### Четыре варианта в одной таблице

| Вариант | Хранилище | Рост | Адреса элементов | Применение |
| --- | --- | --- | --- | --- |
| `xstack` динамический | собственный кучный буфер | авторасширение | инвалидируются при росте | универсальное умолчание |
| `xfixedstack` фиксированный | буфер вызывающего | отказ при заполнении | стабильны на период привязки | глубина известна, нулевое выделение на горячем пути |
| `xblockstack` блочный | цепочка блоков | добавление блока без переезда | **никогда не инвалидируются** | адреса элементов нужны надолго |
| указательный | те же три контейнера + элемент `ptr` | как у носителя | сам указатель стабилен | хранение ссылок на объекты |

### Жизнь одного стека кадров

На примере стека кадров парсера все четыре варианта в одном рабочем потоке:

```diagram flow
- Старт: Init привязывает хранилище - фиксированный стек к локальному массиву, динамический с нуля
- Кадр в стек: Push пишет копию элемента - фиксированный без выделений, динамический расширяется по надобности
- Возврат: Pop выбрасывает последний кадр - LIFO гарантирует форму рекурсии
- Границы: Push в полный стек не удается (фиксированный) / Pop из пустого не удается (у всех)
- Финал: Unit возвращает - фиксированный не трогает буфер вызывающего, динамический освобождает собственный
```

### Контракт нулевого выделения

`Init` фиксированного стека привязывает дескриптор к буферу вызывающего (локальный массив, статическая память, кусок арены — что угодно), после чего Push/Pop идут целиком в этой памяти — **никаких выделений**, и контрактный тест `_noalloc` в репозитории это гарантирует (сестра системы внедрения отказов главы 6: одна доказывает «пути отказа корректны», другая — «путь без выделений действительно существует»). Push в полный стек и Pop из пустого — обе границы дают явные ошибки, без выхода за границы и без падений.

### Стабильные адреса: блочный стек

Рост динамического стека — переезд целиком, все указатели на элементы инвалидируются. Когда это становится проблемой? Когда «элементы стека ссылаются извне» — каноническая форма «стек как рабочая зона»: рабочий кадр каждого уровня обратен кадрам более глубоких уровней (указатель на родителя в дереве, вышележащий контекст парсера), и переезд отправляет все эти обратные ссылки в висячие. Блочный стек `xblockstack` расчленяет хранилище в цепочку блоков: при росте добавляется новый блок, а **старые остаются на месте** — адрес элемента, взятого из стека, действителен на всём жизненном цикле стека. «Внутри стека ещё и указатели на элементы стека» звучит редко, но в паттерне «стек как рабочая зона» (рабочий кадр каждого уровня рекурсии цитируется более глубокими) это живая потребность. Цена: обход через блоки, константа чуть выше.

### Семантика LIFO и парирование ошибок

Pop из пустого стека возвращает `false` и оставляет запись в поточном слоте ошибки — в примере после цикла `xrtClearError` стирает это «ожидаемое неудачей». Это бытовое применение дисциплины «успех не чистит слот» главы 4: **потоком управляет возвращаемое значение, слот ошибки служит диагностике, остаточную ошибку после достижения границы активно стираем** — не позволяйте утечке проникать в следующую логику.

## Примеры

### Первая полная программа: рабочий стек без выделений

Из репозиторного образца `examples/containers/fixed_stack/main.c`, имитация стека кадров парсера:

```embed path="examples/containers/fixed_stack/main.c" title="examples/containers/fixed_stack/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/containers/fixed_stack/main.c -lws2_32 -liphlpapi
function=3 position=30
function=2 position=20
function=1 position=10
```

**Что только что произошло.** (1) `pStorage[8]` — физическое хранилище стека, обычный локальный массив; параметры `xrtFixedStackInit` — «дескриптор, буфер, ёмкость в байтах, размер элемента». (2) После трёх кадров и выборки вывод идёт в порядке LIFO `3/2/1` — «последним пришёл, первым ушёл» — вся семантика стека и самая «запросто» ломаемая (если при работе со стеком вам нужен порядок очереди — вам нужна очередь главы 21). (3) При пустом стеке Pop возвращает `false` и завершает цикл, `xrtClearError` стирает запись о пустоте — см. «парирование ошибок» выше. (4) Ёмкость 8, положили 3 — девятый Push не удастся, а не выйдет за границу: **потолок — линия обороны, данная ёмкостью**; в связке с границами ресурсов главы 3 спецификации вида «глубина разбора ≤ 128» получают физического носителя. Заодно счёт: 128 кадров × 16 байт = 2 КБ — один стековый массив вмещает всё рабочее состояние, даже арена (глава 7) не нужна; вот как выглядит «нулевое выделение» в мемориальной книге.

### Вторая полная программа: стабильные адреса блочного стека

Из `examples/containers/block_stack/main.c` — проверка неизменности адресов элементов в процессе роста, машинное свидетельство обещания «никогда не инвалидируются»:

```embed path="examples/containers/block_stack/main.c" title="examples/containers/block_stack/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/containers/block_stack/main.c -lws2_32 -liphlpapi
count=21 blocks=6 root=100 stable=yes
```

**Что только что произошло.** (1) Вложено 21 элемент (включая корневое значение 100), хранилище само раскололось на 6 блоков — рост без переезда. (2) Програмна записала по пути адрес некоторого элемента, а после полной укладки перечитала и проверила доступность содержимого: `stable=yes` — эмпирическое доказательство «адреса элементов не инвалидируются никогда». (3) Контрольный опыт стоит проделать руками: та же последовательность на динамическом стеке — адрес давно сменил мир. Когда это свойство дорого? Когда элементы стека цитируются структурами вне стека — например, древесные алгоритмы, где рабочий кадр ссылается на родительский.

### Таблица соответствий стека и рекурсии

При переписывании рекурсивной функции в явный стек перенос аргументов имеет фиксированный приём: «локальное состояние каждого уровня» функции ужимается в структуру кадра (тип элемента); «рекурсивный вызов» становится «push + continue»; «возврат на уровень выше» становится «pop»; «входные параметры» становятся «начальным кадром». Сопоставьте: таблица локальных переменных → поля кадра, глубина стека вызовов → Count стека, риск переполнения стека → потолок ёмкости (явный, настраиваемый, отказывающий). Эта таблица будет прямо использована в парсере главы 31 и в обходах AVL тома 3 — рекурсия в явный стек не упражнение, а линия безопасности парсера перед недоверенным вводом.

## Контракты

- **Парность**: `Init`/`Unit` в паре; `Unit` фиксированного стека не освобождает буфер вызывающего (он ему никогда не принадлежал).
- **Нулевое выделение**: после привязки фиксированный стек никогда не выделяет на Push/Pop; полный стек и пустой стек — обе границы с явными ошибками.
- **Время жизни адресов**: рост динамического инвалидирует; фиксированный стабилен на период привязки; блочный — никогда не инвалидирует; выбирая, сперва спросите «будут ли элементы стека цитироваться извне».
- **Парирование ошибок**: потоком правит возвращаемое значение; остаточную ошибку границы стираем по использовании (`xrtClearError`).
- **Указательная разновидность**: указательный стек ведает только слотами указателей; владение и освобождение элементов — целиком на вызывающем.

## Ловушки

Две ловушки главы: одна про время жизни адресов (одного корня с ловушкой 1 массивов главы 14 — судьба непрерывного хранения), другая про разрыв между ёмкостью и спецификацией. Первая — техническая, вторая — инженерная; инженерные ловушки обычно дороже.

### Ловушка 1: использование указателя на элемент после расширения динамического стека

Симптом: висячий указатель того же семейства, что у массивов, в коде вида «при push заодно запомнил адрес элемента в стеке».

Причина: элементы динамического стека живут в его собственном буфере; рост — переезд целиком.

```c bad
exampleframe* pTop = (exampleframe*)xrtStackPeek(&tFrames, 0);
xrtStackPush(&tFrames, &tNext);      /* расширение с переездом */
pTop->Position = 42;                  /* висяк */
```

```c good
xrtStackPush(&tFrames, &tNext);      /* сперва push */
exampleframe* pTop = (exampleframe*)xrtStackPeek(&tFrames, 0);
/* нужен долгосрочно стабильный адрес: смените на xblockstack или xfixedstack */
```

### Ловушка 2: ёмкость фиксированного стека по принципу «сейчас хватает»

Симптом: пришёл ввод с более глубокой вложенностью — Push терпит неудачу посреди разбора; путь обработки ошибки принял полурасобранное состояние за полное.

Причина: потолок фиксированного стека — физический факт, заданный при создании; «сейчас хватает» — не спецификация; спецификация — границы ресурсов главы 3 (`iMaxDepth`).

```c bad
exampleframe pStorage[4];            /* худший тест - 3 уровня - взрыв в первый же день в проде */
xrtFixedStackInit(&tFrames, pStorage, sizeof(pStorage), sizeof(exampleframe));
```

```c good
exampleframe pStorage[128];          /* выровнен с iMaxDepth границ ресурсов */
xrtFixedStackInit(&tFrames, pStorage, sizeof(pStorage), sizeof(exampleframe));
/* до разбора проверить глубину входа <= 128 (один из трёх шлюзов границ), сверх - отвергнуть целиком */
```

## Упражнения

### Базовое: три кадра LIFO

Воспроизведите главный образец: три кадра в стек, все выброшены, печать в порядке выброса (порядок перепутан — значит вам нужна очередь, а не стек; глава 21 ждёт); затем проверьте, что четвёртый Pop возвращает `false` и `Count` обнуляется.

### Продвинутое: сопоставитель скобок

Скобочный баланс на фиксированном стеке: сканируйте `((a)(b))`, левую скобку кладите с позицией, правую — выбрасывайте пару; правая скобка при пустом стеке или непустой стек в конце — обе сообщают позицию ошибки. Подсказка: элемент стека хранит «позицию + вид скобки», ёмкость — по максимальной глубине вложенности.

### Вызов: сравнение переездов двух стеков (квантификация стабильности адресов)

На одном входе (1000 элементов, каждые 100 — запись адреса вершинного элемента) прогоните динамический и блочный стеки, выведите число изменений адреса. Критерии приёмки: у динамического адрес меняется несколько раз, у блочного — всегда ноль; затем измерьте суммарное время push в обеих версиях и запишите квантифицированный вывод о «цене стабильного адреса».

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Четыре варианта | динамический `xstack` (универсальный) / фиксированный `xfixedstack` (нулевое выделение) / блочный `xblockstack` (стабильные адреса) / указательный (ссылки) |
| Фиксированный стек | `Init(句柄, 缓冲, 字节数, 元素大小)`; ёмкость и потолок глубины границ ресурсов — один источник |
| Границы | Push в полный не удается, Pop из пустого не удается; потоком правит возвращаемое значение, у обеих границ явный класс ошибки |
| Время жизни адресов | рост инвалидирует (динамический) / стабильно на период привязки (фиксированный) / никогда (блочный) |
| Гигиена ошибок | остаточную ошибку границы стираем `xrtClearError` |
| Порядок выбора | нулевое выделение — сперва фиксированный; стабильность адреса — блочный; без ограничений — динамический |
| Выравнивание ёмкости | ёмкость фиксированного стека = потолок глубины границ ресурсов, оба числа из одного источника (одна константа, две ссылки) |
| Формула переписывания | рекурсия в явный стек: уровень вызова = push, return = pop; глубина переходит из системного стека в явную ёмкость |
| Гигиена ошибок | Pop из пустого возвращает false и правит циклом; остаточную ошибку активно чистим, не течёт в следующую логику |
