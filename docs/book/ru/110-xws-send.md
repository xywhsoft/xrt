## Ориентация

Глава 109 утвердила три состояния владения отправкой (copy/ref/take); эта глава проходит путь отправки до конца. **writer** (`xwswriter`): потоковая фрагментация длинных сообщений — `xrtWsConnBeginText` открывает, `WriterWrite` идёт кусками, `WriterFinish` завершает; заголовок и состояние сжатия writer имеют стабильные размеры (содержимое не меняет раскладку сетевого объекта); **сжатая отправка**: writer сжатия `BeginTextCompressed` (форма permessage-deflate, согласованного в главе 96, на отправляющей стороне — при включённом сжатии **действует та же семантика противодавления и владения**); **матрица владения**: copy/ref/take × text/binary × синхронно/Future — полная комбинация; «девять видов отправки» строки 3 обхода и есть эта матрица. Отказы отправки соблюдают атомарное владение: непринятое остаётся у вызывающего, после приёма освобождает соединение.

## Введение

Отправить снимок журнала на 10 МБ: путь copy сперва копирует 10 МБ (память ×2, потом очередь); путь ref требует «один непрерывный блок памяти» (снимок и так один — подходит); но что если снимок **генерируется потоково** (ещё не накоплен)? Путь writer: генерируешь и тут же `WriterWrite` — каждый кусок идёт прямо в поток кадров, память постоянна, фрагментация автоматична (опкод первого кадра, continuation, FIN — автоматизация правил фрагментации главы 94 на отправке). Шаг дальше: снимок — сильно повторяющийся текст, сжатие экономит 90% — `BeginTextCompressed` открывает writer сжатия, интерфейс производителя не меняется (всё те же Write/Finish), сжатие происходит внутри writer — **«потоковость» и «сжатие» комбинируются ортогонально**.

Инженерные детали writer на высоте: «заголовок и состояние сжатия стабильны по размеру; hover, события или динамическое содержимое не меняют раскладку сетевого объекта» — форма памяти сетевого объекта предсказуема (экономика Worker главы 63, продлённая на слой раскладки); атомарность пути отказа (запись упала на середине — принятые куски освобождает соединение, непринятые ваши) позволяет восстанавливаться после ошибек без угадывания состояния.

## Понятия

### Жизненный цикл writer

```diagram state
простой -> запись: BeginText/BeginBinary/BeginTextCompressed (на Worker-владельце соединения)
запись -> запись: WriterWrite x N (любая разбивка - протокольная фрагментация автоматична)
запись -> завершено: WriterFinish (последний кусок + FIN + конец сообщения)
запись -> отброшено: WriterDestroy (путь отказа для незавершённого сообщения)
```

Три входа соответствуют типу сообщения и сжатию: `BeginText`/`BeginBinary` (обычные), `BeginTextCompressed`/`BeginBinaryCompressed` (сжатые — требуют, чтобы соединение согласовало permessage-deflate). **Границы кусков не связаны с границами кадров**: вы пишете Write в ритме бизнеса, writer кадрует по протокольной политике — большие куски режутся автоматически, маленькие могут склеиваться; FIN появляется только на Finish (ровно один финал на сообщение).

### Writer сжатия: та же семантика

При включённом сжатии writer несёт внутри deflater (интеграция `xwsdeflater` главы 96 в соединение): каждый кусок сжимается в поток кадров, RSV1 помечает только первый кадр, no-context-takeover сбрасывает словарь на границах сообщений по согласованию — **интерфейс Write/Finish для вызывающего полностью идентичен обычному writer**. «При включённом сжатии держится та же семантика противодавления и владения» — AGAIN всё тот же AGAIN, освобождение всё то же ровно-один-раз — поведение объектов сжатия главы 96, без потерь перенесённое на путь отправки соединения.

### Матрица владения и атомарное правило

| Форма | copy | ref | take |
| --- | --- | --- | --- |
| При постановке | копирует немедленно | запоминает ссылку, ноль копий | принимает выделенную память |
| В очереди | соединение держит копию | исходный блок заимствован | соединение владеет единолично |
| Готово/отказ | - | release ровно один раз | соединение освобождает |
| Отказ до приёма | вызывающий ничего не теряет | остаётся у вызывающего | возвращается вызывающему |

Девять синхронных отправок (обход) = три состояния владения × {text, binary, ping/управление}; формы Future добавляют измерение способа ожидания. **Правило выбора**: короткие сообщения copy (цена копии пренебрежима); статические/разделяемые большие блоки ref (одно выделение, много отправок — примитив широковещательной рассылки главы 111); уже выделенная передача take (экономия последней копии).

### Writer и цепочки буферов

Формы take/buffer могут передать соединению **цепочку сетевых буферов XRT** (глава 64) напрямую — сгенерированная цепочка кусков попадает в очередь отправки без «сплющивающего копирования»; заголовок кадрирования writer собирается с головой цепочки одной Vec-отправкой (глава 67). Нулевое копирование пути отправки распространяется с «ссылок» на «цепочки».


```term
$ gcc -O1 -DXRT_MODULE_ALL -I extlibs/xws/single -include xws.h impl.c extlibs/xws/examples/websocket/writer/main.c -lws2_32 -liphlpapi
WebSocket Writer example is ready
```

**Что только что произошло.** (1) `xrtWsConnBeginText(连接)` (соединение) открывает текстовый writer; цикл зовёт `WriterWrite` на каждый кусок, **последний кусок идёт через `WriterFinish`** (запись + FIN за один вызов) — стандартная форма цикла writer. (2) Отказ на середине — `WriterDestroy`: путь отказа для незавершённого сообщения (соединение остаётся рабочим; не отправлено только это сообщение). (3) Сигнатура функции берёт массив кусков — образец имеет шаблонную форму (main проверяет готовность); реальные вызовы происходят в обратных вызовах Worker (дисциплина главы 109). **Почему writer, а не накопить-и-отправить**: куски приходят из потоковой генерации (курсоры/конвейеры/дампы) — накопление целого сообщения и есть пик памяти; writer развязывает «ритм генерации» и «ритм отправки».

```embed path="extlibs/xws/examples/websocket/writer_deflate/main.c" title="extlibs/xws/examples/websocket/writer_deflate/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I extlibs/xws/single -include xws.h impl.c extlibs/xws/examples/websocket/writer_deflate/main.c -lws2_32 -liphlpapi
（压缩 writer 就绪自检通过后正常退出）
```

**Что только что произошло.** (1) Единственное отличие — вход: `xrtWsConnBeginTextCompressed`; дальше цикл Write/Finish/Destroy **дословно совпадает** с обычным writer. «Сжатие — свойство writer, а не переписывание процесса отправки» — код вызывающего получает сжатие без единой правки. (2) Предусловие: соединение согласовало permessage-deflate (слой согласования главы 96, конфигурация маршрутизации главы 112); открытие writer сжатия на несогласованном соединении падает на входе. (3) Семантику сжатия гарантирует writer: RSV1 на первом кадре, сброс словаря по согласованию, потолок распаковки у противоположной стороны — **отправляющей стороне не нужно вникать в детали правил сжатия главы 96**; согласование зафиксировало поведение — поведение определено. Вместе с `writer_ref` (вариант writer для ссылочных кусков — потоковый финал статичных больших блоков) три образца пути отправки образуют полную матрицу.

## Контракты

- **Жизненный цикл writer**: Begin (три входа: text/binary/compressed) → Write×N → Finish (FIN) или Destroy (отказ) — одно из двух обязательно; вызов на Worker-владельце соединения.
- **Развязка кусок-кадр**: ритм кусков вызывающего не связан с протокольным кадрированием; FIN ровно один раз; управляющие кадры нельзя вставлять внутрь сообщения своего writer (отправная сторона правила обхода главы 94 — чтобы послать Ping, сперва Finish или через вход уровня соединения).
- **Writer сжатия**: отличие — только вход; интерфейс Write/Finish как у обычного writer; предусловие — согласование; RSV1/словарь/потолок гарантирует writer.
- **Стабильные размеры**: заголовок и состояние сжатия writer фиксированы — раскладка сетевого объекта не зависит от содержимого.
- **Атомарность владения**: непринятое остаётся у вызывающего, после приёма соединение освобождает ровно один раз; take может передавать цепочки буферов (голова цепочки достигает нулевого копирования).
- **Выбор трёх состояний**: короткое = copy; статичное/разделяемое = ref; передача выделенного = take — девять синхронных комбинаций плюс семейство Future.
- **Единое противодавление**: записи writer также ограничены отметками — при AGAIN кусок не принят (можно повторить в точности).
- **Обрезка**: `websocket_writer`/`websocket_deflater` независимы — соединения без writer не платят ничего.

## Ловушки

### Ловушка 1: writer открыт и не закрыт (утечка или половина сообщения)

Симптом: на соединении больше нельзя отправить новое сообщение — предыдущий writer всё ещё висит (сообщение не завершено); или забыли Destroy — состояние writer занимает соединение.

Причина: writer — **эксклюзивная транзакция отправки** на соединении: после Begin обязательно Finish (отправлено) или Destroy (отказ) — третьего состояния «пусть полежит» нет.

```c bad
pWriter = xrtWsConnBeginText(pConn);
write_some(pWriter);
/* Finish/Destroy забыты: отправочная сторона соединения заперта */
```

```c good
pWriter = xrtWsConnBeginText(pConn);
if ( pWriter == NULL ) { return XNET_RESULT_ERROR; }
for ( ... ) {
	if ( WriterWrite(...) != XNET_RESULT_OK ) {
		xrtWsWriterDestroy(pWriter);   /* путь отказа обязателен */
		return Result;
	}
}
return xrtWsWriterFinish(pWriter, LastChunk);
```

### Ловушка 2: writer сжатия на несогласованном соединении

Симптом: `BeginTextCompressed` возвращает NULL — соединение не согласовало permessage-deflate, вход сжатия падает сразу.

Причина: сжатие — **способность после согласования** (глава 96): согласование расширений при установке соединения решает, есть ли сжатие на этом соединении. «Хочу сжать» на отправке не создаёт способность из воздуха.

```c bad
/* deflate не предлагался при согласовании */
pWriter = xrtWsConnBeginTextCompressed(pConn);  /* NULL: способности нет */
```

```c good
/* конфигурация сервера/клиента объявляет deflate (глава 112: маршрутизация/конфигурация клиента) */
/* после успешного согласования выбирать вход по способности соединения */
if ( conn_deflate_negotiated(pConn) ) {
	pWriter = xrtWsConnBeginTextCompressed(pConn);
} else {
	pWriter = xrtWsConnBeginText(pConn);   /* откат на обычный */
}
```

### Ловушка 3: ref-блок тронут после release

Симптом: редкие падения после обратного вызова release — вызывающий снова читал/писал этот блок после release.

Причина: контракт ref — «после release владение полностью перешло» — обратный вызов release есть последний шаг. Сохранение между обратными вызовами (дисциплина представлений главы 109) в сочетании с временем release легко споткнуться на асинхронных путях.

```c bad
xrtWsConnBinaryRef(pConn, &Ref);
/* ... где-то на асинхронном пути ... */
use(Buf);   /* release мог уже произойти: висячий */
```

```c good
/* после release блок не трогать; для переиспользования возвращать его в пул внутри обратного вызова release
   (глава 22) и брать снова только через пул */
static void releaseToPool(ptr pCtx, cbytes pData, size_t iSize) {
	pool_return((pool*)pCtx, (ptr)pData);   /* вернуть, а не освободить */
}
```

## Упражнения

### Базовое: сравнение трёх входов

Одно и то же многочастное содержимое отправьте через BeginText/BeginBinary/BeginTextCompressed (на соединении с согласованным deflate); противоположная сторона проверяет по типу и сжатию. Критерии приёмки: все три сообщения декодируются на той стороне в то же содержимое; сжатая версия заметно меньше по байтам канала (измерить).

### Продвинутое: конвейер генерация → отправка

Источник-курсор (имитация 4 КБ в миллисекунду) отправляет напрямую через writer: Write следует ритму генерации, Finish завершает у источника; измерить пиковую память. Критерии приёмки: пик не зависит от объёма (уровня МБ); AGAIN на середине обрабатывается без потери кусков (семантика повтора).

### Вызов: сравнение стоимости трёх состояний

Одно и то же сообщение 1 МБ отправьте по 100 раз в каждом из copy/ref/take: посчитать выделения, скопированные байты и время (инструменты главы 6). Критерии приёмки: три набора данных сходятся с выводом контракта (copy копирует, ref ноль копий одно выделение, take ноль копий ноль выделений); написать вывод выбора для вашего сценария.
