## Ориентация

Исполнитель — **абстракция ресурса исполнения**: задачи подаются ему, а не открывают потоки напрямую — пул-переиспользование и перенос работы (work stealing) реализованы на этом слое; бизнес видит только **подачу и завершение**. Двойная форма задач: **подал и забыл** (`xrtExecutorSubmit` — исполнилось и всё, без возвращаемого значения; тысяча задач-счётчиков образца executor — эта форма) и **Future-задачи** (`xrtTaskSubmit` возвращает Future — валюта главы 57); **пакетный интерфейс** (SubmitBatch — амортизация синхронных расходов); **протокол остановки** (`xrtExecutorClose` прекращает приём + `Wait` осушает — изоморф закрытию очереди главы 21). Пул задач (xtaskpool) файловой асинхронности главы 47 — специализированная форма семейства исполнителей; эта глава разбирает общую версию.

## Введение

Модель «каждой задаче по потоку» банкротится в трёх местах. **Масштаб**: десять тысяч конкурентных задач = десять тысяч потоков = взрыв памяти (по 1 МБ стека) — пул-переиспользование гоняет десять тысяч задач на нескольких десятках потоков. **Накладные расходы**: создание потока — системный вызов миллисекундного порядка; у частых коротких задач расходы превышают саму задачу; подача в пул — микросекунды (постановка в безблокировочную очередь). **Управление**: у тысячи голых потоков остановка, ожидание и сбор ошибок каждый сам по себе; исполнитель даёт этой пачке потоков единый протокол остановки Close+Wait и единую статистику.

Формула ценности исполнителя: **переиспользование потоков (масштаб) + лёгкая подача (расходы) + единая остановка (управление)**. Со стороны бизнеса меняется лишь замена «открыть поток» на «подать задачу» — в главе 47 вы уже так делали (пул задач файловой асинхронности); эта глава проясняет полный интерфейс исполнителя и его протокол остановки.

## Понятия

### Двойная форма задач

```diagram flow
- Забытая задача: xrtExecutorSubmit(исполнитель, функция, данные) - без возвращаемого значения
- Future-задача: xrtTaskSubmit(пул_задач, функция, данные, токен_отмены) -> Future
- Пакет: SubmitBatch / пакетные варианты TaskSubmit - группу в очередь за один раз
- Выбор: нужен результат/отмена -> форма Future; чистый побочный эффект (счётчики, уведомления, очистка) -> забыть
```

**«Забыть» и Future — не иерархия рангов**, а развилка потребностей: задачи с чистым побочным эффектом (сброс журналов на диск, обновление кеша, статистическая отчётность) с Future — расточительство (никто не ждёт); задачи с результатом (вычисление, запрос) — обязательно Future (модель доставки главы 57). Параметр токена отмены естественно живёт в Future-форме (дерево главы 53 прошивает пул задач).

### Минимальный контур подачи-завершения

`xrtExecutorCreate(配置)` (конфигурация) строит экземпляр (число потоков и глубина очереди настраиваемы — глубина это клапан противодавления: заполнено — подача отказывает, а не копится бесконечно); сигнатура задачи семейственна процедуре корутины (`ptr(ptr)` или void-форма по входу); `xrtExecutorWait` ждёт всех (`WaitFor/Until` — варианты со сроком). Контур образца executor: подать 1000 «забытых» задач (каждая атомарно наращивает счётчик) → Wait → `completed: 1000` — простейшая форма **подачи, исполнения, сведение**.

### Протокол остановки: Close + Wait

| Шаг | Семантика |
| --- | --- |
| `xrtExecutorClose` | прекращает приём новых задач (повторная подача отказывает); уже поставленные **исполняются** |
| `Wait` / `WaitFor` | ждёт осушения очереди и завершения в полёте - остаток не теряется |
| Destroy | после завершения всего - разрушение ресурсов |

Полностью изоморф разделу Close очереди главы 21 (протокол остановки главы 47) — **закрытие это «прекратить приём», а не «аннулировать»**: остаток задач исполняется, результаты Future-задач забираются как обычно. Образец executor_tour проверяет: `close+wait closed=1 queued=0` — Close, затем Wait до осушения и нулевая очередь: машинное свидетельство.

### Пул задач против планировщика: финальное сопоставление

Таблица главы 55 в конце тома повышается до **финальной редакции** (обе главы изучены): пул задач исполняет **функции** (без стека — до конца, без уступки на середине); планировщик исполняет **корутины** (со стеком — Park/Sleep уступают и восстанавливают). **Комбинированная форма** — инженерный стандартный ответ: блокирующую/CPU-работу, встреченную внутри корутины, Post-ят в пул задач; по завершении Future/продолжение доставляет результат обратно в корутину на стороне планировщика (межмодельная форма продолжения главы 57) — **корутины — скелет ожидания, пул задач — мышцы вычислений**. Сетевой движок тома 7 — именно эта комбинация в полном виде.

### Полная программа: контур тысячи задач

Из образца репозитория `examples/concurrency/executor/main.c`:


```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/concurrency/executor/main.c -lws2_32 -liphlpapi
completed: 1000
```

**Что только что произошло.** (1) `xrtExecutorCreate(NULL)` — NULL берёт конфигурацию по умолчанию (потоки и глубина очереди по платформе; для настройки передайте конфигурацию — глубина и есть противодавление). (2) 1000 «забытых» задач поданы — каждая атомарно наращивает счётчик (атомики главы 10 — единственное разделение между задачами; сводная статистика завершена без блокировок). (3) `Wait` ждёт всех — `completed: 1000` доказывает: все 1000 задач исполнены на потоках пула, ни одна не потеряна. (4) Обратите внимание: **ни для одной задачи не открыт поток** — пул переиспользовал фиксированные потоки; расходы подачи — микросекундная постановка в очередь. Этот 62-строчный контур — минимальное полное употребление исполнителя.

### Полная программа: пакет и остановка

Из `examples/concurrency/executor_tour/main.c` — пакетный интерфейс и протокол Close+Wait:

```embed path="examples/concurrency/executor_tour/main.c" title="examples/concurrency/executor_tour/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/concurrency/executor_tour/main.c -lws2_32 -liphlpapi
executor: batch=3 stats(submitted>=3 completed=3) ok
executor: close+wait closed=1 queued=0 ok
```

**Что только что произошло.** (1) `SubmitBatch` одной операцией ставит три задачи — пакет амортизирует синхронные расходы (редакция пакетного интерфейса очереди главы 21 для исполнителя); статистика (submitted/completed) сверяется по пакетам. (2) После Close повторная подача отказывает (проверка прекращения приёма), поставленные продолжают исполняться; Wait до осушения — `queued=0` свидетельствует обнуление очереди. (3) Порядок двух шагов протокола нерушим: сперва Close (иначе Wait мог бы вечно ждать между старыми задачами и новыми подачами), потом Wait (Destroy лишь после исполнения остатка). (4) Future-формы задач (`xrtTaskSubmit` с токеном отмены) развёрнуты в семействе образцов future/executor — глава 57 их уже научила, эта глава компонует.

## Контракты

- **Двойная форма**: «забыть» (побочный эффект) / Future (результат + отмена) — развилка потребностей, не ранг.
- **Противодавление встроено**: настроенная глубина очереди и есть потолок — заполнено, подача отказывает, а не копится (дисциплина главы 21).
- **Протокол остановки**: Close прекращает приём (остаток идёт) → Wait осушает → Destroy — порядок железный; изоморф закрытию очереди.
- **Пакетный интерфейс**: группа задач в очередь за раз — амортизированная синхронизация; статистика сверяется по пакетам.
- **Дисциплина задач**: функции задач без вечных циклов (кроме как с уважением к токену отмены); длинные задачи принимают токен и ставят контрольные точки (глава 53).
- **Комбинация моделей**: планировщик ведает скелетом ожидания, пул — мышцами вычислений; между моделями — Future/Post.

### От примеров к инженерии: три хозяина исполнителя

**Параллельные вычисления** (арена Future-формы): пакетная обработка, обработка изображений, анализ данных — фрагменты данных подаются Future-задачами, сведение через `future_combine` или Wait по одной; глубина пула = числу ядер как отправная точка (граница вычислительности), излишек подач стоит в очереди (противодавление). **Фундамент асинхронного IO** (форма главы 47): файловая асинхронность, DNS-разрешение, ожидание внешних процессов — блокирующий IO оборачивается в задачу пула, вызывающий берёт Future и не ждёт; глубина по потребностям IO-конкурентности (IO-плотно можно сверх числа ядер — ожидание CPU не занимает). **Вычислительный пристрой планировщика** (комбинированная форма): корутина встретила CPU-или-блокирующий участок → Post в пул → завершённый Future/продолжение → обратно в корутину планировщика — стандартное разделение труда сетевого движка тома 7. Глубина пула у трёх хозяев разная: граница CPU — по ядрам, граница IO — по бюджету конкурентности, смешанно — по измерениям: **глубина это параметр производительности** (объект методов бенчмаркинга главы 136).

### Панорама семейства исполнителей

«Ресурс исполнения» в XRT не один; панорама бережёт от путаницы. **xexecutor** (эта глава): общий исполнитель — «забыть» + пакет + протокол Close/Wait; модель задачи — «функция до конца». **xtaskpool** (глава 47): пул задач — `xrtTaskSubmit` возвращает Future, токен отмены — параметр первого класса; специализированный фундамент файловой асинхронности; отношение с исполнителем — «одно семейство, разные акценты»: у taskpool глубже интеграция Future/отмены, у исполнителя полнее пакет и статистика. **xcosched** (глава 55): планировщик корутин — не пул задач (гоняет корутины, не функции), но его насосный цикл занимает ту же позицию «ресурса исполнения». Трое делят общий базовый словарь (очередь, противодавление, остановка); выбор по форме задачи: функции → executor/taskpool, корутины → sched, смешанно → комбинация.

### Взгляд эксплуатации: экономика ёмкости пула

Глубина пула не выбирается на глаз — у неё есть экономика. **Мало**: параллелизма недостаточно (ядра простаивают) или IO-конкурентности недостаточно (пропускная способность упирается в пул) — симптомы: глубина очереди хронически полна, время ожидания задач велико. **Много**: память потоков (стеки), переключение контекста (CPU-перебор бесполезен — ядер столько), давление на нижний поток (IO-перебор валит число соединений базы) — симптомы: память растёт, переключения высоки, нижний поток ошибается. **Настройка по измерениям**: три набора данных вместе — кривые глубины очереди (хронически полна → добавить или расширить нижний поток), распределение длительностей задач (статистика главы 6 или таймирование главы 41), системные метрики (CPU/память/переключения). Отправные значения: CPU-тип = ядра, IO-тип = бюджет конкурентности (80% ёмкости нижнего потока), смешанный стартует с CPU-типа и растёт по измерениям. **Глубина не «чем больше, тем лучше»** — она «привратник ёмкости нижнего потока».

## Ловушки

### Ловушка 1: вечный цикл в задаче не даёт остановиться

Симптом: Close+Wait никогда не возвращается — одна задача крутит вечный цикл, осушение отодвигается за горизонт; остановка по тайм-ауту убивает принудительно, оставляя незавершённое состояние.

Причина: задача игнорирует отмену — остановка исполнителя предполагает завершаемость задач; вечный цикл без контрольных точек затыкает протокол.

```c bad
static void taskForever(ptr pData)
{
	while ( true ) {
		Poll();   /* вечный цикл - токен отмены не смотрится */
	}
}
```

```c good
static void taskCancellable(ptr pData, xcancel* pCancel)   /* Future-форма несёт токен */
{
	while ( !xrtCancelRequested(pCancel) ) {   /* контрольная точка (глава 53) */
		Poll();
	}
	/* отмена попала - задача возвращается, осушение движется */
}
```

### Ловушка 2: утечка ресурсов, созданных в «забытых» задачах

Симптом: забытая задача создаёт Future/ресурсы, которые никто не освобождает — утечка на каждую задачу; лестница живых объектов статистики ползёт.

Причина: «никто не ждёт» в форме «забыть» не значит «никто не отвечает» — владеющие продукты, созданные внутри задачи, обязаны завершиться внутри задачи.

```c bad
static void taskLeak(ptr pData)
{
	xvalue* pTmp = xrtValueInt(42);   /* создал и бросил - освобождать некому */
	Report(pTmp);
	/* нет Release - окно утечки забытой задачи */
}
```

```c good
static void taskClean(ptr pData)
{
	xvalue* pTmp = xrtValueInt(42);
	Report(pTmp);
	xrtValueRelease(pTmp);   /* создано в задаче - в задаче и завершено */
}
```

## Упражнения

### Базовое: сопоставление двух форм

Одно и то же вычисление (квадрат) десять раз в форме «забыть + атомарный результат» и в форме «Future + Value» — по одному выводу о объёме кода, способе сведение и чтении результата.

### Продвинутое: бенчмарк пакетной подачи

1000 задач: поштучно против десяти пакетов по 100 — сравните суммарное время подачи и пропускную способность (статистика главы 6 или таймирование); порядок выгоды пакета — в вывод.

### Вызов: исполнитель смешанной нагрузки

Настроенный исполнитель: CPU-задачи (Future-форма, отменяемые) + имитация IO-задач («забыть», со сроком) вперемешку; полный протокол остановки (Close → Wait со сроком → статистика незавершённых). Критерии приёмки: доля нагрузки настраивается; дерево отмены прошивает Future-задачи (задачи в полёте завершаются в пределах 2 секунд после остановки); статистика незавершённых сходится с журналом.

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Двойная форма | ExecutorSubmit «забыть» / TaskSubmit→Future (результат + отмена) |
| Противодавление | глубина очереди и есть потолок - заполнено, подача отказывает, копления нет |
| Протокол остановки | Close прекращает приём (остаток идёт) → Wait осушает → Destroy - порядок железный |
| Пакет | SubmitBatch амортизирует синхронизацию; статистика сверяется по пакетам |
| Дисциплина задач | вечных циклов нет (или с контрольными точками токена); продукты задачи завершаются в задаче |
| Комбинированная модель | планировщик ведает ожиданием, пул вычислением - Future/Post между моделями |
