## Ориентация

После трёх автоматических поведений главы 100 кэш — самое большое и самое колоритное из них. Слой `http_client_cache` после подключения Store (`xhttpcache`) в конфигурацию Client делает **поиск, доставку при попадании, оценку свежести, условную валидацию, сохранение, сборку частичных ответов и инвалидацию unsafe-методов полностью автоматически** — ваш код не меняется ни на строку, второй запрос того же URL выходит из локального хранилища. Протокольная сторона полностью следует RFC 9111: `Cache-Control` запроса (no-store/no-cache/only-if-cached/возрастные ограничения) и хранимость ответа обрабатываются единым публичным парсером политики кэша — клиент не изобретает приближённых семантик. Объекты хранения остаются открытыми — приложение, прокси, собственный персистентный бэкенд используют тот же контракт Store. Глава разбирает конфигурацию, четыре режима вызова, контракт хранения и условную конкурентную фиксацию.

## Введение

Зачем клиенту встроенный кэш, а не «бизнес сам сохранит ответы»? Три причины.**Корректность**: суждение о хранимости (`no-store`/`Vary: *`/ответы с аутентификацией/правила общих и приватных), расчёт свежести (max-age/Expires/поправка возраста), условная валидация (слияние 304 по ETag/Last-Modified) — каждое тонкое правило RFC; самописное «положу в Map, истеку по времени» на реальных заголовках ответов ошибается кто во что горазд.**Компонуемость**: сборка частичного содержимого Range-запросов (локальные фрагменты + дозапрос к источнику) требует согласованности со структурой хранения — снаружи не навесить.**Инвалидация**: после успешного unsafe-метода инвалидация связанных представлений того же источника (`Location`/`Content-Location`) — часть протокола кэша. xhttp реализует этот свод правил один раз — сконфигурировал Store, выиграли все.

## Понятия

### Сборка и режимы вызова

```diagram flow
- Сборка: xrtHttpCacheCreate -> ClientConfig.Cache.Store -> после Create свою ссылку можно отпустить
- Прибыл запрос: определение режима (четыре режима) -> поиск в кэше (главный ключ = метод + действующий URI + раздел + объявление Vary)
- Попадание и свежесть: прямая доставка (без выхода в сеть)
- Попадание, но истекло: условная валидация (ETag/If-Modified-Since) -> при 304 слияние записи и доставка
- Промах/выключено: к источнику -> ответ по хранимости решает, входить ли в Store
```

Четыре режима на уровне вызова: `XHTTP_CLIENT_CACHE_DEFAULT` (соблюдать политику запроса/ответа/хранения — обычный путь), `DISABLED` (на этот раз обойти чтение, запись и инвалидацию), `RELOAD` (принудительная валидация у источника или перезагрузка; успешный ответ всё же может обновить кэш — кнопка «обновить»), `ONLY` (сеть запрещена; без записи **синтезируется 504** — офлайн-режим). Четыре режима складываются с семантикой заголовков запроса без конфликта — заголовок `only-if-cached` обрабатывает тот же парсер политики.

### Контракт хранения: что входит в Store

- **По умолчанию приватный кэш**; `Shared` явно переключает общую семантику (поля и правила авторизации различаются).
- **Не входит в Store**: `no-store`, нехранимые коды состояния, `Vary: *`, запрещённые к общему хранению аутентифицированные/приватные ответы.
- **Эвристика свежести**: без явной свежести можно включить ограниченную эвристику по `Last-Modified` — по умолчанию 10%, максимум сутки, можно выключить целиком (консервативный дефолт, приватность и корректность прежде всего).
- **Рост по надобности**: кодированное тело растёт только после реального прибытия, на каждый Call ничего не резервируется; `MaxBody` (по умолчанию 8 MiB) — жёсткий потолок захвата одного дозапроса — сверх него захват прекращается, но **по умолчанию fail-open** (сетевой ответ продолжает доставляться, просто не кэшируется); малые тела стартуют с 256 Б, удваиваясь.
- **Дисциплина освобождения**: после сохранения или повторной выдачи кандидат-запись, снимки полей и захваченное тело освобождаются до публикации финала — не живут в удерживаемом вами результате.

### Условная фиксация и конкурентность

Слияние 304, обновление метаданных HEAD, сборка Range-фрагментов — **без обычного перезаписывающего Put** — они используют текущую версию Store `Replace`/`RemoveRecord`: при конфликте фиксации 304 (победил конкурентный обновлятель) текущий запрос всё равно доставляет собственный проверенный снимок, а кэш сохраняет результат конкурентного обновлятеля — **не терять обновление ради сохранения своего взгляда**. Этот оптимистический параллелизм — та же мысль, что «правила инвалидации» контейнеров главы 18: изменили после вашего чтения — условие записи не сошлось, каждый идёт своей дорогой.

### Сборка Range и инвалидация unsafe

**Локальная сборка Range**: запрошен `Range: bytes=0-99`, а локально есть запись `0-199` — режется прямо из кэша (без выхода в сеть); если локально только фрагмент, сложность «локальный фрагмент + дозапрос недостающего» ограничивается `MaxRanges` (по умолчанию 16) — сортировочная работа, временные массивы и multipart-разрастание ограничены.**Инвалидация unsafe**: успешные POST/PUT/DELETE инвалидируют целевой URI вместе с односайтовыми `Location`/`Content-Location` представлениями, которым ответ разрешил — согласованность «записал-прочитал» гарантируется протоколом, а не напоминанием приложения.

### Ключ раздела

`PartitionKey` копируется при фиксации и служит изоляции одного URI по пользователям/сайтам/арендаторам — главный ключ содержит раздел.**Почему нельзя полагаться только на `Vary`**: `Vary` различает по заголовкам запроса (например `Vary: Authorization`), но «какие заголовки различать» объявляет отвечающий — не объявил, и доступ общ shared; ключ раздела — **активная изоляция вызывающего** (базовая линия многотенантного клиента). Изоляция приватных данных — решение вызывающего; протокольный инструмент лишь инструмент.

## Контракты

- **Сборка**: Store в конфигурацию Client — и всё автоматически (поиск/доставка/валидация/хранение/сборка/инвалидация); Client держит ссылку; без Store слой не входит в горячий путь.
- **Четыре режима**: DEFAULT/Disabled/Reload/Only (без записи синтезируется 504); с семантикой заголовков запроса унифицированы одним парсером, без самодеятельных приближений.
- **Главный ключ**: метод + действующий URI + ключ раздела + фактически объявленные записью поля Vary.
- **Не хранится**: no-store/незранимые коды состояния/Vary:*/запрещённые к общему хранению аутентифицированные приватные ответы.
- **Эвристика**: по умолчанию 10%·Last-Modified·максимум сутки·можно выключить.
- **Потолки**: MaxBody — жёсткий потолок захвата одного дозапроса (по умолчанию 8 MiB), сверх — fail-open; MaxRanges по умолчанию 16 ограничивает сложность сборки; рост по надобности, без резервирования.
- **Условная фиксация**: 304/HEAD/Range через версионное условие Replace — при конфликте доставляется свой снимок, сохраняется конкурентный обновлитель.
- **Инвалидация**: успех unsafe инвалидирует целевой URI + разрешённые ответом односайтовые Location/Content-Location.
- **Разделы**: PartitionKey копируется при фиксации; приватная изоляция — разделом, не Vary.
- **Обрезка**: `HTTP_CLIENT_CACHE` зависит от общего семейства протокольных модулей кэша (policy/control/time/validate/range/store/status независимы).

## Ловушки

### Ловушка 1: принять MaxBody за общую ёмкость Store

Симптом: установили `MaxBody = 16 MiB` и решили, что кэш займёт максимум 16 MiB — через часы работы память растёт до сотен MiB.

Причина: `MaxBody` — потолок **захвата одного дозапроса** (насколько велики записи, которые ещё кэшируются); общая ёмкость Store и вытеснение — в `xhttpcacheconfig` (конфигурация при создании Store). Две ручки ведают двумя разными вещами.

```c bad
ClientConfig.Cache.MaxBody = 16u * 1024u * 1024u;   /* решили, что это общая ёмкость */
pCache = xrtHttpCacheCreate(NULL);                    /* общая ёмкость по умолчанию не тронута */
```

```c good
xhttpcacheconfig CacheConfig;
xrtHttpCacheConfigInit(&CacheConfig);
CacheConfig.MaxBytes = 64u * 1024u * 1024u;   /* общая ёмкость Store + вытеснение */
pCache = xrtHttpCacheCreate(&CacheConfig);
ClientConfig.Cache.Store = pCache;
ClientConfig.Cache.MaxBody = 16u * 1024u * 1024u;   /* потолок одного захвата */
```

### Ловушка 2: многопользовательский клиент делит кэш без разделов

Симптом: приватный ресурс, запрошенный пользователем A, при том же URL попадает напрямую пользователю B — **межпользовательская утечка данных**.

Причина: главный ключ кэша по умолчанию не содержит пользовательского измерения; `Vary: Authorization` действует, только если отвечающий объявил — не объявил, и доступ общ. Многопользовательским/многотенантным обязательно задавайте ключ раздела.

```c bad
/* все пользователи - один Client и один Store, без разделов */
pClient = xrtHttpClientCreate(pEngine, &Config);   /* B попадает в приватный ответ A */
```

```c good
/* на пользователя (или арендатора) свой ключ раздела - главный ключ содержит раздел */
xrtHttpCallOptionsInit(&Options);
Options.Cache.PartitionKey = user_partition(user);
pCall = xrtHttpClientDo(pClient, pReq, &Options, on_done, pCtx);
/* приватная изоляция - активное решение вызывающего; инструмент за вас не угадывает */
```

### Ловушка 3: обрабатывать синтетический 504 режима ONLY как сетевую ошибку

Симптом: в офлайн-режиме (`CACHE_ONLY`) без записи возвращается 504 — код идёт по пути «шлюз упал» с алертом.

Причина: 504 — **синтезированная локальная семантика**: «сеть запрещена, кэша нет» — это не сетевая ошибка, а детерминированный результат офлайн-политики. Обработка должна идти в ветку «офлайн, нет содержимого» (подсказка/деградированный UI), не в повтор или алерт.

```c bad
if ( status == 504 ) {
	alert_gateway_down();   /* офлайн-промах принят за сетевой сбой */
}
```

```c good
if ( offline_mode && status == 504 ) {
	show_offline_empty(url);   /* локальный синтетический 504: офлайн и без кэша */
}
```

## Упражнения

### Базовое: сверка попадания и дозапроса

Дважды подряд запросите один URL локального сервиса: сравните `Info.ResponseWireBytes` второго (должно быть 0 — попадание) и возрастную информацию в заголовках ответа. Затем третий раз в режиме `RELOAD`. Критерии приёмки: Wire-байты трёх прогонов согласуются с семантикой режимов; тело попадания байт-в-байт совпадает с первоисточником.

### Продвинутое: наблюдение условной валидации

Сервер возвращает ответ с ETag; после истечения кэша (или принудительного RELOAD) запросите снова — захватом пакетов или журналом сервера убедитесь: второй запрос несёт условные заголовки, ответ 304, клиент доставляет **слитое полное представление** (код состояния 200, не 304). Критерии приёмки: вызывающий никогда не видит внутренний 304 (проверка контракта); тело попадания совпадает с первоисточником.

### Вызов: офлайн-первый клиент

Реализуйте `fetch_offline_fallback(Url)`: сначала `CACHE_ONLY` (попадание — используем); при 504 откат к обычному режиму с выходом в сеть и записью в кэш. Протестируйте весь процесс с выключенной сетью. Критерии приёмки: с кэшем офлайн работает; без кэша — явная офлайн-ошибка (различайте «сеть отключена» и «сервер 5xx»); запись в кэш соблюдает хранимость ответа (no-store не попадает в хранилище — проверяется последующим офлайн-поведением).
