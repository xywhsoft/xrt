## Ориентация

«Добавить аутентификацию» в HTTP — задача выбора из трёх семейств схем.**Basic**: `Authorization: Basic base64(用户:密码)` (пользователь:пароль) — открытый текст (приемлемая форма только под TLS), по строке на каждом конце.**Bearer**: `Authorization: Bearer <令牌>` (токен) — носитель эпохи OAuth2/JWT; клиент только несёт его.**Digest**: сервер выдаёт nonce-вызов, клиент отвечает `H(用户:域:密码)` (пользователь:область:пароль) — протокол вызов-ответ, где **пароль не выходит в сеть**, со встроенной защитой от повторов (nonce + счётчик nc); сервер ведёт жизненный цикл nonce, таблицу повторов и квитанцию `Authentication-Info`. xhttp реализует оба конца всех трёх схем как структурированные API: построение на клиенте (`xrtHttpBasicWrite`/`BearerWrite`/ответ Digest), чтение на сервере (три состояния `xrtHttpServerRequestBasicAuth/BearerAuth/DigestAuth`), полная цепочка проверки Digest (четыре состояния verify у `xrtHttpDigestVerify` + потокобезопасная таблица повторов). Отсюда собирается middleware авторизации главы 104.

## Введение

Три формы развёртывания, каждая на своём месте. Инструменты интрасети: Basic + TLS достаточно — по строке кода на каждом конце; пароль открытый текст, но туннель шифрованный. API-платформы: Bearer — выдача/обновление токенов дело платформы, сервер только проверяет токен; «аутентификация» клиента — просто принести его. Недоверенная среда или протокольное соответствие (защита пароля в семантике HTTP): Digest — дайджесты паролей на сервере, вызов-ответ защищает от повторов; цена — сервер поддерживает состояние nonce и повторов.**Цена неправильного выбора**: Basic поверх открытого текста HTTP равносилен трансляции пароля;.stateless Bearer на платформе, где нужно отзывать токены, равносилен невозможности отзыва; использовать Digest как «более безопасный Basic», не управляя истечением nonce, — окно повторов открыто как прежде.

Единая форма auth-API заслуживает внимания: всё идёт через три состояния `XHTTP_NEXT_END/ITEM/ERROR` (отсутствует/действителен/ошибка) — тот же контракт, что у структурированного чтения полей (главы 91/103); построение вызова «дописывает» (AddChallenge — сосуществование многих схем), квитанция «устанавливает» (SetDigestInfo — единственное поле) — многозначная/единственная семантика RFC ложится на форму API.

## Понятия

### Basic: по строке на каждом конце и базовая линия открытого текста

Клиент `xrtHttpBasicWrite(用户, 密码, 输出, 容量, &长度)` (пользователь, пароль, вывод, ёмкость, &длина) производит значение поля `Basic <base64>`; сервер `xrtHttpServerRequestBasicAuth(请求, 解码缓冲, 容量, &长度, &描述符)` (запрос, буфер декодирования, ёмкость, &длина, &дескриптор) — **результаты декодирования Basic и Digest заимствуют буфер вызывающего** (короткий буфер публикует только точную нужную длину; ошибка очищает дескриптор, оставляя длину и тело вызывающего нетронутыми — половину открытого текста вперёд не фиксируем). Дисциплина базовой линии: Basic только под TLS; Basic поверх открытого текста `http` — авария конфигурации.

### Bearer: ношение токенов и вызовы

Клиент `xrtHttpBearerWrite` производит `Bearer <token>`; сервер `xrtHttpServerRequestBearerAuth` берёт представление токена (заимствует снимок запроса — сам токен принадлежит вашему слою проверки: локальная проверка подписи, запрос к базе, вызов сервиса авторизации).**Граница безопасности Bearer — в управлении токенами**: выдача, истечение, отзыв, области минимальных прав — протокольный слой лишь носитель; вход построения вызова 401 (`WWW-Authenticate: Bearer error="invalid_token"`) ведает синтаксисом, политика — приложению.

### Digest: вызов, ответ и четыре состояния проверки

```diagram flow
- Вызов: сервер 401 + WWW-Authenticate: Digest realm/nonce/qop/algorithm/opaque (AddChallenge)
- Ответ: клиент кэширует H(A1)=H(пользователь:realm:пароль); считает request-digest по nonce+nc
- Проверка: сервер ищет H(A1) (по имени пользователя/userhash) -> заполняет дескриптор проверки (метод/target/вызов)
  -> xrtHttpDigestVerify -> приговор четырёх состояний
- Квитанция: после VALID DigestRspAuth генерирует rspauth -> SetDigestInfo ставит Authentication-Info
- Повторы: только VALID фиксирует nc; ReplayCheck - потокобезопасная таблица повторов (распределённо ReplayKey + общее хранилище)
```

Точная семантика четырёх состояний: `XHTTP_DIGEST_VERIFY_VALID` (подпись и доказательство верны), `_STALE` (**подпись и доказательство верны, но nonce истёк** — клиенту следует повторить со свежим nonce; это не провал), `_INVALID` (доказательство неверно — отвергнуть), `_ERROR` (ошибка ввода/структуры).**Только VALID фиксирует монотонный nc** — ранняя фиксация позволила бы ошибочному доказательству захватить счёт легитимного клиента (таблица повторов отравлена). Управление nonce: встроено в вход по умолчанию; собственные nonce или вращающееся кольцо ключей — комбинация двух уровней `xrtHttpDigestProofVerify`+`NonceVerify`. Квитанция `Authentication-Info` (взаимная аутентификация rspauth + вращение nextnonce) генерируется после успешной проверки из того же контекста доказательства — полный замкнутый цикл вызова и ответа.

### Формы развёртывания защиты от повторов

Один процесс: `xrtHttpDigestReplayCheck` — потокобезопасная таблица повторов с жёсткой ёмкостью; много процессов/распределённо: `xrtHttpDigestReplayKey` генерирует канонический ключ, общее хранилище делает **атомарное обновление максимума с истечением** (nc — монотонный счётчик — max-обновление с семантикой CAS). Окно повторов = срок nonce; срок — параметр баланса безопасности и опыта.

### Разбор вызовов на клиенте

`xrtHttpChallengeNext` итерирует многосхемные вызовы в ответе 401 (`Digest realm=..., Basic ...` смешанные объявления) — клиент выбирает схему по возможностям: кэш пароля — Digest, токен — Bearer, откат — Basic. Слой политики автоматического повтора (глава 99), получив 401, собирается отсюда.

## Контракты

- **Три состояния едины**: семейство чтения `END` (отсутствует)/`ITEM` (действителен)/`ERROR` (дублирующееся поле, нелегальный синтаксис, несовпадение схемы, провал декодирования); дублирующийся Authorization — протокольная ошибка Header.
- **Граница заимствования**: общие результаты и Bearer заимствуют снимок запроса; результаты декодирования Basic и Digest заимствуют буфер вызывающего; короткий буфер публикует точную длину, ошибка не трогает состояние вызывающего.
- **Базовая линия Basic**: открытый текст (base64 не шифрование); только под TLS; по одному вызову API на каждый конец.
- **Граница Bearer**: проверка/отзыв/права токена — прикладному слою; построение синтаксиса вызова — слою аутентификации.
- **Четыре состояния Digest**: VALID/STALE (подпись верна, nonce истёк — повторяемо)/INVALID (доказательство неверно)/ERROR; только VALID фиксирует nc.
- **Управление nonce**: по умолчанию встроено; собственное — комбинация ProofVerify+NonceVerify; срок = окно повторов.
- **Таблица повторов**: один процесс ReplayCheck (потокобезопасная, жёсткий потолок); распределённо ReplayKey + общее хранилище с атомарным max.
- **Вызов/квитанция**: Add дописывает многие схемы; Set ставит единственный Authentication-Info (rspauth+nextnonce); статус 401/407 автоматически не меняется — политика приложению.
- **Обрезка**: `HTTP_AUTH`/`HTTP_DIGEST` независимы; семейство алгоритмов SHA-2 опционально.

## Ловушки

### Ловушка 1: Basic поверх открытого текста HTTP

Симптом: захват пакетов видит `Authorization: Basic <base64(密码)>` (пароль) — пароль фактически транслируется.

Причина: base64 — кодирование, не шифрование. Вся безопасность Basic — от транспортного слоя; под TLS он уровня «защита от подглядывания через плечо».

```c bad
/* http:// интрасетевой адрес + Basic: в захвате/журнале прокси интрасети сплошные пароли открытым текстом */
xrtHttpRequestSetBasicAuth(pReq, User, Pass);
send_http(url);   /* без TLS */
```

```c good
/* Basic идёт только с https */
if ( !url_is_https(pUrl) ) {
	return error("basic auth requires TLS");
}
xrtHttpRequestSetBasicAuth(pReq, User, Pass);
```

### Ловушка 2: проверка Digest не различает STALE и валит всё как провал

Симптом: легитимный клиент с истёкшим nonce получает 401 и вылетает из логина — опыт ломается; или наоборот, INVALID принят за STALE с разрешением повтора — брутфорс-доказательства крутятся бесконечно.

Причина: четыре состояния обязаны обрабатываться по веткам: STALE — «начните заново со свежим nonce» (клиент уже имеет H(A1) и повторяет бесшовно), INVALID — «доказательство просто неверно» (отвергнуть и посчитать).

```c bad
switch ( xrtHttpDigestVerify(&V) ) {
default:
	reject_and_logout();   /* STALE тоже принят за провал */
}
```

```c good
xhttpdigestverifycheck R = xrtHttpDigestVerify(&V, Key, Ctx, Now, Life, Skew, NULL);
if ( R == XHTTP_DIGEST_VERIFY_VALID ) { accept(); }
else if ( R == XHTTP_DIGEST_VERIFY_STALE ) {
	challenge_with_fresh_nonce();   /* клиент повторит со свежим nonce */
} else {
	reject_and_count();             /* INVALID/ERROR: отвергнуть + посчитать */
}
```

### Ловушка 3: фиксация счётчика nc до проверки

Симптом: счётчик таблицы повторов захвачен ошибочными доказательствами — следующий запрос легитимного клиента признаётся повтором и отвергается.

Причина: nc — монотонный счёт «запросов, уже израсходованных под этим nonce»; запрос INVALID не должен занимать номер — контракт ясно говорит «фиксирует только VALID».

```c bad
verify_partial(&V);                 /* проверена только подпись */
replay_commit(nonce, nc);           /* занять номер сперва - ошибся или нет */
if ( full_verify(&V) ) { accept(); }
```

```c good
if ( xrtHttpDigestVerify(&V, Key, Ctx, Now, Life, Skew, NULL) ==
		XHTTP_DIGEST_VERIFY_VALID ) {
	replay_commit(nonce, nc);       /* номер - только при полностью верном доказательстве */
	accept();
}
```

## Упражнения

### Базовое: матрица вызовов трёх схем

Постройте вызов с Digest+Basic+Bearer; клиент разбирает и выбирает схему по конфигурации (есть пароль/есть токен/ничего), печатая выбор. Критерии приёмки: все три конфигурации выбирают верную схему; параметры вызова (realm/nonce) читаются как структура.

### Продвинутое: замкнутый цикл вызов-ответ Digest

Сервер (сервер + middleware главы 103) выдаёт вызов Digest; клиент разбирает nonce, считает ответ, отправляет; серверный `DigestVerify` идёт по четырём веткам. Повторите запрос, проверьте рост nc. Критерии приёмки: первый запрос VALID; повтор того же nonce отвергнут таблицей повторов; истёкший nonce проходит через STALE, и повтор успешен.

### Вызов: шлюз Bearer с отзывом токенов

Middleware шлюза Bearer: поиск токена в локальном кэше (Map + TTL главы 18), при промахе — в сервис авторизации (симуляция); список отзыва поддерживается (отзыв инвалидирует кэш). Критерии приёмки: действительный токен проходит, недействительный 401, отозванный — 401 немедленно; путь попадания в кэш без вызовов бэкенда (проверка подсчётом); токены никогда не попадают в журнал (дисциплина главы 76).
