## Ориентация

Финал восьмого тома. Возобновление сессии решает чистую задачу производительности: полное рукопожатие стоит одной проверки сертификатов и нескольких асимметричных операций (1–2 RTT), восстановительное рукопожатие с помощью PSK, выведенного из прошлой сессии, сжимает это почти до одного RTT и до нуля передач сертификатов — водораздел пользовательского опыта мобильных сетей и частых коротких соединений. В главе 81 была описана клиентская грань употребления (кеш билетов/`TakeResume`); здесь — полный цикл и контракт объекта: **объект возобновления `xtlsresume`** (билет + PSK + привязка маршрута в одном неизменяемом значении; разделяется между потоками, стратегия кеширования — ваша), серверные **подпись и приём** (обе стороны уже подготовлены главой 85) и пример двойного рукопожатия-цикла — сессия первая подписывает билет, клиент принимает его, сессия вторая восстанавливается по PSK+DHE. Границы безопасности тоже доведены до конца: возобновление всегда сохраняет ECDHE (прямая секретность не деградирует), ошибка binder — провал аутентификации, привязка маршрута не даёт билету «гулять по чужим доменам».

## Введение

Ваш API-шлюз принимает почти десять тысяч TLS-соединений в секунду, каждое полное рукопожатие — примерно 2 RTT плюс проверка цепочки сертификатов: накладные расходы рукопожатия превышают время обработки большинства самих запросов. А клиент? Мобильное устройство рукопожатается заново при каждом пробуждении, в слабой сети 300 миллисекунд рукопожатия — уже ощутимое запинание. Ответ TLS 1.3: по завершении рукопожатия сервер отправляет **NewSessionTicket** (билет), клиент сохраняет «билет + выведенный из рукопожатия PSK»; при следующем соединении ClientHello несёт билет и **binder** (HMAC, посчитанный на PSK, — доказательство «я и в самом деле тот самый клиент»); сервер, проверив binder, пропускает стадию сертификатов, стороны выводят новые ключи из PSK + свежего ECDHE — быстро, экономно и без уступок прямой секретности.

Настоящая проектная задача — «кем управляется билет». Ответ XRT: **объект-значение + ваш кеш** — `xtlsresume` упаковывает активы возобновления в неизменяемый объект (глубокая копия, подсчёт ссылок, обнуление при освобождении), а где хранить — в Map в памяти, на диске или в Redis — решает приложение; протокольный слой глобального кеша не ведёт (потребности многопроцессности/мультитенантности/персистентности слишком различны). Эта граница «библиотека даёт значение, приложение даёт стратегию» — стержень главы.

## Понятия

### Объект возобновления: неизменяемый блок активов

`xtlsresume` при создании глубоко копирует ticket, PSK, SNI, ALPN и опциональную идентичность партнёра; после одного точного выделения объект **неизменяем**; подсчёт ссылок допускает разделение между потоками; перед освобождением последней ссылки весь блок обнуляется (переиспользуется `xrtSecureZero`). Ограничения (пока принимается только TLS 1.3): ticket 1..65535 байтов, длина PSK равна длине дайджеста комплекта, срок жизни 1..604800 секунд, ALPN ≤255 байтов, SNI отвергает встроенные нулевые байты. Срок действия — полуоткрытый интервал `[IssuedAt, ExpiresAt)`; **откат настенных часов до момента подписи — безопасная недействительность** (срок не продлевается); `xrtTlsResumeTicketAge` после проверки срока действия округляет возраст до миллисекунд и делает 32-битное модульное сложение с `AgeAdd` — обскуррация возраста, предписанная протоколом, встроена. Представления, публикуемые `ResumeInfo`, действительны, пока жива ссылка; среди них **`Secret` — чувствительное представление только для чтения**: не изменять и не журналировать без защиты (санитизация журналов — дисциплина главы 76).

Опциональный `PeerIdentity` — домен идентичности вызывающего, не участвующий в кодировании линии: храните дайджест уже проверенного листового сертификата прошлой сессии, и у «наследования аутентифицированной идентичности» восстановительным соединением появляется посадочная площадка (глава 81: новый билет наследует исходный `PeerIdentity`).

### Цикл: подпись → приём → восстановление

```diagram flow
- Сессия первая (полное рукопожатие): проверка сертификатов + ECDHE + двусторонний Finished → READY
- Подпись: сервер ServerTicket(ticket, срок, &объект-возобновления) → NewSessionTicket отправлен клиенту; владение объектом возобновления передано серверному вызывающему (помещение в хранилище - за вами)
- Приём: клиент получил билет → глубокая копия билета/SNI/ALPN/идентичности → TakeResume передаёт ссылку приложению
- Кеш: стратегия приложения (Map в памяти / диск / Redis; ёмкость, вытеснение, изоляция арендаторов)
- Сессия вторая: ClientConfig.Resume = объект → ClientHello с билетом + binder + обычным key share
- Приём: Resume-колбэк сервера ищет билет → проверка версии/комплекта/SNI/ALPN/срока/возраста → PSK+DHE → пропуск сертификатов
```

Четыре ключевых пункта. ① **binder живёт в ClientHello** — «доказательство владения PSK» происходит в момент отправки Hello (`accepted=not yet`: принял ли сервер, выяснится только с ServerHello — семантика главы 81). ② **Сервер может отказать**: билет истёк, маршрут не совпал, стратегия ёмкости — клиент безопасно откатывается к полному рукопожатию (`TlsClientResumed` станет true лишь после приёма сервером). ③ **Всегда PSK+DHE**: восстановительное соединение всё равно несёт key share x25519, свежий ECDHE подмешивается в выведение — даже при утечке PSK ключи сессии остаются под защитой текущего ECDHE (прямая секретность не деградирует). ④ **Привязка маршрута**: при опущенных SNI/ALPN клиент **точно наследует** привязку объекта; явный SNI обязан совпадать полностью, явный список ALPN обязан содержать протокол билета — билет не может «зайти в гости» к другому домену или протоколу.

### Поверхность API двух сторон

- **Серверная подпись** (глава 85): `xrtTlsServerTicket` (со своим ticket) или `TicketNew` (32 байта защищённого случайного + 86400 секунд по умолчанию); при `XTLS_AGAIN` выход равен `NULL` и состояние не меняется — повтор после опорожнения.
- **Клиентский кеш**: `ResumeLimit` (0..64, по умолчанию 4) ограничивает запас, при заполнении вытесняется самый старый; `TakeResume` передаёт ссылку в порядке приёма; `ResumeDropped` считает отброшенные по отключению/вытеснению/OOM — OOM кеша не трогает уже готовые соединения.
- **Следующее соединение**: `ClientConfig.Resume = 对象` (сессия держит независимую ссылку — вашу можно тут же Release); истёкший/не вступивший в силу/запрещённый политикой комплекта/не совпадающий по маршруту отклоняются **до выделения сессии** — плохой билет не входит в машину состояний.

## Контракты

- **Контракт объекта**: глубокая копия одним выделением, неизменяемость, разделяемость подсчётом ссылок, обнуление до освобождения последней ссылки; только TLS 1.3; границы полей (ticket 1..65535 / PSK=длине дайджеста комплекта / срок 1..604800 / ALPN≤255 / SNI без встроенных нулевых байтов).
- **Семантика времени**: срок действия — полуоткрытый интервал `[IssuedAt, ExpiresAt)`; откат настенных часов — безопасная недействительность без продления; `TicketAge` сперва проверяет срок, затем 32-битное модульное сложение; при неудаче выход не меняется.
- **Чувствительные представления**: `Info().Secret` — только чтение, чувствительно: не изменять, не журналировать без защиты; `PeerIdentity` — домен идентичности вызывающего, в линию не попадает.
- **Серверная подпись**: владение объектом переходит вызывающему; глобального кеша нет; при AGAIN выход NULL и состояние неизменно — повторяемо; жёсткие лимиты проверяются заранее.
- **Клиентский кеш**: `ResumeLimit` 0..64, по умолчанию 4, при заполнении вытесняется самый старый; `TakeResume` передаёт ссылку; отбрасывания считаются без ложных срабатываний; OOM кеша не трогает готовые соединения.
- **Согласование восстановления**: binder с ClientHello доказывает владение PSK; принять или нет — решает сервер; при отказе безопасный откат к полному рукопожатию (key share несётся всегда).
- **Принудительность PSK+DHE**: ECDHE сохраняется всегда, прямая секретность не деградирует; чистого PSK нет, 0-RTT нет.
- **Привязка маршрута**: опущено — точное наследование; явный SNI — полное равенство, явный ALPN — обязательное включение протокола билета; несовпадение отклоняется до выделения сессии.
- **Граница аутентификации**: метаданные билета совпали, а binder ошибочен = провал аутентификации (fatal, без деградации) — встроено в серверную машину состояний, колбэк не должен подделывать «найдено».

## Ловушки

### Ловушка 1: PSK как обычный буфер отправлен в журнал или метрики

Симптом: при разборе инцидента печатается содержимое объекта возобновления — секрет PSK попадает в журнальную систему, то есть «удостоверение следующего рукопожатия» навсегда архивируется.

Причина: Secret представления `ResumeInfo` — чувствительное представление только для чтения; «неизменяемость» объекта-значения не значит «нечувствительность». Дисциплина главы 76 «ключи не идут в журнал» действует и здесь.

```c bad
xrtTlsResumeInfo(pResume, &Info);
log_debug("ticket=%.*s psk=%.*s",   /* PSK в журнал: утечка */
	(int)Info.Ticket.Size, Info.Ticket.Data,
	(int)Info.Secret.Size, Info.Secret.Data);
```
```c good
xrtTlsResumeInfo(pResume, &Info);
/* ticket не секретен - можно дайджест; PSK - только длина и факт наличия */
log_debug("ticket=%zu bytes psk=%zu bytes expires=%lld",
	Info.Ticket.Size, Info.Secret.Size,
	(long long)Info.ExpiresAt);
```

### Ловушка 2: восстановление отвергнуто — сразу ошибка без повтора

Симптом: после рестарта сервера (билеты в памяти потеряны) все клиенты «падают» — «откат к полному рукопожатию» принят за путь ошибки.

Причина: восстановление — согласование, а не гарантия: сервер потерял билеты, истёк срок, отказала стратегия ёмкости — всё это норма; ожидаемое поведение протокола — **автоматически уйти в полное рукопожатие** (ClientHello и так несёт key share). Считать это аварией — не понять семантику `accepted=not yet`.

```c bad
if ( !xrtTlsClientResumed(pSession) ) {
	return error("resume rejected");   /* нормальный откат принят за сбой */
}
```
```c good
/* запрос после завершения рукопожатия: resumed - лишь намёк на производительность, само соединение столь же безопасно */
bool bResumed = xrtTlsClientResumed(pSession);
metrics_record("tls_resumed", bResumed);
/* возобновлено или нет, соединение уже аутентифицировано полным рукопожатием или PSK - пользуйтесь напрямую */
```

### Ловушка 3: повторное использование билета через «домены маршрутизации»

Симптом: во внутренней сервисной сетке один и тот же клиентский код ходит в несколько окружений (prod/staging), билеты «гуляют» — соединения падают или (хуже) наследуется чужая идентичность.

Причина: билет привязан к SNI/ALPN, но **если несколько окружений делят один SNI**, объектный слой различить их не может — binder после «гуляния» может случайно пройти, а `PeerIdentity` унаследует идентичность другого окружения. Изоляция маршрутов — ответственность прикладного слоя.

```c bad
/* один глобальный кеш обслуживает все окружения */
g_ResumeCache = cache_create();
resume = cache_take(g_ResumeCache, host);   /* host одинаковый, окружение разное */
```
```c good
/* в ключ кеша добавить домен маршрутизации (окружение/арендатор/кластер) или отдельный кеш на домен */
resume = cache_take(cache_for(env), host);
/* радикальнее: при создании объекта хранить метку окружения в PeerIdentity,
   после восстановления сверять метку и лишь тогда использовать */
```

## Упражнения

### Базовое: щуп границ объекта

Три серии негативных экспериментов над примером resume: длину PSK изменить на 31 (≠ длина дайджеста комплекта), срок жизни 0, SNI со встроенным `\0` — убедиться, что создание отвергается, и прочитать цепочку ошибок. Критерии приёмки: все три серии падают на этапе создания; сообщения об ошибках различают категорию поля.

### Продвинутое: кеш билетов в памяти с TTL

Реализуйте `resume_cache`: ключ (SNI, хеш ticket), ёмкость 64, вытеснение по истечении TTL, потокобезопасность (примитивы главы 52); сверка счётчика вытеснений с `ResumeDropped`. Подключите к двойному циклу (переделка resume_tour): сессия вторая берёт билет из кеша. Критерии приёмки: 10 повторных кругов — все восстановления успешны; при ёмкости 1 вытеснение предсказуемо; PSK на всём пути не покидает границ кеша (просмотр кода).

### Вызов: сравнительный бенчмарк восстановления

На мосте в памяти главы 85 измерьте: полное рукопожатие против восстановительного, по 1000 раз — (a) число раундов Drive, (b) суммарные байты в обе стороны, (c) наличие сообщений сертификатов. Выведите таблицу сравнения и объясните источник каждого различия (наличие сертификатного рейса, число круговых поездок, размер Hello). Критерии приёмки: данные воспроизводимы (фиксированный источник времени); направления различий согласуются с проектными ожиданиями TLS 1.3; вывод ясно отвечает, при какой нагрузке выигрыш восстановления максимален.

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Объект возобновления | билет+PSK+привязка маршрута (SNI/ALPN)+опциональная идентичность; неизменяемое значение, разделяемые ссылки, обнуление при освобождении |
| Границы объекта | только TLS 1.3; ticket 1..65535; PSK=длине дайджеста комплекта; срок 1..604800; ALPN≤255 |
| Семантика времени | `[IssuedAt, ExpiresAt)` полуоткрытый; откат часов — безопасная недействительность; TicketAge — 32-битное модульное сложение |
| Пять станций цикла | полное рукопожатие → подпись ServerTicket → приём TakeResume → кеш приложения → PSK следующего соединения |
| Семантика binder | с ClientHello доказывает владение PSK; приём выяснится с ServerHello (accepted=not yet) |
| Семантика отката | при отказе автоматически полное рукопожатие (key share всегда); resumed — намёк на производительность, не суждение безопасности |
| PSK+DHE | восстановление всё равно с ECDHE; прямая секретность не деградирует; нет чистого PSK/0-RTT |
| Привязка маршрута | опущено — наследование; явно — полное равенство/включение; несовпадение отклоняется до выделения; междоменная изоляция — за приложением |
| Границы кеша | библиотека даёт объект-значение: Limit 0..64/вытеснение/счёт отбрасываний на клиенте; после серверной подписи управляет вызывающий |
| Граница аутентификации | метаданные совпали + ошибка binder = провал аутентификации, fatal; встроено в протокол, не обходится |
