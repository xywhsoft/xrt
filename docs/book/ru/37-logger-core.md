## Ориентация

Журналирование — первая наблюдаемость сервиса. Ядро журнальной модели XRT — разделённая пара: **Logger** (`xrtLogCreate`, имя и порог уровня) и **Sink** (`xrtLogSinkCreate`, пункт назначения вывода) — один Logger может нести несколько Sink, один Sink переиспользуется несколькими Logger; запись, пройдя фильтр уровня Logger, транслируется на все Sink, а **структурные поля** (`xrtLogFieldInt` и другие) доходят с записью прямо до Sink, и тот потребляет их по-своему. Глава разъясняет это разделение и полный рецепт собственного Sink — фундамент для понимания пяти встроенных Sink следующей главы.

## Введение

Три простые потребности пробивают потолок журналирования через printf. Первая: в разработке DEBUG заливает экран, в продакшене нужны только WARN и выше — фильтрация уровней не может держаться на комментировании printf и перекомпиляции. Вторая: одна и та же запись должна идти и в консоль, и в файл (в разных форматах) — пункт назначения не может быть приварен к месту вызова журнала. Третья: к сообщению `request complete` лучше приложить `request_id=42` — при разборе «какой запрос» дороже «какое сообщение», а printf умеет только склеивать строки руками.

Три потребности указывают на одну структуру: **фильтрация уровней** (порог Logger), **разделение вывода** (трансляция Sink), **структурные поля** (поля идут с записью; Sink решает, как показать — текстовый Sink печатает, JSON-Sink собирает в объект fields). Дополнительные дивиденды разделения Logger/Sink разворачиваются в двух следующих главах: пять встроенных типов Sink из коробки (глава 38) и асинхронный Sink, уводящий запись на диск с горячего пути (глава 38).

## Понятия

### Разделение труда Logger и Sink

```diagram flow
- Logger: имя (http/db/auth) + порог уровня (записи ниже порога отбрасываются прямо здесь)
- Sink: имя + собственный порог уровня + функция записи + пользовательские данные
- Композиция: xrtLogAttach вешает Sink в Logger - один носитель много, один Sink переиспользуется
- Подача: xrtLog(x) / xrtLogFields(с полями) -> после фильтра трансляция на все Sink
```

Два порога, каждый на своём посту: порог Logger — **политика модуля** (в модуле db включён DEBUG, остальные на INFO), порог Sink — **политика пункта назначения** (консоль берёт только ERROR, файл принимает всё). Запись обязана пройти двое ворот, прежде чем лечь на диск, — `xrtLogSinkSetLevel` регулирует на ходу (операционная тема главы 38).

### Собственный Sink: четыре элемента и три дисциплины

Четыре элемента `xlogsinkconfig`: **имя** (читаемое для эксплуатации), **порог уровня**, **функция записи** (сигнатура `xlogresult (const xlogrecord*, ptr)`), **пользовательские данные** (носитель цели вывода — FILE*, сокет, что угодно). Три дисциплины функции записи: **запись заимствована** — внутри обратного вызова ссылку удерживать нельзя (память записи принадлежит пути подачи и истекает по возвращении); **семантика возвращаемого значения** — `XLOG_RESULT_WRITTEN`/`_ERROR` суммируются и репортятся Logger (отказ одного Sink не валит остальные); **ноль промежуточных распределений** — функция записи горячего пути форматирует и пишет напрямую, не распределяя на каждую запись (прямой fprintf образца — эталон).

### Структурные поля: значения идут с записью

| Конструктор | Тип поля |
| --- | --- |
| `xrtLogFieldInt` / `Float` | числовые поля |
| `xrtLogFieldString` | строковое поле (представление) |
| `xrtLogFieldTime` | поле времени (значение в микросекундах) |
| `xrtLogFieldError` | **поле ошибки** — xerror главы 4 доставляется прямо в журнал |
| `xrtLogFieldNull` | сигнальное значение пустоты |

Ценность полей — в **свободе потребителя**: текстовый Sink может игнорировать поля или печатать пары ключ-значение, JSON-Sink собирает их в объект `fields` (форма вывода json-образца главы 38), а ваш собственный Sink может отбирать только интересующие поля для тревожной сигнализации. `xrtLogFieldError` заслуживает отдельного упоминания — объект ошибки входит в журнал с полностью сохранённой цепочкой причин (глава 4), и при разборе «что за ошибка + почему» видно одним взглядом.

### Система уровней

Пять уровней `XLOG_TRACE/DEBUG/INFO/WARN/ERROR` (числового возрастания). Соглашения о семантике уровней: TRACE — чертёж отладки (вплоть до «смущающе подробных» деталей), DEBUG — диагностика разработки, INFO — бизнес-веха, WARN — автоматически восстановимая аномалия, ERROR — сбой, требующий вмешательства человека. Опыт настройки порогов: **в продакшене Logger на INFO, DEBUG включается по модулям** — глобальный DEBUG это потоп журналов; адресное включение — вот диагностика.

## Примеры

### Полная программа: собственный Sink и структурные поля

Из образца репозитория `examples/logging/core/main.c` — около 60 строк через весь цикл Logger/Sink/поля:

```embed path="examples/logging/core/main.c" title="examples/logging/core/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/logging/core/main.c -lws2_32 -liphlpapi
[INFO] example: request complete
```

**Что только что произошло.** (1) `exampleWrite` — это весь собственный Sink: fprintf пишет напрямую в формате `[级别] 名字: 消息` ([уровень] имя: сообщение), `xrtLogLevelName` превращает перечисление в читаемое имя, `ferror` решает между WRITTEN и ERROR — все три дисциплины (заимствование/возвращаемое значение/ноль распределений) соблюдены. Заметьте: поля он **не потребляет** — request_id этим Sink проигнорирован, и это ровно воплощение тезиса «способ потребления полей решает каждый Sink сам». (2) `Config.UserData = stdout` — та же функция записи с stderr или файловим указателем станет другим пунктом назначения; пользовательские данные — универсальный слот Sink. (3) `xrtLogCreate("example", XLOG_DEBUG)` строит Logger, `xrtLogSinkCreate` — Sink, `xrtLogAttach` компонует их — сборка в три шага. (4) `xrtLogFields` подаёт запись с одним целочисленным полем; возвращаемое значение сверяется с WRITTEN — отказы пути подачи тоже проверяются (Sink полон или закрыт). (5) Порядок финала: сперва `SinkFree`, потом `LogFree` — Sink это ресурс по ссылке, он может быть освобождён независимо до освобождения Logger.

Из `examples/logging/printf/main.c` — удобная форма форматной подачи:

**Что только что произошло.** Подача в стиле printf (семейство `xrtLogPrintf`; строка формата принимает C-строки, не представления) внутри идёт через форматирование главы 25 — `"request=%u status=%u"` и аргументы склеиваются в текст сообщения за один шаг у входа подачи. **Выбор между слоем удобства и структурными полями**: поля для машинного потребления всегда через `LogFields` (поля хранят типы, JSON-Sink собирает их в объект); склеенные сообщения для человеческих глаз — через слой printf; при смешивании помните: «поле, вошедшее в текст сообщения, больше не структурированные данные».

## Контракты

- **Заимствованная запись**: функция записи Sink не удерживает ссылок на запись; представления полей также истекают с обратным вызовом.
- **Возвращаемые значения**: WRITTEN/ERROR суммируются Logger; отказ одного Sink не задевает остальные.
- **Ноль распределений**: функция записи пишет напрямую, не распределяя на каждую запись.
- **Два порога**: порог Logger — политика модуля, порог Sink — политика пункта назначения; запись проходит двое ворот до диска.
- **Поля хранят типы**: структурные поля идут через `LogFields`; слой printf собирает только показательный текст.
- **Поле ошибки**: `xrtLogFieldError` несёт объект ошибки главы 4 — вся цепочка причин входит в журнал.

### От примеров к инженерии: три хозяина журналирования

**Библиотечный код** (модули, написанные для других): никакого глобального Logger — принимайте Logger, внедрённый вызывающим, или стройте независимый экземпляр по имени модуля (префиксы `xrt/db`, `xrt/http` естественно делят домены); библиотека никогда не трогает Sink напрямую (политика вывода — привилегия приложения). **Прикладной сервис**: сборка на старте — дерево Logger и набор Sink по конфигурации (пять встроенных типов главы 38 плюс собственный тревожный Sink), уровни читаются из переменных окружения или конфигурации, при грациозной остановке Flush и освобождение (дисциплина финала асинхронного Sink — в следующей главе). **Инструментальные программы**: одного консольного Logger плюс одного текстового Sink достаточно — printf, улучшенный до сорта; пять минут сборки — польза на всю жизнь. Общая дисциплина трёх хозяев: **сборка журналирования концентрируется рядом с main** — создание Logger, рассыпанное по бизнес-коду, — отправная точка дрейфа конфигурации.

### Одна привычка: перед записью подумайте о поиске

Первый потребитель журнала — «вы, разбуженный в три часа ночи через три дня». Перед каждой записью прошепчите три вопроса: **можно ли по ней локализовать проблему** (есть ли корреляционное поле вроде request_id); **верен ли уровень** (это веха INFO или сбой ERROR); **верен ли порядок величин** (сколько этих записей в секунду на пике — выдержит ли диск). Записи, не прошедшие три вопроса, не пишутся вовсе: журнал, будучи написанным, — обязательство; поисковый — актив. Структурные поля — техническая опора привычки: корреляционные поля в LogFields, уровень по таблице семантик, объём наблюдается при нагрузочных тестах — статистика и ротация главы 38 — операционное продолжение привычки.

## Ловушки

### Ловушка 1: сохранение указателя записи в обратном вызове Sink

Симптом: последующее использование сохранённых указателей записи или полей читает висячее содержимое — та же семья, что ловушки заимствованной итерации глав 18/32.

Причина: запись живёт на стеке подачи и возвращается сборщиком по возврату обратного вызова; сохранение ссылки принимает её за владеющий объект.

```c bad
static xlogresult slowWrite(const xlogrecord* pRecord, ptr pData)
{
	gPending = pRecord;          /* сохранено глобально "на потом" - висяче по возврату */
	return XLOG_RESULT_WRITTEN;
}
```

```c good
static xlogresult slowWrite(const xlogrecord* pRecord, ptr pData)
{
	queue_push(pData, pRecord);  /* очередь делает глубокую копию: поля и сообщение копируются до постановки */
	return XLOG_RESULT_WRITTEN;
}
```

### Ловушка 2: глобальный DEBUG в продакшене

Симптом: потоп журналов — диск забит, настоящие ERROR утоплены; производительность сползает с объёмом.

Причина: порог уровня — это политика, а не умолчание — глобальный DEBUG превратил «диагностику разработки» в «постоянное состояние».

```c bad
xlogger* gLog = xrtLogCreate(XRT_STR_LITERAL("app"), XLOG_DEBUG);
/* DEBUG на все модули: каждый SQL, каждое попадание в кеш пишется на диск */
```

```c good
xlogger* gLog = xrtLogCreate(XRT_STR_LITERAL("app"), XLOG_INFO);
xlogger* gDbLog = xrtLogCreate(XRT_STR_LITERAL("db"), XLOG_DEBUG);
/* DEBUG только адресно на модуль db - точная диагностика, контролируемый объём */
```

## Упражнения

### Базовое: проверка двойного порога

Постройте Logger с DEBUG и Sink с порогом WARN; подайте по очереди TRACE/DEBUG/INFO/WARN/ERROR — пересчитайте, сколько записей реально дошло до функции записи.

### Продвинутое: тревожный Sink

Напишите собственный Sink, интересующийся только записями уровня ERROR с полем ошибки; при попадании извлеките поля и отправьте в свой «канал тревоги» (подойдёт printf-имитация); остальные записи возвращают WRITTEN, ничего не записывая, — демонстрация права выбора потребления полей.

### Вызов: кольцевой Sink в памяти

Реализуйте Ring Sink: кольцевой буфер на фиксированные N записей; Write копирует запись (сообщение + поля глубоко; память из пула или арены главы 22); предоставьте `dump()`, экспортирующий последние N строк текстом. Критерии приёмки: после 1000 подач dump — ровно последние N; ноль утечек (статистика главы 6 подтверждает); сама функция записи без распределений (память под копии подготовлена при создании Sink).

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Разделение | Logger (имя + порог) / Sink (пункт назначения + порог); один носитель — много, один Sink — переиспользуется |
| Четыре элемента | имя / уровень / функция записи / пользовательские данные — весь собственный Sink |
| Три дисциплины | запись заимствована и не удерживается / семантика возвращаемого значения / ноль распределений в функции записи |
| Семейство полей | Int/Float/String/Time/Error/Null — с типами, прямо до Sink |
| Слой удобства | подача в стиле printf; машинные поля — всегда через LogFields |
| Семантика уровней | TRACE чертёж / DEBUG диагностика / INFO веха / WARN восстановимо / ERROR вмешательство человека |
| Политика порогов | продакшен Logger INFO + адресный DEBUG по модулям |
