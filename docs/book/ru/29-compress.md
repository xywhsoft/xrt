## Ориентация

Модуль compress реализует сжатие Deflate и обёртку gzip-контейнером — стандартный алгоритм транспортного кодирования HTTP, файлового сжатия, архивации журналов. Два режима употребления закрывают два класса сценариев: **разовое** (`DeflateAll`: вход-представление, выход — владеющий буфер; беззаботный путь для малых и фиксированных данных) и **потоковое** (`Init/Process/Finish`: подача кусками; сетевые потоки и большие файлы не грузятся в память целиком). Две инженерные нити проходят через главу: **детерминированность продукта** (одна конфигурация и один вход — байт в байт одинаковый выход; предпосылка адресации по содержимому и кеширования) и **бюджет накладных расходов** (gzip-контейнер стоит фиксированные 18 байтов; малые данные могут «сжаться» в большую величину). Том 4 закрывается этой главой — полный инструментальный конвейер обработки текста собран, и со следующей главы мы входим в структурированные данные (value/JSON/XSON), целиком стоящие на фундаменте этого тома и тома 3.

## Введение

Три типовые нагрузки. **Тело HTTP-ответа**: текст от нескольких КБ до нескольких МБ; сжатие срезает объём передачи на 70%+ — но обрабатывать нужно потоково: сервер не обязан копить весь ответ в памяти ради сжатия. **Архивация журналов**: ночью дневные журналы пакуются в `.gz` — большой файл подаётся кусками, потребление памяти не зависит от размера файла. **Снимок конфигурации**: несколько КБ структурного текста — разовый API закрывает дело в три строки; но сперва надо пройти проверку бюджета накладных расходов (ниже). Общий вопрос трёх нагрузок — **когда сжимать**: заголовок и хвост gzip стоят около 18 фиксированных байтов; 34 байта насыщенного повторами текста сжимаются до 30 — чем меньше данные и чем выше их случайность, тем тоньше выигрыш, вплоть до отрицательного. «Не сжимать ниже 1 КБ и уже сжатые форматы (сами jpg/zip)» — обычная эмпирическая линия HTTP-промежуточного ПО; первое упражнение главы заставит вас построить собственную линию на цифрах вашей машины — эмпирическая линия это старт, измеренная линия — линия вашего проекта.

## Понятия

### Два режима (сперва запомните форму, потом функции)

```diagram flow
- Разовое: DeflateAll берёт вход-представление + конфигурацию -> владеющий gzip-буфер; малые данные в три строки
- Потоковое: Init создаёт -> Process кормит кусками -> Finish завершает; память не зависит от общего размера
- Переиспользование: Reset обнуляет состояние потока и начинает заново - второй кусок данных не строит внутренние структуры заново
```

Три состояния потокового режима изоморфны `xutf8state` главы 27 — «машина состояний + подача кусками + маркер конца» — универсальная форма XRT для неограниченных данных. `Process` может делить как угодно (размер куска не влияет на продукт — выходы потокового и разового режимов **байт в байт одинаковы**, это подтвердится в примере); `Finish` завершает и порождает трейлер.

### Gzip-контейнер и детерминированность

`DeflateAll` по умолчанию выдаёт формат gzip: 10 байтов заголовка + поток Deflate + 8 байтов хвоста CRC32/длины. В заголовке есть инженерное свойство «магического уровня»: **одна конфигурация и один вход дают байт в байт одинаковый выход** — без метки времени и прочих переменных полей (в отличие от утилиты gzip, которая по умолчанию встраивает время). Детерминированность покупает три вещи: адресацию по содержимому (отпечатки главы 12 как ключи кеша — одни данные в любой момент сжимаются в один ключ), снимки для тестов (сжатый продукт можно целиком записать в утверждение) и распределённую согласованность (продукты разных узлов сравнимы байт в байт).

### Уровень сжатия и границы ресурсов

Центральный параметр конфигурации — Level (0~9: 0 — упаковать без сжатия, 6 — по умолчанию, 9 — минимальный объём и минимальная скорость). Опыт выбора уровня: **6 для сетевой передачи** (кривая выигрыша резко выполаживается после 6), **9 для архивного хранения** (нечувствительно ко времени), **4 и ниже при тесном CPU**. Со стороны границ ресурсов: размер выхода при распаковке объявляется сжатыми данными, но **распаковка недоверенного входа обязана получить верхний предел** — оборона от zip-бомб (крошечный вход, разворачивающийся в исполинскую выдачу) это и есть семейство `iMaxInputBytes` из `xrtresourcelimits` главы 3, настроенное на сценарий распаковки; при работе со сжатыми данными извне выставлять его обязательно.

### Стык с HTTP

В главах HTTP тома 9 вы увидите полную цепочку `Content-Encoding: gzip`; здесь готовится плоскость данных: тело ответа сжимается потоково (сжимаем, пока отправляем), статические файлы сжимаются заранее и разово (`.gz` лежит на диске), при неудачном согласовании — откат без сжатия. У Base64 главы 28 здесь тоже комбинированное место: gzip + Base64 — стандартная двойка «сжатие в текстовый канал».

## Примеры

### Полная программа: разовое сжатие и бюджет накладных расходов

Из образца репозитория `examples/compress/deflate/main.c`:

```embed path="examples/compress/deflate/main.c" title="examples/compress/deflate/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/compress/deflate/main.c -lws2_32 -liphlpapi
plain=34 gzip=30
```

**Что только что произошло.** (1) `xrtDeflateConfigInit` берёт конфигурацию по умолчанию (Level 6, gzip-контейнер) — структура конфигурации сперва Init, потом меняются нужные поля: единая поза на всю библиотеку. (2) 34 байта насыщенного повторами текста сжимаются в 30: поток Deflate занимает около 12 байтов (повторы съедены словарным сопоставлением), плюс фиксированные 18 байтов контейнера — **бюджет накладных расходов** как на ладони: как бы коротки ни были данные, 18 байтов контейнера никуда не денутся; линия 34→30 — эмпирическое доказательство «тонкого выигрыша на малых данных». (3) Детерминированность продукта проверяется руками: сожмите дважды и сравните байт в байт (`Hash64` главы 12 даёт самый быстрый отпечаток) — одинаковый отпечаток и есть машинное свидетельство детерминированности.

### Полная программа: полный потоковый интерфейс и круговой проход

Из `examples/compress/stream_tour/main.c` — кусковое сжатие, потоковая распаковка и переиспользование состояния одной витриной:

```embed path="examples/compress/stream_tour/main.c" title="examples/compress/stream_tour/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/compress/stream_tour/main.c -lws2_32 -liphlpapi
compress: deflate valid/done/size ok (split=2 writes)
compress: inflate roundtrip original=51
compress: reset reuse second-stream ok
compress: config corrupt rejected
```

**Что только что произошло.** (1) Потоковый Deflate получает данные в два куска (`split=2`), а gzip на выходе байт в байт совпадает с разовой версией — кускование лишь способ подачи и не меняет продукт; это гарантирует взаимозаменяемость сервера «сжимаем по мере приёма» и преконфигурированного продукта «сжали блоком». (2) Потоковый Inflate разворачивает gzip обратно в 51 байт оригинала — `roundtrip` есть окончательный судья корректности сжатия. (3) После `Reset` тот же объект состояния начинает второй поток — внутренний словарь и прочие структуры переиспользуются; высокочастотное сжатие мелких кусков (по потоку на строку журнала) не строит и не рушит всё заново. (4) Последняя строка — валидация конфигурации: умышленно нелегальный Level — и сжатие отвергается до старта; «плохая конфигурация умирает на входе» — N-е повторение той же философии, что строгий разбор главы 26 и STRICT-перекодирование главы 27.

## Контракты

- **Два режима**: малые данные — `DeflateAll` в один шаг; потоковое `Init/Process/Finish` держит память независимо от общего объёма; кускование продукт не меняет.
- **Детерминированность**: одна конфигурация и один вход — байт в байт; годится для адресации по содержимому и тестовых снимков.
- **Бюджет накладных расходов**: gzip-контейнер — фиксированные ~18 байтов; на малых данных выигрыш может стать отрицательным — постройте собственную линию «минимального сжимаемого размера».
- **Выбор уровня**: сеть 6, архив 9, чувствительность к CPU 4-; кривая выигрыша резко выполаживается после 6.
- **Линия обороны распаковки**: для недоверенного входа — обязательный верхний предел выхода (границы ресурсов), защита от бомб распаковки.
- **Потоковая форма**: Init/Process/Finish + переиспользование Reset — универсальный потоковый паттерн, изоморфный `xutf8state`.

### Карта выбора алгоритма сжатия

Deflate — не единственный алгоритм сжатия; при инженерном выборе стоит знать его соседей. **Deflate/gzip** (эта глава): король совместимости — браузеры, командная строка и стандартные библиотеки всех языков его знают; сжатие среднее; CPU дешёв. **zstd/br** (внешние библиотеки): лучше и по степени, и по скорости, но тянут сторонние зависимости — по принципу нуля зависимостей XRT их нет в ядре, интегрируйте со стороны хоста. **Семейство LZ4**: сверхбыстро, но степень низкая — для обмена данными в памяти, чувствительного к задержкам. Практическое дерево решений: **открытая совместимость → Deflate (выбора нет — это лингва франка)**; внутренние замкнутые линии с чувствительностью к метрикам → оценивайте внешние алгоритмы; память/реальное время → без сжатия или LZ-класс. Три вещи, которым учит глава — потоковый режим, бюджет накладных расходов, границы ресурсов — верны для любого алгоритма: меняется алгоритм, не дисциплина; эти три и есть ствол инженерии сжатия.

### От примеров к инженерии: три хозяина сжатия

**Транспортное промежуточное ПО**: висит на пути ответа, сжимает потоково, решает «жать или нет» по типу содержимого и размеру — сюда приземляется линия суждения ловушки 1. **Архивные пакетные задачи**: ночные проходы сканируют каталоги и порождают `.gz` — упражнение-вызов и есть его прототип; детерминированный продукт делает инкрементальные архивы проверяемыми. **Сжатие одиночных сообщений**: мгновенные сообщения, записи телеметрии — сперва бюджет накладных расходов, потом решение; большинство одиночных сообщений сжимать не нужно, правильный ответ — накопить пачку и сжать её. Поверх трёх хозяев — одна общая дисциплина: **сжимать как можно ближе к источнику** — данные, сжатые один раз у источника и не разворачиваемые по пути, экономят порядок CPU по сравнению с «развернуть и сжать на каждом прыжке».

## Ловушки

### Ловушка 1: безусловное сжатие малых данных

Симптом: после промежуточного ПО «gzip для всего» малые ответы замедлились, а объём передачи даже вырос; мониторинг показывает рост CPU без экономии полосы.

Причина: фиксированные накладные расходы контейнера плюс низкая избыточность малых данных — бюджет `plain=34 gzip=30` на малом конце норма, а не исключение; дожимать уже сжатые форматы (картинки, zip) — чистый убыток.

```c bad
if ( Response.Size > 0 ) {   /* сжимать, пока есть данные */
	Compress(&Response);      /* 300 байтов JSON могут сжаться в 320 */
}
```

```c good
if ( Response.Size >= 1024 && !AlreadyCompressed(Type) ) {
	Compress(&Response);      /* жать только за эмпирической линией и только сжимаемое */
}
```

### Ловушка 2: распаковка недоверенных данных без предела

Симптом: при обработке загруженных извне архивов память сервиса взлетает и его кладут на лопатки — отчёт службы безопасности гласит «бомба распаковки».

Причина: степень сжатия Deflate может быть чудовищной (одно содержимое повторено десять тысяч раз); крошечный вход разворачивается в исполинский выход — распаковка без предела отдаёт право распределения атакующему.

```c bad
bytes pPlain = xrtInflateAll(pGzipView, &iSize, NULL, 0);   /* без предела */
/* атакующий протягивает 10 КБ входа, на выходе 4 ГБ - процесс падает на месте */
```

```c good
xrtresourcelimits Limits;
xrtResourceLimitsInit(&Limits);
Limits.iMaxInputBytes = 64 * 1024 * 1024;   /* верхний предел выхода распаковки 64 МБ */
bytes pPlain = xrtInflateAll(pGzipView, &iSize, &Limits, 0);
if ( pPlain == NULL ) {
	RejectUpload();   /* превышение - отказ; линия обороны на границах ресурсов, не в бизнес-слое */
}
```

## Упражнения

### Базовое: бюджет накладных расходов

Сожмите насыщенный повторами текст и случайные байты на 10, 50, 100, 500 и 1000 байтах, записав таблицу из десяти строк «оригинал/сжато/отношение» — найдите линию размера, где «сжатие начинает окупаться» для вашей формы данных, сверьте с бюджетом 34→30 из текста и напишите вывод из одной фразы: «где моей сцене провести линию».

### Продвинутое: потоковое против разового (доказательство детерминированности)

Одни и те же данные сожмите один раз `DeflateAll` и один раз потоково «пятью кусками Process»; утвердите совпадение продуктов байт в байт; затем посчитайте отпечатки `Hash64` обоих продуктов для быстрейшего сравнения. Подсказка: это и есть доказательство предпосылки доверия ключу кеша.

### Вызов: преконфигурирование статических ресурсов HTTP (полная форма хозяина-архива)

Просканируйте текстовые ресурсы каталога (.html/.css/.js) и для файлов за линией размера породите файлы-спутники `.gz`: сжатие потоковое (память не зависит от размера файла), оригиналы сохраняются, метки времени `.gz` синхронны с оригиналами. Критерии приёмки: пиковая память преконфигурирования каталога в 100 МБ ниже 10 МБ; продукты `.gz` детерминированы (отпечатки не меняются при перезапуске); файлы ниже линии размера пропускаются и попадают в список.
