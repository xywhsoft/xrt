## Ориентация

`xreader`/`xwriter` — потоковая абстракция XRT: один и тот же интерфейс `ReadFull`/`WriteFull`/`Seek` работает поверх буферов памяти, файлов и сетевых потоков — **бизнес-код пишется один раз, пункт назначения решает адаптер**. Семантика `Full` — её забота о вас: прочитать или записать ровно указанное число байтов, частичное выполнение — отказ; заготовка цикла повторов на случай короткого чтения/записи исчезает. Глава разбирает ключевые контракты Reader/Writer, встроенные адаптеры (буфер памяти, файл, собственные обратные вызовы) и построчный читатель — высокочастотный сборный узел.

## Введение

Коду сериализации нужно выдать продукт: в тестах — в буфер памяти (утверждение по содержимому), на диск — в файл, в сеть — в поток сокета. Прямой вызов `fwrite` — три пункта назначения, три экземпляра кода; собственный «интерфейс записи» — и вы заново изобретаете модуль io. `xwriter` стандартизует это изобретение: бизнес-код программствует против интерфейса (`xrtWriterWriteFull(W, 数据, 长度)` (W, данные, длина)), а пункт назначения — выбор адаптера в одну строку: `xrtWriterFromBuffer` (память), файловый адаптер (глава 44) или ваш адаптер на обратных вызовах (демонстрация в образце stream_tour).

Семантика `Full` решает другую заготовку, которую пишут каждый день: `fwrite` может записать мало (написано 3 байта из 10 запрошенных) — учебник учит циклу while; `WriteFull` забирает цикл в библиотеку: **либо все 10 байтов записаны, либо отказ**, и возвращаемое значение — окончательный вердикт. Сторона чтения симметрична, семантика EOF у `ReadFull` явная (прочитано меньше запрошенного — отказ: EOF не ошибка, но «не дочитано» — отказ).

## Понятия

### Два интерфейса и семантика Full

```diagram flow
- Reader: Read/ReadFull/Seek/Tell - прочитать полностью или отказ
- Writer: Write/WriteFull/Seek/Flush - записать полностью или отказ
- Адаптеры: Buffer (память) / File (диск) / собственный обратный вызов - одна строка меняет пункт назначения
- Освобождение: Destroy адаптера возвращает сам адаптер, не трогая нижележащий ресурс
```

Разделение `Read` и `ReadFull`: первый «читает сколько может» (потоковое потребление — взял кусок, обработал кусок); второй «читает ровно запрошенное, иначе отказ» (структурное чтение — заголовок сообщения фиксированно 16 байтов, значит читаем ровно 16). Сторона записи симметрична. Мнемоника выбора: **потоковая обработка — обычная версия (сколько взял, столько обработал); фиксированные структуры — версия Full (недобор — отказ)** — обе семантики ясны; ловушка — смешение.

### Адаптер памяти: буфер как пункт назначения

`xrtWriterFromBuffer(&tBuffer)` адаптирует xbuffer главы 15 в Writer — заимствование, а не владение: после уничтожения адаптера буфер жив, ритм `Take` для забора содержимого не меняется. Это позволяет «сперва накопить в памяти, потом решить куда» и «писать сразу в файл» делить один и тот же код сериализации — тесты утверждают по буферу, продакшен меняет файловый адаптер, бизнес-код без правок.

### Построчный читатель: стандартная деталь потокового текста

`xlinereader` (образец line) оборачивает произвольный Reader в «построчную итерацию» — разрезание по строкам, строки-представления заимствованы, конец по EOF. Общее основание сканирования журналов, построчной конфигурации и протоколов с кадрированием по строкам (прелюдия главы 71). Разделение труда со строчным разрезанием строк главы 25: **полный текст уже в памяти** → Split строк; **строки приходят из потока** → построчный читатель (целиком грузить не нужно).

### Собственные адаптеры: обратный вызов как интерфейс

Когда у вашего пункта назначения нет встроенного адаптера (шифровальный конвейер, слой сжатия, сетевой протокол), выход — адаптер на обратных вызовах: предоставьте колбэки read/write и пользовательские данные, контракт интерфейса прежний. Собственный reader/writer образца stream_tour демонстрирует полную форму (включая момент вызова колбэка Close — утверждение `custom close=1`).

## Примеры

### Полная программа: Writer в памяти и точечная перезапись

Из образца репозитория `examples/io/buffer/main.c`:

```embed path="examples/io/buffer/main.c" title="examples/io/buffer/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/io/buffer/main.c -lws2_32 -liphlpapi
hello xrtld
```

**Что только что произошло.** (1) Адаптер `xrtWriterFromBuffer` заимствует буфер — каждая запись WriteFull ложится прямо в него (дополнением), ноль промежуточных копий. (2) `Seek(XSEEK_START, 偏移)` (смещение) перезаписывает в точке: вернуться и поправить уже записанные байты — поза протокольного кодирования «записали заголовок, потом вернулись заполнить поле длины» (та же семья, что BufferWrite главы 15, но через единый интерфейс). (3) `WriterDestroy` возвращает только адаптер — сам буфер жив, содержимое читается и печатается напрямую. Во всём коде ни одного `fwrite`/`memcpy`: решение о пункте назначения сжато в строку адаптера.

### Полная программа: построчный читатель

Из `examples/io/line/main.c` — построчное потребление произвольного Reader-а:

```embed path="examples/io/line/main.c" title="examples/io/line/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/io/line/main.c -lws2_32 -liphlpapi
1: INFO server started
2: WARN queue is busy
3: ERROR request failed
```

**Что только что произошло.** (1) Память сперва адаптируется в Reader (`xrtReaderFromMemory`), затем **принимается** построчным читателем (`xrtLineReaderTake` передаёт владение — после этого исходный указатель Reader-а трогать нельзя); 1024 — начальная ёмкость строки, сверхдлинные строки растут автоматически, буфер расширяется только по фактической длине строки. (2) `xrtLineReaderNext` возвращает три состояния: `XLINE_NEXT_LINE` (строка взята) / `XLINE_NEXT_END` (EOF) / состояние отказа — смешанные концы строк (CRLF вместе с LF) и последняя строка без перевода обработаны корректно. (3) Каждая строка — **заимствованное представление** (поле `Text` у `xlineview`) — срок действия до следующего Next (дисциплина главы 18 прежняя). (4) В режиме приёма `xrtLineReaderDestroy` закрывает и нижележащий Reader — один Destroy собирает всё. Образец stream_tour оставлен для полного чтения: он проходит копирование чтения-записи, Seek/Tell, EOF, собственные адаптеры и момент Close — девять утверждений на девять групп интерфейсов.

## Контракты

- **Семантика Full**: прочитать/записать полностью или отказ; короткое чтение/запись — отказ, а не частичный успех; при EOF ReadFull отказывает («не дочитано» — факт, а не ошибка; семантика слота ошибки — глава 4).
- **Единый интерфейс**: один и тот же бизнес-код над памятью/файлами/сетью — пункт назначения решает только строка адаптера.
- **Заимствованная адаптация**: адаптер Buffer заимствует буфер; Destroy возвращает адаптер, не трогая нижележащий ресурс.
- **Заимствованные строки**: построчный читатель выдаёт представления строк, срок действия — до следующей строки.
- **Собственные адаптеры**: обратные вызовы + пользовательские данные реализуют любое назначение; колбэк Close срабатывает ровно один раз, при Destroy.

### От примеров к инженерии: три хозяина потоковой абстракции

**Сериализация в трёх средах** (полная форма образца один): код структурного вывода смотрит на Writer — тесты подключают адаптер памяти для утверждений, диск подключает файловый адаптер (глава 44), сеть — адаптер протокольного потока (том 7); пункт назначения — выбор адаптера одной строкой, логика сериализации написана один раз. **Конвейер разбора протоколов**: сетевые байты → Reader → заголовок фиксированной длины ReadFull → построчный читатель или дочитка тела до полноты — HTTP-парсер тома 7 и есть промышленная версия этого конвейера. **Обрабатывающий конвейер**: Reader → слой декодирования (потоковая форма перекодирования главы 27) → бизнес-потребление — собственные адаптеры оборачивают «промежуточную обработку» в поток, слои конвейера компонуются единым интерфейсом. Три хозяина сообща подтверждают одну фразу: **ценность абстракции интерфейса не в «подключается много назначений», а в «бизнес-код не движется при смене назначения»**.

### Отношение к буферам главы 15 и файлам главы 44

Разделение трёх слоёв легко перепутать; одно сравнение всё расставляет. **xbuffer (глава 15)**: накопитель байтов — накопил, потом забрал; у него своя семантика памяти. **Адаптеры io (эта глава)**: **приспосабливают** буфер/файл/что угодно к единому интерфейсу — они не владеют данными, они конвертируют интерфейсы. **Файловый модуль (глава 44)**: управление жизненным циклом файла (открыть/закрыть/атрибуты/асинхронность), чьи чтение и запись могут войти в единый интерфейс через адаптеры io. Отношение композиции: файловый адаптер внутри использует файловый модуль, адаптер буфера — xbuffer; слой io — интерфейсный слой над ними обоими. Выбор в коде: важно «как накапливается содержимое» → буфер напрямую; важно «единообразный интерфейс чтения-записи» → эта глава; важен «файл как ресурс» → глава 44.

### Взгляд на дизайн: минимальная полнота интерфейса

Интерфейсная поверхность слоя io крошечная — чтение, запись, позиционирование, сброс, закрытие: пять действий. Но они ровно покрывают все потребности потоковых данных: это **минимальная полнота** — каждый интерфейс высокочастотен, удаляемой избыточности нет. На фоне «больших и полных» потоковых библиотек (десятки удобных функций) минимальная полнота окупается дважды: адаптеры пишутся легко (пяти колбэков достаточно — собственный адаптер стоит копейки), поведение выводится легко (семантических комбинаций мало, ловушек мало). Проектируя собственные слои абстракции, сверяйтесь по этой планке: **точка равновесия между числом интерфейсов и выразительностью лежит там, где «ни один интерфейс нельзя удалить»** — лишние удобные функции принадлежат композиции на бизнес-слое, а не членству в слое интерфейсов.

## Ловушки

### Ловушка 1: чтение структур фиксированной длины обычным Read

Симптом: изредка разъезжается разбор — заголовок говорит 512 байтов, а парсер стартовал после 300 прочитанных; на низкой нагрузке всё чисто, на высокой (или медленной сети) — эпизодически.

Причина: обычный `Read` семантики «сколько смог»; возвращаемое значение — фактически прочитанный объём — использовано как «запрошенное пришло», и при коротком чтении структура разъезжается.

```c bad
xrtReaderRead(R, Header, 16);           /* сколько смог: может прочитать только 9 байтов */
Parse(Header);                           /* разбор 9 байтов как 16-байтовой структуры - смещение */
```

```c good
if ( !xrtReaderReadFull(R, Header, 16) ) {
	return false;   /* меньше 16 байтов: EOF или прерывание - обрабатываем как отказ */
}
Parse(Header);
```

### Ловушка 2: сохранение представлений строк из построчного читателя

Симптом: та же семья, что ловушки заимствования глав 18/25 — сохранённая «строка» дрейфует после следующей итерации.

Причина: построчный читатель переиспользует внутренний буфер — память, на которую указывает представление, перезаписывается следующей строкой.

```c bad
const char* gFirstLine;
while ( xrtLineReaderNext(pLines, &Line) == XLINE_NEXT_LINE ) {
	if ( gFirstLine == NULL ) {
		gFirstLine = Line.Data;   /* сохранено представление - перезапишется следующим Next */
	}
}
```

```c good
str sFirst = NULL;
while ( xrtLineReaderNext(pLines, &Line) == XLINE_NEXT_LINE ) {
	if ( sFirst == NULL ) {
		sFirst = xrtStrDupView(Line);   /* чтобы жила долго - копируем */
	}
}
```

## Упражнения

### Базовое: сериализация в два пункта назначения (доказательство ценности абстракции)

Напишите код сериализации (структура из двух-трёх полей); прогоните его с Writer-ом в памяти и Writer-ом в файл — продукты совпадают байт в байт; утверждение по буферной версии, фиксация на диск файловой, бизнес-код без правок.

### Продвинутое: читатель сообщений фиксированной длины (семантика Full на практике)

Реализуйте чтение протокола через ReadFull: цикл «заголовок длины 4 байта + тело N байтов» — чистый выход на EOF, пропуск пустых heartbeat-сообщений нулевой длины, отказ на сверхдлинные (>1 МБ) как на злонамеренный вход.

### Вызов: считающий адаптер

Реализуйте собственный Writer: оборачивает другой Writer, считает записанные байты и число вызовов, тревожит по порогу (подача через журнал главы 37); Close ровно один раз (срабатывает в Destroy). Критерии приёмки: обёрнутый файловый Writer пишет 1000 записей, счётчик совпадает с фактическим размером файла; при вложении двух считающих адаптеров внутренний и внешний счётчики согласованы.

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Два интерфейса | Reader/Writer; Seek/Tell/Flush в комплекте |
| Семантика Full | прочитать/записать полностью или отказ; фиксированные структуры — всегда Full, потоковое потребление — обычная версия |
| Адаптация памяти | `WriterFromBuffer` заимствует буфер; Destroy не трогает сам буфер |
| Построчное чтение | `xlinereader` превращает любой Reader в построчные представления; строки заимствованы не дольше итерации; Take принимает, Destroy закрывает и нижележащий поток |
| Собственные | обратные вызовы + пользовательские данные реализуют любое назначение; Close ровно один раз при Destroy |
| Смысл | один код сериализации в трёх средах — память/файл/сеть - бизнес-код не движется при смене назначения |
| Трёхслойное разделение | xbuffer копит содержимое / слой io конвертирует интерфейсы / файловый модуль ведает ресурсом |
| Три состояния строки | NEXT_LINE строка взята / NEXT_END конец потока / состояние отказа - смешанные концы и отсутствие хвостового перевода корректны |
