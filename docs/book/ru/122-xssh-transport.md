## Ориентация

Серия SSH открывается. В отличие от «высокоуровневой интеграции» TLS (том 8), философия xssh — **радикальное расслоение**: четыре нижних блока независимы, без выделений и тестируемы по отдельности — **wire** (`ssh_wire`: кодирование/декодирование базовых типов SSH boolean/uint32/string/mpint); **packet** (`ssh_packet`: бинарная пакетная рамка RFC 4253 — длина/padding/нагрузка, не привязана ни к шифру, ни к сети); **packet AES-GCM** (`ssh_packet_aes_gcm`: пакетная обёртка aes128/256-gcm OpenSSH — заголовок длины открытым текстом как AAD, шифрование на месте, шестнадцатибайтовая метка); **transport core** (`ssh_transport_core`: свободная от буферов композиция кодека пакетов + протокольного порядка + бюджетов rekey — синхронный, callback-ный, Future и корутинный клиенты ведут **один и тот же контракт состояния**). Следующие шесть глав строятся на этом слое.

## Введение

Форма линии SSH — «луковица»: прикладные данные (в каналах) завёрнуты в шифрованные пакеты, шифрованные пакеты — в TCP. Пакетная рамка (раздел 6 RFC 4253) фиксирует форму луковицы — `packet_length（4B）| padding_length（1B）| payload | padding` (длина пакета (4Б) | длина паддинга (1Б) | нагрузка | паддинг), причём padding выравнивает весь пакет по блоку (блоки шифра или защита от анализа трафика). **Почему callback паддинга обязателен**: `xrtSshPacketWrite` требует от вызывающего `xsshpaddingproc` и никогда молча не пишет нули — ядро не несёт зависимости от ГСЧ (свобода обрезки); transport пользуется PRNG сессии, тесты — детерминированным паддингом.

Ключевое решение транспортного ядра — **трёхфазная транзакция отправки/приёма** (Prepare/Commit/Abort): отправка сперва `WritePrepare` — итоговый линейный пакет пишется в буфер вызывающего (в этот момент sequence/nonce/бюджет **ещё не двинуты**); после принятия сетевой очередью `WriteCommit` продвигает их; при `XNET_RESULT_AGAIN` тот же линейный пакет сохраняется для повтора при writable (**переподготавливать нельзя** — sequence не переиспользуется); отказ — `WriteAbort` отбрасывает добавленные байты. Максимум один пакет в ожидании фиксации на направление — при противодавлении память не держится и счётчики не переиспользуются.

## Понятия

### wire: система типов SSH

«Формат сериализации» протокола SSH — всего пять базовых типов: `boolean` (1Б), `uint32` (4Б big-endian), `uint64` (8Б), `string` (4Б-префикс длины + байты), `mpint` (целочисленная форма string — каноничное неотрицательное кодирование, лишние знаковые биты сняты). `xsshwriter`/`xsshreader` — пара курсоров без выделений (изоморфна курсорам DER главы 77): `WriterInit` привязывает буфер вызывающего, `WriterWrite*` пишет каждый тип, `Size` отчитывается о выходе; на стороне чтения `ReaderInit/Read*` заимствует ввод и читает по типам. **Строгость**: усечение отвергается, хвостовые данные (на уровне сообщения) отвергаются, неканоничный mpint отвергается — весь словарь парсера сообщений SSH.

### packet: рамка и атомарность

`xrtSshPacketMeasure(载荷长, 块长, &padding长, &packet长)` (длина нагрузки, длина блока, &длина паддинга, &длина пакета) вычисляет рамку: нулевая длина блока берёт минимум RFC 8; явная длина блока 8..255; паддинг минимум 4 байта, весь пакет выровнен по блоку; полная линейная длина `4 + packet_length`. `xrtSshPacketWrite(writer, 载荷, ..., padding回调, 上下文)` (writer, нагрузка, ..., callback паддинга, контекст) даёт полный линейный пакет — callback сперва пишет в стековую рабочую область, к цели переходит лишь при успехе (**writer и номер последовательности при отказе не меняются**). `xrtSshPacketRead(reader, 预算, ..., &packet视图)` (reader, бюджет, ..., &представление пакета) возвращает заимствующее ввод `xsshpacketview`: короткий пакет — `XSSH_NEED_MORE` (инкрементально ждём данные — изоморфизм трёх состояний всей библиотеки); уродливая длина/выравнивание/padding — протокольная ошибка; сверх бюджета — `XSSH_ERROR_OVERFLOW`. **Номера последовательности**: uint32 заворачивается естественно; NULL игнорирует их (самостоятельный инструмент рамки). **Атомарность**: reader завершает всю проверку на копии; только полный успех продвигает ввод, публикует представление и наращивает последовательность — отказ никогда не двигает наполовину.

### packet AES-GCM: AEAD-пакеты OpenSSH

Общая обёртка `aes128-gcm@openssh.com`/`aes256-gcm@openssh.com`: 4-байтовый `packet_length` **остаётся открытым текстом и служит AAD**; `padding_length|payload|padding` шифруется на месте; хвост — 16-байтовая метка. `xsshaesgcm` — **однонаправленное состояние** (чтение и запись инициализируют каждое своё; одно состояние конкурентно не продвигается): ключ 16/32 байта, начальный IV 12 байтов (первые 4 — фиксированный IV + последние 8 — big-endian счётчик вызовов); **счётчик нарастает на каждый пакет и останавливается перед UINT64_MAX, никогда не заворачиваясь** (нулевая терпимость к переиспользованию nonce — дисциплина главы 74, ставшая протокольной). Четыре входа: `AesGcmMeasure` (вычисление рамки с выравниванием на 16) / `AesGcmWrite` (строит в неподтверждённой области writer и шифрует на месте, ноль heap-выделений) / `AesGcmRead` (**сперва аутентификация, потом расшифровка** в буфер вызывающего — провал аутентификации не меняет выходного открытого текста; успех с нелегальной структурой обнуляет расшифрованное тело) / `AesGcmInvocation` (запрос счётчика следующего пакета). Отказы (ёмкость/усечение/callback/аутентификация/исчерпание состояния) не продвигают ни reader, ни writer, ни sequence, ни counter.

### transport core: композиция без буферов и NEWKEYS

```diagram flow
- Отправка: WritePrepare (итоговый пакет в буфер вызывающего, без продвижения) -> успех очереди -> WriteCommit (продвигает sequence/nonce/бюджет)
  -> при AGAIN (XNET_RESULT_AGAIN) сохранить исходный пакет и повторить -> для отказа WriteAbort
- Приём: Inspect (читаем 4Б заголовка длины) -> агрегировать ввод по WireSize -> ReadPrepare (аутентификация + классификация + проверки состояния)
  -> верхний слой разбирает payload -> ReadCommit / ReadAbort (аутентифицированный пакет отвергнут -> ядро закрывается, без фальшивого отката)
- NEWKEYS: после постановки пакета своей стороны направление записи закрывается, активирует SetWriteAesGcm; после аутентификации пакета противоположной стороны SetReadAesGcm
  -> сброс последовательности strict-kex + обнуление счётчиков rekey направления + переключение cipher одним вызовом
  -> KexComplete истинно лишь после срабатывания обоих направлений
```

**Семантику ReadAbort стоит прожевать**: кодек уже потребил этот пакет — отвергнуть аутентифицированный пакет значит, что протокольный слой больше не доверяет; transport закрывается сразу, «не изображает откат номера последовательности с продолжением общения» (откат последовательности = изготовление окна повторного воспроизведения). **Автоматическое распознавание**: Prepare автоматически распознаёт три класса особых пакетов KEXINIT/NEWKEYS/USERAUTH_SUCCESS — бюджеты rekey продвигаются на этих границах. **Граница сетевой адаптации**: буфер отправки можно отдать напрямую `xrtNetStreamSend/SendRef`; приём может заимствовать непрерывный участок `xrtNetStreamBuffer` — слой адаптации ведает лишь противодавлением/жизненным циклом/deadline/cancel, **правила SSH не переimplements**.

**Что только что произошло.** (1) `xsshwriter` привязывает 32-байтовый стековый буфер; `xrtSshPacketWrite` пишет 8-байтовую нагрузку `\2ignore` (номер сообщения 2 = SSH_MSG_IGNORE) — детерминированный callback `exampleSshPadding` даёт паддинг (только для образца; продакшн передаёт `xrtSshSecurePadding` или PRNG сессии — карточка контракта прямо говорит «детерминированный паддинг образца нельзя использовать в реальном SSH transport»). (2) `xrtSshPacketRead` вызывается дважды: первый без выходного параметра (лишь проверка), второй берёт `xsshpacketview` — три представления `PacketSize/Payload/Padding` заимствуют ввод. (3) Параметр бюджета `8u` — явный потолок; реальный transport берёт согласованный лимит. Совпадение круга означает самосогласованность рамки: SSH-редакция паттерна круга DER главы 77.

## Контракты

- **Строгость wire**: усечение/хвосты/неканоничный mpint отвергаются; пара курсоров без выделений; байты writer при отказе неизменны.
- **Пакетная рамка**: длина блока 8..255 (ноль = умолчание 8); паддинг ≥4, весь пакет выровнен по блоку; линейная длина `4+packet_length`.
- **Обязательность callback паддинга**: без молчаливого заполнения нулями; callback сперва в стек, потом фиксация; `XSSH_ERROR_CALLBACK` отличим от протокольных ошибок.
- **Атомарность reader**: вся проверка на копии проходит до продвижения ввода/публикации представления/наращивания последовательности; короткий пакет NEED_MORE; сверх бюджета OVERFLOW.
- **Состояние GCM**: однонаправленное, независимая инициализация; IV = fixed(4) + counter(8 big-endian); счётчик останавливается на UINT64_MAX без заворота.
- **Атомарность GCM**: сперва аутентификация, потом расшифровка; отказ не двигает reader/writer/sequence/counter; провал аутентификации не меняет открытый текст; успех с нелегальной структурой обнуляет тело.
- **Алиасинг GCM**: pPlain не перекрывает ввод/состояние; записываемый Payload не перекрывает область этого вывода (сохранение пути шифрования на месте).
- **Транзакция отправки**: Prepare не продвигает; Commit продвигает; AGAIN сохраняет исходный пакет для повтора (без переподготовки); Abort отбрасывает; максимум один ожидающий пакет на направление.
- **Транзакция приёма**: Inspect→агрегация→ReadPrepare (аутентификация + классификация)→ReadCommit/Abort; ReadAbort закрывает ядро (аутентифицированный пакет не откатывается).
- **NEWKEYS**: направление записи закрыто до успеха SetWriteAesGcm; сброс strict-kex + обнуление счётчиков + переключение cipher одним вызовом; KexComplete лишь при обоих направлениях.
- **Граница сети**: слой адаптации ведает противодавлением/жизненным циклом/deadline/cancel — правила SSH принадлежат ядру и не переimplements.

## Ловушки

### Ловушка 1: повторный Prepare после AGAIN

Симптом: противоположная сторона сообщает об отказе MAC/аутентификации или просто отключается — переподготовка создала новый пакет, чей sequence/nonce конфликтует с уже стоящим в очереди.

Причина: Prepare не продвигает счётчики именно ради повторов при AGAIN: **сохраните тот же линейный пакет и повторите постановку в очередь в неизменном виде**. Повторный Prepare = пересборка с новым паддингом/nonce, развилка счётчиков против старого пакета, возможно уже частично принятого очередью.

```c bad
if ( prepare(&Core, Buf) == OK ) {
	if ( enqueue(Buf) == AGAIN ) {
		prepare(&Core, Buf);   /* пересобран: риск развилки nonce/последовательности */
		enqueue(Buf);
	}
}
```

```c good
xrtSshTransportCoreWritePrepareWithPadding(&Core, Buf, ...);
if ( enqueue(Buf) == XNET_RESULT_AGAIN ) {
	wait_writable();          /* сохранить исходный пакет */
	enqueue(Buf);             /* повторить в неизменном виде */
}
/* Abort — только при решении не отправлять */
```

### Ловушка 2: у packet-слоя забыли потолок бюджета пакетов

Симптом: злой сервер объявляет сверхпакет — чтение растёт и растёт до OOM.

Причина: `iMaxPacketSize` с нулём берёт лимит по умолчанию, но **бюджет — линия обороны, а не опция**; даже в сценариях самостоятельного инструмента передавайте его явно (хотя бы константу умолчания — самодокументирование).

```c bad
xrtSshPacketRead(&Reader, 0u, 0u, NULL, &Packet);  /* полагается на умолчание - намерение бюджета неясно */
```

```c good
xrtSshPacketRead(&Reader, XSSH_PACKET_MAX_DEFAULT, 0u,
	NULL, &Packet);   /* явный бюджет: код как документ */
```

### Ловушка 3: одно состояние GCM на чтение и запись

Симптом: шифрование и расшифровка путаются — расшифровка пакета N взяла counter пакета N+1.

Причина: `xsshaesgcm` — **однонаправленное** состояние; в SSH у каждого направления свои ключ, IV и счётчик; одно состояние на обе стороны — два направления делят счётчик.

```c bad
xsshaesgcm Gcm;
xrtSshAesGcmInit(&Gcm, Key, IV);
write_packet(&Gcm, ...);   /* используется для записи */
read_packet(&Gcm, ...);    /* и для чтения: конфликт counter */
```

```c good
xsshaesgcm WriteGcm, ReadGcm;
xrtSshAesGcmInit(&WriteGcm, C2SKey, C2SIv);  /* клиент -> сервер */
xrtSshAesGcmInit(&ReadGcm, S2CKey, S2CIv);   /* сервер -> клиент */
```

## Упражнения

### Базовое: круг пяти типов wire

Writer-ом/reader-ом записать и прочитать по одному boolean/uint32/uint64/string/mpint; проверить круг и байтовую форму (против примеров кодирования RFC 4251). Критерии приёмки: каноничное кодирование mpint (снятие знакового бита) выводимо вручную; усечённый ввод отвергается.

### Продвинутое: эксперименты на границах пакетной рамки

Сканировать `PacketMeasure` по нагрузкам 0–100 байтов, построить изменения padding/packet_length; проверить разницу выравнивания при длине блока 8 и 16. Затем построить чтение сверх бюджета и проверить OVERFLOW. Критерии приёмки: измеренные значения сходятся с формулами RFC 4253 §6.

### Вызов: двунаправленный GCM-канал

Два процесса (или два ядра в одном) строят GCM-канал на выведенных из KEX ключах двух направлений: обмен 1000 пакетов, счётчики монотонны, assert, что после пакета UINT64_MAX-1 запись отвергается (исчерпание состояния — имитировать малым счётчиком). Критерии приёмки: полный дуплекс без ошибочных пакетов; путь исчерпания счётчика отказывает явно, без заворота.

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Четыре блока | wire (типы) → packet (рамка) → aes_gcm (шифрованные пакеты) → transport core (композиция + порядок + rekey) |
| Типы wire | boolean/uint32/uint64/string/mpint; курсоры без выделений; строгое отвержение |
| Пакетная рамка | 4Б длина + 1Б длина паддинга + нагрузка + паддинг; выравнивание по блоку; линейная длина = 4+packet_length |
| Callback паддинга | обязателен; сперва стек, потом фиксация; ошибки CALLBACK отдельно от протокольных |
| Атомарность reader | вся проверка на копии до продвижения; NEED_MORE/OVERFLOW/протокольная ошибка — три состояния |
| Форма GCM | заголовок длины открытым текстом как AAD; нагрузка шифруется на месте; метка 16Б; counter не заворачивается |
| Атомарность GCM | сперва аутентификация, потом расшифровка; любой отказ не двигает ни один счётчик |
| Транзакция отправки | Prepare (без продвижения) → Commit / AGAIN сохраняет / Abort; один пакет на направление |
| Транзакция приёма | Inspect→агрегация→Prepare→Commit/Abort (закрывает ядро) |
| NEWKEYS | активация по направлениям; сброс strict-kex одним вызовом; оба живы — тогда KexComplete |
| Граница сети | буферы напрямую в Send/SendRef/Buffer — слой адаптации правила SSH не переimplements |
