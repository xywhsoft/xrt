## Ориентация

Отображения решают «найти значение по ключу»: таблица маршрутов находит статистику по пути, таблица сессий — состояние по ID, кэш — запись по ключу. XRT даёт два семейства: **`xmap`** с ключом — произвольной байтовой строкой (`xbytesview`, включая вложенные нули), итерация в **порядке вставки**; **`xintmap`** с ключом — нативным `int64` (без вычисления хеша), итерация в **порядке возрастания ключей** — и на разреженных ключах это самый быстрый «разреженный массив». Оба делят один ритм употребления — герой главы `GetOrAdd`: «найти или создать» за один шаг, возвращающий **указатель на нуль-инициализированный слот значения**; сценарии счёта — просто `++`. Это высокочастотный контейнер, по употребимости уступающий только массиву, и центральная клетка таблицы выбора главы 23.

## Введение

Подсчёт попаданий маршрутов HTTP-сервиса: каждый запрос прибывает, по пути находится счётчик маршрута и инкрементируется; путь, которого никогда не было, получает новый счётчик. В записи «сперва проверить наличие, при отсутствии вставить, после вставки инициализировать» каждое звено имеет путь отказа, и две трети кода — защита размером с ноготь. Хуже то, что «поиск дважды» — `Has` ищет раз, `Add` внутри локализует ещё раз, и горячий путь напрасно жжёт двойное хеширование.

`GetOrAdd` склеивает три шага в один: ключ существует — возвращается имеющийся слот; не существует — **вставляется нуль-инициализированный новый слот**, и возвращается он; выходной параметр сообщает, была ли это вставка. Сценарий счёта становится двумя строками: взять слот, прибавить. Это наглядный пример «форма API решает форму кода» — хороший интерфейс делает правильную запись самой короткой.

## Понятия

### Два семейства, два вида ключей

| Измерение | `xmap` байтовые ключи | `xintmap` целочисленные ключи |
| --- | --- | --- |
| Тип ключа | `xbytesview` (произвольная двоичность) | `int64` (нативный) |
| Вычисление ключа | хеширование (семейство SipHash) | прямое битовое отображение, ноль вычислений |
| Порядок итерации | **порядок вставки** (внутренняя цепь порядка) | **возрастание ключей** |
| Типовые сценарии | строковые ключи, ключи кодирование-отчётов, конфигурации и отчёты | ID сессий, разреженные индексы, экспорт по ID |

В мире байтовых ключей «пути, имена полей, отпечатки» — законные ключи: `xbytesview` не требует нуль-терминации; двоично-безопасное соглашение главы 3 действует и для ключей. Целочисленные ключи перепрыгивают хеширование и локализуют напрямую; на малых непрерывных ключах это самый быстрый разреженный массив; итерация — по возрастанию ключей, «экспорт всех сессий в порядке ID» обходится без шага сортировки.

### Значения инлайн: ноль попозиционных выделений

Как и у `xarray` со значимой семантикой, **значения отображения хранятся инлайн в слотах** — `Init` нужен только размер значения. Вставка десяти тысяч записей статистики маршрутов — выделения уровня контейнера (рост массива корзин), а не десяти тысяч. Жизненный цикл значений следует контейнеру: один `Unit` возвращает всё. Хотите хранить большие объекты или объекты, принадлежащие elsewhere? Сделайте типом значения указатель (`sizeof(ptr)`) и дополните его дескрипторами slot_map главы 17 — комбинация «отображение локализует + дескриптор достаёт» во всей полноте предстанет в таблице соединений главы 67.

### Трёхчастный контракт итерации

```diagram flow
- IterBegin: фиксирует снимок порядка и берёт ссылку (на время итерации контейнер не менять)
- IterNext: шаг вперёд, выдаёт представление ключа и указатель значения; NULL в конце
- IterEnd: освобождает ссылку снимка - все три части обязательны
```

Итерация выдаёт ключ как **заимствованное представление** (`xbytesview`), значение как **указатель внутрь слота** — срок действия обоих ограничен итерацией (после следующего `Next` или `End` нет гарантий). «Не менять контейнер во время итерации» — дисциплина семантики снимка: вставки и удаления инвалидируют снимок; если нужно обходить с правками, сперва соберите обрабатываемые позиции в массив (глава 14), а правьте после конца итерации.

### Повторные ключи и семантика неудач

Семейство вставки `xmap` при существующем ключе возвращает **имеющийся слот** (без перезаписи, без ошибки) — «вставка как взятие слота» ведёт себя как `GetOrAdd` минус флаг создания. Удаление идёт по ключу; отсутствующий ключ — неудача. Все пути неудач оставляют контейнер нетронутым (второе и третье из трёх соглашений контейнеров главы 14 действуют здесь как обычно).

## Примеры

### Первая полная программа: статистика маршрутов и итерация в порядке вставки

Из репозиторного образца `examples/containers/map/main.c`:

```embed path="examples/containers/map/main.c" title="examples/containers/map/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/containers/map/main.c -lws2_32 -liphlpapi
/health requests=1 status=200
/metrics requests=8 status=204
```

**Что только что произошло.** (1) `xrtMapInit(&tRoutes, sizeof(routestat))` передаёт только размер значения — вся структура `routestat` лежит инлайн в слоте, а не указателем. (2) `GetOrAdd("/health")` при первом обращении: вставка нуль-инициализированного слота (`bNew=true`), и после возврата указателя слота вы **прямо** делаете `Requests++` и пишете код состояния — соглашение «новый слот уже обнулён» убирает три шага инициализации. Второй маршрут так же укладывается в две строки. (3) Итерация выводит в **порядке вставки** `/health`, `/metrics` — не в хаосе хеш-значений; свойство исходит из внутренней цепи порядка, а его ценность — стабильность: экспорт конфигураций, генерация отчётов, тестовые утверждения — всё воспроизводимо точно. (4) `IterNext` выдаёт представление ключа и указатель значения парой; печать ключа через `%.*s` — поза главы 3. (5) `IterEnd` освобождает ссылку снимка, `Unit` возвращает контейнер — трёхчастная итерация плюс уборка контейнера, без пропусков.

### Вторая полная программа: целочисленные ключи и итерация по ключам

Из `examples/containers/int_map/main.c`, ID сессий от отрицательных до миллионных:

```embed path="examples/containers/int_map/main.c" title="examples/containers/int_map/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/containers/int_map/main.c -lws2_32 -liphlpapi
session=-9 requests=3 authenticated=no
session=1000001 requests=1 authenticated=yes
```

**Что только что произошло.** (1) Ключи `-9` и `1000001` разнесены на миллион — целочисленное отображение совершенно нечувствительно к разреженности; это и есть употребление «разреженного массива»: индексы не обязаны быть непрерывными, память расходуется по фактическому числу записей. (2) Вывод идёт в **порядке возрастания ключей**: `-9` перед `1000001`, в обратность порядку вставки — в этом сущность разделения труда с порядком вставки `xmap`; выбирая, сперва спросите «какой порядок обхода мне нужен — порядок бизнеса (вставки) или порядок ключей (сортированный)». (3) Ритм `GetOrAdd` в точности совпадает с байтовым — выучите один ритм, и вы водите оба семейства.

### Форма производительности и ёмкость

Портрет сложности хеш-отображения ровен: операции с одним ключом амортизированно O(1) (вычисление хеша + локализация корзины), итерация O(n) со стабильным порядком. Стратегия ёмкости совпадает с трёхчастным набором главы 14: `Reserve` растит заранее, избавляя от повторных перехеширований при загрузке, `Trim` ужимает после перехода в только-чтение. Две практические детали: во-первых, хеширование ключа выполняется внутри контейнера (байтовые ключи идут семейством SipHash, ключ держит сам контейнер) — вызывающему не нужно предварительно считать хеш, вы передаёте сам ключ; во-вторых, итерация `xintmap` по порядку ключей означает, что «экспорт списка сессий, сортированного по ID», обходится без сортировки — на логарифмических объёмах данных эта экономия нередко весит больше самих поисков. Поместите оба семейства в таблицу выбора главы 23: локация по ключу по плечу обоим; нужен порядок вставки — `xmap`, нужен порядок ключей и предельная скорость — `xintmap`.

### От образцов к инженерии: три хозяина отображения

Где живёт дескриптор отображения, таков его роль. **Временная статистика внутри функции**: дескриптор на стеке + `Unit` в конце — одношаговые задачи вроде подсчёта слов получают двухстрочный жизненный цикл. **Таблицы долгой жизни**: висят на объекте сервиса — `Init` при старте, `Unit` при остановке; таблицы маршрутов и сессий — эта форма: они живут сквозь запросы, и дисциплина итерации (три части, запрет вставок-удалений) должна пониматься под внешней синхронизацией глав конкурентности (том 6). **Слоты со указателями**: объявите тип значения `sizeof(ptr)` и кладите в слот указатель на объект или значение дескриптора slot_map главы 17 — в составной структуре «отображение локализует, дескриптор достаёт» отображение отвечает только за прыжок «ключ → дескриптор», сами объекты живут в пуле или slot_map. Три формы покрывают подавляющее большинство инженерных употреблений; таблица соединений главы 67 — третья форма в конкурентном масштабе.

## Контракты

- **Семантика GetOrAdd**: при наличии возвращается имеющийся слот; при отсутствии вставляется **нуль-инициализированный** слот и возвращается; выходной параметр `bNew` различает оба случая.
- **Значения инлайн**: значения живут в слотах, один `Unit` возвращает всё; при типе значения `ptr` владение объектом остаётся у вызывающего.
- **Три части итерации**: `Begin`/`Next`/`End`, без пропусков; на время итерации запрет вставок-удалений; представление ключа и указатель значения действуют до конца итерации.
- **Обещание порядка**: `xmap` — порядок вставки, `xintmap` — возрастание ключей; вывод воспроизводим точно и годится в тестовые утверждения.
- **Двоично-безопасные ключи**: байтовые ключи могут содержать вложенные нули; длина — по представлению, не по нуль-терминатору.
- **Формы хозяина**: временная статистика (дескриптор на стеке), долгоживущие таблицы (на объекте сервиса), ключ-к-дескриптору (значения держат `ptr`) — у каждой формы своя дисциплина уборки.

### Частый вопрос: почему нет «потокобезопасного отображения»

Ни один контейнер тома 3 не потокобезопасен — это не недосмотр, а слоистое решение. Блокировка внутри контейнера означает, что каждый `GetOrAdd` проходит через замок; однопоточная программа платит за синхронизацию впустую. А правильная гранулярность многопоточной программы обычно не в одиночной контейнерной операции — «найти + решить + записать» нужна внешняя согласованность, которую контейнерный замок не гарантирует. Поэтому XRT отдаёт синхронизацию примитивам тома 6: читающих много — оберните всю таблицу rwlock, межпоточную передачу — в канал, подлинную конкурентность — осколками (по отображению на поток, периодические слияния). Таблица выбора главы 23 ещё раз напомнит об этом в колонке «потоки» — выбирайте контейнер без мыслей о конкурентности, пишите конкурентность без надежд на контейнер.

## Ловушки

### Ловушка 1: сохранение указателей, выданных итерацией

Симптом: использование сохранённого ключа или указателя значения после итерации читает устаревшее или висячее; на малых объёмах изредка нормально.

Причина: итерация выдаёт адреса внутри слотов и заимствованные представления; следующий `Next`/`End` или любая правка контейнера могут их инвалидировать.

```c bad
routestat* pSaved = NULL;
xbytesview KeySaved;
xrtMapIterBegin(&tRoutes, &tIterator);
while ( (pStat = xrtMapIterNext(&tIterator, &Path)) != NULL ) {
	pSaved = pStat;      /* сохранение указателя итерационного периода */
	KeySaved = Path;
}
xrtMapIterEnd(&tIterator);
pSaved->Requests++;      /* итерация закончена - срок указателя тоже */
```

```c good
xrtMapIterBegin(&tRoutes, &tIterator);
while ( (pStat = xrtMapIterNext(&tIterator, &Path)) != NULL ) {
	Process(&Path, pStat);   /* использовать и выбрасывать внутри итерации */
}
xrtMapIterEnd(&tIterator);
/* для долгого хранения: на итерации копируйте ключи/значения в массив, обрабатывайте массив после */
```

### Ловушка 2: вставки и удаления во время итерации

Симптом: падения, пропущенные или продублированные записи; воспроизведение зависит от числа записей и тайминга операций — стабильно повторить почти невозможно.

Причина: итерация стоит на снимке порядка; вставки и удаления производят сборку внутренностей заново (реорганизацию), и снимок расцепляется со структурой.

```c bad
xrtMapIterBegin(&tRoutes, &tIterator);
while ( (pStat = xrtMapIterNext(&tIterator, &Path)) != NULL ) {
	if ( pStat->Requests == 0 ) {
		xrtMapRemove(&tRoutes, Path);   /* удаление из отображения посреди итерации */
	}
}
```

```c good
xarray tDead;
xrtArrayInit(&tDead, sizeof(xbytesview));
xrtMapIterBegin(&tRoutes, &tIterator);
while ( (pStat = xrtMapIterNext(&tIterator, &Path)) != NULL ) {
	if ( pStat->Requests == 0 ) {
		xrtArrayPush(&tDead, &Path);    /* сперва собрать ключи (память-источник ключей обязана жить до конца удалений) */
	}
}
xrtMapIterEnd(&tIterator);
for ( size_t i = 0; i < tDead.Count; i++ ) {
	xrtMapRemove(&tRoutes, *(xbytesview*)xrtArrayGet(&tDead, i));
}
xrtArrayUnit(&tDead);
```

Примечание: хорошая версия собирает представления ключей — память-источник представления обязана жить до завершения удалений; литеральные или внешнебуферные ключи удовлетворяют этому естественно, а ключи, удерживаемые контейнером, следует собирать копиями (например, `xrtTempDup` в арену).

## Упражнения

### Базовое: подсчёт частот слов

Прочитайте фрагмент английского (достаточно захардкоженной строки), посчитайте частоты слов с ключом-словом, выведите все записи в порядке вставки. Подсказка: деление по пробелам, счёт через `GetOrAdd`; перед выводом выпишите ожидаемый порядок записей (порядок вставки) и сверьте с программой.

### Продвинутое: два семейства рядом

Одни и те же данные сессий (ID от -5 до 100) загрузите в `xmap` (ключи — 8-байтовые двоичные представления) и в `xintmap`, пронаблюдайте разницу порядков итерации; затем посчитайте `Hash64` главы 12 для «байтовых строк ключа» — интуиция цены против прямых целочисленных ключей.

### Вызов: полный LRU (отображение + список + вытеснение по потолку)

LRU с пределом ёмкости: `xmap` хранит «ключ → запись», запись встраивает `xlistnode` связного списка (глава 17) в цепь свежести; get при попадании `MoveFront`, put сверх ёмкости вытесняет хвост и удаляет из отображения. Критерии приёмки: ёмкость 3, последовательность обращений 1/2/3/1/4 — вытесняется 2; после вытеснения число записей отображения совпадает с числом узлов цепи; ноль утечек (утечка исключена).

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Два семейства | `xmap` байтовые ключи, порядок вставки / `xintmap` целочисленные ключи, возрастание |
| Взятие слота | `GetOrAdd` находит-или-создаёт за шаг; новые слоты нуль-инициализированы; выходной параметр `bNew` |
| Значения инлайн | значения живут в слотах, `Unit` возвращает всё; объекты храните как значения `ptr` + дескрипторы |
| Три части итерации | `Begin`/`Next`/`End`; указатели итерационного периода не покидают итерацию; правки в середине запрещены |
| Двоичные ключи | `xbytesview` с нулевыми байтами законен; длине — верить |
| Разреженный массив | на малых непрерывных ключах `xintmap` — самый быстрый разреженный массив |
| Ёмкость | `Reserve`/`Trim` — те же имена и смыслы, что у трёхчастного набора; хеширование внутри контейнера |
| Правило выбора | экспорт в порядке вставки → `xmap`; в порядке ключей или целочисленные ключи → `xintmap` |
