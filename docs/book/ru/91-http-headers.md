## Ориентация

Глава 88 рассказала, «как разобрать одно поле»; эта глава — «как употреблять семейство полей». В HTTP-заголовках есть партия полей с собственной **структурной грамматикой**: параметры через точку с запятой у `Content-Type` (`charset=UTF-8; boundary="part;42"` — значения могут содержать кавычки и точки с запятой), token-списки `Connection`/`Upgrade` (согласование возможностей соединения — решающий вход рукопожатия WebSocket из главы 94), `Expect` (ожидания клиента — поток 100 Continue), `TE`/`Trailer` (транспортное кодирование и возможности trailer, глава 90). У каждого семейства свои ловушки разбора (экранирование quoted-string, регистр токенов, повторяемые поля), и XRT даёт каждой семье независимый малый модуль — `ParamNext` итерацию параметров, `FieldTokenFind` поиск токена, `xrtHttpTeParse` сводное согласование. Повседневный ящик инструментов прокси, посредников и реализаторов протоколов.

## Введение

Реализуя разборщик multipart-форм, первый шаг — вытащить boundary из `Content-Type: multipart/form-data; boundary="part;42"` — значение с кавычками, и **внутри кавычек точка с запятой** (boundary может её содержать!). Режущий `strchr(';')` здесь ломается: `part;42` разрезается пополам. Или пишете проверку WebSocket-обновления: содержит ли `Connection` токен `upgrade`? Регистр, пробелы, кавычки — ручная проверка опять куча граничных случаев.

Общее у двух сцен: **грамматика значения сложнее, чем «похоже на текст»** — RFC 9110 определяет для разных семейств разную грамматику (token-list, параметры через точку с запятой, quoted-string), у каждой — канонические правила разбора и исторические дыры реализаций. Специализированный слой XRT реализует правила каждого семейства малыми независимыми API: декодирование кавычек на слое параметров, регистронезависимый поиск на слое токенов, согласование q-значений на слое TE (глава 90 уже показывала). Глава проходит по семействам: какова грамматика, как пользоваться API, где ямы.

## Понятия

### Слой параметров: мир точек с запятой и quoted-string

Грамматика «параметров через точку с запятой» у значений полей (Content-Type, Content-Disposition и др.): `主值; key=value; key2="quoted string"` (главное значение; key=value; key2="строка в кавычках"). API-тройка:

- `xrtHttpParamNext(值, &偏移, &参数)` (значение, &смещение, &параметр): итерация с выдачей `xhttpparam` — представление `Name`, `Flags` (`XHTTP_PARAM_HAS_VALUE` — разрешены параметры без значения), исходное представление Value.
- `xrtHttpParamValueWrite(&参数, 输出, 容量, &长度)` (&параметр, вывод, ёмкость, &длина) (&параметр, вывод, ёмкость, &длина): **декодирует quoted-string и пишет значение** — кавычки сняты, `\"` разэкранировано, атомарность ёмкости. boundary=`"part;42"` декодируется в `part;42` — точка с запятой благополучно живёт.
- `xrtHttpParamCount`/`ParamFind`/`ParamBuild`: счёт, поиск по имени, построение новой строки параметров.

Почему «итерация выдаёт исходные представления, декодирование отдельным шагом»: большинству сцен потребления нужно лишь сравнить имя параметра или длину — не трогать кавычки стоит ноль; декодирование — только когда содержимое значения действительно нужно.

### Слой токенов: возможности соединения

`Connection`/`Upgrade`/`Transfer-Encoding` — token-списки (вотчина TokenNext главы 88); специализированный слой добавляет **семантический поиск**: `xrtHttpFieldTokenFind` — есть ли указанный токен в значении поля (без учёта регистра). «Содержит ли Connection upgrade» — ответ одной строкой; на этом стоят проверка рукопожатия WebSocket главы 94 и поэлементное отслаивание полей прокси (поля, перечисленные в `Connection`, надо удалить перед пересылкой — итерацию этого списка даёт `xrtHttpConnectionNext`).

### Expect и 100 Continue

Перед отправкой большого тела клиент спрашивает «примет ли сервер»: `Expect: 100-continue`. `xrtHttpExpectFields`/`ExpectValid` решают, несёт ли запрос легальное ожидание 100-continue — сервер отвечает `100 Continue` и принимает тело либо отказывает 417.**Почему заслуживает отдельного семейства**: тайминг 100 переплетается с потоком тела (сервер может ответить 100, принять тело, затем дать финальный статус), и реализаторы легко упускают снисходительный путь «тело отправлено без ожидания 100» — специализированный слой стандартизирует вердикт, тайминг остаётся слою соединения.

### Полное семейство поиска по массиву полей

Массив полей, разобранный в главе 89, получает семейство поиска (реализовано в фундаментном слое, переиспользуется слоем заголовков): `xrtHttpFieldFind` (первый по имени), `xrtHttpFieldNext` (итерация одноимённых многозначных — сцена Set-Cookie), `xrtHttpFieldGet`/`FieldGetUnique` (взятие значения/семантика уникальности — `GetUnique` для полей, «семантически появляющихся однажды»; повтор — ошибка), `xrtHttpFieldNameEqual` (сравнение без учёта регистра), `xrtHttpFieldTokenCursorInit`+`FieldTokenCount` (счёт токенов и курсор). Это семейство — полный словарь «спросить заголовок», фундамент решений посредника по Route/Cache-Control.

### Поверхность обрезки семейств

По макросу возможностей на семейство (`HTTP_HOST`/`HTTP_PARAM`/`HTTP_TARGET`/`HTTP_TE`/`HTTP_CONNECTION`/`HTTP_EXPECT`/`HTTP_TRAILER`/`HTTP_UPGRADE`...): встроенный клиент несёт только Host+Param без обновления и Expect; шлюз — всё. Семейства не тянут зависимостей друг от друга — обрезка по-настоящему независима.

### Расслоение специализированных семейств

```diagram flow
- Фундамент (глава 88): FieldParse - представления полей + TokenNext - итерация списков
- Семейство параметров: ParamNext/ValueWrite - параметры через ; и декодирование quoted-string
- Семейство семантического поиска: FieldFind/FieldGetUnique/FieldTokenFind - регистронезависимый поиск
- Специализированные семейства: TE/Encoding/Upgrade/Expect/Trailer/Connection - независимо обрезаемые малые модули согласования
```

### Первая полная программа: итерация параметров и декодирование кавычек

Программа ниже из `examples/http/param/main.c` — стандартное лекарство ловушки quoted-string:

```embed path="examples/http/param/main.c" title="examples/http/param/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/http/param/main.c -lws2_32 -liphlpapi
charset = UTF-8
boundary = part;42
```

**Что только что произошло.** (1) Вход `charset=UTF-8; boundary="part;42"` — два параметра. (2) `ParamNext` выдаёт их по одному: первый со значением (флаг `HAS_VALUE`), Name=`charset`, исходное Value=`UTF-8` (голый токен — декодировать не нужно, но и через ValueWrite корректно); второй Name=`boundary`, исходное значение — **в кавычках `"part;42"`**. (3) `ParamValueWrite` декодирует: кавычки сняты, внутренняя точка с запятой сохранена целиком — вывод `part;42`.**Это изнанка места крушения метода strchr**: точка с запятой в кавычках не режется, парность кавычек проверяется, последовательности экранирования восстанавливаются — всё делает декодер. Нехватка ёмкости — ноль записей, в согласии с общебиблиотечной атомарностью.

## Контракты

- **Итерация параметров**: исходные представления вперёд (Name/Value в кавычках), флаг `HAS_VALUE` отличает параметры без значения; декодирование (ValueWrite) по надобности — снятие кавычек и восстановление экранирования, атомарность ёмкости.
- **Семантический поиск токенов**: `FieldTokenFind` без учёта регистра; имена полей из списка `Connection` итерирует `ConnectionNext` — основа поэлементного отслаивания hop-by-hop.
- **Семантика уникального значения**: `FieldGetUnique` для однозначных полей — повтор это ошибка, а не «взять первый» (молчаливый выбор = согласие на двусмысленность).
- **Expect**: `ExpectFields`/`ExpectValid` выносят наличие и легальность ожидания; тайминг 100 — слой соединения.
- **Объявление Trailer**: список, анонсированный полем `Trailer`, доступен запросу — сверка с массивом чтения главы 90.
- **Согласование q**: целые-в-тысячных (TE/Encoding — общая модель); неупомянутое q=0.
- **Независимая обрезка семейств**: макросы семейств взаимно независимы; `ParamValueCursorInit/ValueNext` дают итерацию значений без декодирования.
- **Ноль распределений**: API семейств — только заимствованные представления + буферы вызывающего.

## Ловушки

### Ловушка 1: параметры режутся strchr — точка с запятой в кавычках ломает

Симптом: граница multipart извлечена неверно — `boundary="part;42"` разрезано на `boundary="part` и `42"`, разбор формы полностью неверен.

Причина: в грамматике параметров `;` (точка с запятой) внутри quoted-string — не разделитель. Ручная резка не знает контекста кавычек.

```c bad
char* p = strtok(Value, ";");   /* ; из part;42 принята за разделитель */
```

```c good
xhttpparam Param; size_t iOff = 0;
while ( (N = xrtHttpParamNext(Value, &iOff, &Param)) ==
		XHTTP_NEXT_ITEM ) {
	char Buf[64]; size_t iSize;
	if ( (Param.Flags & XHTTP_PARAM_HAS_VALUE) &&
			xrtHttpParamValueWrite(&Param, Buf,
				sizeof(Buf), &iSize) ) {
		use(Param.Name, Buf, iSize);   /* декодированное значение: part;42 целиком */
	}
}
```

### Ловушка 2: поиск токена с учётом регистра

Симптом: проверка `Connection: keep-alive, Upgrade` через `strstr(value, "upgrade")` возвращает NULL — рукопожатие WebSocket отвергнуто.

Причина: семантика HTTP-токенов регистронезависима, а регистр в сети разнообразен (`Upgrade`/`upgrade`/`UPGRADE` — всё легально).

```c bad
if ( strstr(Field.Value, "upgrade") != NULL ) {
	/* регистр "Upgrade" не попадает: легальное рукопожатие отвергнуто */
}
```

```c good
if ( xrtHttpFieldTokenFind(Fields, iCount,
		XRT_STR_LITERAL("upgrade")) ) {
	/* без учёта регистра + контекст кавычек - дело API семейства */
}
```

### Ловушка 3: обработка повторов однозначного поля «взять первое»

Симптом: `Content-Length: 11` и `Content-Length: 12` вместе; код обрабатывает первое, игнорируя второе — фронт и тыл понимают по-разному: вариант контрабанды.

Причина: семантически единственное поле, встретившееся дважды, — ошибочный вход. «Взять первое» молча распускает двусмысленность — выбирает понимание за атакующего.

```c bad
xstrview V = first_field("Content-Length", ...);
parse_length(V);   /* второй CL остаётся без спроса */
```

```c good
xstrview V;
if ( !xrtHttpFieldGetUnique(Fields, iCount,
		XRT_STR_LITERAL("Content-Length"), &V) ) {
	reject("conflicting content-length");  /* повтор = отказ */
}
```

## Упражнения

### Базовое: прогнать обход пяти семейств

Прогоните образцы small_fields и param, помечая для каждой строки вывода семейство и API. Замените вход param на `boundary="a\"b"` (экранированная кавычка) и проверьте декодирование. Критерии приёмки: восстановление экранирования верно (`a"b`); путь параметра без значения проходит ветку HAS_VALUE-ложь.

### Продвинутое: потребитель Content-Type

Реализуйте `content_type(字段值, &主类型, &子类型, 参数数组, 容量)` (значение поля, &главный тип, &подтип, массив параметров, ёмкость): вырезать два сегмента `multipart/form-data` и все параметры (декодирование кавычек). Проверить на `text/plain` (без параметров) и `multipart/mixed; boundary="x;y"; charset=UTF-8` (многопараметрический с кавычками и точкой с запятой). Критерии приёмки: оба вывода сходятся с ручной выкладкой; главный/подтип сравниваются после нормализации регистра.

### Вызов: отслаиватель hop-by-hop полей

Реализуйте обработку hop-by-hop прокси: итерация `Connection` на список имён + стандартное hop-by-hop множество (Connection/Keep-Alive/TE/Trailer/Upgrade), удаление попаданий из массива полей (со сжатием массива), затем `FieldBlockWrite` обратно. Критерии приёмки: после отслаивания запроса `Connection: keep-alive, X-Push` поле `X-Push` исчезло, `Connection` сохранён, но без удалённого пункта; сквозные поля (Accept и др.) нетронуты; ноль распределений кучи.
