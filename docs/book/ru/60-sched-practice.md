## Ориентация

Заключительная глава тома 6 (композиционного типа) собирает инструменты всего тома в **запускаемый скелет службы**: насос планировщика как цикл событий (глава 55), по корутине на соединение для прямого обслуживания (главы 54/55), Channel как внутренняя шина сообщений (глава 56), вычислительные/CPU-участки в пристрое пула задач (глава 58), Future/продолжения мостят оба мира (глава 57), группы задач — структурный жизненный цикл и грациозная остановка (глава 59 + дерево отмены главы 53 + сигнальный триггер главы 48). Тезис композиционной главы: **ценность параллельных инструментов не в одиночном употреблении, а в сборке в целую программу, которая «запускается, наблюдаема и останавливается»** — скелет этой главы и есть репетиция сетевого движка тома 7.

## Введение

Полный список требований mini-HTTP-службы: принимать соединения (IO-событийно); прямая логика на каждое соединение (прочитать запрос → обработать → записать ответ); части запросов требуют тяжёлых вычислений (цикл событий блокировать нельзя); сотрудничество внутренних компонентов (ограничитель частоты, агрегатор статистики); грациозная остановка (сигнал → прекратить приём → осушить в полёте → принудительный выход по сроку). Каждое требование соответствует инструменту тома 6 — но инструмент порознь полного требования не закрывает: планировщик без пула — вычисления клинят насос; пул без группы — остановке не в чем сводиться; группа без дерева отмены — остановка не распространяется.

Сборка — единственный путь. Глава проходит полный скелет вдоль потока данных — каждая станция помечена, какая глава что дала и почему так выбрано. Снимите со скелета детали протокола — и получите сетевой движок тома 7 (с главы 63); там вы увидите ту же основу в индустриальной форме, нагруженную TCP/TLS/HTTP.

## Понятия

### Панорама скелета

```diagram flow
- Цикл событий: насос PollFor планировщика (глава 55) - главный цикл потока
- Приём: корутина-приёмник (висит на событиях слушателя) -> новое соединение -> корутина соединения xrtCoGo (главы 54/55)
- Корутина соединения: чтение->обработка->запись по прямой; тяжёлый участок Post в пул (глава 58) + Park ждёт результата (глава 55)
- Задача пула: CPU-вычисление завершилось -> публикация Future (глава 57) -> Wake будит корутину соединения
- Внутренняя шина: статистика/сообщения ограничителя в Channel (глава 56) -> потребляет корутина-агрегатор
- Жизненный цикл: служебная группа (глава 59) держит все подгруппы соединений; сигнал (глава 48) -> корневой токен (глава 53) -> отмена всего дерева
- Остановка: Cancel группы -> каждая корутина ощущает в точке уступки -> очистный стек завершает -> Wait группы со сроком -> Destroy
```

### Три ключевых решения сборки

**Решение первое: граница раздела между потоком-насосом и пулом**. Поток цикла событий (планировщик) ведёт всю **ожидающую** логику (соединения, протоколы, координацию); пул задач ведёт все **вычислительные** участки (тяжёлый счёт, блокирующий IO). Критерий границы: этот код **уступает или держит** — уступающий (ждёт данных, ждёт событий) принадлежит планировщику, держащий (считает, блокирующе зовёт) — пулу. Что при смешении: вычисления клинят насос (ловушка 1 главы 55), или ожидание занимает пул (растрата конкурентности пула). **Решение второе: сообщения против общей памяти**. Корутины соединений **не делят ничего** (у каждой свой стек); потоки данных между корутинами (статистическая отчётность) идут через Channel — приземление «внутри компактно, снаружи ясно» (разделение CSP главы 56). Агрегатор статистики — единственная корутина с состоянием (владеет счётчиками), все обновления сообщениями. **Решение третье: этажность остановки**. Сигнал → корневой токен → Close планировщика (глава 55) + Cancel служебной группы (глава 59) — двойной канал: планировщик прекращает насос, группа завершает; они сотрудничают, а не дублируют (Close ведает «новые работы не доводятся», Cancel — «всё в полёте завершается»).

### Прогулка по потоку данных

Запрос с тяжёлым вычислением от начала до конца: (1) корутина-приёмник получила новое соединение (событие слушателя разбудило её Wake-ом) → `xrtCoGo` корутина соединения; (2) корутина соединения читает запрос (Park-уступка, пока событие IO в ожидании); (3) обработка нашла тяжёлый участок → `xrtTaskSubmit` в пул (с Future подгруппы) → корутина соединения Park-ом ждёт результата; (4) поток пула вычислил → Promise Resolve → `xrtCoWake` корутины соединения; (5) корутина соединения восстановилась, собрала ответ, записала (событие записи); (6) статистическое сообщение TrySend-ом в Channel (заполнен — выброшено: деградационная семантика «статистику можно терять») → агрегатор потребляет. Весь путь: **в потоке-насосе ноль блокировок, в потоках пула ноль ожидания, в сообщениях ноль блокировок** — три «ноля» суть проверяемые метрики правильности сборки.

### Прогулка по остановке

Последовательность остановки (полная вторая половина главы 48 о сигналах): (1) обратный вызов сигнала ставит флаг остановки (лёгкая работа — дисциплина главы 48); (2) главный цикл видит флаг: слушатель закрыт (прекратить приём) → Request корневого токена (глава 53) → Cancel служебной группы + Close планировщика; (3) каждая корутина соединения ощущает отмену в точке Park/Yield → очистный стек в обратном порядке (глава 54) → финал Cancelled; (4) задачи пула в полёте выходят на контрольных точках (хорошая форма ловушки 1 главы 58); (5) WaitFor группы (льготные 5 секунд — конвенция главы 48) → все финалы — грациозный выход; по истечении — запись числа незавершённых и Destroy на выход. (6) Итоговый отчёт статистики (stats группы — слияние наблюдения главы 59) в журнал.

### Контрольный список сборки

Пишете свой параллельный скелет — проходите пять пунктов: **в насосе ноль блокировок** (на потоке планировщика ни одного блокирующего вызова — пройдитесь по коду всех корутин); **всякое ожидание отменяемо** (у каждого Park/Wait/Recv есть токен — на остановке нет мёртвых ожиданий); **финалы троичны** (успех/отказ/отмена считаются и рапортуются раздельно — ловушка 2 главы 59); **жизненные циклы совпадают** (границы областей каждого класса ресурсов ясны: подгруппа соединения = соединение, группа службы = служба, пул = движок — порядок разрушения обратен зависимостям); **наблюдение насквозь** (глубина очереди, Active группы, счётчики отмен, цикл насоса — посты конвейера главы 49 в параллелизме открыты все). Пять зелёных — и скелет перерастает «запускается» в «готов к выкладке».

## Примеры

### Полная программа: ядро-кольцо скелета (цикл событий + корутины + пул)

Минимальное запускаемое ядро сборки — насос, корутины соединений, вычислительный пристрой, шина сообщений, каждый на своём месте:

```c
/* service_core.c - ядро-кольцо скелета тома 6: планировщик + корутины + пул + канал */
#define XRT_MODULE_ALL
#define XRT_IMPLEMENTATION
#include <xrt.h>
#include <stdio.h>

static xcosched* gSched;
static xtaskpool* gPool;
static xchannel* gStats;
static xatomic32 gDone;

static void aggregate(ptr pData)          /* тело корутины-агрегатора статистики */
{
	ptr Item;
	while ( xrtChannelRecv(gStats, &Item) == XWAIT_OK ) {
		(void)xrtAtomic32FetchAdd((xatomic32*)pData, 1, XMEMORY_RELAXED);
	}
}

static int computeHeavy(int Input)        /* имитация тяжёлого вычисления (в пуле) */
{
	int Sum = 0;
	for ( int i = 0; i < Input * 100; ++i ) {
		Sum += i % 7;
	}
	return Sum;
}

static ptr workerTask(ptr pData)          /* задача пула: вычислить и опубликовать */
{
	int Input = (int)(uintptr_t)pData;
	int Result = computeHeavy(Input);
	return (ptr)(uintptr_t)Result;
}

static ptr connection(ptr pData)          /* корутина соединения: прямая логика */
{
	int Input = (int)(uintptr_t)pData;
	xfuture* Job = xrtTaskSubmit(gPool, workerTask,
		(ptr)(uintptr_t)Input, NULL);      /* пристрой-пул (глава 58) */
	if ( Job == NULL ) {
		return NULL;
	}
	if ( xrtFutureWait(Job) != XWAIT_OK ) {  /* в насосе без блокировок - прямой ожидание здесь ради простоты демонстрации */
		xrtFutureDestroy(Job);
		return NULL;
	}
	int Value = (int)(uintptr_t)xrtFutureValue(Job);  /* заимствованное чтение (глава 57) */
	xrtFutureDestroy(Job);
	(void)xrtChannelTrySend(gStats, (ptr)(uintptr_t)Value);  /* отчёт по шине (глава 56) */
	return (ptr)(uintptr_t)Value;
}

int main(void)
{
	xatomic32 Count;
	xcoro* Agg;
	xtaskpoolconfig PoolCfg = { 2, 32, 0 };

	xrtAtomic32Init(&Count, 0);
	xrtAtomic32Init(&gDone, 0);
	gSched = xrtCoSchedCreate();               /* цикл событий (глава 55) */
	gPool = xrtTaskPoolCreate(&PoolCfg);       /* вычислительный пристрой (глава 58) */
	gStats = xrtChannelCreate(64);             /* шина сообщений (глава 56) */
	if ( (gSched == NULL) || (gPool == NULL) || (gStats == NULL) ) {
		return 1;
	}
	Agg = xrtCoGo(gSched, aggregate, &Count);  /* корутина-агрегатор */
	for ( int i = 1; i <= 3; ++i ) {
		(void)xrtCoGo(gSched, connection, (ptr)(uintptr_t)i);
	}
	(void)xrtCoSchedRun(gSched);              /* насос до завершения всех корутин */
	xrtChannelClose(gStats);                   /* осушение (трёхстороннее правило главы 56) */
	(void)xrtCoSchedRun(gSched);               /* агрегатор потребляет остаток */
	xrtCoSchedDestroy(gSched);
	(void)xrtTaskPoolClose(gPool);             /* протокол остановки пула (глава 58) */
	xrtTaskPoolWait(gPool);
	xrtTaskPoolDestroy(gPool);
	printf("aggregated=%d\n", (int)xrtAtomic32Load(&Count, XMEMORY_ACQUIRE));
	return 0;
}
```

```term
$ gcc -O2 -DXRT_MODULE_ALL -DXRT_IMPLEMENTATION -I single service_core.c -lws2_32 -liphlpapi
$ ./a.exe
aggregated=3
```

**Где стоит этот код.** Инструменты тома в одной раме: насос `xrtCoSchedCreate` как главная линия, три корутины соединений `xrtCoGo` с конкурентной прямой логикой, тяжёлое вычисление `xrtTaskSubmit`-ом в пристрой пула, канал `xrtChannelCreate` как статистическая шина, корутина-агрегатор потребляет. **Трёхфазный финал** в обратном порядке зависимостей: насос Run до пустоты → Close канала и осушение → Run снова (агрегатор потребляет остаток) → Close+Wait пула — протоколы остановки каждого слоя (главы 55/56/58) сцеплены в правильном порядке. `aggregated=3` свидетельствует: все три сообщения соединений дошли до шины и все потреблены. Обратите внимание: `xrtFutureWait` в корутине соединения в настоящем скелете должен быть Park-ожиданием Wake (в насосе блокировок нет — здесь прямой Wait ради простоты демонстрации; аннотация ловушки 1 главы 55 применима).

### Три новых пункта проверки станций (четыре тома 4 — параллельная редакция)

Глава 35 дала четыре пункта для конвейера данных, глава 49 — редакцию наблюдения; параллельный скелет добавляет три. **Пункт первый: единоличное владение данными**. Каждая параллельная сущность (корутина/задача) владеет своими данными; между сущностями — только сообщения или Future; агрегатор статистики — единственная корутина, владеющая счётчиками (все обновления через канал); если две корутины могут писать одну переменную, сборка уже ошибочна. **Пункт второй: пути ошибок тоже структурны**. Написано ли поведение скелета после отказа задачи — подгруппа соединения вешает в группу и провалившийся Future (виден в stats), отказные ответы идут тем же каналом (потребитель разбирает по классу финала); «успех прогнали, про отказ не думали» в параллелизме — семя остановочной аварии. **Пункт третий: вложенность разложима**. Каждый слой скелета (насос/шина/пул/группа) тестируется отдельно — применение конвейерного мышления главы 49 на слое сборки: входы-выходы каждого слоя ясны (сообщения/задачи/финалы), слои организованы формой станций-функций главы 35 — только тестируемые слои смеют компоноваться.

### От скелета к сетевому движку: анонс тома 7

Отображение этого скелета на сетевой движок тома 7 стоит прописать в заключительной главе. **Насос планировщика → порт событий** (пять бэкендов главы 63: IOCP/epoll/kqueue/io_uring/select — PollFor насоса соответствует интерфейсу ожидания порта); **корутина соединения → событийные обратные вызовы Stream движка** (таблицы колбэков Accept/Read/Close золотого стандарта главы 65 — том 7 выражает их обратными вызовами, а не корутинами напрямую, но планировщик может обернуть колбэчи корутинами); **пристрой пула задач → Worker-пул сетевого движка** (изоморф — вычисления не клинят IO-потоки); **шина сообщений → внутренние статистические/управленческие каналы движка**; **служебная группа → последовательность остановки движка** (глава 65: «колбэчи Close могут ещё завершаться на Worker-ах; разрушение Engine ждёт» — редакция Wait группы задач для движка). Отображение не тождество — том 7 добавляет над скелетом слои протоколов (автомат состояний TCP, TLS, HTTP) и продакшен-детали (уровни противодавления, буферы с подсчётом ссылок) — но **пятипунктовый контрольный список скелета дословно применим к сетевому движку**. Читайте том 7 с диаграммой скелета этой главы, спрашивая у каждой главы «на каком месте скелета крепится этот слой».

### Итоги тома: опись активов тома 6

Том 6 закрывается; переучёт. **Слой примитивов**: четырёхшаговый жизненный цикл потока, четвёрка (мьютекс/условие/квота/rw-блокировка), четыре условия deadlock-а и профилактика порядком блокировок (глава 52). **Слой сотрудничества**: тройка токена отмены и дерево распространения (53), четыре состояния-три финала и очистный стек корутины (54), тройка планировщика и три формы семейства насоса (55), ёмкость/трёхстороннее закрытие/Select/интеграция отмены Channel (56), четыре состояния/продолжения/комбинаторы/семейство ожидания Future (57), двойная форма/протокол остановки/пакет исполнителя (58). **Структурный слой**: пятёрка группы задач/перечень финалов/области родитель-потомок/Done Future (59). **Ментальные модели**: линия отмены, трёхслойный конвейер сборки, общее-против-сообщений, лестница стоимости ожидания, три гранулярности, генеалогия структурного параллелизма. Плюс навык сборки этой главы — этот список и есть фундамент «читать любую современную параллельную библиотеку, проектировать собственную параллельную архитектуру». С тома 7 все эти инструменты входят в бой.

## Контракты

- **Три ноля**: поток-насос без блокировок, потоки пула без ожидания, пути сообщений без взаимной блокировки — проверяемые метрики правильности сборки.
- **Критерий разделения**: уступающее — планировщику, держащее — пулу; граница по признаку «уступает ли».
- **Двойной канал остановки**: Close планировщика (прекратить доводку) + Cancel группы (завершить в полёте) — сотрудничество, не дублирование; порядок и дежурство со сроком — в паре.
- **Финал в обратном порядке**: насос → шина → пул (обратный зависимостям); у каждого слоя свой протокол остановки (главы 55/56/58).
- **Совпадение жизненных циклов**: подгруппа соединения = соединение, группа службы = служба — граница области и есть граница ресурсов.
- **Пять пунктов наблюдения**: глубина очереди, Active группы, счётчики отмен, цикл насоса, троица конечных состояний — порог выкладки.

### Путь эволюции: три уровня итераций скелета

Скелет не проектируется одним заходом; у трёх уровней своя отдача. **Уровень первый (запускается)**: насос + корутины + пул, минимальное кольцо тройки — образец один этой главы; проверка трёх нолей, проход потока данных. **Уровень второй (останавливается)**: добавить сигналы, дерево отмены, служебную группу, дежурство со сроком — остановочное кольцо образца два главы 59; проверка последних трёх пунктов списка (ожидания отменяемы/финалы троичны/циклы совпадают). **Уровень третий (наблюдаемо)**: подключить конвейер главы 49 — глубина очереди, Active группы, цикл насоса в структурный журнал; добавить внедрение отказов (глава 6) для проверки путей отказа. Большинство проектов останавливается на уровне «полтора» — «запускается, но не умеет грациозно останавливаться» — самый частый технический долг параллельных систем; второй уровень — порог выкладки, третий — порог эксплуатации. Примерно по неделе на уровень — вложения в скелет окупаются полностью с первой ночной тревогой.

### Взгляд на производительность: три точки настройки скелета

Узкие места производительности скелета стоят в трёх предсказуемых местах. **Цикл насоса** (срок PollFor): длинный — задержка отклика на события, короткий — холостое вращение жжёт CPU — старт с 10 мс, настройка по требованиям задержки (интерактив ~1 мс, пакетный ~50 мс); доля вращения — обратная связь настройки (пункт приёмки упражнения-вызова). **Глубина пула** (экономика главы 58): CPU-тип = ядра, IO-тип = бюджет конкурентности — решает доля тяжёлых вычислений; после измерения распределения длительностей задач — по формулам главы 58. **Ёмкость канала** (три числа главы 56): статистическая шина рапортует TrySend-ом с выбросом при заполнении (ёмкость 64 для сглаживания) — деградационная семантика выбрасываемых сообщений записана в проекте; канал запросов — малые значения по потребностям передачи противодавления. Общий принцип трёх точек: **сперва на умолчаниях, подключить наблюдение, настроить по данным** — параллельный выпуск главы 136 об анализе производительности вернётся с инструментами.

### Последнее напоминание: скелет — живой документ

Код скелета (с контрольным списком из пяти пунктов и комментариями решений сборки) должен поддерживаться как **живой документ** команды: новичок входит через скелет (быстрее, чем десять глав книги — теория вернётся позже); новая служба стартует копией скелета (решения сборки уже проверены); изменение архитектуры сперва в скелете (три ноля зелёные — потом бизнес-код). Симптомы гниения скелета: какой-то пункт списка хронически красен, комментарии решений разошлись с кодом, никто не может изложить протокол остановки какого-то слоя — любой симптом открывает окно рефакторинга. **Сопровождаемость параллельной системы не в объёме кода, а в ясности структуры** — скелет и есть физический носитель этой структуры. Несите его в том 7.

## Ловушки

### Ловушка 1: неверный порядок сборки — корутины раньше насоса

Симптом: подача корутин отказывает или крушится — зависимые планировщик/пул/канал ещё не построены (или уже разрушены), а их уже употребляют.

Причина: компоненты скелета имеют порядок зависимостей (насос прежде корутин, шина прежде производителей) — инициализация в обратном зависимостям порядке, разрушение в прямом.

```c bad
(void)xrtCoGo(gSched, worker, NULL);    /* сперва подали корутину */
gSched = xrtCoSchedCreate();             /* потом построили насос - цель подачи недействительна */
```

```c good
gSched = xrtCoSchedCreate();             /* сперва насос (фундамент зависимостей) */
gPool = xrtTaskPoolCreate(&PoolCfg);     /* затем пристрой */
gStats = xrtChannelCreate(64);           /* затем шина */
(void)xrtCoGo(gSched, worker, NULL);     /* работу подаем последней - зависимости готовы */
```

### Ловушка 2: остановка пропустила слой — пул закрыт, шина не осушена

Симптом: после остановки статистика не досчиталась — сообщения висят в канале без потребителя; или задачи пула ещё пишут в закрытый канал (буря ошибок).

Причина: трёхслойная остановка (насос/шина/пул) прошла два слоя — у каждого слоя свой протокол, пропущенный слой и есть пропущенное завершение.

```c bad
xrtCoSchedClose(gSched);
(void)xrtCoSchedRun(gSched);   /* насос осушен */
xrtTaskPoolDestroy(gPool);      /* пул разрушен сразу - статистика в шине застряла навсегда */
```

```c good
xrtCoSchedClose(gSched);
(void)xrtCoSchedRun(gSched);   /* насос осушен (производители остановлены) */
xrtChannelClose(gStats);
(void)xrtCoSchedRun(gSched);   /* шина осушена (потребители завершились) */
(void)xrtTaskPoolClose(gPool);
xrtTaskPoolWait(gPool);        /* пул осушен - все три слоя собраны */
xrtTaskPoolDestroy(gPool);
```

### Отладочная прогулка: три частых отказа скелета

Отказы уровня скелета (не баги одиночных инструментов) — три частые формы и пути локализации. **Отказ первый: периодические пики задержки отклика** — чьё-то тяжёлое вычисление побежало прямо в насосе (скелетная редакция ловушки 1 главы 55): локализация по кривой цикла насоса (пики совпадают с классом запросов) → скан кода корутин этого класса на блокирующие вызовы → перенос в пристрой пула. **Отказ второй: остановка изредка подвисает** — какой-то слой не завершён или какое-то ожидание неотменяемо: локализация по кривой Active группы (после остановки не обнуляющиеся пункты) → проверка формы ожиданий этого класса задач (с токеном ли RecvCancel, есть ли контрольные точки у задач пула) → добавить отменяемое ожидание. **Отказ третий: статистика не сходится** — сообщения потеряны (выброс TrySend при заполнении — это дизайн, но выброс там, где его не проектировали) или потребитель не осушён (остановка пропустила слой): локализация сравнением трёхуровневой статистики (отправлено/принято/агрегировано) по направлению расхождения → по направлению искать точку потери. Локализация всех трёх отказов держится на наблюдении (конвейер главы 49) — **без наблюдения скелета отладка возвращается в эпоху гаданий**.

### Эхо главы 35: два конвейера рядом

Эта глава и глава 35 — два композиционных конвейера книги; сопоставление замыкает их. **Конвейер данных** (глава 35): текст на входе → обработка деревом значений → текст на выходе — синхронно, однопоточно, цепочка станций-функций. **Конвейер службы** (эта глава): события на входе → обработка корутинами → поток сообщений → сведение финалов — асинхронно, многопоточно, сборка компонентов скелета. Общее скелетное мышление: у станций/компонентов по одной ответственности, контракты входа-выхода явные, каждый тестируется отдельно; различие — **измерение времени**: станции конвейера данных идут по порядку, компоненты конвейера службы исполняются конкурентно, поэтому у последнего добавляются отмена, сведение и наблюдение — три измерения, ненужные конвейеру данных. Оба конвейера сливаются в томе 7 — сетевой движок есть и конвейер данных (разбор протоколов), и конвейер службы (управление соединениями) — читайте том 7 с контрольными списками обеих глав, и каждая глава находится на своём месте конвейера.

## Упражнения

### Базовое: воспроизвести тройку

Воспроизведите ядро-кольцо скелета (образец один вдвое меньше: насос + две корутины + канал) — выведите статистическое свидетельство; затем нарочно Destroy пула раньше срока и пронаблюдайте ошибку (понять порядок зависимостей).

### Продвинутое: отменяемые соединения

Добавьте корутинам соединений токен отмены (глава 53): по отмене — завершение очистным стеком, финал Cancelled; главная программа Cancel-ит все соединения, затем WaitFor сводит со сроком — проверка пункта «всякое ожидание отменяемо».

### Вызов: полный скелет

Соберите полный скелет службы: остановка по сигналу + корутина-ограничитель (Channel принимает запросы, «корзина токенов» ограничивает скорость) + три конкурентных соединения (в каждом вычислительный пристрой) + трёхуровневая статистика служебной группы. Критерии приёмки: пять пунктов списка по одному (вывести контрольный лист); вся остановка < 5 секунд; трёхуровневая статистика сходится; глава 6 подтверждает ноль утечек. Скелет сохраните — сетевые главы тома 7 нагрузят его протоколами.
