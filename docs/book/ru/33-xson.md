## Ориентация

JSON не выражает слишком многого: двоичные данные требуют ручного Base64, метки времени — строковых договорённостей, множества и отображения с целыми ключами вырождаются в массивы; каждый зазор — ещё один слой собственных конвенций, каждый слой — мина совместимости. **XSON — строгое надмножество JSON**: легальный JSON автоматически легален как XSON, плюс четыре первоклассных типа — `bytes("...")` (инлайновый Base64), `time("...")` (метка времени ISO), `set[...]` (множество с дедупликацией) и `intmap{...}` (отображение с целыми ключами). Парсер — тот же, что в главе 31 (событийные обратные вызовы различают по полю типа; расширенные типы больше не вырождаются в строки), сериализация записывает все четыре типа как есть — **полный круговой проход без стоимости конвенций**. Когда выбирать XSON и когда держаться JSON — глава даёт правила решения.

## Введение

Истинная форма одной внутренней конфигурации: приватный ключ сертификата — двоичные данные (в JSON только Base64-строка, потребитель обязан знать «эту строку надо декодировать»); срок действия — метка времени (строкой или числом? чей часовой пояс?); допустимые порты — множество (а повторы в JSON-массиве? потребитель сам дедуплицирует?); параметры соединения — отображение номер порта → описание (ключи JSON-объекта только строки — кто конвертирует между "80" и 80?). Четыре поля — четыре конвенции, документация на две страницы, и всё равно кто-то ошибается.

Ответ XSON — сделать эти четыре формы **первоклассными типами**: `bytes("AAEC...")` несёт собственное объявление кодирования, `time("2026-07-31T00:00:00Z")` унифицирует UTC в микросекундах, `set[80, 443]` дедуплицирует самой семантикой, `intmap{80: "http"}` отображает с родными целыми ключами — у `xvalue` дерева значений (глава 30) эти четыре типа уже есть, XSON лишь не даёт сериализации расплющивать их. **Дизайн надмножества** гарантирует плавность: существующие JSON-инструменты работают как раньше, JSON-части документа XSON легальны для любого JSON-парсера.

## Понятия

### Четыре расширенных типа

```diagram flow
- bytes("AAEC/w=="): двоичные данные инлайном Base64 - без внешних ссылок, читается обратно как значение bytes
- time("2026-07-31T00:00:00Z"): ISO 8601 - разбор нормализует в UTC, события дают целое число микросекунд
- set[...]: множество с дедупликацией - семантика множеств главы 19, сериализация проходит круг как есть
- intmap{ 80: "http" }: отображение с целыми ключами - ключи больше не обязаны становиться строками
```

Все четыре типа имеют соответствия в дереве значений (глава 30): значения Bytes/Time, контейнеры set/intmap — сериализация XSON это просто полное отображение «дерево значений ↔ текст» без потери информации о типах. Поток событий (SAX) тоже различает: поле Type у `xxsonevent` прямо помечает расширенный тип — потребителю не нужно гадать, «не спрятано ли время в этой строке».

### Смысл строгого надмножества

Три свойства, каждое стоит проговорить отдельно. **Прямая совместимость**: любой легальный JSON-документ легален как XSON — переименовать существующие конфигурации `.json` в `.xson` стоит нуля. **Обратная несовместимость**: документ XSON с расширенными типами нелегален для чистого JSON-парсера (`bytes(` не JSON-синтаксис) — XSON только для каналов, «где оба конца — XRT или договорились об XSON». **Взаимонепричастность**: парсер один и тот же, разбор идёт по фактическому содержимому — дерево из JSON-документа не содержит расширенных типов, из XSON-документа может; конфигурационной системе не нужно вести два кодовых пути под два формата.

### Правила выбора против JSON

| Сценарий | Выбор | Причина |
| --- | --- | --- |
| Открытый внешний API | JSON | лингва франка, любой клиент разберёт |
| Внутренние конфигурации | XSON | двоичные данные/время/множества в родном виде, ноль конвенций |
| Данные между внутренними сервисами | XSON | оба конца подконтрольны, полный круг типов |
| Конфигурации для ручного редактирования | JSON или XSON | ISO-строку человеку писать приятнее числа микросекунд |

Центральная переменная правила — **подконтролен ли получатель**: подконтролен → XSON с полными типами; неподконтролен → JSON ради совместимости. Смешанная форма тоже обычна: поля открытого API — типы JSON, промежуточное представление внутренней обработки — дерево значений (в нём всегда полные типы): преобразование на границе, внутри без компромиссов.

### Позиционирование ошибок и строгость

XSON наследует всю строгость главы 31: три шлюза границ ресурсов, отвержение дубликатов ключей, ошибки со строкой и столбцом. Ошибки разбора расширенных типов также локализуются до символа — нелегальный месяц в `time("2026-13-01...")` указывается прямо в позиции.

## Примеры

### Полная программа: круговой проход всех типов

Из образца репозитория `examples/data/xson/main.c` — четыре расширенных типа одной записью-чтением:

```embed path="examples/data/xson/main.c" title="examples/data/xson/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/data/xson/main.c -lws2_32 -liphlpapi
{
  "blob": bytes("AAEC/w=="),
  "updated": time("2026-07-31T00:00:00Z"),
  "roles": set[ ... ],
  "ports": intmap{ 80: "http", 443: "https" }
}
bytes = 4
time = 1785456000000000
{"code":200,"tags":set["xrt"]}
```

**Что только что произошло.** (1) Сегмент сериализации: четыре типа дерева записаны как есть — `bytes("AAEC/w==")` с объявлением кодирования, `time(...)` ISO-строкой, `set[...]` и `intmap{...}` каждое своей скобочной семантикой. **Информация о типах видна в тексте** — читателю документа не нужна таблица конвенций. (2) Сегмент разбора: `bytes = 4` — Base64 декодирован обратно в 4 двоичных байта; `time = 1785456000000000` — ISO-строка нормализована в целое число микросекунд UTC (мера `xtime` главы 3). (3) Последняя строка — компактная сериализация (без красоты): форма `set["xrt"]` в одну строку; машинный канал — компакт, диск для просмотра — красота, выбор тот же, что у JSON.

### Полная программа: файловый круг и позиционирование ошибок

Из `examples/data/xson_tour/main.c`:

```embed path="examples/data/xson_tour/main.c" title="examples/data/xson_tour/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/data/xson_tour/main.c -lws2_32 -liphlpapi
xson: valid +/- and read(config) ok
xson: error location line=1 ok
xson: file roundtrip parse/read -> write/stringify ok
xson: sync write via callback ok
xson: sink writer full value domain ok
```

**Что только что произошло.** (1) Валидация и чтение: проверка легальности документа XSON и чтение полей конфигурации одним заходом. (2) Позиционирование ошибок: подайте вход без запятой — `line=1` сообщает точно; способность локализации JSON-а главы 31 унаследована дословно. (3) Файловый круг: разбор → чтение полей → запись обратно → сериализация, замкнутый контур подтверждает сохранность типов. (4) Запись через обратный вызов: вывод сериализации отдаётся кусками через обратный вызов — форма потоковой записи на диск или прямого подключения к sink, как у Writer-а главы 31. (5) Запись в sink покрывает всю область значений: скаляры и все четыре расширенных типа проходят через sink по очереди — полные типы выражает не только DOM; потоковая запись тоже не теряет типов. Пять «ok» вместе — доказательство: «у XSON тот же инженерный набор, что у JSON, только типов больше».

## Контракты

- **Строгое надмножество**: легальный JSON обязательно легальный XSON; парсер один; JSON-документы не содержат расширенных типов.
- **Круг четырёх типов**: bytes/time/set/intmap сериализуются и разбираются как есть, без стоимости конвенций.
- **Нормализация времени**: `time(...)` разбирается в нормализованные микросекунды UTC (мера `xtime`); сериализация пишет ISO 8601.
- **Правило выбора**: получатель подконтролен → XSON с полными типами; неподконтролен → JSON ради совместимости; преобразование на границе, внутри без компромиссов.
- **Наследованная строгость**: три шлюза, отвержение дубликатов, строка-столбец ошибок — полностью согласовано с JSON.
- **Компакт и красота**: машинный канал — компакт, диск для просмотра — красота; правила выбора те же, что у JSON.

### От примеров к инженерии: три хозяина XSON

**Внутренние конфигурации** (главная площадка): загрузка на старте → дерево значений → слияние главы 30 — двоичные ключи, сроки действия, множества прав и отображения портов всё первоклассно, потребительский код без преобразований. Это прямой целевой сценарий дизайна XSON. **Внутренняя сервисная шина**: сериализация сообщений между сервисами — оба конца XRT, полный круг типов стирает кодирующие слои с обеих сторон; в паре с очередью главы 21 выбор по каналу: передать дерево значений напрямую (без сериализации) или передать XSON-сериализацию (через процессы).**Выход понижения на внешней границе**: когда наружу нужен JSON — понижение по конвенции (хорошая форма ловушки 1); логика понижения сосредоточена в пограничном модуле, внутренние деревья значений хранят полные типы. Общая точка трёх хозяев: **информация о типах внутри всегда первоклассна и понижается только на явно размеченной границе**.

### Контраст: одна конфигурация в двух записях

Запишите «конфигурацию сертификата» в обоих форматах — и различия выпрыгивают сами. Форма JSON: `{"key": "AAEC...", "expire": "2026-07-31T00:00:00Z", "ports": [80, 443, 80]}` — key требует документации, что это Base64; expire — конвенции ISO и часового пояса; массив ports с повторами, и потребитель должен дедуплицировать. Форма XSON: `{"key": bytes("AAEC..."), "expire": time("2026-07-31T00:00:00Z"), "ports": set[80, 443]}` — три поля самоочевидны, в потребительском коде по одной строке точного чтения. Суть контраста не в том, что «XSON короче» (может быть и длиннее), а в том, что **конвенции переехали из документации в синтаксис** — документация забывается и теряется, синтаксис же принудительно исполняется парсером. В этом весь смысл «первоклассных типов».

## Ловушки

### Ловушка 1: отправка XSON неподконтрольному получателю

Симптом: внешние интеграторы сообщают «ваш JSON нелегален» — их парсер падает синтаксической ошибкой на `bytes(` или `set[`.

Причина: расширенный синтаксис XSON нелегален для чистых JSON-парсеров — «над» надмножества действует только для XRT и договорившихся сторон.

```c bad
/* внешний API напрямую возвращает XSON-сериализацию */
str sBody = xrtXsonStringify(pResponse, false, NULL);
HttpReply(200, sBody);   /* JSON-парсер клиента: syntax error */
```

```c good
/* на внешние каналы только JSON: расширенные типы явно конвертируются на границе */
str sBody = xrtJsonStringify(pResponse, false, NULL);
/* bytes/time переводятся в оговорённые JSON-формы до выхода (полевая документация прописывает это) */
```

### Ловушка 2: чтение значения time как строки

Симптом: чтение поля времени даёт отказ или пустоту — «в сериализации же строка `time("...")`».

Причина: time в XSON — **первоклассный тип**: в дереве значений его тип Time, а не String; `GetString` отказывает по семантике точного чтения главы 30 (несовпадение типа).

```c bad
xstrview When;
xrtValueGetString(pUpdated, &When);   /* тип Time - точное чтение отказывает */
```

```c good
xtime When;
xrtValueGetTime(pUpdated, &When);     /* GetTime читает целое число микросекунд */
/* для показа отформатируйте сами (модуль времени главы 42) */
```

## Упражнения

### Базовое: распознавание типов

Разберите документ XSON, содержащий по одному из четырёх расширенных типов; напечатайте имя типа каждого поля через `xrtValueType`; затем сериализуйте обратно в текст и убедитесь, что пометки типов сохранены как были.

### Продвинутое: миграция конфигурации

Переведите JSON-конфигурацию (с полем-строкой Base64, полем-строкой ISO-времени и массивом портов) в полно-типовую форму XSON: повышение типов полей (строка → bytes/time, массив → set/intmap), перевод кода разбора на точное чтение, сравнение объёма и читаемости до и после. Подсказка: ценность миграции должна проявиться в «потребительский код стал проще» — пересчитайте, сколько строк преобразования вы удалили.

### Вызов: экспортёр двух форматов

Реализуйте `export(值树, 格式)` (дерево значений, формат): XSON выводит полные типы; JSON при выводе понижает расширенные типы по конвенции (bytes → Base64-строка, time → ISO-строка, set → массив, intmap → объект со строковыми ключами), объявляя конвенцию понижения в заголовочном поле. Критерии приёмки: круг XSON экспорт-импорт равен по каждому типу; JSON-экспорт разбирается любым JSON-парсером; таблица соответствия полей двух форматов генерируется автоматически.
