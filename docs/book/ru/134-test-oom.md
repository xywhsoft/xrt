## Ориентация

Глава 133 показала OOM-тестирование как одно из четырёх оружия; эта глава **расширяет его в полную дисциплину** — за 185 файлами `_oom` стоит строгая методология. Четыре блока: **поточечное вращение** (циклическое перечисление «N-е выделение отказывает» — «каждое выделение, отказывая, проверяется отдельно», а не «какое-то однажды откажет»); **три формы провального распределителя** (`xrtMemDebugFailAfter` — счётная / самописная квотная (Limited+Remaining — форма OOM-теста map) / полностью провальная (`FailAllocator` у test_oom) — у каждой свой сценарий); **выживание системы ошибок при истощении** (отчёт об ошибке в OOM не выделяет память — при отказе `xrtErrorCreate` слот сохраняет `XERR_MEMORY`: сообщить «нет памяти» самой этой операции память не нужна); **отладочная куча, вооружённая** (FailAfter вместе с потоком событий — внедрённый отказ аудируем; карантина ловит двойное освобождение/UAF — формы сбоев не ограничиваются отказом выделения). Одна цель: **«нет ресурсов» из рантайм-предположения становится исчерпывающе перечисленным фактом**.

## Введение

Необходимость поточечного вращения видна из одного вывода: в функции 5 выделений — очистка при отказе 3-го отличается от отказа 5-го (первая откатывает два полных побочных эффекта, вторая четыре с половиной); тестирование только «1-го отказа» (или вовсе без) оставляет 4 пути очистки неисполненными — любая утечка наполовину инициализированного/порча состояния среди них идёт прямо в прод. Метод вращения: точка отказа сканирует от 1 до 5 (каждый раунд перезапускает полный поток) — **каждый путь очистки исполнен, каждое состояние отказа утверждено**. 185 файлов — развёртка этого сканирования по всем модулям — само число есть доказательство дисциплины.

Выживание системы ошибок заслуживает отдельного акцента: если бы путь сообщения об ошибке требовал выделения, в OOM получилось бы «отчёт об отказе отказывает» — отладчик видит молчаливое падение вместо структурированной ошибки. Объект ошибки XRT (глава 4) избежал этого в проекте (неизменяемые объекты с минимальным выделением, при отказе деградация категории в статическую `XERR_MEMORY`) — а test_oom и есть машинная проверка этого обещания: «проверить, что отчёт об ошибке OOM сам не запрашивает память» — первая строка его комментария.

## Понятия

### Поточечное вращение: форма перечисления

```diagram flow
- Сборка: квотный распределитель (Limited=true, Remaining=N)
- Цикл: N убывает от стартового -> каждый раунд сбрасывает тестируемый объект -> полный прогон потока
  -> тройное утверждение: отказ в возврате / состояние не изменилось (продолжает работать или безопасно разрушается) / ошибка верна
- Завершение: поток успешен (Remaining всё ещё >0 - прошли за последней точкой выделения)
- Сверка весь путь: Reset/Snapshot отладочной кучи - ноль утечек каждый раунд
```

Сильное утверждение «состояние не изменилось» двухуровневое: **продолжает работать** (OOM временен — после освобождения памяти тот же объект работает как раньше, например map после неудачной вставки всё ещё ищет); **безопасно разрушается** (минимум путь Destroy не падает второй раз — очистка наполовину инициализированного полна). Оба уровня — контракт: первый — качество, второй — нижняя планка.

### Три формы провального распределителя

| Форма | Механизм | Применение |
| --- | --- | --- |
| Счётная (`xrtMemDebugFailAfter(N)`) | первые N успешны, N+1-й отказывает; Clear сбрасывает и триггер-бит | одно-точечная инъекция + аудит событий (приложения и тесты делят) |
| Квотная (самописная: `Fail`/`Limited`/`Remaining`) | пересылает вниз, пока не исчерпается квота | сканирование вращением (Remaining убывает — это и есть скан) |
| Полностью провальная (`FailAllocator`) | всегда NULL | крайние пути (быстрая проверка отказа самого первого выделения) |

Три формы — «памятный бюджет как управляемая ручка» — тестирование из бинарного мира «есть память/нет» входит в точный мир «в какой момент нет».

### Выживание системы ошибок при истощении

Цепочка утверждений `test_oom` — образец: `xrtMalloc(32)==NULL` + категория ошибки `XERR_MEMORY` + домен `xrt.memory`; затем `xrtErrorCreate(...)==NULL` (выделение самого объекта ошибки отказывает) + **в слоте всё ещё XERR_MEMORY** — «отказ создания ошибки не затирает факт OOM». Это проверяет глубокое обещание «минимальных зависимостей» главы 4: канал ошибок сохраняет работоспособность при истощении ресурсов. **Семантика деградации при полном OOM** (многократно в контрактах): «если OOM сделал невозможным выделение даже объектов ошибки, деградировать в статический XERR_MEMORY» — не каждый отказ несёт богатый контекст, но **каждый отказ виден**.

### Расширение форм сбоев: не только отказ выделения

Карантин отладочной кучи (глава 6) расширяет инъекцию сбоев на **сторону освобождения**: двойное освобождение, использование после освобождения (UAF) — отложенное переиспользование карантина делает такие ошибки в тестах **неизбежно видимыми** (а не молча проходящими). Комбинация `_mutation`-тестов с OOM (мутация + поточечный отказ) — предельная форма давления: уродливый ввод × истощение ресурсов — глубочайшие углы парсера тоже освещены. Та же дисциплина в расширениях: поточечный откат xhttp, OOM-шлюз серверной маршрутизации xws — **каждая библиотека-расширение везёт свой _oom-матрицу** (тот же шлюз после наложения манифестов главы 130).

### Почему OOM-дисциплина C-библиотек строже, чем у управляемых языков

Сопоставление показывает необходимость этих вложений. В управляемых языках (Java/Go/C#) отказ выделения — `Throwable` — рантайм подстилает разматывание стека, GC гарантирует возврат — платформа забирает большую часть очистительной ответственности приложения. У C такой подстилки нет: отказ выделения — просто `NULL` в возврате, **очистка на 100% в ответственности вызывающего** — каждое поле наполовину инициализированной структуры, каждый блок частично построенного контейнера кто-то обязан вернуть в правильном порядке. 185 файлов _oom XRT — поточечная приёмка «обязанности возврата». Библиотек того же масштаба с такой плотностью почти нет — OOM-обработка большинства C-библиотек останавливается на «критический путь проверил NULL» — это и есть корень «случайных утечек памяти, в конце концов замораживающих OOM» во встраиваемых и долго работающих сервисах: не какой-то NULL пропущен, а какой-то путь очистки никогда никем не пройден. Вращательное перечисление делает «каждый путь очистки пройден» машинной гарантией — в этом вся его ценность.

## Контракты

- **Вращательное перечисление**: скан точек отказа покрывает каждое выделение — каждый путь очистки исполнен и утверждён.
- **Тройное утверждение**: отказ в возврате / состояние не изменилось (продолжает работать или безопасно разрушается) / ошибка верна (категория + домен).
- **Дисциплина сверки**: ноль утечек каждый раунд (Reset/Snapshot отладочной кучи перекрёстно).
- **Три формы распределителя**: счётная/квотная/полностью провальная — ручка точна до «в какой момент».
- **Выживание ошибки**: отчёт в OOM не выделяет память; при отказе создания ошибки слот сохраняет XERR_MEMORY.
- **Семантика деградации**: при невозможности выделить объект ошибки — деградация в статический XERR_MEMORY — отказы видны всегда.
- **Инъекция на стороне освобождения**: карантин ловит двойное освобождение/UAF — формы сбоев покрывают пути освобождения.
- **Комбинированное давление**: мутация × поточечный отказ — пространство произведения уродливого ввода и истощения ресурсов.
- **Расширения — тот же закон**: каждая библиотека-расширение с собственной _oom-матрицей — наложение манифеста есть наложение шлюза.

## Ловушки

### Ловушка 1: OOM-тест не сбрасывает состояние инъектора

Симптом: со второго раунда вращения всё «отказывает» — триггер-бит FailAfter первого раунда всё ещё висит; или Remaining квотного распределителя не заполнен заново — проверяется «всегда отказ», а не «отказ в N-й раз».

Причина: инъектор состояние держит — каждый раунд цикла обязан сбрасывать полностью (FailClear/заполнение Remaining/пересборка тестируемого объекта). Забытый сброс превращает «перечисление» в «повторное тестирование первого состояния».

```c bad
for ( N = 1; N < 100; N++ ) {
	fail_after(N);
	run_flow();        /* остатки триггер-бита/квоты прошлого раунда - при N>1 всё отказывает */
}
```

```c good
for ( N = 1; N < 100; N++ ) {
	reset_injector();   /* Clear триггер-бита / заполнить квоту */
	rebuild_target();  /* пересобрать тестируемый объект в согласованную стартовую точку */
	fail_after(N);
	run_flow();
	assert_three();    /* тройное утверждение */
}
```

### Ловушка 2: утверждён «отказ в возврате» на уже испорченном объекте

Симптом: тест проходит, прод падает — тест после утверждения отказа выбросил объект (Destroy не шёл); вызывающий в проде прошёл путём очистки и наступил на наполовину инициализированное поле.

Причина: **«безопасно разрушается» — обязательный пункт теста** — Destroy пути отказа обязан реально исполниться в тесте (это удостоверение исполнения путей очистки).

```c bad
testRequire(op(&Obj) == false, "oom");
/* сразу return - Destroy в состоянии отказа ни разу не исполнялся */
```

```c good
testRequire(op(&Obj) == false, "oom");
testRequire(destroy(&Obj), "失败态可安全销毁");  /* путь очистки исполнен */
```

### Ловушка 3: утверждение ошибки смотрит только категорию, не домен

Симптом: OOM выдан как `XERR_IO` или ошибка параметра — тест (только категория) пропускает — логика повторов верхнего уровня идёт не в ту ветку («нет памяти» принято за «временную IO-ошибку», буря повторов).

Причина: категория и домен вместе образуют идентичность ошибки (глава 4); OOM-тесты утверждают оба — неверный домен есть неверный отчёт.

```c bad
testRequire(xrtErrorKind(xrtGetError()) == XERR_MEMORY, "kind");
/* домен не проверен: MEMORY домена xrt.io тоже пройдёт */
```

```c good
testRequire(xrtErrorKind(xrtGetError()) == XERR_MEMORY, "kind");
testRequire(strcmp(xrtErrorDomain(xrtGetError()),
	"xrt.memory") == 0, "domain");   /* двойное утверждение категория+домен */
```

## Упражнения

### Базовое: ощущение трёх форм

На один и тот же код с 3 выделениями инъекция всех трёх форм: FailAfter(2) (отказ 3-го)/квота 2 (эквивалент)/полный отказ (отказ 1-го). Критерии приёмки: утверждения точек отказа трёх форм совпадают; вы понимаете эквивалентность и различие (счётная несёт аудит событий).

### Продвинутое: обёртка вращения

Написать родовой ротатор `oom_scan(被测流程, 最大点数)` (тестируемый поток, максимум точек): внутренний цикл инъекция-сброс-утверждение-сверка. Прогнать вставку map главы 18. Критерии приёмки: скан завершается автоматически (за последней точкой выделения); ноль утечек каждый раунд; намеренно оставить утечку на пути очистки — ротатор называет раунд.

### Вызов: произведение мутация × OOM

Мутационные тесты парсера (скажем, percent-кодирования) плюс поточечный отказ: внешняя мутация ввода, внутренний скан точек отказа — выборка комбинаций (полное произведение слишком велико). Критерии приёмки: стратегия выборки обоснована (скажем, 1 точка отказа на 10 мутаций); найден дефект «виден только при уродливом вводе + истощении» — или доказано его отсутствие.
