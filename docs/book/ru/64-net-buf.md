## Ориентация

`xnetbuf` — **ссылочно-цепочечный буфер** сетевого слоя: данные организованы цепочкой span (сегментов), а не сплошным блоком — естественная форма сетевых данных (прибытие по сегментам, частичное потребление); **четыре типа добавления** делятся по владению (копия/заимствование/захват/колбэк освобождения) — язык владения главы 5 полностью высажен на IO-буферы; **сшивка и потребление** (Pullup непрерывизирует префикс, Consume потребляет префикс — продвижение без копий); **пул буферов** (xnetbufpool — переиспользование сегментных блоков, сток распределений). Это прямой носитель приёма/передачи движка — `SendBuffer`-эхо без копий золотого стандарта главы 66 — его сцена.

## Введение

Жизнь одного отрезка сетевых данных: прибытие сегментами (сегменты TCP, датаграммы UDP) → сборка в сообщение → частичное потребление (заголовок прочитан, тело осталось) → отправка дальше. Сплошной буфер (xbuffer главы 15) подходит под «накопить и взять», но сетевая форма «сегментное прибытие + частичное потребление» заставляет сплошность копировать на каждом шаге — заголовок пришёл, копия; тело добавилось, ещё копия; заголовок потреблён, снова перенос.

Ссылочно-цепочечный буфер меняет модель: данные живут цепочкой сегментов — **прибытие становится сегментом (ноль копий), потребление продвигает указатель (ноль копий), и только когда нужен сплошной вид — Pullup (локальная копия)**. Четыре типа добавления сводят все источники (принятый отрезок, заголовок на стеке, блок malloc, внешняя память с колбэком) в одну цепочку — различия владения объявляются на входе и освобождаются каждое по-своему на выходе (Clear). Пул позволяет переиспользовать сегментные блоки (узлы цепочки) — счёт распределений на высокочастотных путях приёма/передачи падает почти до нуля.

## Понятия

### Четыре типа добавления: полный набор владения

| Вход | Владение | Типичный источник |
| --- | --- | --- |
| `xrtNetBufAppend` | Копия | Безопасное включение произвольной памяти |
| `xrtNetBufAppendBorrow` | Заимствование | Стек/статические данные вызывающего (на выходе не освобождаются) |
| `xrtNetBufAppendTake` | Захват | Блок xrtMalloc (на выходе xrtFree) |
| `xrtNetBufAppendRef` | Колбэк | Внешняя память + функция освобождения (на выходе колбэк) |

Четыре типа — буферная версия полного набора **владение/заимствование/управление** главы 5 (копия — вид владения, Take — передача владения, Borrow — заимствование, Ref — настраиваемое управление). Пример buf_tour собирает "hello world" из четырёх сегментов по одному на тип — с утверждением **корректности освобождения**: колбэк AppendRef обязан сработать ровно один раз после Clear. **Prepend** (вставка в голову цепочки) и **Move** (перенос целиком) дополняют операции формы.

### Форма и потребление

```diagram flow
- Запросы формы: Empty / Size / SpanCount / Spans — обзор цепочки
- Pullup(префикс N): непрерывизировать первые N байт (локальная кросс-сегментная копия — предпосылка разбора заголовков)
- Peek(смещение): просмотр копированием со смещением (цепочку не трогает)
- Find(байт): кросс-сегментный поиск (локация разделителя, XRT_NPOS при промахе)
- Consume(N): потребить префикс N байт (продвижение головы цепочки — продвижение без копий)
```

**Pullup — мост между цепочкой и сплошным видом**: разбору протокола нужна сплошная память для заголовков (чтение memcmp/struct) — Pullup стягивает первые N байт в первый сегмент (при нехватке копирует и сливает), остальную цепочку не трогая; **Consume — продвижение без копий**: потребление N байт лишь освобождает пройденные сегменты — цикл «прочитал заголовок → потребил» машины состояний протокола идёт без лишних копий. Вместе эти две операции — **стандартный движок разбора протоколов** (разбор заголовков HTTP главы 85 собирается из них).

### Резерв и фиксация

`Reserve + Commit/Cancel`: резервирование N байт **записываемого места** в хвосте цепочки (прямой выходной путь в сеть — движок резервирует, заполняет и фиксирует в сегмент, когда надо отправить); Cancel отбрасывает незафиксированный резерв. Это канал записи без копий на стороне отправки — поза заполнения перед Send движка.

### Пул буферов

`xrtNetBufPoolCreate` (ConfigInit настраивает размер сегмента/уровни) — сегментные блоки берутся из пула, Clear возвращает их — счёт распределений высокочастотных путей стремится к нулю (идея пулинга главы 22, высаженная на IO-сегменты). `PoolTrim` поджимает пустые сегменты; запросы информации пула несут счётчики занятых/свободных (поля наблюдения). **Отношение пула и буфера**: буфер (логика цепочки) не требует пул — голая цепочка тоже работает (malloc на сегмент); движок и высокочастотные сценарии сочетаются с пулом — `PoolGet` берёт буфер с сегментами, Clear автоматически возвращает в пул.

(3) Тройка потребления: Prepend (вставка в голову), Pullup (непрерывизация префикса — предпосылка кросс-сегментного разбора заголовков), Peek/Find/Consume (просмотр/поиск/продвижение) — полная операционная панель движка разбора протоколов. (5) Move: цепочка-источник переносится целиком в цель, источник пустеет — передача буфера без копий (фундамент передачи ссылки главы 66). (6) Trim возвращает пустые сегменты + **release-cb fired once** — колбэк AppendRef сработал ровно один раз, свидетельство корректности освобождения (приёмка принуждения владения).

## Контракты

- **Четыре типа владения**: копия/заимствование/захват/колбэк — объявление на входе, каждое своё освобождение на выходе (колбэк Ref ровно один раз).
- **Форма цепочки**: сегментированность без копий; сплошной вид через Pullup (локально), потребление через Consume (продвижение без копий).
- **Канал резерва**: Reserve → заполнить → Commit в сегмент / Cancel отбросить — запись без копий на стороне отправки.
- **Пулинг**: сегментные блоки возвращаются в пул для переиспользования; Trim поджимает; информация пула несёт занятые/свободные (наблюдение).
- **Передача Move**: перенос целой цепочки без копий — буферная версия передачи ссылки (фундамент SendBuffer главы 66).

### От примеров к инженерии: три хозяина цепочки буферов

**Приёмно-передающая грань движка** (самый горячий путь): колбэк движка вручает `xnetbuf` (цепочка сегментов — данные уже в сегментах, ноль копий), обработчик потребляет (Consume, продвижение без копий), эхо двигает напрямую (передача ссылки SendBuffer — центральная демонстрация золотого стандарта); сторона отправки заполняет через Reserve/Commit. Ни одной копии на всём пути — ссылочная цепочка во всей красе.**Парсеры протоколов**: Pullup(длина заголовка) → разбор → Consume(заголовок) → цикл — фундамент разбора заголовков HTTP главы 85; Find находит разделители (протоколы с разделителями), Peek просматривает (диспетчеризация после распознавания типа). **Перенос данных**: файл → сеть (блок, прочитанный асинхронно в главе 47, AppendTake в цепочку — захват без копий), сеть → файл (цепочка Move в канал записи) — обмен данными между IO-доменами с цепочкой в роли контейнера. Три хозяина делят одно: **цепочка — валюта плоскости данных** — в противовес дереву значений как валюте плоскости управления тома 4 (управление: деревья значений, данные: цепочки — две валюты, каждая своим каналом, рукопожатие через доменное имя (разобранные адреса-результаты)).

### Разделение труда с xbuffer главы 15 и асинхронностью главы 47

Три буферных инструмента легко путаются — одна таблица ставит меру. **xbuffer (глава 15)**: сплошной накопитель байт — «накопить и взять» (чтение файлов, накопительная стадия декодирования протоколов); семантика копий, Take уносит сплошной блок. **xnetbuf (эта глава)**: ссылочная цепочка сегментов — «сегментное прибытие, частичное потребление» (сетевой приём/передача, машины состояний протоколов); продвижение без копий, посегментное владение. **Результаты асинхронных файлов (глава 47)**: `xfiledata` — один блок данных одного IO (владеющий) — его Data можно AppendTake в цепочку (файл → сеть без копий). Выбор по форме данных: сплошные потребности — xbuffer, цепочечное потребление — xnetbuf, поблочная передача — filedata → Take в цепочку. Типичный конвейер протокольного стека: порт принимает сегменты → цепочка → разбор заголовков → тело копится в xbuffer → дерево значений — каждый инструмент на своём месте.

### Взгляд дизайна: границы нулевого копирования

Вся эта глава — о нулевом копировании, но знайте его границы. **Правильное место нулевого копирования**: перемещение данных на горячих путях (выполняется на каждое сообщение) — движок к обработчику, обработчик дальше; **разумное место копий**: пересечение границ (непрерывизация протокольной границы — Pullup локально), смена владения (нестабильный источник Borrow меняется на Append-копию), малые данные (копия нескольких байт заголовка дешевле управления сегментами). **Критерий**: большие данные с ясным жизненным циклом → нулевое копирование; малые данные или сложные циклы → копия ради простоты. 11 байт в четырёх сегментах в buf_tour — педагогическое преувеличение: реальную гранулярность сегментов решает буферная политика движка (размер сегмента в конфигурации пула); цепочка, которую видит обработчик, уже разумно сегментирована. **Цена злоупотребления нулевым копированием — умственная нагрузка** (окна заморозки, контракты заимствования, колбэки освобождения) — каждый урок языка владения главы 5 выплачивается здесь.

## Ловушки

### Ловушка 1: заимствованный сегмент переживает источник

Симптомы: из цепочки читаются повисшие данные — сегмент Borrow после освобождения источника становится диким указателем; зависит от таймингов, трудно воспроизвести.

Причина: контракт Borrow — «источник живёт, пока жива цепочка»; досрочное освобождение источника нарушает контракт (цепочечная версия дисциплины заимствования главы 3).

```c bad
void appendStack(xnetbuf* Buf)
{
	char Header[4] = { 0, 1, 2, 3 };
	xrtNetBufAppendBorrow(Buf, Header, 4);   /* заимствуем стековый массив */
}   /* функция вернулась — кадр стека реколлектится, сегмент в цепочке повисает */
```

```c good
void appendCopy(xnetbuf* Buf)
{
	char Header[4] = { 0, 1, 2, 3 };
	xrtNetBufAppend(Buf, Header, 4);   /* копия в цепочку — время жизни источника не важно */
	/* или Take (захват malloc-блока) / Ref (настраиваемое освобождение) по источнику */
}
```

### Ловушка 2: цепочка как сплошная память без Pullup

Симптомы: редкая порча разбора заголовков — заголовок, пересекающий сегменты, читается склеенным неверно; с одним сегментом нормально, с несколькими — падает.

Причина: цепочка не гарантирует сплошности — прямой `memcpy(buf, Spans[0].Data, HeaderSize)` видит только первый сегмент (заголовок может стоять на двух).

```c bad
xnetspan Spans[8];   /* массив вызывающего (возвращает фактическое число сегментов) */
size_t nSpans = xrtNetBufSpans(Buf, Spans, 8);
memcpy(Header, Spans[0].Data, 8);   /* копируется только первый сегмент — порча при кросс-сегментном заголовке */
```

```c good
if ( xrtNetBufSize(Buf) >= 8 ) {
	xrtNetBufPullup(Buf, 8);   /* непрерывизировать префикс 8 байт (локальная кросс-сегментная копия) */
	xnetspan Out[1];
xrtNetBufPullup(Buf, 8, Out);
memcpy(Header, Out[0].Data, 8);
}
```

## Упражнения

### Базовое: воспроизведение четырёх типов

Соберите "hello world" из четырёх сегментов по одному на тип добавления; напечатайте Size и SpanCount; после Clear удостоверьтесь, что колбэк Ref сработал ровно один раз.

### Продвинутое: цикл потребления заголовков протокола

Смоделируйте TLV-поток: случайно сегментированный байтовый поток входит в цепочку → Pullup(4) читает длину → Find находит разделитель → Consume потребляет запись целиком → цикл, пока не остаётся меньше записи — стандартный цикл цепочечного разбора (репетиция главы 85).

### Вызов: бенчмарк приёма/передачи с пулом

Одну и ту же нагрузку (миллион сегментов по 1 КБ входит/потребляется) прогоните на голой цепочке и цепочке с пулом — сравните число распределений (статистика главы 6) и время. Критерий приёмки: пуловая версия распределяет на два порядка меньше; время заметно выигрывает; после Trim свободные пула в нуле (чистое завершение); таблица сравнения в отчёте.
