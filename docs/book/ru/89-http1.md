## Ориентация

Поверх фундамента главы 88 эта глава собирает полный **слой сообщений HTTP/1**: `xrtHttp1RequestParse`/`xrtHttp1ResponseParse` разбирают заголовки запроса/ответа из сети в структуру «стартовая строка + массив полей» (трёхзначный возврат, заимствованные представления), `xrtHttp1ResponseWrite` упаковывает строку состояния и поля за один раз, а поиск по полям напрямую использует фундаментные `xrtHttpFieldFind`/`FieldNext` (поиск без учёта регистра по разобранному массиву). Ключевое слово дизайна — **привязанный массив**: `xhttp1head` привязывает предоставленный вызывающим массив полей — один Head на поток, используемый вновь и вновь, ноль распределений на запрос; это фундаментный путь рантайма xhttp и самодельных шлюзов. Тело (chunked и прочее) — тема кадрирования главы 90; эта глава останавливается на «пустой строке, завершающей блок заголовков».

## Введение

Сервер HTTP/1 обрабатывает десятки тысяч запросов в секунду, каждый заголовок около 1 КБ с дюжиной полей. Если каждый разбор распределяет массив полей и освобождает его после — блокировки и фрагментация аллокатора становятся узким местом раньше всего, а путь восстановления после OOM добавляет удар. Ответ XRT виден в самой форме API: `xrtHttp1HeadInit(&Head, Fields, 8)` привязывает **стековый массив вызывающего** к Head — разбор лишь заполняет массив представлениями; следующий запрос переиспользует тот же Head и массив, распределений ноль.

Второе проектное решение — **трёхзначный возврат**: `XHTTP1_READY` (полный заголовок прибыл), `XHTTP1_MORE` (входа мало, ждать данных), `XHTTP1_ERROR` (структура нелегальна). С соглашением «отказ не продвигает» потоковый сервер может бездумно «принял отрезок — попробовал разобрать — MORE: принял ещё» — HTTP-редакция цикла кадрирования главы 71.

## Понятия

### Разбор: от байтов к структуре

`xhttp1head` после разбора: `Method`/`Target` (запрос) или `Status`/`Reason` (ответ), `Version`, массив полей (`Fields`/`FieldCount` — зона заполнения привязанного массива), `Bytes` (общее число байтов блока заголовков с завершающей пустой строкой — тело начинается отсюда). Модель трёхзначного возврата:

```diagram state
输入不足 -> XHTTP1_MORE: 等待更多数据（不消费、不报错）
结构完整 -> XHTTP1_READY: 视图发布，Bytes 给出正文偏移
结构非法 -> XHTTP1_ERROR: 字段数超限/起始行非法/头不完整语义
```

Запрос и ответ делят структуру Head (роль определяет вход вызова: `RequestParse`/`ResponseParse`). `ResponseParse` принимает параметр метода — семантика ответа зависит от метода запроса (ответ HEAD без тела; этот контекст в Plan главы 90 станет жёстким правилом).

### Транспортные привязки парсера (http1_net / http1_tls)

Вход `RequestParse`/`ResponseParse` — **непрерывная память** — форма тестовых векторов и целых буферов. Настоящий приёмный путь выдаёт **цепочку буферов** движка (заголовок может быть разрезан на два блока, глава 64), а TLS-соединение — **поток открытого текста через записи** (глава 86). Слой привязок подключает парсер к этим двум настоящим источникам: `xrtHttp1RequestParseBuffer`/`xrtHttp1ResponseParseBuffer` потребляют `xnetbuf` (представления Head заимствуют буфер; только при заголовке на стыке выделяется непрерывный префикс по надобности — «функция не потребляет вход; вызывающий потребляет Head.Bytes после обработки»); `xrtHttp1RequestParseTls`/`xrtHttp1ResponseParseTls` едят `xtlsstream` напрямую (открытый текст не потребляется; на стыке записей объединяется только Header — без буфера фиксированного размера на соединение). В каждой привязке по две функции, но сигнатуры и трёхзначная семантика полностью совпадают с версиями в памяти: **привязка тонка, потому что парсер с самого дизайна оставил «откуда приходят байты» параметру** — защита лимитов, трёхзначные возвраты и дисциплина нуля выделений переносятся целиком. Сервер xhttp главы 103 и потоковый сервис главы 107 в своей основе идут именно по этим двум привязкам.

### Поиск и обход

Типовые операции после разбора: по массиву `Head.Fields` напрямую применяются `xrtHttpFieldFind`/`FieldNext` главы 88 (без учёта регистра — имена HTTP-полей семантически регистронезависимы; одноимённые многозначные поля обходятся по порядку, стиль Set-Cookie), `xrtHttpFieldGet`/`FieldGetUnique` (взятие значения и семантика уникальности). В комбинации с токен-итератором главы 88 они покрывают составные суждения вида «содержит ли Connection upgrade» — HTTP-обновление главы 93 (рукопожатие WebSocket) использует именно эту комбинацию.

### Упаковка: строка состояния + поля одной записью

`xrtHttp1ResponseWrite(版本, 状态码, 短语, 字段数组, 数量, 输出, 容量, &长度)` (версия, код состояния, фраза, массив полей, количество, вывод, ёмкость, &длина) — строка состояния и блок полей пишутся **за один раз**: "HTTP/1.1 200 OK\r\nContent-Type: ...\r\n\r\n". Атомарность ёмкости как в главе 88: нехватка — ноль записей. Запросная сторона зеркально — `xrtHttp1RequestWrite`.**Почему не собирать printf-ом**: каждый шаг пути сборки может отказать на середине (полсообщения), а детали формата (пробелы строки состояния, терминаторы полей) расползаются по коду — однократная упаковка собирает их в один вход, прогнанный через мутационное тестирование.

### Потолки и оборона

`xhttp1limits` (опционально передаётся в Parse) управляет: потолком числа полей (ёмкость привязанного массива — естественный потолок), потолком общей длины блока заголовков, потолками длины метода/цели.**Почему обязательно**: злой клиент может прислать блок заголовков на 2 ГБ — парсер без потолков это усилитель памяти. Умолчания консервативны, прокси-сценарии расширяют по надобности — потолки это решение развёртывания, а не глобальная константа.

### Предвестие слоёв Message и Body

API этой главы — до «конца блока заголовков». `MessageParse` главы 90 комбинирует «заголовок + тело» за один раз (для малых сообщений), семейство `Body` читает тело потоково (для прокси «принял-переслал») — оба слоя делят разбор заголовков этой главы.

## Контракты

- **Привязанный массив**: Head привязывает массив полей вызывающего; число полей естественно ограничено ёмкостью массива; перед переиспользованием Head чистить не нужно (каждый Parse строит заново).
- **Трёхзначный возврат**: `READY`/`NEXT`/`ERROR`; `NEXT` ничего не потребляет и не сообщает об ошибке; отказ не продвигает (семантика повтора как в кадрировании главы 71).
- **Заимствование представлений**: Method/Target/Status/Reason/поля заимствуют вход; `Bytes` — длина блока заголовков с завершающей пустой строкой (старт тела).
- **Семантика поиска**: имена полей без учёта регистра; одноимённые многозначные поля обходятся по порядку; промах — явный отказ, не значение NULL.
- **Атомарность упаковки**: строка состояния + поля одной записью; нехватка ёмкости — ноль записей; успех публикует общую длину.
- **Потолочная оборона**: limits управляют общей длиной блока/метода/цели; разбор без потолков — усилитель памяти; умолчания консервативны.
- **Семантика метода**: разбор ответа несёт контекст метода запроса (правило «HEAD/204 без тела» исполняет Plan главы 90).
- **Ноль распределений на запрос**: пути разбора и упаковки без кучи (Head/массив/буферы предоставляет вызывающий).
- **Обрезка**: `HTTP1_HEAD`/`HTTP1_BODY`/`HTTP1_MESSAGE` — независимые макросы возможностей, зависящие от фундамента HTTP.

## Ловушки

### Ловушка 1: после NEXT повторный Parse всего объёма (или не продвинули смещение)

Симптом: «принял отрезок — попробовал» потокового сервера превращается в мёртвый цикл или повторный разбор тех же байтов — холостое вращение CPU или задвоение полей.

Причина: семантика `NEXT` — «этого входа мало»: правильное действие — **дописать** новые данные в тот же буфер и Parse снова (вход повторяется с начала; парсер гарантирует отсутствие побочных эффектов на пути NEXT); либо продвинуться по возвращённому потреблённому смещению. Обращаться с ним как с «ошибкой», выбрасывая буфер, — возврат в ад сборки.

```c bad
while ( recv(buf) > 0 ) {
	if ( Parse(buf) == XHTTP1_MORE ) {
		continue;   /* пробуются только новые байты: никогда не соберётся */
	}
	break;
}
```

```c good
/* буфер с дописыванием (глава 64): всё принятое копится в одном отрезке */
while ( recv_append(&In) > 0 ) {
	if ( xrtHttp1RequestParse(view(&In), &Head, NULL, NULL) ==
			XHTTP1_READY ) {
		break;   /* байты после Bytes - тело/следующий запрос */
	}
}
```

### Ловушка 2: массив полей открыт «впритык»

Симптом: чуть более длинный запрос (легален, но полей на два больше) не разбирается — сервер «случайно» отвергает часть клиентов.

Причина: ёмкость привязанного массива — жёсткий потолок. У здоровых браузеров 15-25 полей в заголовке — обычное дело; прокси-цепочки ещё дописывают семейство X-Forwarded-*.

```c bad
xhttpfield Fields[4];   /* отвергает большинство реальных запросов */
xrtHttp1HeadInit(&Head, Fields, 4);
```

```c good
xhttpfield Fields[32];   /* практика: реальные запросы 25 + запас на форвардинг */
xrtHttp1HeadInit(&Head, Fields, 32);
/* действительно сверхдлинные сценарии: ERROR различает «превышение числа полей»;
   прокси расширяет или явно отвергает (само по себе решение против злоупотреблений) */
```

### Ловушка 3: упакованный ответ забыл ограничение содержимого, кроме Content-Length

Симптом: самописный ответ без Content-Length и без объявления chunked — клиент не знает, когда кончается тело, висит до тайм-аута или закрытия соединения.

Причина: тело HTTP/1 обязано нести объявление ограничения (Content-Length, chunked или «конец по закрытию соединения» — надёжно только для семантики HTTP/1.0). API упаковки пишет поля за вас, но **поле ограничения — семантика, которую обязаны предоставить вы**.

```c bad
xrtHttp1ResponseWrite(XHTTP_VERSION_1_1, 200, OK,
	NoFields, 0, Out, sizeof(Out), &iSize);
send(Out, iSize);
send(Body, BodySize);   /* без ограничения: клиент не знает, когда конец */
```

```c good
static const xhttpfield F[] = {
	{ XRT_STR_INIT("Content-Length"), XRT_STR_INIT("11") }
};
xrtHttp1ResponseWrite(XHTTP_VERSION_1_1, 200,
	XRT_STR_LITERAL("OK"), F, 1, Out, sizeof(Out), &iSize);
send(Out, iSize);       /* заголовок объявляет 11 байтов */
send(Body, 11);         /* тело ровно 11: ограничение полное */
```

## Упражнения

### Базовое: сопоставление двух методов

Замените запрос образца http1 на POST (с `Content-Length: 5` и телом в 5 байтов), после разбора напечатайте `Head.Bytes` и проверьте «тело начинается с Bytes». Критерии приёмки: Bytes сходится с ручным подсчётом; представление тела соответствует исходным байтам.

### Продвинутое: стресс-тест обрывков

Подавайте 41-байтовый запрос случайными кусками по 1..N байтов (имитация TCP-сегментации), после каждого дописанного куска Parse — посчитайте, с какого куска наступает READY. Затем нарочно вставьте уродство (имя поля с двумя двоеточиями подряд) и проверьте ERROR с неповреждённым предыдущим состоянием. Критерии приёмки: любой порядок кусков в итоге READY; ошибочный вход сообщает ERROR при прибытии куска с уродством.

### Вызов: парсер конвейеризованных запросов

В одном буфере склеены два полных запроса (HTTP/1.1 pipelining): разобрать первый (Bytes находит границу) → потребить → разобрать второй на остатке. Реализуйте `parse_pipelined(输入, 回调)` (вход, обратный вызов) циклом до NEXT. Критерии приёмки: оба запроса разобраны верно; неполный второй останавливается на NEXT с продолжаемым буфером; весь путь — один Head/один массив, ноль распределений.

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Основные входы | RequestParse / ResponseParse (три состояния); ResponseWrite / RequestWrite (упаковка одной записью) |
| Привязанный массив | HeadInit привязывает массив полей вызывающего; ёмкость — потолок числа полей; переиспользование без распределений |
| Три состояния | READY (Bytes = старт тела) / MORE (ждать данных, без побочных эффектов) / ERROR (не продвигает) |
| Поиск | HeadFind без учёта регистра; многозначные поля по порядку; в паре с TokenNext для суждений о списках |
| Упаковка | строка состояния + поля одной записью; нехватка ёмкости — ноль записей; поля ограничения (CL/chunked) - семантическая ответственность вызывающего |
| Потолки | limits управляют блоком/методом/целью; умолчания консервативны; против усиления памяти |
| Контекст метода | разбор ответа несёт метод запроса; правило «HEAD/204 без тела» исполняет Body Plan |
| Слой Message | заголовок + тело за один раз (малые сообщения); семейство Body потоковое (глава 90) |
| Ноль распределений | пути разбора/упаковки без кучи; Head/массив/буферы — от вызывающего |
| Транспортные привязки | ParseBuffer ест цепочку буферов / ParseTls ест TLS-поток — сигнатуры и три состояния как в версии в памяти; объединение только через блоки/записи |
