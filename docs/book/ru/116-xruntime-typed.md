## Ориентация

Четыре главы xruntime завершаются. Семейство typed-контейнеров (`xtypedarray`/`xtypedstack`/`xtypedlist`/`xtypedtree`/`xtypedset`/`xtypeddict`) разделяет **один контракт значений времени исполнения** поверх шести структур данных: заимствованные неизменяемые описания типов, ведомые описаниями семейства операций над значениями, управляющие жизненным циклом значений (копия/перемещение/сравнение/хеш/разрушение — всё через таблицу описаний; факты о типах главы 113, исполненные контейнерами), единые глаголы владения (Set/Add/Push копирует, Take/Pop перемещает, SetTake атомарно переносит при отказе, Clone глубоко копирует), единая атомарность отказа (многошаговые операции идут в рабочем хранилище до фиксаации; отказ не ломает видимого состояния). **Инженерные моменты**: расширение **переиспользует внутренние быстрые пути контейнеров XRT напрямую** (базовые реализации не копируются — typed-слой есть «ведомая типами оболочка»; массив int64 работает так же быстро, как массив главы 14); операции над двумя контейнерами требуют **равенства указателей описаний** (одного ID/имени мало — жизненный ABI и частный контекст невзаимозаменяемы). Восемнадцать глав тома 11 здесь закрываются.

## Введение

Зачем typed-контейнеры? C-контейнеры глав 14–23 (`xarray(int64)` и др.) — **типизация на этапе компиляции** — быстро, статично, но тип вмерзает в момент компиляции. Сценарии языка-хозяева (скриптовые массивы, JSON, загружаемый назад в память, обмен данными плагинов) требуют контейнеров с **типами времени исполнения**: «тип элементов этого массива — то описание по имени `app.Counter` из реестра» — один код контейнеров, диспетчеризация операций над значениями по описанию во время исполнения. Наивный подход — массив `void*` плюс разбросанные обратные вызовы — приведения в каждой операции всюду; typed-слой концентрирует диспетчеризацию в таблице описаний: **один код контейнеров, всё поведение типов — в xrttype**.

Отношение к динамическим значениям `xvalue` главы 31: xvalue — «одно динамическое значение» (самоописывающееся размеченное объединение); typed-контейнеры — «наборы однотипных элементов» (описание на уровне контейнера, ноль накладных расходов метки на элемент — массив int64 это непрерывные int64, а не массив Value). Они дополняют друг друга: Value хорош для гетерогенных деревьев (JSON), typed — для однородных наборов (скриптовые массивы/таблицы полей объекта).

## Понятия

### Общий контракт: шесть семейств, одно лицо

| Глагол | Семантика |
| --- | --- |
| `Set`/`Add`/`Push`/`Insert` | копирует исходное значение — контейнер владеет новым, исходное остаётся у вызывающего |
| `SetTake` | атомарный при отказе перенос — при успехе исходное восстанавливается в пустое |
| `Take`/`Pop` | перемещает в инициализированный выход — контейнер больше не владеет |
| `Remove`/`Clear`/`Unit` | один Drop на каждое владеемое значение |
| `Clone`/`Merge`/алгебра множеств | глубокая копия — без скрытого разделяемого владения |

**Легальность адресов**: API, принимающие адрес полного типизированного значения, допускают «внешнее значение или точный живой слот этого контейнера» — адреса, указывающие в структуру контейнера/метаданные/запасную ёмкость/паддинг/середину слота, **отвергаются до чтения или записи**; выход и источник перемещения обязаны лежать вне памяти контейнера (контейнерная версия защитной проверки).

### Особые грани шести семейств

- **array** (непрерывное хранение): фиксированная/переменная длина, доступ по индексу, семейство Concat/Equals.
- **stack** (LIFO): Push/Pop/Peek.
- **list** (разреженные целочисленные ключи): вставка/удаление, итерация по порядку — форма скриптового списка.
- **tree** (упорядоченные родовые ключи): ведомое сравнением упорядоченное отображение — типу ключа нужны операции сравнения.
- **set** (уникальные значения): хеш-или-порядковая дедупликация — типу ключа нужны хеш/сравнение.
- **dict** (текстовые ключи): словарь со строковыми ключами — нагрузка узла динамических полей главы 114 (`xrtdynamicfields`) — это он и есть.

### Равенство указателей описаний: почему одного ID мало

Буквально из контракта: «операции с двумя typed-контейнерами требуют, чтобы описания типов элементов были **одним и тем же указателем**. Одинаковый ID, имя, размер или таблица операций **недостаточны**, чтобы доказать взаимозаменяемость жизненного ABI и частного контекста двух описаний.» Два модуля статически объявили «одинаковый» тип? Указатели разные — взаимодействия нет: **встроенные типы XRT и типы, регистрируемые хозяином, должны использовать процессно-канонические описания** (тот же указатель, что возвращает `xrtTypeInt64()`). Это правило уничтожает опасность «содержимое одинаковое, а место объявления разное» (неявный раскол частного контекста/жизни).

### Переиспользование, а не копия

Расширение **переиспользует внутренние быстрые пути контейнеров XRT напрямую** — непрерывное хранение `xtypedarray` и есть внутренняя структура array главы 14; typed-слой добавляет входы, «диспетчеризирующие операции над значениями через таблицу описаний». Выгода двусторонняя: производительность (быстрый путь push int64 не замедляется под typed-оболочкой) и сопровождение (один код алгоритмов контейнеров — идея пул-изации главы 22 в ещё одной форме, «переиспользование реализаций»).

### Атомарность отказа (общая)

При отказе выделения/инициализации значения/копии/перемещения: публично видимые элементы, ключи, порядок, владение **не меняются** — многошаговые операции (Clone/Merge/алгебра множеств) сперва завершаются в отдельном рабочем хранилище и фиксируются один раз; очистка при отказе уничтожает только успешно построенные в этот раз значения, сохраняя нижележащую ошибку как причину. Финальная категория OOM всегда `XERR_MEMORY`. Это продолжает дисциплину атомарности операций Value главы 31 и контейнеров главы 18 — typed-слой не расслабляется из-за «динамичности».

### Место typed-контейнеров в четырёх главах xruntime

```diagram flow
- Система типов (глава 113): описание xrttype - источник фактов об операциях/сравнении/хеше
- Объекты и графы (глава 114): счётные объекты - контейнер может быть нагрузкой и получить идентичность объекта
- Динамические вызовы (глава 115): значения callable - циркулируют как элементы контейнеров
- Typed-контейнеры (эта глава): шесть ведомых описаниями семейств - взаимодействие только при равных указателях описаний
```

```term
（输出 count/joined/index 的数组操作自检行）
```

**Что только что произошло.** (1) `xrtTypedArrayInit(&Values, xrtTypeInt64())` — ведомо **каноническим описанием встроенного int64**: последующие Push копируют int64 (решает Ops описания), Equals сравнивает по int64 — в коде контейнера ноль специфичной для int64 логики. (2) После трёх Push `Clone` глубоко копирует, `Concat` склеивает (Values+Copy = 6 элементов), `Equals(Values, Copy)` решает равенство — глаголы владения работают по общему контракту (Clone глубоко, без разделения). (3) Печать count=3, joined=6, index=найденная позиция — **массив типов времени исполнения ведёт себя изоморфно C-массиву**; отличие только в том, что «тип приходит из описания». Подставьте `xrtTypeString()` или пользовательский тип — тот же набор API (всё ведомо описанием).

## Контракты

- **Заимствование описаний**: шесть семейств заимствуют неизменяемый xrttype; стабильно на время регистрации и жизни контейнера (дисциплина главы 113).
- **Равенство указателей**: межконтейнерные операции требуют одинакового указателя описаний — одинакового ID/имени/размера/таблицы операций мало; встроенные и типы хозяина — процессно-канонические описания.
- **Диспетчеризация операций над значениями**: всё через семейство операций описания (ведомость таблицей) — контейнеры с нулём типоспецифичного кода.
- **Глаголы владения**: семейство Set копирует / SetTake атомарно переносит / семейство Take перемещает / семейство Remove по одному Drop / семейство Clone глубоко копирует.
- **Легальность адресов**: адреса значений — только внешние или точные живые слоты этого контейнера; структура/метаданные/ёмкость/паддинг/середина слота отвергаются; выход и источник перемещения вне контейнера.
- **Атомарность отказа**: видимое состояние неизменно при отказе; многошаговые сперва в рабочее хранилище, потом фиксация; OOM всегда XERR_MEMORY с сохранённой причиной.
- **Переиспользование реализаций**: внутренние быстрые пути контейнеров XRT напрямую — ноль налога производительности от typed-оболочки, один код алгоритмов.
- **Граница обычных C-контейнеров**: C-контейнеры без счёта ссылок и идентичности объекта — слабые ссылки/возврат циклов компонуются через runtime_object с контейнером в роли нагрузки.
- **Особенности семейств**: array непрерывный / stack LIFO / list разреженно-упорядоченный / tree сравнительно-упорядоченный / set уникальный / dict текстовые ключи — каждый специализирован поверх общего контракта.

## Ловушки

### Ловушка 1: взаимодействие «одинаковых типов» с разными указателями описаний

Симптом: Concat/сравнение двух контейнеров с «совершенно одинаковыми» типами элементов отвергается — каждый модуль статически объявил тип с одним именем.

Причина: равенство указателей — жёсткое правило; одинаковое содержимое не доказывает взаимозаменяемости жизненного ABI и частного контекста. Единообразно используйте процессно-канонические описания (встроенный `xrtTypeInt64()` / процессно-канонические описания реестра).

```c bad
/* описания Counter, статически объявленные в модулях A и B независимо */
xrtTypedArrayConcat(&A_Array, &B_Array);   /* указатели описаний разные: отвергнуто */
```

```c good
/* один источник описаний на весь процесс: брать процессно-каноническое из реестра */
const xrttype* T = host_registry_find("app.Counter");
xrtTypedArrayInit(&A, T); xrtTypedArrayInit(&B, T);
xrtTypedArrayConcat(&A, &B);   /* один указатель: взаимодействие возможно */
```

### Ловушка 2: после Clone разделяются значения, «казавшиеся независимыми»

Симптом: клонировали контейнер, изменили один — другой следом; в значениях спрятаны ссылки/дескрипторные элементы.

Причина: Clone — **глубокая копия**, но «глубина» определяется Ops типа элементов: копия ссылочного элемента (значения-объекта) — это **наращивание сильной ссылки** (Copy=Ref у ObjectValueOps главы 114) — сам объект остаётся разделяемым (ровно как и должно быть у типов с ссылочной семантикой). Ожидание «разделить даже объекты» требует элементного собственного Clone.

```c bad
pCopy = xrtTypedArrayClone(&Objs);   /* клон массива объектов: ссылки +1, не новые объекты */
mutate(pCopy);                        /* изменилось тело: «изменился» и исходный контейнер */
```

```c good
/* ссылочная семантика - это свойство: много контейнеров делят один объект (возврат - забота графа) */
/* для действительно независимых копий: тип элемента даёт Ops глубокого Clone */
```

### Ловушка 3: typed-контейнер как корень графа объектов (потерянная трассировка)

Симптом: ссылки объектов, удерживаемые контейнером, граф не трассирует — цикл течёт.

Причина: обычные typed-контейнеры **не несут** счёта ссылок и идентичности объекта — граф трассирует runtime_object (глава 114). Правильные пути: контейнер как нагрузка объекта (контейнер сам — объект) или узлы динамических полей (нагруза dict трассируется через операции значения типа).

```c bad
/* голый typed array держит ссылки объектов в надежде, что граф сам обнаружит */
xrtTypedArrayPush(&Arr, &ObjRef);   /* граф не знает о существовании Arr */
```

```c good
/* сделать контейнер объектом (нагруза держит контейнер) -> объект входит в граф -> InstanceOps.Trace перечисляет элементы
   или использовать xrtdynamicfields (узлы-словари полей трассируют нативно) */
```

## Упражнения

### Базовое: обход шести семейств

Прогнать каждый из шести контейнеров через минимальный цикл (Init → две операции → Destroy) — с одним типом элемента (int64). Критерии приёмки: глаголы владения согласованы между семействами; атомарность отказа (имитация OOM) оставляет видимое состояние каждого семейства неизменным.

### Продвинутое: полиморфный список

list с типом элемента `xrtTypeValue()` (упаковка динамических значений главы 31) — хранить int/string/object три вида значений и обходить с печатью (диспетчеризация по Kind). Критерии приёмки: три вида сосуществуют; глубокие клоны независимы (элементы со семантикой значений); сортировка по сравнению Value.

### Вызов: движок полей объекта

Таблица полей в стиле `xrtdynamicfields`: объект (глава 114) + нагруза typed dict + set/get/перечисление полей + трассировка графа объектов (сбор циклов у самоссылающихся полей). Критерии приёмки: сильные ссылки полей перечисляются Trace; самоссылочные циклы возвращаются в безопасной точке; типы полей вперемешку (int/string/объект).
