## Ориентация

Вторая половина TCP охватывает три продвинутых блока: **четыре семейства отправки** (Vec сбор / Ref ноль копий + колбэк освобождения / Take захват / File посылка файла ядром) с **бюджетом записи** (потолок WriteLimit / запас Writable / в полёте Pending — тройка противодавления отправки); **чтение и ограничения Worker** (Buffer/Read/Consume только внутри Worker — грань потребления буферов прямой передачи; межпоточно через Post); и **серверная форма** (xnetserver — вытягивающий Accept (соединения из очереди), Future Accept и блокирующий Accept сосуществуют, многослушание и общие порты). Четыре состояния и эхо золотого стандарта (глава 67) — базовая форма; эта глава — её полное цветение.

## Введение

Три продвинутых сценария. Сценарий один: файловый сервер должен отправить файл 1 ГБ — прочитать весь файл в память и Send — катастрофа (взрыв памяти); `xrtNetStreamSendFile` (посылка файла ядром + ограниченные диапазоны — место приземления sendfile, анонсированное главой 45) не проходит через пользовательские буферы. Сценарий два: прокси пересылает вниз цепочку сегментов, принятую сверху — копировать перед отправкой расточительно; `SendRef` передаёт напрямую ссылкой (ноль копий + колбэк освобождения). Сценарий три: сервер должен ограничить отправочный откат одного соединения (злонамеренный клиент не читает — буферы раздуваются без границ); **бюджет записи** (потолок WriteLimit, Pending в полёте, запас Writable) — принуждение противодавления на стороне отправки.

Общая тема трёх сценариев — **владение и бюджет грани отправки** — язык главы 5 во всей полноте на выходе IO: Send копирует, SendVec собирает и копирует, SendRef заимствует + колбэк, SendTake захватывает, SendFile делегирует ядру. Пять ступеней выбираются по «откуда данные и кто освобождает» — взаимно однозначно с четырьмя типами добавления буферов главы 65 (те входят в цепочку, эти выходят из неё).

## Понятия

### Четыре семейства отправки и посылка файла

| Вход | Владение | Подходит |
| --- | --- | --- |
| Send | Копия | Безопасный путь малых данных (глава-золотой стандарт) |
| SendVec | Сбор-копия | Несколько буферов одной отправкой (батчинг главы 21) |
| SendRef / SendRefs | Ссылка + колбэк освобождения | Прямая передача цепочки сегментов (ноль копий — родня SendBuffer золотого стандарта) |
| SendTake | Захват | Блок xrtMalloc (движок освобождает после отправки) |
| SendFile | Делегация ядру | Посылка диапазона файла (бэкенд sendfile/mmap) |

**Колбэк освобождения SendRef**: срабатывает ровно один раз, когда данные отправлены (или поток разрушен) — та же дисциплина, что AppendRef главы 65; SendRefs — многосегментный вариант (целая цепочка сегментов одной отправкой). **Диапазон SendFile**: смещение + длина ограничены — поблочная посылка файла управляет памятью (буфер ядра на блок, а не на весь файл).

### Бюджет записи: тройка противодавления отправки

```diagram flow
- WriteLimit(N): потолок бюджета отправки на соединение (в полёте + в очереди <= N)
- Pending(): текущие байты в полёте/очереди — датчик уровня
- Writable(): запас = Limit - Pending — безопасный объём подачи
- Send сверх бюджета: неудача или блокировка (по форме вызова) — точка укуса противодавления
- В пару управление потоком: Pause/Resume — после Pause движок держит данные (страховка памяти)
```

**Полная цепь противодавления**: пир перестаёт читать → окно TCP сжимается → буферы движка копятся → Pending приближается к Limit → новые Send отвергаются → **верхний слой замечает** (обработчик видит неудачу отправки / необходимость ждать) — медленный потребитель не может утащить память сервиса вниз. Pause/Resume — ручная передача (семантика Pausable: после Pause движок удерживает данные без продвижения — верхний слой решает выбросить или разорвать). Очередное противодавление главы 21 в версии соединения.

### Чтение и ограничения Worker

**API внутри Worker** (Buffer/Read/Consume и др. — обязаны вызываться в потоке Worker, владеющего Stream): грань потребления буферов прямой передачи (Buffer берёт цепочку, Consume продвигает — операции главы 65 напрямую на данных движка); **межпоточный вход** (`xrtNetPost` доставляет задачу в Worker Stream — engine-версия Post планировщика главы 56); **семейство ожидания** (Wait/WaitAvailable блокирующие — рандеву из не-Worker потоков; WaitAvailableAsync в форме Future — для оркестрации). **Зачем ограничение**: предпосылка безблокировочных операций прямой передачи — «один поток»; ограничение Worker — engine-версия дисциплины привязки планировщика главы 56; межпоточно исполнение передаётся через Post, а не блокировкой — дисциплина нулевых замков повсюду.

### Сервер: двуликий Accept и общие порты

`xnetserver` (TCP Server): **вытягивающий Accept** (соединения из очереди — пришло одно, взял одно; верхний слой напрямую управляет троттлингом/диспетчеризацией — форма примера tcp_server); **Future Accept** (на стороне событийного цикла — удобно для оркестрации); **блокирующий Accept** (из не-Worker потока — управляющий поток ждёт соединений).**Сосуществование двух лиц** — реальная форма эпохи миграции (пример tcp_server_sync: Future и блокирующее извлечение на одном Server в одной сцене). **Многослушание и общие порты**: один Server — несколько конечных точек (двухстековый v4+v6); общие порты в стиле SO_REUSEPORT (утверждение `shared-port=1` в server_tour — платформенная поддержка совместного прослушивания многих процессов). **Статистика Accept** (accepted/queued — поля наблюдения сервиса).

### Остановка и шторм: серверная уборка

Close слушателя (прекратить приём — вытянуть accept в полёте), потолок соединений (глубина очереди ServerConfig — противодавление приёма: при заполнении отказывать новым, а не стоять бесконечно), порядок остановки (Listener → Stream → Engine — порядок главы 67 в серверной версии). **Точка обработки шторма соединений**: ограничение глубины очереди Accept + быстрый отказ (низкая цена ошибки) — а не принять и разорвать (ресурсы уже выделены).

### Полная программа: тур по всему семейству Stream

Из примера репозитория `examples/network/tcp_stream_tour/main.c` — полная приёмка семейств отправки + бюджет + управление потоком + полузакрытие:


```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/network/tcp_stream_tour/main.c -lws2_32 -liphlpapi
stream-tour: config write-limit>=64k writable>=0
sends: vec+ref+refs+take+file = 53 bytes verified
worker-read: buffer=8 read="buf-" consume=4 socket+setevents+setdata=ok
waits: read=1 available=1 available-async=1 write=1
flow: pause=held resume=delivered
shutdown: peer-eof=1 stats(sent=65) error=(none)
```

**Что только что произошло.** (1) Конфигурационный уровень: WriteLimit не меньше 64k, Writable стартует с 0 — отправная точка тройки бюджета записи. (2) **Совместное выступление четырёх семейств отправки**: Vec+Ref+Refs+Take+File отправляют по отрезку, 53 байта сверены целиком — все пять ступеней владения пройдены на одном потоке. (3) Строка worker-read: тройка чтения внутри Worker (Buffer = 8 байт доступно, Read берёт "buf-", Consume продвигает на 4) + Socket/SetEvents/SetData — практика API ограничения Worker. (4) Строка waits: четыре формы ожидания (блокирующее чтение / снимок Available / Async Future / ожидание записи), по одной на каждую. (5) Строка flow: после Pause данные held (движок удерживает без продвижения), после Resume delivered — два такта управления потоком. (6) Строка shutdown: пир читает EOF, счётчик sent статистики (65 = 53 + 12 дополнительных байт), error=(none) — чистое конечное состояние. Этот тур — приёмка всех операций плоскости данных Stream — чек-лист для продакшн-кода.

## Контракты

- **Пять ступеней отправки**: Send копия / Vec сбор / Ref ссылка + колбэк ровно один раз / Take захват / File делегация ядру — выбор по источнику (соответствие четырём типам входа в цепочку главы 65).
- **Бюджет записи**: потолок WriteLimit + уровень Pending + запас Writable — принуждение противодавления на стороне отправки против медленных потребителей.
- **Ограничение Worker**: Buffer/Read/Consume только внутри Worker; межпоточно через Post — дисциплина нулевых замков.
- **Управление потоком**: Pause/Resume — ручная передача: пауза удерживает данные, верхний слой решает выбросить или разорвать.
- **Двуликий Accept**: вытягивающий/Future/блокирующий сосуществуют — постепенная миграция.
- **Противодавление приёма**: ограничение глубины очереди Accept + быстрый отказ — шторм останавливается за дверью.

## Ловушки

### Ловушка 1: досрочное освобождение данных после SendRef

Симптомы: приёмник изредка получает грязные данные — колбэк отправки ещё не пришёл, а источник уже освобождён; одно семейство с ловушкой 1 главы 65.

Причина: SendRef — отправка ссылкой; окно заморозки данных до колбэка освобождения (движок его читает).

```c bad
char* Block = xrtMalloc(1024);
Fill(Block);
xrtNetStreamSendRef(Stream, Block, 1024, releaseCb, Ctx);
xrtFree(Block);   /* освободили до колбэка — движок ещё читает */
```

```c good
xrtNetStreamSendTake(Stream, TakeBlock, 1024);   /* захват — движок освобождает после отправки */
/* или SendRef + колбэк: колбэк срабатывает ровно когда данные больше не ссылаются — не трогайте до него */
```

### Ловушка 2: отправка без бюджета взрывает память

Симптомы: память сервиса растёт вместе с медленными клиентами — один клиент не читает, буферы движка копятся без границ; OOM-падение в пике ночного трафика.

Причина: WriteLimit не установлен — отправка без потолка, и откат сжимающегося окна TCP весь сваливается в память сервиса.

```c bad
xnetstreamconfig Config;
xrtNetStreamConfigInit(&Config);   /* по умолчанию без ограничения бюджета */
xrtNetStreamSend(Stream, HugeData, HugeSize);   /* безграничный откат */
```

```c good
xnetstreamconfig Config;
xrtNetStreamConfigInit(&Config);
Config.WriteLimit = 1u << 20;   /* бюджет 1 МБ */
/* перед отправкой проверяем запас */
if ( xrtNetStreamWritable(Stream) < Need ) {
	WaitOrPause(Stream);   /* противодавление укусило — ждать или ставить на паузу, не наваливаться */
}
```

## Упражнения

### Базовое: сравнение пяти ступеней

Одни и те же данные отправьте каждой из пяти ступеней (ступень File — через временный файл) — полная сверка на приёмнике; моменты освобождения каждой ступени (колбэк/захват) печатаются и подтверждаются.

### Продвинутое: эксперимент противодавления

Медленный клиент (читает 1 байт, пауза 100 мс) + сервер шлёт интенсивно: с WriteLimit против без ограничений — наблюдайте кривую памяти сервиса (статистика главы 6) и уровень Pending; проверьте путь обработки сверхбюджета.

### Вызов: сервис раздачи файлов

Статический файловый сервис: много клиентов конкурентно скачивают один файл — SendFile поблочно по диапазонам (блочный бюджет) + WriteLimit на клиента + глобальный потолок приёма. Критерий приёмки: раздача файла 1 ГБ держит пиковую память сервиса <100 МБ (доказательство блоков + бюджета); медленные клиенты не мешают остальным; остановка полностью убирается (протокол тройки); скачивания сверяются поп клиентски Hash64.
