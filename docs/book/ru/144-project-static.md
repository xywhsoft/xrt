## Ориентация

Последняя глава книги. Проект 6 (**статический файловый сервер** webserv): HTTPS обслуживает каталог сборки фронтенда — безопасный вход (TLS + сертификаты), статические отображения (префикс URL ↔ каталог на диске + защита от выхода из корня), условные запросы (ETag/304), возобновление загрузок (Range/206), согласование сжатия (gzip для сжимаемых текстов), журнал доступа и graceful-остановка. Это **слияние шести проектов**: обработка строк logstat (журналы), конфигурация configd (адрес прослушивания и отображения каталогов читаются из конфигурации), семантика Range у xdl (на этот раз со стороны сервера), жизненный цикл долгоживущих соединений pushd (HTTP keep-alive и TLS-сессии) — плюс специализация статического слоя (главы 104/131) и сжатия (глава 108). И это **общее стягивание карты знаний книги**: от третьей строки кода до этой главы знания тринадцати томов и ста сорока четырёх глав сходятся в одном настоящем развёртываемом сервисе. За приёмкой — финал книги: чему вы научились и куда идти дальше.

## Введение

Сцена требования: артефакты сборки фронтенда (HTML/CSS/JS/картинки, ~5000 файлов) нуждаются в производственном статическом сервисе — требуется HTTPS (автовыбор сертификатов), конкурентность (пик скачиваний при релизе сборки), условные запросы (согласование кэша клиента — 304 экономит 95% трафика), возобновление загрузок (большой файл можно продолжить после обрыва), сжатие (gzip текстов экономит 70%), журнал доступа (аудит и анализ). nginx может — но вам нужна **программируемость**: своя политика кэша, маршрутизация по арендаторам, связка с внутренними системами — конфигурационный DSL универсального сервера быстро превращается в диалект, который трудно отлаживать; напишите на XRT — всё поведение есть прозрачная логика C-кода. **Это не продолжение учебного упражнения, а демонстрация инженерного решения**: когда сложность конфигурации универсальной детали превышает сложность собственного кода, собственный код становится рациональным — слоистость XRT держит стоимость «написать свою производственную деталь» под контролем (ядро webserv этой главы меньше трёхсот строк, остальное — библиотечные слои).

**Критерии приёмки**: (1) все типы файлов обслуживаются корректно (MIME/кодировка); (2) `../` и кодированный выход наружу — все 404 (проверка сканером безопасности); (3) согласование ETag: второй запрос 304 с нулевым телом; (4) Range: одинарный интервал 206 + multipart на многие; (5) gzip: тексты сжимаются, картинки как есть (матрица согласования Accept-Encoding); (6) 500 конкурентных соединений, устойчивость под пиком скачиваний (повторное использование keep-alive); (7) TLS: автовыбор сертификата по SNI, современные шифронаборы; (8) журнал доступа JSON Lines (форма главы 138); (9) graceful-остановка (полный цикл Drain); (10) ноль утечек stats за весь прогон.

## Понятия

### Архитектура: полная карта слоёв

```diagram flow
- Безопасный вход: TLS Server (сертификаты + SNI) — главы 85/86
- Слой HTTP: Server + Router + промежуточное ПО (журнал) — главы 103/104
- Статический слой: http_server_static — отображения каталогов / защита от выхода / MIME / ETag / Range — глава 104
- Слой сжатия: согласование reply_compress — глава 108
- Наблюдаемость: logger JSON Lines + stats — главы 37/6
- Жизненный цикл: пятисегментные тайм-ауты по умолчанию + Drain — глава 103
```

Каждый из шести слоёв — главная тема какой-то предыдущей главы — **webserv не изобрёл ни одного слоя**, вся его работа — межслойная сборка и бизнес-клей (конфигурируемость отображений каталогов, белый список политики сжатия). Это финальная проверка «слоистой» философии книги: **хорошие системы собирают, а не пишут**.

### Список семантики статического сервиса

| Семантика | Реализация | Главы |
| --- | --- | --- |
| Отображение пути | префикс URL ↔ префикс каталога; после нормализации проверка префикса (защита от выхода) | 104/43 |
| MIME | табличный поиск по расширению | 104 |
| ETag | отпечаток содержимого; If-None-Match → 304 | 104/108 |
| Range | одинарный интервал 206 + Content-Range; многие интервалы multipart | 90/108 |
| Сжатие | согласование q Accept-Encoding + белый список типов | 108/91 |
| Заголовки кэша | Cache-Control по типам (HTML коротко / активы долго) | прикладной слой |
| Каталог | хвостовой слэш → index.html; без слэша → редирект | 104 |

**Ревизия защиты от выхода** (ядро безопасности): запрос `/static/../secret.key` — отображение статического слоя после склейки делает проверку «нормализованный путь остался в корне» (ловушка 3 главы 104); **кодированный выход** (`%2e%22%2f` — процентно-кодированный `../`): URL-декодирование происходит до маршрутизации (глава 89) — декодированный путь проходит ту же проверку. **Двойная линия обороны**: слой кодирования не предполагает единственный вход (атакующий может строить многослойное кодирование — после каждого слоя декодирования перепроверка).

### Условные запросы и политика кэша

Генерация ETag: отпечаток содержимого (хеш файла — глава 73) или кортежный отпечаток (размер + время изменения — ноль затрат на хеширование). **Решение: кортежный отпечаток** — статический файл неизменен, пока содержимое неизменно (предположение неизменности артефактов сборки); хеш содержимого — для сценариев высокой безопасности (защита от обмана метаданных). **Политика Cache-Control**: `index.html` — короткий кэш (`max-age=60` — минута до действия после релиза); активы с отпечатком (`app.a3f9.js`) — длинный кэш (`max-age=31536000, immutable` — смена имени файла есть инвалидация кэша — конвенция фронтенд-сборки). **Трафиковый смысл 304**: второе посещение (с кэшем) — нулевое тело — попадания кэша CDN/браузера не тратят полосу сервера (количественно критерий (3): сайт из 5000 файлов, первый визит 50 МБ, второй < 100 КБ накладных расходов заголовков).

### Матрица политики согласования сжатия

Конфигурация webserv для слоя сжатия главы 108: **белый список типов** (text/css/js/json/svg сжимать; jpg/png/woff2 не сжимать — уже сжатые форматы); **минимальная длина** (< 256 Б не сжимать — накладные расходы больше выгоды); **согласование** (q-значения Accept-Encoding — модель тысячных главы 91). **Путь апгрейда пресжатия**: при сборке генерировать соседний файл `.gz` (`app.js.gz`) — при выдаче `Content-Encoding: gzip` отправлять файл напрямую (ноль онлайн-затрат на сжатие — конвенция CDN); базовая версия этой главы жмёт онлайн (малый объём сборки приемлем), пресжатие — направление упражнения.

### Конкурентность и жизненный цикл

**Форма пика скачиваний**: после релиза N клиентов одновременно тянут все активы — на соединение приходится много запросов (повторное использование keep-alive — клиентская сторона в паре с пулом соединений главы 98). **Конфигурация сервера**: MaxConnections (предел конкурентности), WriteSize (аренда нулевого копирования — большие файлы кусками), пятисегментные тайм-ауты по умолчанию (защита от медленных атак — глава 103). **Путь нулевого копирования файловой выдачи**: семейство `xrtHttpConnFile` статического слоя (главы 104/107) — тело файла не входит в пользовательские буферы (транспортное исполнение SendFile главы 71); **уровень памяти** не зависит от размера файла (проверка stats — критерий (10)). **Graceful-остановка**: Drain (новые отвергнуть, в полёте завершить) → сброс журнала → уничтожение — окно нулевого прерывания при релизном рестарте.

### Разбор реализации: форма исходника главной функции сборки

Главная функция сборки webserv — полный путь от чтения конфигурации до старта сервиса (разбор ключевых сегментов над учебными образцами):

```c
int main(int argc, char** argv)
{
	wsvcfg Cfg;
	xnetengine* Eng = NULL;
	xhttpserver* Srv = NULL;
	xhttpserverrouter* Router = NULL;
	xtlsidentity* Ident = NULL;
	int Result = 1;

	/* 1 конфигурация: форма configd (умолчания -> перекрытие окружением -> валидация) */
	wsv_defaults(&Cfg);
	wsv_env_override(&Cfg);            /* глава 42 */
	if ( !wsv_validate(&Cfg, stderr) ) { return 2; }  /* перехват на старте */

	/* 2 Engine и идентичность */
	Eng = xrtNetEngineCreate(NULL);
	if ( (Eng == NULL) || !xrtNetEngineStart(Eng) ) { goto Cleanup; }
	Ident = wsv_load_identity(&Cfg);  /* глава 82: проверка на этапе старта */

	/* 3 маршрутизация: статические отображения + журнальное промежуточное ПО */
	Router = xrtHttpServerRouterCreate(NULL);
	if ( !wsv_mount(Router, &Cfg) ||          /* массив отображений каталогов */
		!xrtHttpServerUse(Router, wsv_log, &Cfg) ||  /* глава 104 */
		!xrtHttpServerRouterFreeze(Router) ) { goto Cleanup; }

	/* 4 сервис: вход TLS + пятисегментные тайм-ауты по умолчанию */
	{
		xhttpservertlsconfig Tls;
		xrtHttpServerTlsConfigInit(&Tls);
		Tls.Handshake.Identity = Ident;
		Srv = xrtHttpServerRouterStartTls(
			Eng, &Cfg.Net, &Tls, Router, NULL);
	}
	if ( Srv == NULL ) { goto Cleanup; }
	wsv_print_endpoint(Srv);          /* журнал прослушиваемого эндпойнта */
	Result = wsv_wait_shutdown();     /* ожидание сигнала/ввода */
	xrtHttpServerDrain(Srv);          /* graceful-остановка */
	wsv_log_flush(&Cfg);

Cleanup:
	xrtHttpServerDestroy(Srv);
	xrtHttpServerRouterDestroy(Router);
	xrtTlsIdentityRelease(Ident);
	xrtNetEngineDestroy(Eng);
	return Result;
}
```
```term
$ gcc -O1 -DXRT_MODULE_ALL -I extlibs/xhttp/single -include xhttp.h impl.c webserv.c -lws2_32 -liphlpapi
webserv listening on https://127.0.0.1:8443 (root=dist)
```

**Пункты разбора.** (1) Четыре шага сборки (конфигурация → Engine/идентичность → маршрутизация → сервис), каждый провал — goto Cleanup — **одно-выходная дисциплина дотянута до главной функции**. (2) `wsv_mount` — конфигурируемость отображений каталогов (цикл по массиву Cfg.Mounts вешает статические точки — много каталогов/много префиксов). (3) Журнальное промежуточное ПО `wsv_log` снаружи маршрутизации — строка JSON на запрос (время/метод/путь/статус/байты/длительность — запись после Close фиксирует полное состояние). (4) Вход TLS через `StartSecure` (идентичность подключена — SNI автоматически выбирает из многих сертификатов). (5) После Drain сброс журнала — **запросы в полёте во время остановки тоже входят в журнал** (последняя полная партия записей). (6) Всякое уничтожение в обратном порядке зависимостей — исполнение семантики Shutdown главы 103. Главная функция — шестьдесят строк — **весь «бизнес» webserv**: остальное — библиотечные слои и помощники wsv_* (конфигурация/отображения/журнал — каждый < 100 строк).

### Общая сводка с опытом шести проектов

Семнадцать инженерных аксиом — **общая ведомость проверки** в webserv (точка приземления webserv у каждой): **приёмка прежде** (десять критериев включая скан безопасности и пик); **форма решает контейнер** (массив отображений / кортеж ETag / построитель строк журнала); **представления живут одним кадром** (запросное представление журнального промежуточного ПО завершается внутри обратного вызова); **слоистая заменяемость** (сменить бэкенд хранилища / сменить политику сжатия — один слой); **факты платформы входят в проект** (системные различия разделителей путей / прав / расположения сертификатов); **бюджет прежде** (пропускная способность = min(диск, сеть) — CPU пренебрежим с обеих сторон); **тестирование в четырёх квадрантах** (матрица семантики + полигон выхода + пик под нагрузкой); **удалённая неопределённость** (клиент может отправить что угодно — перепроверять после каждого декодирования); **протокольные атомарные точки** (согласование ETag — согласованность гарантирует протокол); **временное имя + переименование** (атомарное переключение нового каталога релиза — переворот symlink); **файловая система — авторитет состояния** (ETag из метаданных файла — без собственного кэша); **тестовые двойники** (детерминированный клиент локальной нагрузки); **веер проектируется заранее** (бюджет повторного использования keep-alive под пик); **сверка конечных состояний** (после Drain счёт соединений нулевой); **номера-самовосстановление** (номер версии релиза даёт клиенту детекцию переключения); **тестовый клиент тоже испытуем** (сверка запросов каркаса нагрузки); **интерфейс эксплуатации** (печать эндпойнта + журнал — вот и наблюдаемость). **У всех семнадцати есть точка приземления** — полнота списка опыта и есть полнота проекта.

### Общее стягивание карты знаний

webserv (и весь том шести проектов) прошёл все главы — инвентаризация по томам: **том 1** (главы 3-8: от первой программы до обрезки — фундамент всего); **том 2** (главы 10-12: числа и хеши — принцип отпечатков ETag); **том 3** (главы 13-23: контейнеры — база таблиц отображений и очередей запросов); **том 4** (главы 25-35: текст и данные — цепочка разбора URL/заголовков/JSON-журналов); **том 5** (главы 36-49: системные сервисы — повседневность журналов/файлов/путей/каталогов/асинхронного IO); **том 6** (главы 50-60: конкурентность — фундамент корректности конкурентности соединений); **том 7** (главы 61-71: сеть — транспортная база TCP/буферов/Engine); **том 8** (главы 72-87: безопасность — все уровни входа TLS); **том 9** (главы 88-96: ядро протоколов — байтовая семантика HTTP/WS); **том 10** (главы 97-108: xhttp — прямой инструментарий этого сервиса); **том 11** (главы 109-128: библиотеки расширений — источник инструментов pushd/xdl); **том 12** (главы 129-136: инженерная практика — дисциплина развёртывания/тестирования/тонкой настройки); **том 13** (главы 137-144: проекты — спираль опыта). **Сто сорок четыре главы, шесть проектов, семнадцать аксиом, около 650 тысяч слов пояснений** — вот всё хозяйство этого учебника. Унести вы должны не шпаргалку API (есть на сайте), а **глазомер слоистости и дисциплину рук** — они работают на любой C-кодовой базе.

## Контракты

- **Двойная защита от выхода**: после склейки нормализация и проверка префикса; многослойное декодирование — перепроверка после каждого слоя — зелёный полигон восьми форм выхода есть основа приёмки.
- **Кортеж ETag**: размер + время изменения (предположение неизменности сборки); 304 с нулевым телом.
- **Два уровня кэша**: HTML-вход короткий кэш (max-age=60) / активы с отпечатком длинный (immutable) — имя файла и есть механизм инвалидации.
- **Белый список сжатия**: семейство сжимаемых текстов; уже сжатые форматы как есть; порог минимальной длины.
- **Range на сервере**: одинарный интервал 206 + Content-Range; многие multipart — дополняет клиент xdl до полной протокольной грани.
- **Нулевое копирование**: тело файла через семейство ConnFile — память не зависит от размера файла.
- **Предел конкурентности**: MaxConnections + пятисегментные тайм-ауты по умолчанию — защита от медленных атак и пика.
- **TLS**: подбор сертификата по SNI; современные наборы; позиция верификатора (у сервера нет верификатора, но есть идентичность).
- **Журнал JSON Lines**: строка на запрос (время/метод/путь/статус/байты/длительность) — форма file_json.
- **Остановка**: Drain отвергает новых и завершает старых → сброс журнала → уничтожение — окно релиза без прерываний.

### Получение цифр бенчмарка и ёмкости

Ёмкостные выводы webserv получать методом главы 135 (не с потолка): **бенчмарк пропускной способности** — имитация пика (500 виртуальных клиентов тянут весь сайт) меряет req/s и точку насыщения полосы (диск или сеть заполняется первым — бюджет указывает направление масштабирования); **распределение задержек** — P50/P99 задержки запросов (агрегация поля длительности журнала — продукт меток времени главы 41); **якоря сравнения** — при той же нагрузке разрыв с nginx (зрелая реализация sendfile/epoll) и анализ источников разрыва (накладные вызовы библиотечного слоя / без ядровой тонкой настройки / без мультипроцесса — в большинстве сцен разрыв < 2 раз приемлем, потому что главный выигрыш — программируемость); **sweep** — двумерный скан числа соединений × размера файлов (у малых файлов при высокой конкурентности и больших при низкой — две формы, у каждой своя точка насыщения). **Форма ёмкостного вывода**: «один инстанс 4C8G: малые файлы — X тыс. req/s (P99 < Y мс), большие — Z ГБ/с — сверх того добавляйте инстансы или ставьте CDN впереди». Эти цифры идут в документ развёртывания — **продукт бенчмарка есть вход эксплуатации**.

### Процесс релиза и версионная политика

webserv сам как релиз (метаинжиниринг — проект тоже софт): **атомарное переключение каталогов** — новая версия собирается в `releases/v{ts}/`, symlink `current` переворачивается (атомарное переключение на уровне каталога — каталогная версия «временное имя + переименование» главы 142: в любой миг current указывает на одну полную версию); **откат** — symlink обратно на старый каталог (секунды — на два порядка быстрее рестарт-отката); **проверка здоровья** — эндпойнт `/health` (проверка артефактов: существование index.html) — релизный скрипт ждёт здоровья, прежде чем переключать трафик; **непрерывность журнала** — журналы через перезапуски катаются по дням (ротация главы 38) + поле версии (какая версия обработала запрос — якорь при разборе временных проблем). Автоматизационный скрипт релиза сам есть идея configd (конечный автомат конфигурации/версии/здоровья) — **знание последовательности проектов смыкается в последнем кольце производственной эксплуатации**.

## Ловушки

### Ловушка 1: ручная склейка отображений каталогов упускает кодированный выход

Симптом: сканер безопасности сообщает, что `/static/%2e%2e%2fsecret` доступен — прямая склейка `../` ловится, кодированная форма просочилась.

Причина: URL декодируется один раз до маршрутизации (глава 89) — декодирование происходит **до** или **после** вашей проверки — вот что решает позицию линии обороны. Проверка отображения статического слоя идёт по декодированному пути (верно); самодельное отображение, проверяющее до декодирования, — кодированный выход.

```c bad
snprintf(Path, "%s/%s", Root, RawUrlPath);  /* склейка исходного нераскодированного пути */
check_prefix(Path);                           /* проверяется кодированная форма */
```
```c good
/* отображение статического слоя: встроенная нормализованная проверка после декодирования */
/* при своём управлении: сперва декодировать (глава 101) -> нормализовать -> проверять префикс — перепроверять после каждого слоя декодирования */
```

### Ловушка 2: ответ 304 с телом

Симптом: захват пакетов показывает 304 с полным телом — вся оптимизация кэша насмарку (полоса тратится как раньше).

Причина: после попадания условного запроса при ручной сборке ответа забыли, что семантика 304 — **только заголовки**. Путь 304 статического слоя встроен; при самодельной сборке ветка 304 обязана идти через сборку «только заголовки».

```c bad
if ( etag_match ) { reply(304, body); }   /* 304 с телом: нарушение протокола */
```
```c good
if ( etag_match ) {
	respond_headers_only(304, ETag);   /* только заголовки + ETag */
	return;
}
```

### Ловушка 3: все файлы получают длинный кэш

Симптом: релиз новой версии — HTML пользователя ссылается на новые активы, но сам HTML закэширован — белый экран или микс старого и нового.

Причина: политика кэша не различает **входной документ** и **активы с отпечатком**. HTML — вход (сменились ссылки — сменилось содержимое) — только короткий кэш; у имени актива есть отпечаток (смена = новый URL) — только тогда можно immutable.

```c bad
set_header("Cache-Control", "max-age=31536000");  /* все файлы: публикация = инцидент */
```
```c good
if ( is_html ) { cc("max-age=60"); }
else { cc("max-age=31536000, immutable"); }  /* актив с отпечатком */
```

### Замысел дизайна семантической матрицы

Замысел упражнения с шестнадцатью наборами семантической матрицы: типы (HTML/JS/JPG) × условие (попадание/мимо) × Range (нет/одинарный) × сжатие (да/нет) = 3×2×2×2 = 24 (взяты шестнадцать представительных комбинаций). Ценность матрицы не в прохождении, а в **процессе прохождения** — для каждого набора вы сперва пишете ожидание (ручной вывод по протоколу), потом проверяете — любое несовпадение есть слепая зона понимания протокола. Баги настоящих статических серверов почти всегда на пересечениях этих комбинаций (остаток заголовка Content-Encoding у 304+сжатие, ошибочный порядок Range+сжатие, двойное сжатие JPG+сжатие) — **матрица есть систематическое покрытие пространства комбинаций**, эквивалент серверной версии мутационного тестирования главы 132.

## Упражнения

### Базовое: полная семантическая матрица

Прогоните семантическую матрицу по static-сервису: шестнадцать комбинаций типы×условия×Range×сжатие (по запросу минимум на каждую). Критерий приёмки: шестнадцать наборов ответов (статус/заголовки/наличие тела) совпадают с ручным выводом по протоколу.

### Продвинутое: полигон атак на выход

Постройте восемь видов выхода (прямая склейка / однослойное кодирование / двухслойное / концевая точка / обратный слэш / нулевой байт / сверхдлинный / символическая ссылка) против самодельного отображения и статического слоя. Критерий приёмки: статический слой — все 404; у самодельной версии каждый провал локализован и закрыт.

### Вызов: полный webserv

Слияние всего опыта шести проектов: конфигурация (форма configd), вход TLS, сжатие, журнал, Drain, нагрузка (пик 500 соединений — метод главы 135). Критерии приёмки: все десять критериев пройдены; собственный код ядра < 400 строк (остальное — библиотечные слои) — количественное доказательство «собирают, а не пишут».

### Двойной список производительности и безопасности

Последние две страницы перед выходом в прод. **Список производительности**: (1) подтверждение пути нулевого копирования (уровень памяти больших файлов = константа по stats); (2) сверка белого списка сжатия (картинки не жать, тексты жать); (3) уровень повторного использования keep-alive (поле соединения в журнале — повторное использование < 50%: смотреть клиент или тайм-ауты); (4) попадание ETag (доля 304 — ниже 80%: смотреть политику заголовков кэша); (5) пятисегментные тайм-ауты явно (защита от медленных атак — не ставка на умолчания). **Список безопасности**: (1) полигон выхода весь зелёный (8 форм 404); (2) политика шифронаборов TLS (объект политики главы 84 — старые наборы выключены); (3) минимизация прав каталогов (сервисная учётка читает только статический корень); (4) обезличивание журналов (поля токенов в строке запроса — дисциплина главы 76); (5) страницы ошибок не выдают пути (общий текст 404 — серверные пути есть материал разведки). По пять пунктов в каждом — **ни производительность, ни безопасность не фичи, а степень исполнения списков**.

### Последний урок: от читателя к автору

Последний совет учебника — о **смене роли**. Прочитав книгу, вы способны **передать** эту слоистость и дисциплину дальше — а передача есть конечная форма проверки владения. Три пути: **в команде** — взять реальный модуль и написать по нему главу в формате книги (восемь секций скелета, приёмка прежде, пары bad/good) — письмо обнажит места, которые вы «поняли», но не можете объяснить; **в опенсорсе** — внести в XRT расширение или улучшение (список библиотек расширений главы 129 — точка входа: манифест принимает ваш модуль); **в проекте** — повесить список семнадцати аксиом на вики команды (по одной реальной аварии на пункт — ваш архив аварий и есть учебник вашей команды).
