## Ориентация

Сквозная линия тома 7 — «дать данным течь»: адреса (62), порты (63), буферы (64), DNS (65), TCP (66–67), UDP (68), прокси (69), интерфейсы (70). Завершающая глава добавляет два **инструмента сборочного уровня** — они не вводят новых объектов соединений, а склеивают существующие части в полные решения. **Кадровые парсеры** отвечают «как лишённый границ байтовый поток TCP снова становится сообщениями» — вход им даёт `xnetbuf` главы 64, драйвером служат колбэки приёма главы 66; **нативный асинхронный файловый IO** отвечает «как файловому серверу повесить дисковые чтение/запись в тот же событийный цикл, что и сеть» — правила принадлежности Worker главы 63 здесь исполняются снова. Оба — маленькие модули без зависимостей от движка, но каждый держит на себе текстовые протоколы (в стиле Redis/SMTP), частные бинарные протоколы (RPC/игровые серверы) и прокси-кэши со статической раздачей — несколько больших классов реальных нагрузок.

## Введение

Два сценария, одна общность. Сценарий один: вы реализуете текстовый протокол над TCP; клиент шлёт `PING\r\n`, сервер отвечает `PONG\r\n`. Звучит просто, но TCP не обещает «один send — один recv»: три отправки могут прийти склеенными (липкие пакеты), одна отправка может прийти разорванной пополам (полупакеты). Что если `PING\r` пришло первым? Вручную — лихорадочная арифметика индексов. Сценарий два: вы пишете прокси-кэш или файловый сервис; сетевые чтение/запись идут асинхронно на Engine, но чтение файла с диска — блокирующий вызов: один Worker читает диск — и сотни соединений на том же Worker застревают.

Общее у двух сценариев — **проблема границы**. Первому не хватает границ сообщений — их добавляют кадровые парсеры; второму не хватает «единой событийной границы диска и сети» — её добавляют нативные асинхронные файлы: файловые операции подаются прямо в порт завершения Worker, Windows идёт через `ReadFile`/`WriteFile` IOCP, Linux — через `READV`/`WRITEV` io_uring, с диспетчеризацией из того же пула, что и события сокетов; Worker никогда не блокируется на диске.

## Понятия

### Трёхстатный разбор: общий ритм инкрементных кадрировщиков

Два кадрировщика (по строкам, по префиксу длины) делят одну трёхстатную модель возврата:

```diagram state
MORE -> READY: ввод достаточен, разобран один полный кадр
MORE -> MORE: ввода мало, префикс сохраняется в ожидании добавления
READY -> MORE: после потребления текущего кадра — разбор следующего
любой -> ERROR: нелегальная конфигурация / сломанное состояние / кадр сверх лимита
```

`XNET_FRAME_MORE` — **нормальный инкрементный контрольный результат**, ошибки не ставит — это и есть «липкие/полупакеты, поглощённые машиной состояний». При `XNET_FRAME_READY` выходной `xnetframe` описывает один полный кадр в голове текущего ввода: `PayloadOffset`/`PayloadSize` локализуют нагрузку, `FrameSize` — байты целого кадра, `Declared` хранит исходное значение поля длины протокола. `XNET_FRAME_ERROR` несёт структурированную ошибку (четыре вида: `FRAME_CONFIG`/`FRAME_STATE`/`FRAME_LIMIT`/`FRAME_LENGTH`) и обычно означает, что поток протокола больше не заслуживает доверия — закройте соединение или отбросьте ввод и сбросьте кадрировщик.

### Строчное кадрирование: инкрементный поиск с произвольным разделителем

У `xnetlineconfig` три элемента: `Delimiter` (разделитель — **заимствованное представление**, обязанное жить, пока жив кадрировщик; без ограничения длины — годятся `\n`, `\r\n` и даже многобайтовые сигналы), `MaxPayload` (потолок нагрузки, по умолчанию 8192; `SIZE_MAX` — явно без границ), `IncludeDelimiter` (оставлять ли разделитель; по умолчанию убирается). Конфигурация по умолчанию — разделение по LF.

Кадрировщик внутренне хранит указатель блока и смещение внутри блока (`xnetlineframer`), поэтому даже когда ввод рассыпан по множеству однобайтовых ссылочных блоков, позиционирование старого смещения не требует повторного обхода головы цепочки — это водораздел от «сканировать с начала каждый раз» и правильный способ потреблять ссылочные добавления главы 64. Разделитель на границе буферных блоков, самопересечение (разделитель `\r\n` при вводе `\r\r\n`), точное попадание на потолок нагрузки — всё поддерживается.

Один ключевой контракт: после возврата `MORE` от `Next` вызывающий **может только сохранить исходный префикс ввода и добавлять в хвост того же `xnetbuf`**; перед потреблением, заменой, сменой буфера или перестановкой ввода обязателен `xrtNetLineReset` (сохраняет конфигурацию, отбрасывает инкрементный прогресс). Другое применение `Reset` — переиспользование кадрировщика при «начале диалога заново» на том же соединении, экономя одну инициализацию.

### Кадрирование с префиксом длины: одна формула на все случаи

Самое ходовое кадрирование частных бинарных протоколов: поле длины в 1–8 байт заголовка + нагрузка. Общая длина кадра определяется одной формулой:

```text
FrameSize = LengthOffset + LengthSize + Declared + Adjustment
```

- `LengthOffset`/`LengthSize`: позиция и ширина поля длины внутри кадра (1..8 байт); `Order` явно фиксирует порядок байт, независимо от хостового.
- `Adjustment`: знаковая поправка. Если поле длины протокола уже включает заголовок, отнимите его отрицательным значением.
- `Strip`: начало нагрузки — сохранить весь заголовок, убрать только поле длины или срезать весь прикладной заголовок; одно поле, три выбора.
- `MaxFrame`: жёсткий потолок целого кадра (по умолчанию 1 МиБ) — злобные или битые заявленные длины останавливаются здесь.

Конфигурация по умолчанию — «4-байтовая длина big-endian, поле длины убирается, потолок 1 МиБ» — формат большинства RPC. Все границы — конец поля, беззнаковое заявленное значение, знаковая поправка, преобразование `size_t`, strip и потолок — проверяются до доступа к нагрузке; пути «сначала поверить длине, потом читать за границей» не существует.

### Два способа взять кадр: копия и ноль копий

После того как `Next` выдал описание кадра, нагрузку берут двумя способами. **Удобный путь** `xrtNetFrameCopy`: копирует байты нагрузки (не сверх ёмкости выхода) в буфер вызывающего — маленькое сообщение в одну строку. **Путь без копий**: прямо через `xrtNetBufSpans`/`xrtNetBufPeek` главы 64 взять представления нагрузки — большие кадры копировать не нужно. После взятия `xrtNetFrameConsume` точно убирает целый кадр из головы ввода (он сначала проверяет, что диапазон кадра всё ещё целиком в голове; если ввод меняли — отказ с `FRAME_STATE`). Заметьте: описание кадра **заимствует текущий ввод** — после потребления, замены или перестановки префикса ввода старым описанием кадра пользоваться нельзя.

### Нативные асинхронные файлы: диск на порту завершения

Модуль `net_file` подаёт позиционные чтение/запись обычных файлов в порт завершения Network Engine — для файловых сервисов, прокси-кэшей и собственных конвейеров хранения: не создаёт Future, не занимает TaskPool, не копирует нагрузку вызывающего. Пять пунктов:

- **Открытие**: `xrtNetFileOpen` автоматически добавляет флаг `XFILE_ASYNC`; опции — тот же набор, что у `xrtFileOpen` главы 44 (по умолчанию только чтение; новый файл требует явного `XFILE_CREATE|XFILE_WRITE`).
- **Принадлежность Worker**: `Read`/`Write` подаются только в **потоке владеющего Worker** — после первой подачи файл навсегда закрепляется за одним Worker; межпоточная подача получает `XERR_STATE`. Главному потоку нужно инициировать — `xrtNetEnginePost` доставляет действие подачи на Worker (стандартная поза примеров этой главы).
- **Абсолютные смещения**: чтение/запись несут `iOffset` и не зависят от файлового курсора — множественные конкурентные чтения одного файла не мешают друг другу.
- **Единственный финал**: каждая операция возвращает ненулевой идентификатор, а колбэк `xnetcompletion` получает **ровно один** финальныйevento на Worker (`Result`/`Bytes`/`Id` события `xnetportevent` описывают результат). Файл, буферы и completion обязаны жить до прибытия финала. `xrtNetFileCancel` только запрашивает отмену — исходная операция всё равно завершается через completion: финалом может быть `XNET_RESULT_CANCELLED`, а может операция уже успела — тогда `OK`.
- **Бит возможностей**: если у порта Worker нет нативного файлового IO (например, подстраховочный бэкенд SELECT), подача получает `XERR_UNSUPPORTED` — явный отказ, без деградации в блокировку Worker.

Когда все операции завершены, файл закрывается через `xrtClose` — тип дескриптора тот же `xfile` главы 44; всё файловое семейство делит этот единственный вход закрытия, отдельной функции закрытия для асинхронных файлов нет.

### Первая полная программа: строчное кадрирование CRLF и поглощение полупакетов

Следующая программа из `examples/network/frame_line/main.c`: ввод нарочно приходит кусками `first\r` и `\nsecond\r\n` (полупакет переходит разделитель), кадрировщик восстанавливает кадры по одному и демонстрирует переиспользование Reset:


```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/network/frame_line/main.c -lws2_32 -liphlpapi
first
second
reset=ok
```

**Что только что произошло.** (1) Разделитель установлен в `\r\n` (заимствованное представление прямо на литерал); первый кусок `first\r` даёт `MORE` — разделитель пришёл лишь наполовину, кадрировщик записал неразрешённый префикс в инкрементный курсор. (2) Второй кусок `\nsecond\r\n` дописывается в хвост **того же** `xnetbuf` (корректное применение контракта MORE), цикл `Next` последовательно разбирает `first` и `second` как два полных кадра. (3) Каждый кадр проходит три шага «Copy в стековый буфер → печать → Consume точное потребление», `sizeof(sLine) - 1u` оставляет место под хвостовой ноль. (4) В конце `xrtNetLineReset` сохраняет конфигурацию и отбрасывает прогресс — новая сессия переиспользует кадрировщик. Это фундамент кадрирования текстовых протоколов класса Redis/SMTP: **липкие и полупакеты поглощаются машиной состояний парсера, бизнес-код видит только полные сообщения**.


**Что только что произошло.** (1) Файловые опции явно `XFILE_READ|XFILE_WRITE|XFILE_CREATE|XFILE_TRUNCATE` — по умолчанию только чтение, создание объявляется явно, а `xrtNetFileOpen` поверх автоматически добавляет асинхронный флаг. (2) Подача идёт **стандартными двумя скачками**: главный поток `xrtNetEnginePost` доставляет `exampleWriteTask` на Worker 0, а функция задачи **на Worker** вызывает `xrtNetFileWrite` и регистрирует completion — приземлённая форма контракта «подача только во владеющем Worker». Финальный колбэк `exampleDone` записывает `Result`/`Bytes`/`Id`, главный поток крутится в ожидании `bDone` и сверяет три вещи: результат OK, байты сходятся, `Id` события совпадает с возвратом подачи. (3) Чтение с поверкой — та же поза, `memcmp` проверяет содержимое. (4) Секция отмены сначала подаёт большое чтение на 4096 байт, крутится немного, убеждаясь, что оно не завершилось, затем `xrtNetFileCancel` — финал **приходит всегда**, и результат может быть только `OK` (чтение как раз успело) или `CANCELLED`; заметьте, что чтение 4096 байт из 8-байтового файла сразу завершится по EOF, поэтому пример сначала ждёт и лишь потом решает, отменять ли — эта обработка «отмена может проиграть гонку завершению» и есть вид настоящего кода. (5) Уборка: `xrtClose(File)` → остановка Engine → удаление временного файла, порядок менять нельзя.

## Контракты

- **Жизненный цикл кадрировщика**: кадрировщик — объект-значение на стеке вызывающего, без разделяемого состояния; разные экземпляры конкурентно в любых потоках, один экземпляр — последовательные вызовы: всё безопасно; конфигурация (представление разделителя) обязана жить до ухода кадрировщика.
- **Контракт MORE**: после `MORE` разрешено только сохранить исходный префикс ввода и добавлять в тот же `xnetbuf`; перед потреблением/заменой/сменой буфера/перестановкой — обязателен `Reset`; `MORE` ошибки не ставит.
- **Кадр заимствует ввод**: смещения `xnetframe` относительны головы текущего ввода; после изменения префикса старый кадр недействителен; `Consume` проверяет диапазон и потребляет точно.
- **Потолки кадров**: нагрузка строки сверх `MaxPayload` — `FRAME_LIMIT`; переполнение/превышение/нелегальная поправка заявленной длины — `FRAME_LENGTH`; заведомо нелегальная конфигурация — `FRAME_CONFIG`.
- **Принадлежность файла**: `Read`/`Write`/`Cancel` действительны только в потоке владеющего Worker (`XERR_STATE`); после первой подачи файл закреплён за одним Worker; главный поток передаёт через `EnginePost`.
- **Файловые финалы**: операция возвращает ненулевой `Id`; completion получает ровно один финал (`Result`/`Bytes`/`Id`); файл, буферы и completion живут до финала; `Cancel` только запрашивает — финал `OK` или `CANCELLED`.
- **Возможности файла**: бэкенд без нативного файлового IO (подстраховка SELECT) — `XERR_UNSUPPORTED`, без деградации в блокировку; Windows IOCP, Linux io_uring.
- **Закрытие**: `xrtClose` после завершения всех операций; смещение + длина за пределами выразимого — `XNET_ERROR_PORT_SUBMIT`.

## Ловушки

### Ловушка 1: тронули префикс ввода после `MORE` и продолжили кадрировать

Симптомы: редкие `XNET_FRAME_ERROR` + `FRAME_STATE` или кащеево искажённое содержимое кадров — обычно в коде «разобрал наполовину и ушёл обрабатывать другие байты».

Причина: после `MORE` инкрементный курсор кадрировщика заякорен на **исходном префиксе ввода**. Потребление головы, замена буфера, другой `xnetbuf` и даже перенос префикса в другое место рвут якорь — контракт требует `Reset` до любого из этого.

```c bad
if ( xrtNetLineNext(&Framer, &Input, &Frame) ==
	XNET_FRAME_MORE ) {
	xrtNetBufConsume(&Input, 8);   /* тронули префикс: инкрементный курсор повис */
	xrtNetLineNext(&Framer, &Input, &Frame); /* FRAME_STATE */
}
```

```c good
if ( xrtNetLineNext(&Framer, &Input, &Frame) ==
	XNET_FRAME_MORE ) {
	/* единственное законное действие: исходный префикс сохранён, новые данные — в хвост */
	xrtNetBufAppend(&Input, pChunk, iSize);
}
/* если текущий ввод действительно надо отбросить (например, сброс протокола): сначала Reset, затем новый поток */
(void)xrtNetLineReset(&Framer);
```

### Ловушка 2: подача файловых операций прямо из главного потока

Симптомы: подача возвращает 0, в слоте ошибки потока `XERR_STATE` — файл открылся прекрасно, но каждая подача падает.

Причина: `xrtNetFileRead`/`Write`/`Cancel` — интерфейсы только для Worker, вызываемые лишь в потоке владеющего Worker; главный поток — не Worker. Это не дефект, а дизайн: операции порта завершения обязаны подаваться в потоке насоса, и модуль кодом ошибки чётко обозначает границу.

```c bad
/* главный поток: не во владеющем Worker, XERR_STATE, возврат 0 */
iId = xrtNetFileRead(pWorker, File, 0, Buffer,
	sizeof(Buffer), &Completion);
```

```c good
/* стандартные два скачка: Post доставляет задачу на Worker, подача — в функции задачи */
static void submitRead(xnetworker* pWorker, ptr pUserData) {
	exampletask* pTask = (exampletask*)pUserData;
	pTask->iId = xrtNetFileRead(pWorker, pTask->File,
		pTask->iOffset, (void*)pTask->pData, pTask->iSize,
		&pTask->pIo->Completion);
}
xrtNetEnginePost(pEngine, 0u, submitRead, (ptr)&Task);
```

### Ловушка 3: файловый IO на подстраховочном бэкенде SELECT

Симптомы: один и тот же код на Windows (IOCP) работает, а после переезда на встраиваемую цель, где доступен только SELECT, все файловые подачи возвращают 0.

Причина: у бэкенда SELECT нет нативных асинхронных файловых возможностей, и модуль по биту возможностей **явно отказывает** (`XERR_UNSUPPORTED` + `XNET_ERROR_PORT_SUBMIT`), а не тихо деградирует в блокировку Worker — иначе одно дисковое чтение заклинило бы весь событийный цикл, что и есть режим отказа, который дизайн призван уничтожить.

```c bad
iId = xrtNetFileRead(pWorker, File, 0, Buffer,
	sizeof(Buffer), &Completion);
if ( iId == 0u ) {
	/* предположили временную ошибку и зациклились навсегда: вечно UNSUPPORTED */
}
```

```c good
iId = xrtNetFileRead(pWorker, File, 0, Buffer,
	sizeof(Buffer), &Completion);
if ( iId == 0u && xrtErrorIs(xrtGetError(),
	XERR_UNSUPPORTED) ) {
	/* у бэкенда нет нативных файлов: переходите на асинхронный файловый
	   модуль главы 47 или выделенный дисковый поток, а не на повторы */
}
```

## Упражнения

### Базовое: сменить разделитель строчного кадрировщика

Переделайте строчный пример на `IncludeDelimiter = true` с разделителем `\r\n`: с каким окончанием должны выйти две строки? Затем смените на однобайтовый `\n` и разрежьте второй кусок ввода на `\nsec` и `ond\n`, убедившись, что `second` всё равно разбирается. Критерий приёмки: вывод обоих вариантов совпадает с результатом ручного вывода, программа возвращает 0.

### Продвинутое: кадры длины с заголовком сообщения

Спроектируйте протокол «1 байт типа + 2 байта длины little-endian + нагрузка»: настройте `LengthOffset = 1`, `LengthSize = 2`, `Order = XNET_FRAME_LITTLE_ENDIAN`, `Strip = 3`, склейте две записи и скормите одним махом, разберите циклом и напечатайте раздельно по байту типа. Подсказка: формула `FrameSize` здесь 1 + 2 + Declared; двум кадрам достаточно последовательных `Next`/`Consume`.

### Вызов: скелет минимального статического файлового сервера

Из TCP-сервис событийной грани главы 66 + кадрировщик с префиксом длины этой главы + асинхронные файлы реализуйте скелет «клиент шлёт 8-байтовый запрос смещения файла → сервер читает блок 4 КиБ и возвращает»: кадрирование запросов через `xrtNetLengthNext` (инкрементный разбор буфера `Recv` в колбэке Read), дисковое чтение через `xrtNetFileRead` (подача внутри Worker), ответ кадрируется как «4 байта длины + данные» и отправляется `xrtNetStreamSend`. Критерий приёмки: два конкурентных клиента, чередующие запросы, не перепутывают потоки; при старте на бэкенде SELECT — грациозное сообщение об отсутствии возможностей и выход; уничтожение Engine без утечек (сверка со статистикой главы 6).

## Шпаргалка

| Тема | Краткая справка |
| --- | --- |
| Три состояния | `READY` (полный кадр) / `MORE` (ждать добавления, ошибки нет) / `ERROR` (четыре вида кадровых ошибок, поток не заслуживает доверия) |
| Строчное кадрирование | разделитель произвольной длины (заимствование); MaxPayload по умолчанию 8192, SIZE_MAX — без границ; IncludeDelimiter управляетсохранением |
| Контракт MORE | только сохранить префикс + добавлять в хвост того же `xnetbuf`; перед сменой префикса — `Reset` (конфиг остаётся, прогресс сбрасывается) |
| Формула кадров длины | `FrameSize = LengthOffset + LengthSize + Declared + Adjustment`; Adjustment может быть отрицательным |
| Умолчания кадров длины | 4 байта big-endian, поле длины убирается, потолок 1 МиБ; ширина 1..8, порядок байт на выбор, Strip задаёт начало нагрузки |
| Взятие нагрузки | малые сообщения `FrameCopy` (усекается ёмкостью); большие кадры `BufSpans`/`BufPeek` без копий; `FrameConsume` потребляет точно |
| Асинхронные файлы | `NetFileOpen` автоматически XFILE_ASYNC; чтение/запись с абсолютными смещениями; без Future, без TaskPool, ноль копий нагрузки |
| Принадлежность Worker | Read/Write/Cancel только во владеющем Worker (межпоточно XERR_STATE); главный поток — два скачка через `EnginePost` |
| Финалы | ненулевой Id ↔ Id события; completion ровно один; Cancel только запрашивает, финал OK или CANCELLED |
| Возможности бэкенда | IOCP (Win) / io_uring (Linux) нативно; SELECT явно `UNSUPPORTED`, без блокирующей деградации |
| Закрытие | `xrtClose(File)` после всех финалов; кадрировщики/буферы — стековые значения или `BufClear`, отдельного разрушения нет |
