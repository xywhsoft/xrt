## Ориентация

IMAP — «серверно-авторитетный» дуал POP3 (глава 118): почта остаётся на сервере, папки/флаги/поиск/частичное FETCH делаются на сервере — краеугольный камень синхронизации многих устройств. Сложность протокола на порядок выше: **модель помеченных ответов** (каждая команда несёт уникальный tag, ответы сервера связываются по tag — включая конвейеризацию); **механизм literal** (параметры и ответы с произвольными байтами идут через объявления длины `{N}` — синхронные literal ждут подтверждения продолжения, `LITERAL+` без синхронизации); **поток незапомненных событий** (EXISTS/RECENT/FETCH-обновления врываются в любой момент). Расслоение ximap: протокольные примитивы (`imap`: ответы/literal/возможности/команды — объектов ящика не строит и условий поиска не конструирует, **неизвестные расширения достижимы как сырой текст**) → клиент (`imap_client`: двухуровневая модель команд — низкоуровневый конвейер с явными tag плюс последовательный слой удобства) → слой команд-удобств (`imap_command`: безопасная сборка SELECT/LIST/SEARCH/FETCH/IDLE) → специализированные слои (auth/body/message/append/compress).

## Введение

Три механизма IMAP заслуживают открытия. **Первый: потоковые literal.** FETCH письма на 20 МБ — ответ несёт `{20971520}`, за которым сырые байты — клиент **обязан читать сегментами по явной длине**: `ReadLiteral` берёт сегменты в буфер вызывающего, **до завершения читать последующие ответы нельзя** — «размер сообщения не становится фиксированным потолком памяти» есть гарантия протокольного слоя (то же семейство, что построчный поток POP3, но по длине, а не по строкам). **Второй: пуш IDLE.** Команда `IDLE` велит серверу активно проталкивать незапомненные события при прибытии новой почты — серверная версия «длинное соединение ждёт новое» (почтовая редакция SSE). **Третий: конвейеризация.** Низкоуровневый `Send` берёт явные tag — шлёте несколько команд, затем один цикл `Receive` потребляет события в порядке прибытия и связывает завершения по tag — примитив конкурентности IMAP (форма пропускной способности переиспользования соединения).

Привычная защита от инъекций на месте: `CommandWrite` отвергает ошибочные atom/управляющие символы/инъекции линии/превышения; имена ящиков `imap_command` «валидируются и цитируются по правилам IMAP-строк — **дополнительные команды через CRLF не инъектируются**».

## Понятия

### Модель ответов и literal

```diagram flow
- Три класса ответов: tagged (завершение команды - связка по tag) / untagged (начинается с * - поток событий врывается) / continuation (начинается с + - строки продолжения literal)
- Пять состояний статуса: OK/NO/BAD/PREAUTH/BYE (стабильно распознаются)
- Три формы literal: синхронный {N} (ждёт подтверждения продолжения от клиента) / LITERAL+ {N+} (без синхронизации, слать сразу) / binary ~{N}
  - протокольный слой разбирает только длины и маркеры; данные читает машина состояний по длине (ноль копий, ноль неявных буферов)
```

**Бюджеты literal двусторонние**: сторона отправки (APPEND большого письма — композиция главы 120) и сторона приёма (FETCH большого literal). Контракт приёма: на событии `HasLiteral` сперва проверить `Event.Literal.Size` — сверх прикладного бюджета **немедленный Abort** (тело можно не потреблять — защита памяти «сперва меню, потом решать, есть ли»); низкоуровневый потоковый путь **без потолка по умолчанию** (потолок — приложению); слой удобств `imap_message` несёт собственный бюджет 64 МиБ (они не разделяются — каждому слою своя политика).

### Двухуровневая модель команд

- **Низкий уровень** (`Send/SendParts/Write/Continue/Receive/ReadLiteral`): конвейер с явными tag — несколько команд, события по порядку, связь по tag; `SendParts` вставляет пробелы между кусками аргументов и **пишет прямо в линию** (целая временная команда не строится). Представления заимствуют линейный буфер — **недействительны после следующего Receive/Next/ReadLiteral** (семейная дисциплина представлений строк главы 118; здесь и чтение literal — тоже точка инвалидации).
- **Последовательный слой** (`Begin/BeginParts/Next`): автоматические уникальные tag; `Next` выдаёт незапомненные события (`XMAIL_NEXT_ITEM`) и целевое завершение (`XMAIL_NEXT_END`) **раздельными состояниями** — единая форма цикла; пока активна одна последовательная команда, следующую начать нельзя.

### Слой команд-удобств: сводка SELECT и потоковые результаты

`imap_command` покрывает распространённые команды, но **тяжёлых объектов не строит**: `Select/Examine` дают без-выделительную `ximapmailboxinfo` (дайджест фактов ящика; **бит Present различает «не возвращено» и «значение ноль»** — бит присутствия главы 102 в ящичной редакции; ReadOnly берёт режим доступа финального завершения; `MailboxInfoUpdate` вливает последующие события EXISTS/RECENT в ту же сводку). **Управляющие команды** (CREATE/DELETE/RENAME/SUBSCRIBE/CHECK/UNSELECT/CLOSE) полностью потребляют синхронные завершения; **потоковые команды** (LIST/STATUS/SEARCH/FETCH/STORE/COPY/MOVE/EXPUNGE) только безопасно строятся и запускаются — результаты потребляются потоково через `Next`+`ReadLiteral` (слой удобств поток не перерезает). **IDLE**: после входа `Done` завершает — проталкиваемые события идут тем же циклом Receive.

### TLS, сжатие и семантика отказов

**TLS**: неявный/STARTTLS (рукопожатие только после полного потребления tagged OK; **повторный CAPABILITY после апгрейда** — снимок открытого текста не наследуется; верификатор обязателен) — то же тройное семейство, что SMTP/POP3. **COMPRESS** (`imap_compress`): после аутентификации согласовывается DEFLATE-сжатая линия — оптимизация полосы для высоколатентных каналов. **Семантика отказов** троичная: **линия FAILED** (сеть/отмена/тайм-аут/протокольный разлад/провал разбора — «нельзя гарантировать, что следующий байт на границе команды», соединение не переиспользуется); **команда NO/BAD** (отрицание сервером полной команды — клиент **сохраняет восстанавливаемое состояние**, возвращает структурированную ошибку — следующая команда продолжается); **Abort** (стоп без ожидания, повторяем; FAILED и последнее завершение сохраняются до Destroy для диагностики).

## Контракты

- **Примитивы без модели**: объекты ящика не строятся / модели поиска/FETCH не конструируются — неизвестные расширения достижимы сырым текстом.
- **Три класса, пять состояний**: tagged/untagged/continuation; OK/NO/BAD/PREAUTH/BYE стабильно распознаются; все представления заимствованы.
- **Контракт literal**: разбор даёт только длины и маркеры; данные читаются сегментами; до завершения последующие ответы читать нельзя — размер сообщения ≠ потолок памяти.
- **Бюджеты literal**: на низком уровне потолка по умолчанию нет (приложение само проверяет Size и при превышении немедленно Abort); слой message — независимый бюджет 64 МиБ.
- **Двухуровневая модель**: низкий уровень — конвейер явных tag (SendParts пишет прямо в линию) / последовательный слой — автоматический tag + раздельный по состояниям Next; последовательные команды не конкурентны.
- **Точки инвалидации представлений**: любое из Receive/Next/ReadLiteral инвалидирует представления линейного буфера.
- **Слой команд-удобств**: без-выделительная сводка SELECT (бит Present/слияние событий); управляющие команды завершаются синхронно; потоковые команды поток не перерезают.
- **Защита от инъекций**: инъекции команд/имён ящиков отвергаются; управляющие данные идут literal.
- **TLS**: неявный/STARTTLS; повторный CAPABILITY после апгрейда; верификатор обязателен.
- **Сжатие**: COMPRESS после аутентификации; конфигурация сперва Valid.
- **Отказы троичны**: линия FAILED не переиспользуется / команда NO-BAD восстанавливаема / Abort идемпотентен с сохранённой диагностикой.

## Ловушки

### Ловушка 1: чтение literal раньше проверки размера

Симптом: при `HasLiteral` сразу начинается ReadLiteral — следующее письмо 500 МБ (исторический архив), на середине взрывается память или бюджет.

Причина: контракт говорит прямо «сперва проверить `Event.Literal.Size`» — размер в событии, чтение после решения. Потолка по умолчанию на низком уровне нет = потолок — ваша ответственность.

```c bad
if ( Event.HasLiteral ) {
	while ( ReadLiteral(...) ) { consume(); }   /* размер не проверен: 500МБ вливается напрямую */
}
```

```c good
if ( Event.HasLiteral ) {
	if ( Event.Literal.Size > MyBudget ) {
		xrtImapClientAbort(pClient);   /* сверх бюджета: немедленный стоп, тело не есть */
		return;
	}
	while ( ReadLiteral(...) ) { consume(); }
}
```

### Ловушка 2: ожидание завершений конвейера в порядке отправки

Симптом: мёртвое ожидание tagged-ответа команды A — сервер фактически ответил первым B (или втиснул untagged-события).

Причина: ответы IMAP приходят **в порядке прибытия сервером**, порядок отправки не обещан; untagged-события врываются в любой момент — связывайте по tag, потребляйте по прибытию, не ждите в порядке отправки.

```c bad
send(A); send(B);
wait_tagged(A);   /* сервер может ответить B первым: зависание */
wait_tagged(B);
```

```c good
send(A); send(B);
while ( Receive(&Event) ) {
	if ( Event.kind == TAGGED ) { dispatch_by_tag(Event.Tag); }
	else { handle_untagged(Event); }   /* втиснутые события обрабатываются немедленно */
}
```

### Ловушка 3: представления пересекают следующий Receive

Симптом: сохранённые представления ответов/фрагменты читаются как мусор — линейный буфер перезаписан следующим чтением.

Причина: точек инвалидации **три** (Receive/Next/ReadLiteral) — тоньше, чем «следующее чтение» POP3: чтение literal тоже двигает буфер. Хотите сохранить между вызовами — копируйте.

```c bad
Subject = Event.ResponseView;   /* сохранено представление */
Receive(&Event2);               /* буфер уже другой */
use(Subject);                   /* мусор */
```

```c good
Subject = copy_view(Event.ResponseView);   /* копировать до пересечения вызовов */
Receive(&Event2);
use(Subject);
```

## Упражнения

### Базовое: матрица разбора ответов и literal

Постройте образцы tagged/untagged/continuation и синхронных/LITERAL+/binary literal и прогоните примитивы. Критерии приёмки: пять состояний распознаются верно; длины и маркеры трёх форм literal разбираются согласованно.

### Продвинутое: SELECT и слежение за новой почтой

SELECT берёт сводку (бит Present проверен) → вход в IDLE → имитация пуша EXISTS → `MailboxInfoUpdate` вливает → Done выходит. Критерии приёмки: EXISTS/RECENT сводки обновляются с событиями; обработка untagged во время IDLE разделяет состояния верно.

### Вызов: конвейерный FETCH-загрузчик

Конвейер явных tag с 4 конкурентными FETCH (разные диапазоны писем) — потребление по прибытию, связка по tag, literal сегментами на диск. Критерии приёмки: неупорядоченные ответы связываются верно; письмо 20 МБ при постоянной памяти; путь превышения бюджета — чистый Abort.
