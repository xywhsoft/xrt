## Ориентация

Том 12 закрывается: глава 136 дала методологию; эта глава — **практическое руководство** — метод, применённый к самому XRT. Четыре блока: **лестница оптимизации** (счётчики stats → детализация debug → временные бенчмарки — фиксированный порядок «сначала распределения, потом время»; каждая ступень отвечает на другой вопрос); **два рычага** (пулинг — переиспользование объектов горячего пути (выбор между формами pool/pool_page); батчинг — амортизация системных вызовов и атомной координации (цепочка бенчмарк-доказательств глав 21/68)); **отладка памяти на практике** (тройка Reset/Snapshot/VisitLive локализует утечки; карантин ловит двойное освобождение/UAF; stats всегда включён для тревог — три слоя инструментов каждый на месте); **выбор бэкенда** (запрос и бенчмарк переключения корутин — основа выбора, когда переключение контекста миллион раз в секунду). Нити производительности всей книги (экономика скелета главы 62, диагностические поля главы 99, производительная грань матрицы владения главы 111) собираются здесь.

## Введение

Здравый коэффициент оптимизации: **большинство «проблем производительности» — не проблемы алгоритмов** — это избыточные выделения (контейнер на каждый запрос), слишком частые системные вызовы (посылка по одному) или само измерение неверно (шум главы 136). Поэтому первое действие практики — всегда **смотреть счётчики** (stats: malloc_calls/backing — сколько выделилось, сколько дошло до системы), а не время — счётчики детерминированы (без шума и зависимости от среды) и прямо указывают причину; время говорит лишь «медленно», не «почему». XRT фиксирует эту лестницу в инструментах: stats (всегда включённые счётчики) → memory_debug (детализация событий) → bench (временная статистика) — **каждая ступень отвечает на свой класс вопросов**: сколько / которое / как долго.

Количественное наполнение двух рычагов приходит из бенчмарков, цитированных в главе 135: **батчинг** — MPSC одиночно около 8M items/s, батч 32 около 98M (**в 12 раз**: стоимость координации амортизирована); **пулинг** — малый блок попадает в пул с нулём системных вызовов (чтения pooled/backing в stats видны напрямую). Общая суть рычагов: **амортизировать постоянные издержки** — пул амортизирует выделение/освобождение, батч — синхронизацию/вызовы. Практический порядок: сперва спросить «можно ли батчами» (форма бизнеса позволяет — максимальная отдача), потом «стоит ли пулить» (жизненный цикл объектов стабилен — эффективно).

## Понятия

### Лестница оптимизации: три ступени наблюдения

```diagram flow
- Ступень 1 stats (всегда включённые счётчики): malloc_calls / pooled / direct / backing / live
  - отвечает «сколько»: масштаб выделений, попадания в пул, тренд живого (пороги тревог)
- Ступень 2 memory_debug (кратко при разборе): каждое событие + site + карантин
  - отвечает «которое»: точка утечки (файл:строка), сцены двойного освобождения/UAF
- Ступень 3 bench (профилированное время): median + пороги + A/B
  - отвечает «как долго»: до/после оптимизации, сравнение выбора, мониторинг регрессии
```

**Дисциплина лестницы**: перескакивать ступени (сразу мерить время) — самый частый окольный путь: аномалия выделений видна уже на первой. **Стоимость инструментов растёт по ступеням** (счётчики почти ноль / детализация дорогая / бенчмарки минутного уровня) — стоимость диктует политику постоянного включения: первая всегда, вторая при разборе, третья при изменениях.

### Рычаг первый: пулинг

Выбор между формами (`pool` vs `pool_page`): **многостраничный pool** — ёмкость растёт автоматически (страница заполнилась — добавляется), LIFO-список свободных (переиспользование последнего освобождённого слота — кэш ещё тёплый); **одностраничный pool_page** — один непрерывный блок + чистая арифметика указателей (без цепочки страниц и межстраничных адресаций), ёмкость останавливается на пределе — **первый выбор для встраиваемых/объектов горячего пути (узлы AST, кадры сообщений)**. Предпосылка пулинга: **равновеликие объекты + стабильный жизненный цикл** (ритм построил-использовал-освободил повторяется); когда не выполнено (размеры вперемешку/жизнь хаотична), пул только добавляет издержек — практическая перепроверка выбора главы 22. **Проверка stats**: после пулинга доля pooled растёт, backing падает — прямое чтение работы рычага.

### Рычаг второй: батчинг

Батчинг амортизирует два класса издержек: **системные вызовы** (сетевая отправка по одному → семейство Vec за раз — батч-ступень пяти передач главы 68) и **атомная координация** (очередь по одному → пакетное резервирование — 12-кратное доказательство бенчмарка очереди). **Проектное следствие**: когда вызывающий может естественно группировать (много сообщений в кадре/много задач в запросе), **предпочитать пакетные интерфейсы** — это выбор API, а не трюк производительности; группировать нельзя — откат на одиночные (семантика интерфейсов равноценна — пакетная редакция «выучил одно применение, три очередиуниверсальны» главы 21). **sweep фиксирует батч**: отдача батча насыщается (свип очереди выравнивается после 32) — слепое увеличение только добавляет задержку, не пропускную способность — вывод свип-эксперимента главы 136 как выбор.

### Практический поток отладки памяти

**Поток локализации утечек** (боевое построение инструментов главы 6): `xrtMemDebugReset` до подозрительного участка → прогон участка → `Snapshot` → `LiveCount` не к нулю — утечка → `VisitLive` печатает site (файл:строка) → исправить → повторный прогон к нулю. **Поток локализации порчи**: карантин с отложенным переиспользованием делает двойное освобождение/UAF **неизбежно видимыми** (а не молча проходящими) — точка падения + счётчики карантина (JSON-отчёт) перекрёстно локализуют. **Тревоги долгого прогона**: периодическая выборка live/peak из stats — монотонный рост = тренд утечки (не обязательно дожидаться OOM). Три потока делят один принцип: **доказательства ошибок памяти ждут в инструментах** — угадывать не нужно.

### Выбор бэкенда: образец переключения корутин

Критический путь производительности корутин — **переключение контекста** (стоимость одного переключения × миллион в секунду). `xrtCoBackend()` запрашивает текущий бэкенд (семейство ассемблер/POSIX — определяют платформа и сборка); семейство бенчмарков `dev/bench/coroutine` измеряет: `bench_context_switch` (чистая пропускная способность переключения), `bench_create_destroy` (стоимость построения/разрушения корутины — основа пулинга), `bench_sched_post` (диспетчеризация планировщика), `bench_timer_churn` (дрожание фаз таймеров). **Поток выбора**: запрос бэкенда → бенчмарк context_switch → сравнение с переключением потоков (локальная проверка вывода главы 55) — **числа поддерживают проектное решение** (основа выбора корутины против потока).

## Примеры

### Первая полная программа: измерение рычага пулинга

Программа ниже из `examples/memory/pool_page` — микронаблюдение одностраничного пула:

```embed path="examples/memory/pool_page/main.c" title="examples/memory/pool_page/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/memory/pool_page/main.c -lws2_32 -liphlpapi
stride=32 alignment=32 live=0 capacity=256
```

**Что только что произошло.** (1) `stride=32` (шаг слота) и `alignment=32` — **равновеликие слоты**, предпосылка пулинга, выраженная прямо на грани API; capacity=256 останавливается на пределе (граничная семантика одностраничной формы). (2) Сравнение с образцом `pool` (многостраничный: `page_capacity=256 pages=2 ... peak=300` — автоматическое добавление страниц за пределом): **выбор двух форм** читается бок о бок — свобода роста против скорости чистой арифметики указателей. (3) Основа выбора для объектов горячего пути (узлы AST/кадры сообщений): теория главы 22 + граница этого образца + чтение pooled из stats — три грани составляют практическое суждение.

### Вторая полная программа: семантика переиспользования многостраничного пула

Вторая программа из `examples/memory/pool` — измерение LIFO-переиспользования и роста страниц:

```embed path="examples/memory/pool/main.c" title="examples/memory/pool/main.c"
```

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/memory/pool/main.c -lws2_32 -liphlpapi
page_capacity=256 pages=2 empty=2 live=0 peak=300 visited=300
```

**Что только что произошло.** (1) `peak=300 > 256×1` — переполнение ёмкости вызвало добавление страницы (pages=2); после освобождения всё `empty=2 live=0` — страницы есть, но пусты (**следующий раунд переиспользует без выделения** — память пика в обмен на последующие нулевые выделения). (2) Кэш-смысл LIFO-списка (заголовочный комментарий): освобождённый слот входит в голову, следующий Alloc получает **последний освобождённый** слот — кэш ещё тёплый (точка проверки `pReused == pReleased`). (3) Полный цикл рычага пулинга: семантика переиспользования этого образца + чтение pooled из образца stats + бенчмарк уровня queue — **от семантики к наблюдению к числам**, трёхстороннее доказательство рычага.

## Контракты

- **Дисциплина лестницы**: stats (сколько) → debug (которое) → bench (как долго) — счётчики прежде времени; стоимость диктует политику постоянного включения.
- **Батчинг прежде**: когда естественная группировка есть, предпочитаются пакетные интерфейсы — рычаг уровня выбора API; точку насыщения фиксирует sweep.
- **Предпосылки пулинга**: равновеликие объекты + стабильный жизненный цикл; не выполнено — лучше не пулить. Две формы: одностраничная (чистая арифметика/предел)/многостраничная (автоматический рост/LIFO).
- **Тройка утечек**: Reset→Snapshot→VisitLive (site до файл:строка) — доказательства ждут в инструментах.
- **Порча видима**: карантин делает двойное освобождение/UAF неизбежно видимыми — без опоры на удачу.
- **Тревоги долгого прогона**: периодическая выборка live/peak — монотонный рост есть тревога тренда.
- **Бэкенд запрашиваем**: `xrtCoBackend` + семейство бенчмарк-ов coroutine — численный выбор стоимости переключения.
- **Переиспользование наблюдения**: поля Info главы 99 (Wire/Bytes/метки времени) — сетевой осмотр производительности, дополняющий лестницу памяти.

## Ловушки

### Ловушка 1: мерить время, не глядя на счётчики

Симптом: несколько раундов оптимизаций, время не изменилось — в конце оказалось, узкое место — одно системное выделение на запрос (в stats видно с одного взгляда).

Причина: перескакивание ступеней. Время говорит только «медленно»; счётчики говорят «почему» (выделений много/пул не попадает/системные вызовы часты) — первая ступень лестницы всегда дешёвая и всегда включена.

```c bad
/* подозрительно медленно -> сразу править код -> гонять бенчмарк */
tweak_something();
bench();   /* время не изменилось: почему было медленно, неизвестно - правили в пустоту */
```

```c good
/* сперва счётчики: снимок stats - backing аномально высок */
snapshot_stats();
/* локализовать горячее выделение -> пул/батч -> потом мерить время */
```

### Ловушка 2: пул для объектов вперемешку размеров

Симптом: внутренняя фрагментация пула съедает больше памяти, попадания малы — после пулинга stats ухудшаются.

Причина: предпосылка пула — **равновеликость**. Разные размеры (буфер свой на каждый запрос) через пул = потери в каждом классе размеров + издержки управления — практическая грань «не выполнено — не пулить» из главы 22.

```c bad
/* буферы сообщений 32Б..4КБ вперемешку - всё в один пул */
/* внутренняя фрагментация + низкие попадания: памяти больше, производительности меньше */
pool_init(&OnePoolForEverything, 4096);
```

```c good
/* равновеликие кадры/узлы - в пул; вперемешку - в стандартную кучу */
pool_init(&FramePool, sizeof(frame));   /* равновеликие: законно */
/* вперемешку: достаточно проверить stats, что backing разумен */
```

### Ловушка 3: слепое увеличение батча

Симптом: батч с 32 до 512 — пропускная способность не выросла, задержка выросла (ожидание накопления).

Причина: отдача батча насыщается (за пределом амортизации — чистая стоимость ожидания); кривая sweep фиксирует перегиб — после него увеличение батча только добавляет задержку.

```c bad
#define BATCH 512   /* «чем больше, тем быстрее» - пропуск не вырос, задержка выросла */
```

```c good
/* sweep находит точку насыщения: скажем, выравнивается после 32 */
#define BATCH 32    /* перегиб и есть выбор; для чувствительных к задержке сценариев меньше */
```

## Упражнения

### Базовое: две ступени наблюдения в связке

На бизнес-код с выделениями: сперва снимок stats (счётчики), затем тройка debug (детализация) — что отвечает каждая ступень. Критерии приёмки: ступень счётчиков может судить «аномалия или нет»; ступень детализации может назвать site любого события.

### Продвинутое: до/после пулинга

Нагрузка типа узлов AST (равновеликие 32Б цикл построил-использовал-освободил 100 тысяч раз): стандартная куча против pool_page — сравнение backing из stats + временной бенчмарк A/B. Критерии приёмки: после пулинга backing стремится к нулю; улучшение времени согласовано с долей выделений (объяснимо).

### Вызов: сквозной отчёт оптимизации

Выбрать комбинированный сценарий (скажем, разбор JSON + сборка контейнеров): пройти всю лестницу (локализация счётчиками → две оптимизации пул/батч → бенчмарк A/B) — написать отчёт из четырёх секций (среда/находки/изменения/результаты). Критерии приёмки: каждое изменение подкреплено числами; структура отчёта как у dev/bench (архивируем).
