## Ориентация

Модуль file-async поднимает файловый IO от блокирующей модели к **модели «подача-завершение»**: `xrtAsyncFileReadAt/WriteAt` подают операцию и немедленно возвращают **Future** — IO исполняется на привязанном **потоке пула задач** (параллельная редакция пулов главы 22), а вызывающий поток с Future идёт по своим делам; `xrtFutureWait` ждёт завершения, `xrtFutureValue` забирает результат (результат чтения — `xfiledata`: представление данных + размер + смещение + отметка EOF). Слой удобства для целых файлов `xrtFileReadAllAsync/WriteAllAsync` закрывает дело одним шагом. Глава разбирает семантику модели, дисциплины Future (железные законы асинхронной границы) и выбор между синхронностью и асинхронностью.

## Введение

Службе архивации журналов нужно таскать большие файлы: синхронно Read кусок — обработать кусок — записать кусок — однопоточная сериализация, и всё время ожидания диска записывается на счёт обрабатывающего потока. Хотите параллельно таскать три файла? В синхронной модели это три потока, каждый со своей блокировкой (потоки дорогие — бухгалтерия главы 54). Асинхронная модель меняет рамку: **подали запрос «прочитай этот кусок» — и поток свободен** — система завершает IO в фоне и уведомляет вас; один поток может держать в полёте десятки незавершённых IO. Параллельный потенциал диска (NCQ/многоканальность SSD) и освобождение потоков случаются одновременно.

Цена — смена ментальной модели: от «вернулся из вызова — значит завершён» к «вернулся из вызова — значит принято»: момент завершения, поток обратного вызова, пути отказа — всё меняет форму. Задача главы — расписать дисциплины этой модели; она же — файловая репетиция сетевого движка главы 62 (событийного): две главы делят одно мышление «подача-завершение».

## Понятия

### Модель «подача-завершение»

```diagram flow
- Привязка: xrtAsyncFileOpen(путь, флаги, пул задач) -> асинхронный дескриптор (на созданном вами ограниченном пуле)
- Подача: xrtAsyncFileReadAt/WriteAt(дескриптор, смещение, ...) -> Future; приём и есть возврат
- Исполнение: поток пула завершает IO; ограниченная очередь (например 32) даёт противодавление - полный пул отказывает в подаче, не копя бесконечно
- Завершение: FutureWait ждёт / FutureValue берёт xfiledata; Close тоже асинхронен и возвращает Future
```

Ключевое понимание: **получить Future не значит завершиться** — между приёмом и завершением вызывающий поток свободен, но данные не готовы; всякое использование результата обязано сперва пройти Wait (или композицию продолжений тома 6). Пул задач — **созданный вами** (`xrtTaskPoolCreate({线程数, 队列深度, 标志})` — число потоков, глубина очереди, флаги): противодавление ограниченной очереди срабатывает в точке «пул полон — подача отказала», а не в «разрослось до OOM» (файловая версия клапана противодавления главы 21).

### Дисциплины Future: три закона асинхронной границы

**Закон первый: значение заимствовано** — после завершения `FutureValue` возвращает `xfiledata` как **заимствованное** представление, срок действия до следующей операции; чтобы держать долго — скопируйте сами (дисциплина заимствования главы 3).**Закон второй: заморозка буфера** — между подачей и завершением буфер операции неприкосновенен (поток IO читает и пишет его); нужно переиспользовать заранее — берите пул буферов, по буферу на IO.**Закон третий: отказ — тоже завершение** — состояние отказа и состояние успеха у Future проходят одни и те же интерфейсы ожидания/взятия; короткое чтение помечает EOF битом `End` (булево поле `xfiledata`), отказ несёт детали ошибки — код ожидания, написанный только под успех, при заполнении диска зависнет или солжёт.

### Две позы ожидания (выбор есть архитектурное решение)

| Поза | Вход | Применимость |
| --- | --- | --- |
| Блокирующее ожидание | `xrtFutureWait` + `FutureValue` | простые сценарии - цепочки зависимостей, ожидание сбора после пачки подач |
| Композиция Future | Future в комбинаторы тома 6 (продолжения/параллельные слияния) | параллельные системы - оркестровка результатов многих IO |

Блокирующее ожидание — не регресс: пакетный режим **«подать много + ждать всех вместе»** всё ещё быстрее чистой синхронности (IO исполнялись на пуле параллельно), сериализуется только обработка завершений — прагматичный выбор файловой пакетной обработки. Композиция Future — официальное рукопожатие асинхронности с системой параллелизма: глава 58 развернёт продолжения, глава 59 — параллельные слияния групп задач. Слой удобства целых файлов (образец async_whole): `xrtFileReadAllAsync/WriteAllAsync` — целый файл одним шагом; есть вариант с жёстким потолком (`ReadAllLimitAsync` — сверх лимита отказ; часовой границы ресурсов на асинхронном слое).

### Выбор против синхронного слоя (не весь IO должен быть асинхронным)

Сперва холодный душ: не всякому файловому IO нужна асинхронность.**Чтение-запись маленьких конфигураций** — синхронные три строки (глава 44) проще, сложность асинхронности оплачена зря.**Загрузка ресурсов на старте** — последовательная семантика яснее, выигрыш асинхронности миллисекундный.**Перенос больших файлов, параллельная пакетная обработка, IO-плотные службы** — арена асинхронности. Мнемоника: **IO много, каждый велик, параллелится — асинхронно; разрозненные мелочи — синхронно**. Смешивание тоже обычно (старт синхронно, рантайм асинхронно).

### Полная программа: асинхронный цикл запись-чтение

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single impl.c examples/file/async/main.c -lws2_32 -liphlpapi

```

**Что только что произошло.** (1) `xtaskpoolconfig Config = { 2, 32, 0 }` — **ограниченный пул задач**: два потока, глубина очереди 32; IO исполняется на потоках пула, полный пул отказывает в подаче (точка приземления противодавления на файловом слое). (2) `xrtAsyncFileOpen` (пул, путь, опции) привязывает файл к пулу — дальнейшие чтение и запись идут через очередь пула. (3) `xrtAsyncFileWriteAt` и `xrtAsyncFileReadAt` возвращают по Future — помощник `waitValue` образца (Wait + проверка State + взятие Value) и есть полная форма позы блокирующего ожидания; результат чтения несёт представление данных и размер через `xfiledata`. (4) **Порядок чтения и записи гарантируется цепочкой Future** — сперва дождаться завершения записи, потом подавать чтение; зависимости цепочки строятся ожиданием явно (без ожидания — параллельно, порядка нет). (5) Close тоже асинхронен и возвращает Future — закрытие тоже нужно дождаться, только тогда ресурсы дескриптора действительно вернутся; вывод `hello async file` и есть проверка замкнутого цикла записи-чтения.

## Контракты

- **Приём и есть возврат**: возвращение функции подачи означает только приём; состояние завершения доставляется обратным вызовом или объектом ожидания.
- **Железный закон потока обратных вызовов**: обратные вызовы исполняются в системных IO-потоках — лёгкая работа, передача в поток, полные ветви отказа.
- **Пакетное ожидание**: много подач + одно общее ожидание — легальная форма: выигрыш параллельного IO сохранён, обработка завершений сериализована.
- **Вход через Future**: асинхронные операции можно обернуть в Future и ввести в систему параллелизма (глава 58) — стандартный канал композиции и продолжений.
- **Мнемоника выбора**: много, велико, параллелится → асинхронно; разрозненные мелочи → синхронно; смешивание — по фазам.

### От примеров к инженерии: три хозяина асинхронных файлов

**Перенос больших файлов** (арена конвейера): завершение Future чтения куска A запускает подачу записи A и чтения B — качание двойного буфера, на всём пути ноль простоя в ожидании; скелет этого конвейера и есть продвинутое упражнение.**Пакетная архивация** (арена параллельности): N файлов, каждый подаёт чтение целиком → Futures собраны — сжимаем по одному → асинхронная запись назад; глубина пула естественно ограничивает параллелизм (противодавление встроено) — сжатие главы 29 + пулы главы 22 сливаются на асинхронном слое.**Предзагрузка на старте службы** (арена слоя удобства): `ReadAllAsync` параллельно предзагружает несколько ресурсных файлов, главный поток продолжает инициализацию, при надобности Wait — перекрытие времени старта. Общая точка трёх хозяев: **степень параллелизма управляется глубиной пула** — асинхронность это не бесконечный параллелизм, а «контролируемая параллельность».

### Стык с системой задач главы 59

Future и пул задач этой главы — файловый вход в систему задач главы 59: `xrtTaskSubmit` подаёт произвольную функцию в тот же пул — файловый IO и вычислительные задачи делят пул и единое противодавление; комбинаторы Future (глава 58) выражают «слить, когда завершатся и чтение A, и чтение B» декларативной оркестровкой; группы задач (глава 59) управляют «жизненным циклом и отменой десяти архивных задач» как единым целым. Здесь вы учите слой примитивов — пул, дескриптор, Future; том 6 соберёт их в полные параллельные рабочие процессы. С этим взглядом на будущее: у каждой ловушки этой главы в томе 6 есть соответствующее решение слоем-обёрткой.

### Ментальный якорь: принято ≠ завершено

Самая важная фраза главы заслуживает собственного раздела: **приём не равно завершение**. Интуиция синхронного кода (вернулся из вызова = результат доступен) в асинхронном мире не работает — Future это «обещание результата», а не результат. Три конкретных напоминания: читать данные немедленно после получения Future — прямая причина ловушки 2; Close возвращает Future — значит «закрытие тоже ждать»: ресурсы дескриптора вернутся по-настоящему только после завершения Future у Close; «дождаться всех» после пачки подач — это ждать все, а не какую-нибудь одну. Приклейте эту фразу на монитор: она предупреждает восемьдесят процентов ям асинхронного кода.

## Ловушки

### Ловушка 1: тяжёлая работа в обратном вызове Future (убийца пропускной способности)

Симптом: асинхронная пропускная способность падает вместо роста; очередь пула задач растёт; остальные асинхронные операции на том же пуле коллективно задерживаются.

Причина: обратный вызов занимает поток пула задач — пропускную способность пула съедают тяжёлые вычисления, и весь поставленный в очередь IO ждёт.

```c bad
static void onDone(ptr pValue)
{
	ProcessEntireFile(pValue);   /* тяжёлый счёт в обратном вызове Future - занимает поток-планировщик */
}
```

```c good
static void onDone(ptr pValue)
{
	xrtTaskSubmit(gPool, DoHeavyWork, pValue, NULL);   /* лёгкая работа: переподать в пул задач */
}
/* тяжёлое исполняется задачей пула - обратный вызов Future только пересылает (употребление системы задач, глава 59) */
```

### Ловушка 2: прикосновение к буферу сразу после подачи (дисциплина заморозки)

Симптом: изредка грязная запись или чтение наполовину старого наполовину нового — вызывающий поток трогает буфер, и поток IO пула трогает его же.

Причина: буфер в окне заморозки (от подачи до завершения) трогают с обеих сторон concurrently — закон второй пропущен.

```c bad
xrtAsyncFileWriteAt(File, Offset, Buffer, Size, NULL);
memset(Buffer, 0, Size);   /* чистка буфера сразу после подачи - поток пула ещё читает его */
```

```c good
xrtAsyncFileWriteAt(File, Offset, Buffer, Size, NULL);
/* буфер заморожен от подачи до завершения Wait - трогать только после */
/* нужно переиспользовать раньше: пул буферов (глава 22), по буферу на IO */
```

## Упражнения

### Базовое: две операции параллельно (первый урок асинхронной выгоды)

Два файла, по одной асинхронной записи на каждый, общее ожидание — сравните суммарное время с «синхронной записью двух файлов» (на SSD разница заметна); выведите времена обеих версий рядом.

### Продвинутое: конвейерный переносщик

Реализуйте `copy_async(源, 目标)` (источник, цель): завершение чтения куска A запускает запись A и чтение B — чередование конвейера, на всём пути ноль простоя. Подсказка: качание фиксированного набора двойных буферов (пул главы 22).

### Вызов: параллельный архиватор журналов

Десять журнальных файлов параллельно архивируются gzip-ом (потоковое сжатие главы 29): асинхронное чтение + сжатие в рабочем потоке + асинхронная запись, параллельна вся цепь. Критерии приёмки: суммарное время заметно ниже последовательной версии (приведите сравнение); пиковая память ограничена (параллелизм сдерживается пулом буферов); статистика главы 6 подтверждает ноль утечек.
