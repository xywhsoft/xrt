## Ориентация

Сессионная машина главы 86 сама не трогает сеть; клиентский дозвон главы 82 уже тайно пользовался слоем Stream. Эта глава разбирает слой Stream (`xtlsstream`) в лоб: **серверная форма** — в колбэке TCP Accept `xrtTlsStreamAccept` одним шагом строит комбинированный объект «TCP-поток + TLS-сессионная машина», после чего бизнес видит только чтение-запись открытого текста; **событийная модель** — четыре колбэка Open/Read/Writable/Close (та же, что у клиента главы 82); **противодавление** — приём открытого текста через Available + ожидание Writable при короткой записи: медленный клиент не разрывает память сервера; **жизненный цикл** — разделяемая конфигурация с подсчётом ссылок, единый выпуск после закрытия слушателя и всех соединений. Это очередное исполнение общебиблиотечного паттерна «комбинация скелетов»: Engine (глава 64) + Listener/Stream (глава 67) + TLS-сессионная машина (глава 86) слагаются в полный сервис, к которому можно подключиться напрямую `openssl s_client`.

## Введение

Превратить спарринг-эхо главы 86 в настоящий сервис — не хватает лишь «транспортной разводки»: Accept даёт TCP-поток → строится комбинированный объект → рукопожатие бежит само → событийные колбэки разносят открытый текст. Звучит как тонкий слой, но каждая точка — место ловушки: кто кормит байты во время рукопожатия? Где останавливается потребление открытого текста, когда запись упёрлась в противодавление? Как согласовать закрытие соединения и закрытие слушателя, чтобы не возникло утечки памяти? Слой Stream стандартизует эту разводку — вы пишете бизнес-логику в колбэке `Echo`, жизненным циклом и противодавлением ведает комбинированный объект.

Форма сервиса тоже заслуживает взгляда: один процесс, один Engine, один Listener, N TLS-соединений **разделяют** одну и ту же конфигурацию сервера (идентичность/ALPN) и таблицу событий — подсчёт ссылок конфигурации делает «собрали раз, N соединений переиспользуют» без единой копии. Это продолжение одной линии с разделением идентичности главы 83 и верификатора главы 85: **все тяжёлые объекты TLS — неизменяемые разделяемые значения**.

## Понятия

### Построение комбинированного объекта: стороны Accept и Dial

- **Сервер**: `xrtTlsStreamAccept(TCP流, 服务端配置, 流配置, 事件表, 用户数据, &流)` — в колбэке TCP Accept одним шагом строит комбинированный объект; рукопожатие бежит само, по успеху срабатывает Open.
- **Клиент**: `xrtTlsDial/DialAsync` (глава 82) внутри и есть «TCP-дозвон + StreamAttach в клиентском направлении» — у клиента нет отдельного образца Attach, потому что дозвон уже встроил его.

Обе стороны делят тип `xtlsstream` и весь прикладной интерфейс — Send/Available/Buffer/Consume/Close/Abort/State (шпаргалка главы 82). Различие только в способе построения и направлении.

### Событийная модель и жёсткое противодавление

Четыре обратных вызова (колбэка) полностью изоморфны TCP-потоку (глава 67): `Open` (рукопожатие завершено/READY), `Read` (открытый текст прибыл), `Writable` (бюджет отправки восстановлен), `Close` (единственное конечное состояние: `xnetresult` + структурная ошибка). **Механизм жёсткого противодавления**: у зоны приёма открытого текста есть уровень воды (`Available` не ноль — есть необработанное); пока бизнес не потребил, приёмная сторона не продвигается — эхо-служба связывает «потребление открытого текста» и «отправку открытого текста» в один цикл: Span за Span `Send`; короткая запись (`XTLS_AGAIN`) — **пауза потребления** и ожидание `Writable` для продолжения. Окно TCP медленного клиента сжимается → записи TLS не уходят → потребление открытого текста на паузе → уровень приёма неподвижен → память постоянна. Это исполнение обещания «насос без блокировок» главы 62 на TLS.

### Совместное использование конфигурации и жизненный цикл

```diagram flow
- Сборка: идентичность (глава 83) + конфигурация сервера + конфигурация потока + таблица событий - всё на стеке или в разделяемых объектах
- Подключение: на каждое TCP-соединение один StreamAccept, комбинированный объект держит ссылку конфигурации
- Работа: N соединений конкурентно, колбэки исполняются на Worker-е Engine (глава 64)
- Закрытие: Close-колбэк каждого соединения декрементирует счётчик; закрытие слушателя ставит флаг; оба в ноль - единый выпуск разделяемых объектов
```

Разделяемая конфигурация не освобождается до закрытия Listener и всех соединений — образец оркестрирует этот пункт сходки атомарными счётчиками (Connections/ListenerClosed). Правило одиночного соединения то же, что в главе 81: Close/Abort → дождаться `XTLS_STREAM_CLOSED/FAILED` → Destroy.

### Три стыковочные детали, специфичные для TLS

Три стыковки реализации, о которых стоит знать: **байты рукопожатия** кормит комбинированный слой автоматически (вы ни разу не звали Feed — после StreamAccept рукопожатие «дело транспорта»); **транспортный запрос** `xrtTlsStreamTransport(流)` одалживает нижележащий TCP-поток — запросить адрес партнёра в Open (`xrtNetStreamRemote`) для журнала — стандартное движение; **двухуровневое закрытие** — `StreamClose` идёт со стеканием close_notify (глава 82), Close-колбэк срабатывает один раз на конечном состоянии комбинированного объекта. Конфигураций две: `xtlsserverconfig` (протокольная грань: идентичность/ALPN) и `xtlsstreamconfig` (грань потока: уровни воды буферов и пр.) — разделение забот протокола и транспорта доведено до конфигурационного слоя.

```term
$ gcc -O1 -DXRT_MODULE_ALL -I single -include xrt.h impl.c examples/tls/stream/main.c -lws2_32 -liphlpapi
usage: stream <rsa|p256|p384|ed25519> ...
```

**Что только что произошло.** (1) **Главный цикл Echo — эталон жёсткого противодавления**: `Available → Buffer → Front 取 Span → Send(部分受理 iWritten) → Consume(iWritten) → AGAIN 即返回` (доступно → буфер → Front берёт Span → Send с частичным приёмом iWritten → Consume(iWritten) → при AGAIN возврат) — и `Read`, и `Writable` входят в этот единственный путь без дублей; медленный клиент никогда не разорвёт память. (2) **Разводка Accept**: в колбэке TCP Accept `StreamAccept` одним шагом строит комбинированный объект — здесь же `Destroy` (демонстрация владения: успех Accept даёт ссылку, таблица событий приняла дальнейшее; настоящий сервис держит соединение, естественно живущее до закрытия). (3) **Транспортный запрос в Open**: `StreamTransport` одалживает TCP-поток, `Remote` даёт адрес, печатается «TLS client open: адрес» — мост между слоем TLS и транспортным слоем ровно один. (4) **Сходка жизненных циклов**: Close-колбэк декрементирует Connections, ListenerClose ставит флаг — главный поток ждёт обоих нулей и лишь затем освобождает разделяемую конфигурацию; вот закрытая сторона оркестровки «N соединений делят одну сборку». (5) Прочтите рядом с TCP-эхом главы 67: событийная модель, потребление по Span, продолжение после короткой записи — построчно изоморфны; добавились только рукопожатие и двухуровневое закрытие.

## Контракты

- **Построение**: сервер `StreamAccept` (один шаг внутри колбэка Accept); клиент через встроенный attach `TlsDial/DialAsync`; обе стороны делят весь прикладной интерфейс `xtlsstream`.
- **События**: Open/Read/Writable/Close изоморфны TCP-потоку; колбэки исполняются на Worker-е Engine; Close — единственное уведомление о конечном состоянии (результат + структурная ошибка).
- **Жёсткое противодавление**: остановка потребления = остановка приёма — возврат Span за Span + ожидание Writable при короткой записи есть стандартная эхо-форма; память отвязана от самого медленного клиента.
- **Транспортный мост**: `StreamTransport` одалживает нижележащий TCP-поток (только-читающие запросы: адрес/состояние); кешировать между колбэками нельзя.
- **Двухуровневое закрытие**: `Close` идёт со стеканием close_notify; `Abort` рвёт немедленно; одиночное соединение ждёт CLOSED/FAILED прежде Destroy; сервисный уровень ждёт «все соединения + слушатель» в ноль прежде выпуска разделяемой конфигурации.
- **Разделение конфигураций**: `xtlsserverconfig` (протокольная грань) и `xtlsstreamconfig` (грань потока) независимы; конфигурационные объекты разделяемы подсчётом ссылок.
- **Автоматизация рукопожатия**: цикл Feed/Drive исполняет комбинированный слой — приложение никогда не видит шифртекста (граничное измерение `stream_tour` — диагностическое употребление).
- **Обрезка**: `XRT_MODULE_TLS_STREAM` независимо (зависит от NET) — нужна лишь сессионная машина без транспортной комбинации, обрезайте.

## Ловушки

### Ловушка 1: скопировать открытый текст в Read-колбэке и обрабатывать потом

Симптом: пики памяти на высокой пропускной способности — Read-колбэк каждого соединения копирует всю зону приёма в собственную очередь, противодавление повисает в воздухе.

Причина: противодавление слоя Stream построено на «потреблении открытого текста (Consume)»; скопировать — не потребить, приёмная сторона продолжает продвигаться, и ваша очередь становится неограниченным буфером.

```c bad
static void onRead(xtlsstream* pStream, const xnetbuf* pBuffer, ptr pData) {
	queue_push(g_MyQueue, pBuffer);   /* скопировали, но не Consume: противодавление обнулено */
}
```
```c good
static void onRead(xtlsstream* pStream, const xnetbuf* pBuffer, ptr pData) {
	/* сколько можем обработать - столько потребляем; остальное оставляем следующему Read/Writable */
	while ( xrtTlsStreamAvailable(pStream) != 0 ) {
		/* ... Front берёт Span, обработка + Consume ... */
		if ( 下游满了 ) { return; }   /* остановили потребление = остановили приём = противодавление работает */
	}
}
```

### Ловушка 2: слушатель закрыт — и немедленно освобождена разделяемая конфигурация

Симптом: в колбэке последнего соединения доступ к уже освобождённой идентичности/конфигурации — падение ровно на отключении последнего клиента.

Причина: подсчёт ссылок разделяемой конфигурации живёт на каждом соединении — закрытие Listener не равно закрытию соединений; выпуск обязан ждать обоих нулей.

```c bad
listenerClose(...) {
	xrtTlsIdentityRelease(g_Identity);  /* ещё есть активные соединения-пользователи */
}
```
```c good
/* атомарная сходка счётчиков: Connections==0 && ListenerClosed - только тогда единый выпуск */
if ( (xrtAtomic32Load(&Connections, XMEMORY_ACQUIRE) == 0) &&
		(xrtAtomic32Load(&ListenerClosed, XMEMORY_ACQUIRE) != 0) ) {
	release_shared_assembly();
}
/* эту проверку делают оба колбэка - Close и ListenerClose */
```

### Ловушка 3: TCP-поток, одолженный StreamTransport, сохранён на долгое пользование

Симптом: изредка перепутанное поведение — закешированный указатель TCP-потока рассогласовывается после продвижения внутреннего состояния комбинированного объекта.

Причина: `StreamTransport` — диагностическое/запросное представление «транспортного моста на данный момент», не долгий дескриптор. Нужна транспортная способность (запросить адрес, состояние) — берите в момент надобности и пользуйтесь тут же.

```c bad
g_SavedTcp = xrtTlsStreamTransport(pStream);   /* сохранить */
/* несколько колбэков спустя */
send_on_tcp(g_SavedTcp, ...);   /* прямая запись в транспорт мимо слоя TLS: рассогласование состояний */
```
```c good
/* запрашивать по надобности (скажем, журнал в Open); отправка - всегда через Send слоя TLS */
if ( xrtNetStreamRemote(xrtTlsStreamTransport(pStream), &Remote) ) {
	log_client(Remote);
}
xrtTlsStreamSend(pStream, Data, Size, &Written);  /* открытый текст через парадную дверь */
```

## Упражнения

### Базовое: совместная отладка с openssl

Сгенерируйте самоподписанный сертификат, прогоните службу stream и подключитесь `openssl s_client -connect localhost:8443 -alpn http/1.1`; вводите текст и проверяйте эхо; пронаблюдайте адрес клиента, печатаемый сервером. Критерии приёмки: эхо побайтно верно; после разрыва (Ctrl-C или Q) срабатывает Close-колбэк сервера, счётчик соединений в ноль, процесс не выходит (продолжает обслуживать следующее соединение).

### Продвинутое: прокси открытого текста (наблюдение со стороны расшифровки)

Вставьте перед Echo слой «аудита»: в Read-колбэке посчитайте байты открытого текста и число Span каждого соединения, на Close выдайте сводку (всего байтов / средний размер Span / длительность соединения). Критерии приёмки: 4 конкурентных соединения ведут статистику независимо; данные сходятся с отправленным openssl-ом; статистика не копирует открытый текст (по пути нулевого копирования).

### Вызов: шлюз обновления StartTLS

Реализуйте шлюз «сперва команда открытого рукопожатия, потом обновление»: после TCP Accept не сразу TLS, а построчный разбор команд (строчное кадрирование главы 72); получив `STARTTLS\r\n`, зовите StreamAttach и обновляйтесь до TLS (остальные команды до обновления отрабатывают эхом в открытом режиме). Подсказка: один и тот же объект соединения до и после обновления — смотрите клиентский путь starttls в `stream_tour`. Критерии приёмки: на открытой стадии команды нормально отдаются эхом; после обновления открытые команды отвергаются; openssl через подсказку `starttls` завершает обновление и зашифрованную сессию; счётчик соединений и ресурсы обеих стадий вычищены верно.
