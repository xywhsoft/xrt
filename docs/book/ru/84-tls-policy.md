## Ориентация

Все решения безопасности TLS сгущены в двух конфигурационных объектах. **Политика** (`xtlspolicy`): какие версии, suites, группы и подписные схемы разрешены — протокольный белый список; negociación главы 83 берёт её за базу; умолчание и есть действующая линия безопасности (2 версии / 9 suites / 4 группы / 14 схем, без слабых алгоритмов), сужение — лишь сменить массив. **Верификатор** (`xtlsverifier`): решение о доверии — путь по умолчанию идёт «построение цепи из хранилища доверия + проверка назначения + сопоставление имён» (комбинация примитивов глав 79/80); пользовательские колбэки полностью отдают право решения приложению (пиннинг сертификатов, встроенный приватный CA, аудит-журнал), поверх можно наслаивать policy-колбэк, комбинируя CRL/OCSP. Оба неизменяемы, со подсчётом ссылок и конкурентно разделяемы многими сессиями — «определили раз, цитируем везде». Конфигурация клиента главы 81 обретает здесь полную картину.

## Введение

Три реальных потребности. Первая: комплаенс-аудит требует от сервиса «только TLS 1.3 и конкретных двух-трёх suites» — нужно одно место правки, действующее на все соединения, а не разрозненные захардкоженные значения по каждой конфигурации клиента/сервера. Вторая: ваш клиент ходит только на собственный бэкенд, поверхность доверия публичных CA слишком велика — хочется зафиксировать конкретный сертификат (pinning); хранилище доверия главы 80 не умеет «одиночный сертификат как якорь + сравнение отпечатков + аудит-журнал». Третья: экспериментальная среда хочет временно добавить «проверку отзыва» (запрос CRL главы 80), не переписывая логику построения цепи.

Три потребности соответствуют двум слоям главы: объект политики ведает протокольной гранью (первая), три расширительных точки верификатора — гранью доверия (вторая и третья). Ключевой дизайн — **разделение решения и исполнения**: верификатор ведает только «решением о доверии»; подписная проверка протокольного слоя и контроль Finished по-прежнему исполняет XRT, и **никакой колбэк их не обходит** — вы принимаете «верить или нет», а не «правильный ли протокол».

## Понятия

### Объект политики: единственный источник истины протокольных предпочтений

`xtlspolicy` — заимствующая конфигурация: инициализация по умолчанию указывает на процесса- lifetime-константы только-чтения (нуль выделений); сужение — подменить собственными массивами (жизненный цикл покрывает создание контекста):

```diagram flow
- База по умолчанию: xrtTlsPolicyInit -> только-читающие константы (2 версии / 9 suites / 4 группы / 14 схем, все действующие)
- Сужение: заменить указатели массивов и счётчики Versions/Ciphers/Groups/Signatures
- Самосогласованная проверка: xrtTlsPolicyValid - пустые множества / рассогласование версий и suites / схема 1.2 в 1.3 - отказ
- Разделение: Context/конфигурации клиента/сервера делят один и тот же снимок политики
```

Правила проверки (перехват ошибок конфигурации на старте): версии и suites обязаны быть непусты; указатели списков и счётчики согласованы, элементы уникальны и принадлежат встроенным способностям; каждый suite соответствует включённой версии, у каждой версии хотя бы один suite; непустой список подписей обязан годиться хотя бы для одной включённой версии — PKCS#1-схема 1.2 не входит в чисто 1.3-политику. Две границы: политика описывает лишь **предпочтения** и не обещает, что текущая обрезанная сборка содержит соответствующий бэкенд (фактический путь исполнения генерируется при создании сессии вместе с `xrtTlsGroupAvailable` и др.); `KeySharePolicy` может переопределить локальный режим выбора key-share (например `XTLS_KEY_SHARE_PREFER_GROUP`) — публичный ключ какой группы несёт ClientHello, решает он.

### Верификатор: три слоя решения о доверии

`xrtTlsVerifierCreate(配置)` глубоко копирует опциональное хранилище доверия — после создания исходный store можно освобождать или менять; без пользовательских колбэков **обязан** быть предоставлен хотя бы один якорь доверия, пустой store — провал на создании (того же корня, что «не проверять не опция» главы 81). Трёхслойная структура решений:

- **Путь по умолчанию** (`xrtTlsPeerVerify`): проверка пути в явное время (построение цепи главы 80) + ролевая проверка назначения (`digitalSignature` KeyUsage, `serverAuth`/`clientAuth` EKU) + серверная роль сопоставляет запрошенное имя по RFC 9525 (глава 79). Проволочная цепь от листа к корню; якорь из store, присутствия в цепи партнёра не требуется.
- **Verify-колбэк** (полное принятие): `XTLS_VERIFY_ACCEPT` принимает доверие / `REJECT` отвергает / `DEFAULT` откат на неизменяемый store / `ERROR` структурная ошибка. Колбэк получает **структуру партнёра, уже прошедшую криптографическую проверку** (подпись и Finished гарантированы протокольным слоем) — вы решаете только, верить ли. Принятие всё равно не пропускает CertificateVerify и Finished — «принять доверие» не значит «принять протокол».
- **Policy-колбэк** (наслоение проверок): срабатывает после успеха всех проверек по умолчанию, читает `xtlsverifiedpeer` (`Path` от листа к корню без якоря; все представления заимствованы лишь на время колбэка) — комбинируйте CRL (глава 80), OCSP, CT, пиннинг, корпоративные правила, **не строя цепь заново**. Возврат false может ставить ошибку — она обёрнется cause для `XTLS_ERROR_VERIFY`.

Источник времени инъектируется (`xtlsverifytimeproc`): путь и присоединённая политика делят одно и то же определённое время — тесты воспроизводимы, кеш определим; без него `xrtNow()`.

### Граница: ядро TLS тайно не ходит в сеть

Ядро TLS не загружает молча системные корни, не скачивает CRL, не заводит OCSP и не подаёт CT-запросы — загрузка данных и сеть принадлежат отдельному комбинированному слою. Базовый клиент внезапно не заблокируется на файловом или системном API во время проверки (превентивный дизайн «провала системного слоя» главы 76). Нужен CRL — зовите API главы 80 сами в Policy-колбэке; мягкая или жёсткая неудача — ваше политическое решение, верификатор сохраняет однозначный результат для вашего выбора.

### Форма сборки: политика + верификатор + сессия

Полная сборка клиента (декомпозиционный вид образца главы 81):

```diagram flow
- Политика: xtlspolicy сужена до целевой базы -> проверка PolicyValid -> навесить на конфигурацию разделяемого контекста
- Доверие: StoreSystem (или явный Add) -> VerifierCreate глубоко копирует -> Store можно освобождать
- Расширение: колбэки Verify/Policy/Time вливаются по надобности (пиннинг, CRL, определённое время)
- Сессия: ClientConfig{Verifier, ServerName, Protocols} -> сессия держит ссылку -> свою можно Release
```

Снимок политики после привязки контекстом больше не модифицируется — одна конфигурация обслуживает разные аппаратные способности (влитие бэкендов решается при создании сессии).

## Контракты

- **Проверка политики**: непустые версии и suites; согласованность указателей/счётчиков, уникальность элементов, принадлежность встроенным способностям; двустороннее покрытие suite↔версия; список подписей годится хотя бы для одной включённой версии; проверка не модифицирует вход, нуль выделений.
- **Границы политики**: описывает предпочтения, не обещает влитие бэкендов; создание сессии генерирует фактический путь вместе с `GroupAvailable`/AEAD/идентичностью/бэкендами проверки; исходный снимок политики неизменен.
- **KeySharePolicy**: локальный режим выбора key-share (например `XTLS_KEY_SHARE_PREFER_GROUP`) — влияет на группу в ClientHello, сокращает HRR.
- **Принудительность верификатора**: без Verify-колбэка обязателен хотя бы один якорь доверия; пустой store — провал на создании; после глубокого копирования исходный store можно освобождать/менять.
- **Трёхслойность решений**: путь по умолчанию (цепь + назначение + имя) / Verify-колбэк (полное принятие, четырёхзначное решение) / Policy-колбэк (наслоение после полного успеха, представления заимствованы лишь на время колбэка).
- **Протокол не обходится**: решение о принятии не пропускает CertificateVerify и Finished — подпись и целостность гарантированы протокольным слоем.
- **Инъекция времени**: `xtlsverifytimeproc` даёт пути и политике одно определённое время; без него `xrtNow()`.
- **Конкурентность**: верификатор неизменяем, подсчёт ссылок; Verify/Policy/Time-колбэки вызываются конкурентно — не полагаться на локальные для потока изменяемые разделения.
- **Без неявной сети**: не грузить системные корни, не качать CRL, не слать OCSP, не спрашивать CT — дело комбинированного слоя и policy-колбэка.
- **Обёртка ошибок**: колбэк false с ошибкой → `XTLS_ERROR_VERIFY` + cause; без ошибки → явный отказ `XERR_PERMISSION`.

## Ловушки

### Ловушка 1: политика как заявление способностей (не влито — а «настроено»)

Симптом: политика назначила suite ChaCha20, а сборка прошивки не влита с бэкендом ChaCha20 — negociación в рантайме не находит, соединение падает или деградирует в другой suite, вопреки ожиданию конфигурации.

Причина: политика — предпочтение, не обещание: проверка смотрит лишь «принадлежит встроенным способностям сессии», не влитие бэкендов текущей сборки. Фактический путь исполнения генерируется при создании сессии с `GroupAvailable` и др.

```c bad
/* предположили: назначили - работает */
Policy.Ciphers = ChaChaFirst;
Policy.CipherCount = 1;
/* в сборке --feature нет CHACHA20: в целевой среде весь negociación провален */
```
```c good
/* сверить способности до развёртывания: группы через GroupAvailable, suites по манифесту сборки */
if ( !xrtTlsGroupAvailable(XTLS_GROUP_X25519) ) {
	/* доложить о разрыве способностей на старте, не провалом соединения в бою */
}
/* в CI гонять negociación-смок целевой сборки - проверять политику и способности вместе */
```

### Ловушка 2: повторение криптопроверок в Verify-колбэке

Симптом: колбэк сам проверяет подписи и сравнивает Finished — код раздут и легко ошибиться; либо наоборот, решив «приняли проверку», протокольный контроль сочли пропущенным и потеряли бдительность.

Причина: не понято «разделение решения и исполнения»: колбэк получает структуру партнёра, **уже прошедшую криптопроверку** (подпись и Finished гарантированы протокольным слоем и не обходятся); ваша обязанность — «верить или нет» (цепь доверия, пиннинг, аудит), а не «перепроверить протокол».

```c bad
static xtlsverifydecision myVerify(const xtlspeer* pPeer, ptr pCtx) {
	/* повторная проверка подписи: дублирование, ошибкоопасно и уже гарантировано слоем протокола */
	if ( !self_verify_signature(pPeer) ) { return XTLS_VERIFY_REJECT; }
	return XTLS_VERIFY_ACCEPT;
}
```
```c good
static xtlsverifydecision myVerify(const xtlspeer* pPeer, ptr pCtx) {
	/* только решение о доверии: пример - пиннинг сертификата */
	if ( !pin_matches(pPeer /* 叶证书摘要比对 */ ) ) {
		return XTLS_VERIFY_REJECT;
	}
	return XTLS_VERIFY_ACCEPT;   /* протокольную проверку гарантирует XRT */
}
```

### Ловушка 3: удержание заимствованных представлений из Policy-колбэка

Симптом: доступ к представлениям `xtlsverifiedpeer.Path` после возврата колбэка — падение или мусор.

Причина: все представления Policy-колбэка (путь, якорь, сертификаты) **заимствованы только на время колбэка** — возврат инвалидирует их. Для долгого хранения обязательна глубокая копия (копирование байтов DER).

```c bad
static bool myPolicy(const xtlsverifiedpeer* pPeer, ptr pCtx) {
	g_SavedCert = pPeer->Path[0];   /* сохранили заимствованное представление: возврат - и оно висит */
	return true;
}
```
```c good
static bool myPolicy(const xtlsverifiedpeer* pPeer, ptr pCtx) {
	audit_log(pPeer);   /* чтение и запись завершить внутри колбэка */
	/* для долгого хранения: скопировать байты DER здесь, жизненным циклом ведать самому */
	return true;
}
```

## Упражнения

### Базовое: снимок базовой линии и репетиция сужения

Прогоните образец policy и зафиксируйте базу по умолчанию; затем сузьте до «только TLS 1.3 + два suite» (замена массивов + `PolicyValid`) и напечатайте новые счётчики. Критерии приёмки: после сужения Valid проходит; подсунув 1.2-специальную подписную схему в 1.3-only политику, получаете явный отказ Valid — сообщение указывает проблемный список.

### Продвинутое: верификатор пиннинга сертификатов

Реализуйте pinning-верификатор: `Verify`-колбэк сравнивает SHA-256-дайджест листового сертификата с предустановленным массивом отпечатков (потоковый дайджест главы 73 + `ConstTimeEqual`); попадание ACCEPT, промах REJECT. Проверьте локальным вариантом dial главы 81 на самоподписанном сертификате. Критерии приёмки: верный сертификат проходит, смена сертификата немедленно отвергается; сравнение отпечатков постоянного времени (объясните почему).

### Вызов: трёхслойная комбинация с CRL

Соберите верификатор «системное доверие + CRL-проверка в Policy-колбэке»: путь по умолчанию строит цепь (StoreSystem), Policy-колбэк прогоняет для листа `CrlValidate + CrlCheck` главы 80; вердикт REVOKED — отказ, DONE — мягкая неудача (журнал и пропуск), GOOD — пропуск. Сгенерируйте тестовым CA отозванный сертификат для проверки. Критерии приёмки: три вывода отзыва каждый идёт своим путём; CRL читается только при срабатывании колбэка (проверка «без неявной сети» — GOOD/REVOKED определимы без единого хоста); после инъекции фиксированного времени результат воспроизводим.
