## Ориентация

Слой данных (глава 115) определяет, что такое письмо; SMTP определяет, **как отправлять**. Два слоя SMTP в xmail: **протокольные примитивы** (`smtp`: разбор строк ответов, слияние возможностей EHLO, сборка команд — без зависимости от сети; официальный клиент и пользовательские машины состояний на одной реализации); **клиент** (`smtp_client`: синхронная машина состояний сессии — транзакция конверта `READY → MAIL → RECIPIENT → DATA → READY`; без скрытых Engine/DNS-потоков/фиксированных буферов, MIME не строит). Четыре линии: **защита от инъекций** (командный слой отвергает CR/LF и управляющие символы — SMTP худшая зона инъекций заголовков); **потоковая DATA** (dot transparency как инкрементальная машина состояний — состояние начала строки сохраняется между кусками, копия целого сообщения не строится); **CHUNKING** (BDAT шлёт сырые блоки по объявленному числу байтов — без сканирования и экранирования); **TLS в двух формах** (неявный TLS и апгрейд STARTTLS — снимок возможностей после апгрейда не наследуется).

## Введение

SMTP — диалоговый протокол 1982 года: клиент шлёт команды (`EHLO`/`MAIL FROM`/`RCPT TO`/`DATA`), сервер отвечает трёхзначными кодами (`250 OK`/`550 拒绝` (отказ)). Под видимой простотой три современные инженерные проблемы. **Первая: инъекции** — ранние реализации вклеивали пользовательский ввод прямо в командные строки; ввод с CRLF может «провезти» дополнительные команды (классический путь подделки отправителя); `xrtSmtpCommandWrite` отвергает CR/LF и управляющие символы на входе, потолок 512 байтов. **Вторая: dot transparency** — в режиме DATA точка `.` в начале строки тела обязана экранироваться (`.`→`..`), завершение — строка из одиночной `.`; потоковая отправка (без накопления целого сообщения) требует, чтобы состояние экранирования сохранялось **между кусками** — предыдущий кусок закончился на начале строки, следующий начинается с `.`; эта пограничная точка обязана экранироваться. **Третья: двоичные данные** — требования dot transparency и CRLF делают DATA текстовой по природе; BDAT (расширение CHUNKING) шлёт сырые блоки по объявленному числу байтов, двоичные вложения идут без экранирования.

## Понятия

### Протокольные примитивы: ответы, возможности и команды

```diagram flow
- Ответ: MailLineRead (взять строку без CRLF) -> SmtpReplyLineParse (трёхзначный код + многострочный разделитель)
  -> xsmtpreplyparser (согласованность кодов/потолок строк/уникальная завершающая строка) -> SmtpReplyRead (инкрементально)
- Возможности: SmtpCapabilityParse (заимствованные имя и параметры) -> CapabilityAdd (слияние распространённых расширений +
  три формы AUTH + 64-битный SIZE; неизвестные расширения разбираются без занятия слота)
- Команда: SmtpCommandWrite (Verb [Args]\r\n - отвергает управляющие символы/инъекции CR/LF/превышение 512B)
```

**Валидация пути**: `xrtSmtpPathValid` проверяет содержимое reverse/forward-path (без угловых скобок/пробелов/управляющих разделителей) — проверяется только внутренность угловых скобок, команда не строится (разделение ответственности: контент — протокольному слою, сборка команды — командному).

### Клиент: состояние сессии и владение

`xrtSmtpClientOpen`: проверка баннера `220` → отправка EHLO → (только при явных `500/502/504` откат на HELO по конфигурации — прочие коды отказа EHLO отката не дают). Машина состояний `READY → MAIL → RECIPIENT → READY` (один конверт); с CHUNKING после первого блока вход в `CHUNK`, успех LAST возвращает READY. **Владение**: конфигурация заимствуется только на время Open; клиент держит транспорт и последний ответ, **заимствуя** Engine/Resolver/TLS Context/Verifier (уничтожение клиента не трогает разделяемые объекты). **Потоки**: все блокирующие операции принимают абсолютный `xdeadline` + опциональный `xcancel`; **вызывать из обратного вызова Worker-владельца Engine нельзя** (тот же заслон взаимоблокировки, что в главе 97); один клиент не поддерживает конкурентных команд. **Три финала**: `Quit` (протокольное прощание) / `Close` (без QUIT, дождаться закрытия транспорта) / `Abort` (немедленный аварийный стоп из любого непустого состояния, повтор успешен, FAILED сохраняет последний ответ для диагностики).

### Быстрый путь DATA: потоковая dot transparency

`DataBegin/DataWrite/DataEnd` принимают произвольную разбивку: внутренняя инкрементальная машина состояний **сохраняет состояние CRLF и начала строки между кусками**, отправляя dot-transparent-фрагменты напрямую — **копия целого сообщения не создаётся** (отправляющая сторона потоковой передачи больших вложений). `xrtSmtpClientData` — вход-удобство для непрерывного ввода: сперва полностью проверяет CRLF, затем делегирует инкрементальной машине. **За вызывающим остаются** поля MIME, транспортные кодировки и лимит SIZE сервера — клиент ведает линией, не содержимым (содержимое — модули главы 115).

### CHUNKING: быстрый путь BDAT

После объявления сервером CHUNKING: `BdatBegin/BdatWrite/BdatEnd` шлют сырые фрагменты по **объявленному числу байтов** — **без сканирования содержимого, без dot transparency, без добавляемого CRLF**, ноль копий целого блока. Каждый блок синхронно читает `250`; после `4xx/5xx` дальнейшие блоки запрещены (обязателен RSET/закрытие/abort). **Несовпадение объявленной длины**: End отказывается читать ответ, вызывающий может дополнить байты; если невозможно — обязательно прервать. Комбинация BINARYMIME: бит возможностей лишь объявляет поддержку, тип сообщения проходит через родовой параметр `Mail(..., "BODY=BINARYMIME", ...)` — **API конверта для него не дублируется** (сохраняется способность комбинировать произвольные параметры MAIL).

### TLS: неявная форма и апгрейд

Базовый клиент — открытый текст; слой `smtp_client_tls` добавляет две формы: `XMAIL_SECURITY_TLS` (неявная — рукопожатие завершается до баннера, форма порта 465); `XMAIL_SECURITY_STARTTLS` (апгрейд — EHLO объявляет STARTTLS, проверка переключения `220`, перехват TLS на исходном потоке, **повторный EHLO после рукопожатия**). Два жёстких правила: **апгрейд не наследует снимок возможностей** (посредник может срезать возможности — истина в пересогласовании); **верификатор обязателен** — проверка сертификата никогда не пропускается молча («не проверять — не вариант» главы 84 в почтовой редакции).

## Контракты

- **Расслоение протокол/клиент**: примитивы сети не касаются; клиент — сборка машины состояний из примитивов — без второй реализации.
- **Защита от инъекций**: командный слой отвергает управляющие символы/CR/LF, потолок 512B; валидация пути — только внутренность угловых скобок.
- **Дисциплина ответов**: трёхзначные коды согласованы, потолок строк, уникальная завершающая строка; инкрементальный путь `MailLineRead`→`ReplyRead`.
- **Откат EHLO**: только явные `500/502/504` дают откат на HELO по конфигурации; прочие отказы не угадываются.
- **Владение**: конфигурация заимствована на время Open; разделяемые объекты (Engine/Resolver/TLS/Verifier) заимствуются, не уничтожаются; один клиент без конкурентных команд.
- **Дисциплина блокировки**: абсолютный deadline + опциональный cancel; вызов из обратного вызова Worker-владельца запрещён.
- **Три финала**: Quit протокольное прощание / Close пропускает QUIT и ждёт закрытия / Abort немедленный стоп (идемпотент; FAILED хранит ответ).
- **Потоковая DATA**: dot transparency между кусками; ноль копий целого сообщения; CRLF — ответственность вызывающего.
- **BDAT**: объявленные байты идут как есть; без сканирования, без экранирования, без CRLF; каждый блок читает 250; несовпадение длины можно дополнить или прервать.
- **BINARYMIME**: бит возможности + родовой параметр MAIL — без дублирования API конверта.
- **TLS в двух формах**: неявная (до баннера) / STARTTLS (повторный EHLO после апгрейда, старый снимок не наследуется); верификатор обязателен.

## Ловушки

### Ловушка 1: пользовательский ввод вклеен прямо в команду

Симптом: ввод с CRLF в адресе получателя «успешно» отправляется — на деле провозит дополнительные команды (подделка/усиление).

Причина: дом инъекций SMTP: команда — текстово-строчный протокол; голая склейка и есть инъекция. `CommandWrite`/валидация пути — линия обороны; обходить их склейкой строк — обходить оборону.

```c bad
snprintf(Cmd, "RCPT TO:<%s>\r\n", UserInput);   /* инъекция напрямую */
```

```c good
if ( !xrtSmtpPathValid(view(UserInput), false) ) {
	return reject("invalid address");   /* проверить содержимое */
}
xrtSmtpCommandWrite(XRT_STR_LITERAL("RCPT TO"),
	AngleForm, Out, sizeof(Out), &n);   /* вход с инъекционными проверками */
```

### Ловушка 2: старый снимок возможностей после STARTTLS

Симптом: закешированное до апгрейда «поддерживает SIZE» используется для решений после апгрейда — на соединении, где посредник срезал возможности, письмо сверх лимита отвергается (хороший случай) или ошибочно включается CHUNKING (плохой).

Причина: ответ EHLO фазы открытого текста **недостоверен** (MITM может его изменить); после апгрейда обязателен повторный EHLO за истинным снимком — контракт клиента делает это автоматически; собственный кеш возможностей его обходит.

```c bad
caps_before_tls = parse_ehlo();   /* кеш при открытом тексте */
starttls();
	use_caps(caps_before_tls);  /* недостоверный снимок */
```

```c good
starttls();
caps = client_renegotiated_ehlo();   /* клиент повторил EHLO после апгрейда - берём новый */
```

### Ловушка 3: жёсткий End при несовпадении длины BDAT

Симптом: сервер виснет в ожидании недостающих байтов или сообщает протокольную ошибку — объявлено 1024, реально отправлено 1000, затем вызван End.

Причина: контракт BDAT — «объявление = обещание»; при несовпадении End отказывается читать ответ и даёт шанс дополнить; дополнить невозможно — прерывать (счётчик блоков соединения уже неверен, продолжения нет).

```c bad
BdatBegin(1024);
BdatWrite(实际 1000 字节);
BdatEnd();   /* не хватает 24 байтов, жёсткий финал: сервер виснет */
```

```c good
BdatBegin(1024);
sent = BdatWrite(Buf, 1000);
if ( sent < 1024 ) {
	if ( !BdatWrite(Buf + 1000, 24) ) {  /* дополнить */
		xrtSmtpClientAbort(pClient);      /* невозможно: прервать */
	}
}
BdatEnd();
```

## Упражнения

### Базовое: матрица разбора ответов

Постройте четыре потока байтов ответов — однострочный/многострочный/несогласованные коды/без завершающей строки — через LineRead→ReplyRead. Критерии приёмки: легальные группы разбираются верно; нелегальные дают различимые структурированные ошибки.

### Продвинутое: эксперименты защиты от инъекций

Скармливайте `CommandWrite` и `PathValid` вводы с CRLF/управляющими символами/сверхдлиной — проверьте, что всё отвергается. Критерии приёмки: пять классов враждебного ввода (CRLF/голый CR/управляющие байты/сверх 512B/угловые скобки) каждый отвергается правильным входом.

### Вызов: потоковая отправка большого вложения

Путь DATA: вложение 10 МБ потоково кусками по 8 КиБ (dot transparency через границы) — сравните с путём BDAT на том же вложении. Посчитайте пиковую память и байты канала (DATA чуть больше из-за экранирования). Критерии приёмки: оба пути доставляют одинаково; пик пути DATA постоянен; пограничные случаи (граница куска ровно на начале строки / перед точкой) проходят тест-векторы.
