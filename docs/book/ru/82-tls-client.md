## Ориентация

Шесть глав начиная с этой — TLS, конечная точка схождения примитивов тома 8. Эта глава о **клиенте** — стороне, инициирующей соединение. `xrtTlsDial` за один вызов ведёт всю цепочку «разбор DNS → соревновательное TCP-соединение → рукопожатие TLS» и по успеху отдаёт вам шифрованный поток (`xtlsstream`); две формы потребления — колбэки и Future — соответствуют двум стилям кода, событийному и императивному. Глава проходит машину состояний клиента (`HANDSHAKE → READY → CLOSED`), конфигурационную тройку (верификатор/ServerName/ALPN), приём-передачу данных приложения после READY и аутентифицированное закрытие; глава 84 заглянет внутрь рукопожатия — тайминг и расписание ключей, глава 85 развернёт верификаторы и политики. Все предпосылки — из этого тома: проверка сертификатов (главы 80/81), AEAD и деривация ключей (главы 74/75), несущий TCP-поток (глава 67).

## Введение

Сколько шагов сцепляет HTTPS-клиент? Разбор имени хоста (DNS главы 66), соревновательное соединение по нескольким адресам в духе happy-eyeballs (глава 63), после установления TCP — рукопожатие TLS (проверка сертификатов + обмен ключами + двусторонний Finished), и лишь затем отправка запроса и приём ответа — при неудаче любого шага придётся вычистить все ресурсы, построенные ранее. Рукописная оркестрация этого — классическое поле утечек дескрипторов; `xrtTlsDial` сжимает её в один вызов: неудача автоматически откатывает промежуточные ресурсы, успех передаёт ссылку потока колбэку завершения, главный поток обрабатывает только конечное состояние.

Оркестрация у библиотеки, **решения остаются у вас**: какому CA верить (верификатор, глава 85), к какому имени подключаться (SNI берётся из имени хоста автоматически), какой протокол говорить (массив ALPN), каков общий тайм-аут. Это расслоение — фирменное «скелет под управлением, политика вливается» — индустриализованная мысль скелета главы 62, воспроизведённая на слое TLS.

## Понятия

### Машина состояний клиента и цепочка дозвона

```diagram flow
- Подача: xrtTlsDial(Engine, Resolver, имя хоста, порт, конфигурация TLS, конфигурация дозвона, колбэки потока...)
- Разбор: Resolver асинхронно разбирает имя хоста (глава 66)
- Соревновательное соединение: несколько адресов пробуются по порядку (неудача - автоматически следующий)
- Рукопожатие: ClientHello -> ... -> двусторонний Finished (разбор с диаграммами в главе 83)
- READY: ссылка Stream передаётся колбэку завершения, начинается приём-передача приложения
- Конечное состояние: аутентифицированное закрытие (close_notify) или неудача -> освобождение
```

Объект дозвона `xtlsdial` сам по себе уничтожаем — `xrtTlsDialDestroy` не трогает поток, уже находящийся в полёте; общий тайм-аут (`DialConfig.Timeout`) покрывает все фазы. **Контракт пути неудачи**: при провале дозвона или рукопожатия колбэк Stream не публикуется — вы не получите полузакрытый поток; очистка уже выполнена управляемым слоем.

### Конфигурационная тройка

- **Верификатор** (`TlsConfig.Verifier`): рукопожатие с полными сертификатами **обязано явно привязать его**, иначе провал при создании — «без проверки» не опция, а ошибка; это самое большое расхождение позиции со многими библиотеками. Верификатор глубоко копирует снимок хранилища доверия и разделяется несколькими клиентами (разбор в главе 84).
- **ServerName**: SNI и проверочное имя сертификата берутся автоматически из параметра имени хоста — в сцене дозвона вручную заполнять не надо; у нижнего входа `xrtTlsClientCreate` задаются в `xtlsclientconfig.ServerName`.
- **ALPN** (массив `Protocols`): протоколы приложения по приоритету (`h2`, `http/1.1`); результат negociación читаем после рукопожатия. ALPN восстанавливаемого соединения обязан совпадать с привязанным к билету.

### После READY: данные приложения и закрытие

`xtlsstream` после READY — шифрованный двунаправленный поток; грань API изоморфна TCP-потоку главы 67 плюс специфические для TLS вещи: `xrtTlsStreamSend` (открытый текст на входе, шифртекст на выходе; `iWritten` reports принятый объём), `xrtTlsStreamAvailable`/`Buffer`/`Consume` (нуль-копийное потребление принятого открытого текста — Span за Span, тот же словарь, что у цепочки буферов главы 65), `xrtTlsStreamClose` (**аутентифицированное закрытие**: close_notify в очередь, дождаться ответа партнёра, после стекания — CLOSED), `xrtTlsStreamAbort` (немедленный разрыв — путь ошибок). При получении close_notify от партнёра клиент автоматически ставит в очередь один ответ, игнорирует последующие данные и после стекания входит в CLOSED — протокол закрытия исполняет машина состояний, вы лишь один раз зовёте Close.

Двухуровневый бюджет отправки (слой записей TLS `SendLimit` и бюджет записи TCP, глава 68) оба могут заставить Send вернуть «частично принято» — продолжать от смещения `iWritten` стандартная запись (шаблон — `exampleTlsDialSend` из образцов главы). Автоматическая ротация KeyUpdate (смена ключа у критической точки объёма записей) прозрачна для приложения; явная ротация — `xrtTlsClientKeyUpdate`.

### Две формы потребления: колбэки и Future

- **Колбэчная** (`xrtTlsDial` + таблица событий: четыре колбэка `Open`/`Read`/`Writable`/`Close`): `Open` (READY уже наступило — отправлять запрос), `Read` (открытый текст прибыл), `Writable` (бюджет отправки восстановлен — дописать незаконченный префикс), `Close` (единственное конечное состояние, `xnetresult` + структурная ошибка). Главная форма событийных сервисов и инструментов.
- **Future** (`xrtTlsDialAsync`): возвращает `xfuture`; любой поток ждёт `xrtFutureWaitFor`; после `XFUTURE_RESOLVED` — `xrtFutureValue` берёт поток, и `xrtTlsStreamRef` принимает ссылку. Главная форма императивного кода и интеграции с корутинами. Обе формы делят одну конфигурацию дозвона и один объект потока — та же двухформенная традиция, что у разбора DNS главы 66 и дозвона главы 68.

### Восстановление сессии: билеты и PSK

После включения `XRT_FEATURE_TLS_CLIENT_RESUME` клиент деривирует главный секрет восстановления из финального transcript, по каждому `NewSessionTicket` деривирует независимый PSK и глубоко копирует билет (включая фактические SNI/ALPN/идентичность проверенного листового сертификата). `ResumeLimit` (умолчание 4, максимум 64, 0 — запрет) ограничивает запас; полная очередь вытесняет старейший; `xrtTlsClientTakeResume` переносит ссылку, удерживаемую сессией, вызывающему — **межсоединённый кеш остаётся вашим делом**. Следующий ClientHello несёт билет + нормальный key share: сервер принимает — ступень сертификатов пропускается (PSK+DHE, по-прежнему с прямой секретностью), не принимает — безопасный откат в полное рукопожатие; `xrtTlsClientResumed` докладывает фактический выбор. В TLS 1.2 восстановления нет.

**Что только что произошло.** (1) **Сборка верификатора**: снимок `StoreSystem` → `TlsVerifierCreate` (глубокая копия; Store сразу освобождается) — три строки и есть весь «HTTPS default-trust»; разбор в главе 84. (2) **Подача дозвона**: `TlsDial(Engine, Resolver, host, 443, TlsConfig, DialConfig, Events...)` — один вызов сцепляет DNS/соревновательное соединение/рукопожатие; `DialConfig.Timeout = 15s` покрывает все фазы, имя хоста автоматически идёт в SNI и проверочное имя. (3) **Оркестрация в колбэке READY**: в `Open` отправляется минимальный HTTP-запрос — `exampleTlsDialSend` стандартный шаблон двухуровневого противодавления (частичный приём запоминает смещение `Sent`, `XTLS_AGAIN` — возврат в ожидание `Writable`); запрос исчерпан — `StreamClose` аутентифицированно закрывает пишущую сторону, приём ответа продолжается. (4) **Нуль-копийный приём**: в колбэке `Read` печать по Span через `Available/Buffer/Front/Consume` — без копирования целого ответа, сегментное потребление главы 65 переиспользовано как есть. (5) **Конечное состояние и уборка**: колбэк `Close` фиксирует единственное конечное состояние (атомарный флаг даёт главному потоку безопасный выход); cleanup-сегмент уничтожает Dial/Stream/Resolver/Engine/Verifier в обратном порядке зависимостей — любой провал идёт через тот же сегмент, без утечки дескрипторов.

(2) Три шага принятия на успешном пути: `WaitFor → XFUTURE_RESOLVED 检查 → xrtFutureValue 取流 + xrtTlsStreamRef 接引用` (проверка, взятие потока, приём ссылки); сразу после — `FutureDestroy`: ссылки Future и потока переданы в этой точке. (3) **Ожидание возврата ресурсов после Abort** — эксклюзивное знание главы: `Abort` просит немедленный разрыв, но фоновые сетевые ресурсы ещё освобождаются — крутитесь в ожидании `XTLS_STREAM_CLOSED/FAILED` и лишь потом `Destroy`; это «стык жизненных циклов объекта потока и Future» (правило главы 67 «дождаться CLOSED прежде Destroy» дословно действует на TLS-потоке). (4) Прочтите рядом с dial: сборка верификатора/Engine/Resolver в точности та же — две формы различаются только «как получить поток».

## Контракты

- **Принудительность проверки**: рукопожатие с полными сертификатами обязано привязать Verifier, иначе провал на этапе создания; сборка чистого PSK-восстановления (без бэкендов проверки подписи) может опустить.
- **Атомарность дозвона**: неудача любой фазы автоматически вычищает промежуточные ресурсы; при неудаче Stream не публикуется; общий тайм-аут покрывает все фазы; Dial можно уничтожить раньше, не тронув поток в полёте.
- **Машина состояний**: `HANDSHAKE → READY → CLOSED` (или FAILED) только вперёд; `XTLS_AGAIN` — лишь «нужно больше входа или места под вывод», не ошибка.
- **Семантика отправки**: частичный приём `Send` reports через `iWritten`; слой записей TLS `SendLimit` и бюджет записи TCP (глава 68) — противодавление двух уровней; автоматическая ротация KeyUpdate прозрачна.
- **Семантика закрытия**: `Close` ставит close_notify в очередь и ждёт ответа-стекания партнёра; полученный close_notify автоматически отвечается, последующие данные игнорируются; путь ошибок — всегда `Abort`.
- **Границы восстановления**: кеш билетов `ResumeLimit` 0..64 (умолчание 4); `TakeResume` переносит ссылку, межсоединённый кеш — дело вызывающего; ALPN восстановления обязан совпадать с билетом; в 1.2 восстановления нет; 0-RTT не реализован.
- **Нереализованное**: CertificateRequest, аутентификация клиентским сертификатом, 0-RTT, повторный negociación TLS 1.2 — сцены с клиентским сертификатом сейчас недоступны.
- **Потоки**: колбэки исполняются на Worker-е Engine (глава 64); Future-форма ожидаема в любом потоке; Verifier разделяем между сессиями (глава 85).

## Ловушки

### Ловушка 1: без верификатора (или верификатор с пустым хранилищем)

Симптом: хочется «сперва подключиться, потом разберёмся», проверка пропущена — `xrtTlsClientCreate`/дозвон падает сразу; либо самосборный верификатор с пустым store — тот же провал на создании.

Причина: позиция XRT — **не проверять не опция**. Библиотеки с «опциональной проверкой» ежегодно поставляют массу инцидентов с посредником; здесь путь по умолчанию заварен — либо дайте верификатор, либо явно скажите, что делаете (сборка PSK-восстановления).

```c bad
xrtTlsClientConfigInit(&Config);
/* без Verifier: в сборке полного рукопожатия создание сразу падает */
Session = xrtTlsClientCreate(&Config, pPool);
```
```c good
xx509store* pStore = xrtX509StoreSystem();       /* системное доверие */
xrtTlsVerifierConfigInit(&VerifierConfig);
VerifierConfig.Store = pStore;
pVerifier = xrtTlsVerifierCreate(&VerifierConfig);
xrtX509StoreFree(pStore);                        /* после глубокого копирования можно освобождать */
xrtTlsClientConfigInit(&Config);
Config.Verifier = pVerifier;
Session = xrtTlsClientCreate(&Config, pPool);
xrtTlsVerifierRelease(pVerifier);                /* сессия держит ссылку, свою можно отпустить */
```

### Ловушка 2: Send — смотреть только возврат, не iWritten

Симптом: большой запрос изредка обрезан — `Send` вернул `XTLS_OK`, и вы решили, что всё ушло; фактически двухуровневый бюджет принял лишь часть.

Причина: слой записей TLS и бюджет записи TCP оба могут позволить одному `Send` принять только префикс — семантика `XTLS_OK` «вызов успешен», а не «всё в очередь». Полностью изоморфно семантике бюджета записи главы 68.

```c bad
if ( xrtTlsStreamSend(pStream, pRequest, iSize,
		&iWritten) == XTLS_OK ) {
	/* при iWritten < iSize задняя половина потерялась */
}
```
```c good
while ( Sent < RequestSize ) {
	if ( xrtTlsStreamSend(pStream, pRequest + Sent,
			RequestSize - Sent, &iWritten) ==
			XTLS_AGAIN ) {
		return;   /* бюджет полон: ждать колбэк Writable для продолжения */
	}
	Sent += iWritten;
}
```

### Ловушка 3: уничтожить Engine, не дождавшись конечного состояния потока

Симптом: при выходе `xrtNetEngineDestroy` зависает, либо колбэк потока исполняется на освобождённом контексте.

Причина: колбэки потока бегут на Worker-е Engine; уничтожение Engine до CLOSED/FAILED потока — вынуть из-под колбэков исполнительный поток. Порядок главы 67 «попросить закрытие → дождаться CLOSED → Destroy → Engine последним» дословно действует на TLS-потоке, плюс после Abort — дождаться завершения фонового освобождения.

```c bad
xrtTlsStreamAbort(pStream);
xrtTlsStreamDestroy(pStream);
xrtNetEngineDestroy(pEngine);   /* поток, возможно, ещё завершается */
```
```c good
xrtTlsStreamAbort(pStream);
while ( (xrtTlsStreamState(pStream) != XTLS_STREAM_CLOSED) &&
		(xrtTlsStreamState(pStream) != XTLS_STREAM_FAILED) ) {
	xrtThreadYield();
}
xrtTlsStreamDestroy(pStream);
xrtNetEngineDestroy(pEngine);
```

## Упражнения

### Базовое: минимальный HTTPS GET

Прогоните `dial <某真实站点>` (dial <некий реальный сайт>) и пронаблюдайте вывод: запрос отправлен, ответ напечатан по сегментам, аутентифицированное закрытие. Установите `DialConfig.Timeout` в 1 микросекунду и проверьте путь общего тайм-аута и сообщение ошибки. Критерии приёмки: нормальный путь полностью принимает ответ и выходит с кодом 0; путь тайм-аута содержит фазовую информацию в сообщении.

### Продвинутое: зонд negociación ALPN

Сконфигурируйте `TlsConfig.Protocols` как `{"h2", "http/1.1"}` и в колбэке `Open` запросите и напечатайте названный negociación протокол. Затем оставьте только `{"http/1.1"}` и сравните на том же сайте. Подсказка: результат negociación — публичный атрибут сессии; несовпадение ALPN в рукопожатии валит рукопожатие — зафиксируйте различие двух форм провала.

### Вызов: два соединения с восстановлением

Включите `XRT_FEATURE_TLS_CLIENT_RESUME`: после первого соединения `TakeResume` извлекает билет; второй дозвон передаёт билет в конфигурацию; `xrtTlsClientResumed` подтверждает путь PSK (без сертификатных сообщений). Сравните время и байты двух рукопожатий. Критерии приёмки: восстановленное соединение действительно пропускает ступень сертификатов; при несовпадении ALPN билета со второй конфигурацией объяснима причина неудачи; память билетов в конце освобождена целиком (статистика главы 6).

## Шпаргалка

| Тема | Кратко |
| --- | --- |
| Управляемый дозвон | `TlsDial`: DNS → соревновательное соединение → рукопожатие разом; неудача чистит автоматически, полузакрытый поток не публикуется |
| Конфигурационная тройка | Verifier (явно обязателен) / ServerName (автоматически из хоста) / массив ALPN |
| Две формы | колбэчная (Events: Open/Read/Writable/Close) / Future (DialAsync+WaitFor) |
| Семантика отправки | частичный приём смотрят в `iWritten`; TLS SendLimit + бюджет записи TCP — противодавление двух уровней |
