## 引入

调优的常识率：**大多数"性能问题"不是算法问题**——是分配过多（每次请求建容器）、系统调用过频（逐条收发）、或测量本身错了（第 135 章的噪声）。因此实战的第一动作永远是**看计数**（stats：malloc_calls/backing——分配了多少、多少打到系统）而不是看时间——计数是确定性的（无噪声、无环境依赖），且直接指向原因；时间只告诉你"慢"不告诉你"为什么"。XRT 把这条阶梯固化进工具：stats（常开计数）→ memory_debug（事件明细）→ bench（时间统计）——**每级回答一级问题**：多少笔/哪一笔/多长时间。

两大杠杆的量化来自第 135 章引用的基准：**批量**——MPSC 单条约 8M items/s、批量 32 约 98M（**12 倍**：协调成本被摊销）；**池化**——小块命中池零系统调用（stats 的 pooled/backing 读数直接可见）。两个杠杆的共同本质：**摊销固定成本**——池摊销分配/释放、批量摊销同步/调用。实战次序：先问"能批量吗"（业务形态允许即最大收益）再问"该池化吗"（对象生命周期稳定即有效）。

## 概念

### 调优阶梯：三级观测

```diagram flow
- 一级 stats（常开计数）：malloc_calls / pooled / direct / backing / live
  ——回答"多少"：分配规模、池命中率、存活趋势（告警阈值）
- 二级 memory_debug（排障短开）：每笔事件+site+隔离区
  ——回答"哪一笔"：泄漏点（file:line）、双释放/UAF 现场
- 三级 bench（档案化时间）：median+门限+A/B
  ——回答"多长"：优化前后、选型对照、回归监控
```

**阶梯纪律**：跳级（直接测时间）是最常见的弯路——分配异常在一级就能看见。**每级工具的成本递增**（计数近零/明细高/基准分钟级）——成本决定常开策略：一级常开、二级排障、三级变更时。

### 杠杆一：池化

两形态的取舍（`pool` vs `pool_page`）：**多页 pool**——容量自动增长（页满加页）、LIFO 空闲表（复用最近释放的槽——缓存还热）；**单页 pool_page**——一块连续+纯指针算术（无页链无跨页寻址）、容量到顶即止——**嵌入式/热路径对象（AST 节点、消息帧）首选**。池化的前提：**等大对象+生命周期稳定**（建-用-释的节奏重复）；不满足（尺寸杂/生命乱）时池反而增加开销——第 22 章选型判断的实战复查。**stats 验证**：池化后 pooled 占比上升、backing 下降——杠杆生效的直接读数。

### 杠杆二：批量

批量摊销两类成本：**系统调用**（网络收发逐条→Vec 族一次——第 67 章发送五档的批量档）与**原子协调**（队列逐条→批量预留——queue 基准的 12 倍证据）。**设计含义**：调用方能自然分组（一帧多消息/一请求多任务）时**优先批量接口**——这是 API 选型而非性能技巧；不能分组时退单条（接口语义等价——第 21 章"学一种用法三种队列通用"的批量版）。**sweep 定批量**：批量收益有饱和点（queue sweep 显示 32 后趋平）——盲目加大只增延迟不增吞吐——第 135 章扫描实验的选型产出。

### 内存调试实战流

**泄漏定位流**（第 6 章工具的实战编队）：怀疑段前 `xrtMemDebugReset` → 跑段 → `Snapshot` → `LiveCount` 不归零即泄漏 → `VisitLive` 打印 site（file:line）→ 修复 → 复跑归零。**损坏定位流**：隔离区（quarantine）延迟复用使双释放/UAF **必然显形**（而非静默通过）——崩溃点+隔离区计数（JSON 报告）交叉定位。**长运行告警**：stats 的 live/peak 周期采样——单调上升=泄漏趋势（不必等到 OOM）。三流共用一个原则：**内存错误的证据在工具里等着**——不用猜。

### 后端选择：协程切换的样本

协程性能的关键路径是**上下文切换**（每次切换的成本 × 每秒百万次）。`xrtCoBackend()` 查询当前后端（汇编/POSIX 家族——平台与构建决定）；`dev/bench/coroutine` 的基准族量化：`bench_context_switch`（纯切换吞吐）、`bench_create_destroy`（协程建销成本——池化的依据）、`bench_sched_post`（调度投递）、`bench_timer_churn`（定时器抖动）。**选型流**：backend 查询 → context_switch 基准 → 与线程切换对照（第 54 章结论的本地验证）——**数字支持设计选择**（协程化 vs 线程化的决策依据）。

## 契约

- **阶梯纪律**：stats（多少）→ debug（哪笔）→ bench（多长）——先计数后时间；成本决定常开策略。
- **批量优先**：能自然分组优先批量接口——API 选型级杠杆；饱和点由 sweep 定。
- **池化前提**：等大对象+生命周期稳定；不满足不如不池。两形态：单页（纯算术/到顶即止）/多页（自动增长/LIFO 复用）。
- **泄漏三件套**：Reset→Snapshot→VisitLive（site 到 file:line）——证据在工具里。
- **损坏显形**：隔离区使双释放/UAF 必然显形——不靠运气。
- **长运行告警**：live/peak 周期采样——单调上升即趋势告警。
- **后端可查**：`xrtCoBackend` + coroutine 基准族——切换成本的数字选型。
- **观测复用**：第 98 章 Info 字段（Wire/Bytes/时间戳）是网络面的性能体检——与内存阶梯互补。

## 避坑

### 坑 1：不看计数直接测时间

症状：优化几轮时间没变——最后发现瓶颈是每请求一次系统分配（stats 一眼可见）。

原因：跳级。时间只说"慢"；计数说"为什么"（分配多/池未命中/系统调用频）——阶梯的第一级永远便宜且常开。

```c bad
/* 怀疑慢 → 直接改代码 → 跑基准 */
tweak_something();
bench();   /* 时间没变：不知道为何慢，改了个寂寞 */
```

```c good
/* 先计数：stats 快照——backing 异常高 */
snapshot_stats();
/* 定位分配热 → 池化/批量 → 再测时间 */
```

### 坑 2：给杂尺寸对象上池

症状：池的内部碎片吃掉更多内存、命中率低——池化后 stats 反而变差。

原因：池的前提是**等大**。尺寸杂（每请求不同的缓冲）用池=每个尺寸类浪费+管理开销——这是第 22 章选型判断"不满足就不池"的实战面。

```c bad
/* 消息缓冲 32B..4KB 杂尺寸全走一个池 */
/* 内部碎片+低命中：内存反增、性能反降 */
pool_init(&OnePoolForEverything, 4096);
```

```c good
/* 等大帧/节点走池；杂尺寸走默认堆 */
pool_init(&FramePool, sizeof(frame));   /* 等大：合法 */
/* 杂尺寸：stats 验证 backing 合理即可 */
```

### 坑 3：盲目加大批量

症状：批量从 32 提到 512——吞吐没涨、延迟涨了（攒批等待）。

原因：批量收益有饱和点（摊销完了就是纯等待成本）；sweep 曲线定拐点——拐点后加批量只加延迟。

```c bad
#define BATCH 512   /* "越多越快"——吞吐没涨延迟涨 */
```

```c good
/* sweep 找饱和点：如 32 后趋平 */
#define BATCH 32    /* 拐点即选型；延迟敏感场景更小 */
```

## 练习

### 基础：两级观测联动

对一段含分配的业务代码：先 stats 快照（计数）再 debug 三件套（明细）——两级各回答什么。验收标准：计数级能判"是否异常"；明细级能指出任意一笔的 site。

### 进阶：池化前后对比

AST 节点式负载（等大 32B 建-用-释循环 10 万次）：默认堆 vs pool_page——stats 的 backing 对比 + 时间基准 A/B。验收标准：池化后 backing 趋零；时间改善与分配占比一致（可解释）。

### 挑战：端到端调优报告

选一个组合场景（如 JSON 解析+容器组装）：阶梯全走（计数定位→池化/批量两项优化→基准 A/B）——写四节报告（环境/发现/改动/结果）。验收标准：每项改动有数字支撑；报告结构同 dev/bench 报告（可归档）。
