# Set 性能基线 2026-07-28

## 环境

- 系统：Windows 10.0.19045
- CPU：AMD Ryzen 5 5600 6-Core Processor
- GCC：15.2.0，`-O3 -std=c11`，x64
- TinyCC：0.9.27，`-O2 -m32`
- 参数：1,000,000 个 `uint64` 元素插入，10,000,000 次命中查询
- 容量：插入前执行 `xrtSetReserve(1000000)`

键由固定的 64 位混合函数从连续索引生成。插入和查询计时包含键生成，查询逐次验证
返回的规范元素，并累加校验和防止编译器消除热路径。

## 结果

| 编译器 | 插入耗时 | 插入速率 | 查询耗时 | 查询速率 |
| --- | ---: | ---: | ---: | ---: |
| GCC x64 | 193,076,800 ns | 5,179,286.170 ops/s | 903,959,100 ns | 11,062,447.405 ops/s |
| TinyCC `-m32` | 397,551,800 ns | 2,515,395.478 ops/s | 2,261,336,700 ns | 4,422,163.228 ops/s |

两次运行的校验和均为 `12511953174509196366`。

## 结论

当前独立条目实现已经具备稳定地址、平均 `O(1)` 查询和可接受的百万级插入吞吐。
Set 仍保持 `set -> hash64 -> core` 的轻依赖，不为减少每元素分配强制引入 pool。
未来若增加内部页分配或批量预分配，必须同时证明插入吞吐、内存占用和代码体积的综合
收益，并保持删除、`Take`、OOM 原子性和裁剪边界。
