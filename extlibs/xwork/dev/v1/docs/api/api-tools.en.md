# Tool API

> Status: Chinese function-by-function reference, waiting for manual review.

The Tool API defines models that call tools, tool registrations, tool executors, and host service bridges. It is the entry point for xwork to convert model tool calls into approvable and traceable side effects.

## Module positioning

Tool API is responsible for unified tool definition, registration, search and execution entry. It does not directly replace the product's file system, process, terminal, network, or editor implementation; these capabilities are provided by the host through the host service, or adapted through the xwork local host helper.

## Structure fields

### xwork_tool_def

| Field | Description |
| --- | --- |
| `sToolId` | Stable tool id. Required and not empty when registering, the registration function will be copied. |
| `sDisplayName` | Display name. Optionally, registered functions are copied. |
| `sDescription` | Tool description. Optionally, registered functions are copied. |
| `eKind` | Tool type, default `XWORK_TOOL_HOST_SERVICE`. |
| `eHostService` | host service type, the host-service tool needs to be set. |
| `sOperationId` | host operation id. Borrowed at registration and must remain valid during tool registration. |
| `eSideEffect` | Side effect level, default `XWORK_SIDE_EFFECT_READ_ONLY`. |
| `eApprovalMode` | Approval mode, default `XWORK_APPROVAL_DEFAULT`. |
| `bSupportsStreaming` | Whether the tool supports streaming output. |

### xwork_tool_call

| Field | Description |
| --- | --- |
| `sCallId` | The tool call id generated by the model. Borrowed string. |
| `sToolId` | Tool id. Borrowed string. |
| `sArgumentsJson` | JSON parameter. Borrowed string. |

### xwork_tool_result

| Field | Description |
| --- | --- |
| `sOutputText` | The text returned by the tool to the model. The execution party manages the life cycle according to its contract. |
| `sVisibleSummary` | A summary for user interface display. The execution party manages the life cycle according to its contract. |
| `bRetryable` | Whether to retry after failure. The orchestrator can perform retry accordingly. |

## Ownership Rules

- `xwork_runtime_register_tool` copies `sToolId`, `sDisplayName`, `sDescription`.
- `xwork_tool_def::sOperationId` is a borrowed string and must remain valid during tool registration.
- `xwork_runtime_find_tool` and `xwork_get_builtin_tool_def` return borrow pointers.
- `xwork_tool_result` itself does not own a string; the specific string life cycle is determined by the tool executor or host service contract.
- Registered tool records will be released when the runtime is destroyed.

## Common calling sequence

```text
xwork_runtime_options_init

xwork_runtime_register_tool / xwork_runtime_register_builtin_tool

xwork_runtime_destroy
```

### xwork_tool_def_init

Initialization tool definition.

**Function:**

You can call this function before registering the tool to get stable defaults, and then fill in the tool id, display name, side effects, and host service mapping.

**Function prototype:**

```c
XWORK_API void xwork_tool_def_init(xwork_tool_def *pDef);
```

**parameter:**

- `pDef`: Output parameter. Can be `NULL`; `NULL` does nothing. Cleared and set to default enumeration value when not `NULL`.

**Return value:**

none.

**Resource ownership:**

Functions do not allocate heap memory. The caller owns the `pDef` structure storage.

**Additional Note:**

- Default `eKind` is `XWORK_TOOL_HOST_SERVICE`.
- Default `eHostService` is `XWORK_HOST_NONE`.
- Default `eSideEffect` is `XWORK_SIDE_EFFECT_READ_ONLY`.
- Default `eApprovalMode` is `XWORK_APPROVAL_DEFAULT`.

**Example code:**

```c
#include "xwork.h"

int main(void) {
    xwork_tool_def def;
    xwork_tool_def_init(&def);
    def.sToolId = "custom.echo";
    def.sDisplayName = "Echo";
    return 0;
}
```

**Related API:**

- `xwork_runtime_register_tool`
- `xwork_runtime_find_tool`

### xwork_tool_result_init

Initialization tool execution result.

**Function:**

You can call this function before the tool executor or host service writes the results to ensure that the output text, visible summary, and retry flags are in a known state.

**Function prototype:**

```c
XWORK_API void xwork_tool_result_init(xwork_tool_result *pResult);
```

**parameter:**

- `pResult`: Output parameter. Can be `NULL`; `NULL` does nothing. If it is not `NULL`, it will be cleared entirely.

**Return value:**

none.

**Resource ownership:**

The function does not allocate or free strings. The lifetime of `sOutputText` and `sVisibleSummary` is the responsibility of the party who wrote them.

**Additional Note:**

- The current structure does not have a paired reset function because it does not claim to own heap resources.
- If the executor dynamically allocates output strings, you need to define the release method in the executor contract, or use the host's long-term valid buffer.

**Example code:**

```c
#include "xwork.h"

static xwork_status echo_tool(
    xwork_run *run,
    const xwork_tool_call *call,
    xwork_tool_result *result,
    void *user_data
) {
    (void)run;
    (void)call;
    (void)user_data;
    xwork_tool_result_init(result);
    result->sOutputText = "ok";
    result->sVisibleSummary = "echo completed";
    return XWORK_OK;
}
```

**Related API:**

- `xwork_runtime_invoke_host_service`
- `xwork_runtime_invoke_host_service_ex`

### xwork_runtime_register_tool

Register a custom tool.

**Function:**

You can use this function to add product customization tools to the runtime so that the orchestrator can find and execute it by tool id.

**Function prototype:**

```c
XWORK_API xwork_status xwork_runtime_register_tool(
    xwork_runtime *pRuntime,
    const xwork_tool_def *pDef
);
```

**parameter:**

- `pRuntime`: input/output parameters. Must not be `NULL`.
- `pDef`: input parameters. Must be other than `NULL`, and `sToolId` must be a non-empty string.

**Return value:**

- `XWORK_OK`: Registration successful.
- `XWORK_ERROR_INVALID_ARGUMENT`: Invalid runtime, definition, or tool id.
- `XWORK_ERROR_ALREADY_EXISTS`: The same runtime has registered the same tool id.
- `XWORK_ERROR_NO_MEMORY`: Tool record or string copy failed.

**Resource ownership:**

- The runtime has registered tool records.
- Functions copy `sToolId`, `sDisplayName`, `sDescription`.
- The function borrows `sOperationId`, and the caller must ensure that its life cycle covers the tool registration period.

**Additional Note:**

- Tool registration should be completed before run execution and serialized by the caller.
- `eSideEffect` and `eApprovalMode` will participate in policy/approval judgment.

**Example code:**

```c
#include "xwork.h"

int register_echo_tool(xwork_runtime *runtime) {
    xwork_tool_def def;
    xwork_tool_def_init(&def);
    def.sToolId = "custom.echo";
    def.sDisplayName = "Echo";
    def.sDescription = "Return a static response.";
    def.eSideEffect = XWORK_SIDE_EFFECT_READ_ONLY;
    return xwork_runtime_register_tool(runtime, &def) == XWORK_OK ? 0 : 1;
}
```

**Related API:**

- `xwork_tool_def_init`
- `xwork_runtime_find_tool`
- `xwork_runtime_register_builtin_tool`

### xwork_get_builtin_tool_def

Get the built-in tool definition.

**Function:**

You can use this function to view the definition of xwork's known built-in tools, or check whether the tool id is a built-in tool before registering it.

**Function prototype:**

```c
XWORK_API const xwork_tool_def *xwork_get_builtin_tool_def(const char *sToolId);
```

**parameter:**

- `sToolId`: input parameters. Can be `NULL` or the empty string; returns `NULL` when invalid or unknown.

**Return value:**

- Returns the borrow pointer defined by the built-in tool when found.
- Returns `NULL` if not found.

**Resource ownership:**

The return value points to static storage and cannot be released or modified by the caller.

**Additional Note:**

- The return definition can be passed to `xwork_runtime_register_tool`, but it is more common to use `xwork_runtime_register_builtin_tool` directly.
- The built-in definition of `sOperationId` is also a static borrow string.

**Example code:**

```c
#include "xwork.h"

int has_exec_tool(void) {
    return xwork_get_builtin_tool_def(XWORK_TOOL_PROCESS_EXEC) != NULL ? 1 : 0;
}
```

**Related API:**

- `xwork_runtime_register_builtin_tool`
- `xwork_runtime_find_tool`

### xwork_runtime_register_builtin_tool

Register built-in tools.

**Function:**

You can use this function to register xwork built-in tool definitions with the runtime. The actual execution is still provided by the corresponding host service.

**Function prototype:**

```c
XWORK_API xwork_status xwork_runtime_register_builtin_tool(
    xwork_runtime *pRuntime,
    const char *sToolId
);
```

**parameter:**

- `pRuntime`: input/output parameters. Must not be `NULL`.
- `sToolId`: input parameters. Must be a non-empty string for the built-in tool id.

**Return value:**

- `XWORK_OK`: Registration successful.
- `XWORK_ERROR_INVALID_ARGUMENT`: Invalid runtime or tool id.
- `XWORK_ERROR_NOT_FOUND`: This built-in tool does not exist.
- `XWORK_ERROR_ALREADY_EXISTS`: The same runtime has registered the same tool id.
- `XWORK_ERROR_NO_MEMORY`: Tool record or string copy failed.

**Resource ownership:**

Registered tool records are owned by the runtime. The built-in definition itself remains statically borrowed data.

**Additional Note:**

- Registering built-in tools does not mean installing actual capabilities; `xwork_host_services` or local host also needs to be configured.
- Tools such as file writing, process, and terminal should still go through the policy/approval gate.

**Example code:**

```c
#include "xwork.h"

int register_read_text(xwork_runtime *runtime) {
    return xwork_runtime_register_builtin_tool(
        runtime,
        XWORK_TOOL_FILESYSTEM_READ_TEXT
    ) == XWORK_OK ? 0 : 1;
}
```

**Related API:**

- `xwork_get_builtin_tool_def`
- `xwork_runtime_register_tool`
- `xwork_runtime_find_tool`

### xwork_runtime_find_tool

Find registered tools by tool id.

**Function:**

You can use this function to check whether the runtime has registered a tool before execution, and it can also be used to debug whether the tool id requested by the model can be resolved.

**Function prototype:**

```c
XWORK_API const xwork_tool_def *xwork_runtime_find_tool(
    const xwork_runtime *pRuntime,
    const char *sToolId
);
```

**parameter:**

- `pRuntime`: input parameters. Can be `NULL`; returns `NULL` if invalid.
- `sToolId`: input parameters. Can be `NULL` or the empty string; returns `NULL` if invalid.

**Return value:**

- Returns the tool definition borrow pointer when found.
- Returns `NULL` if not found or if the parameter is invalid.

**Resource ownership:**

The return value is owned by the runtime and cannot be released by the caller. The pointer becomes invalid after the runtime is destroyed or the tool record is released.

**Additional Note:**

- The matching rule is exact match of tool id string.
- This function does not trigger tool execution.

**Example code:**

```c
#include "xwork.h"

int runtime_has_tool(const xwork_runtime *runtime, const char *tool_id) {
    return xwork_runtime_find_tool(runtime, tool_id) != NULL ? 1 : 0;
}
```

**Related API:**

- `xwork_runtime_register_tool`
- `xwork_runtime_register_builtin_tool`

### xwork_runtime_invoke_host_service

Call the host service configured by the runtime.

**Function:**

You can use this function to directly call the host service provided by the host to implement file, process, VCS, diagnostic or editor operations. The orchestrator also enters the same boundary when executing the host-service tool.

**Function prototype:**

```c
XWORK_API xwork_status xwork_runtime_invoke_host_service(
    const xwork_runtime *pRuntime,
    xwork_host_service_kind eKind,
    const char *sOperationId,
    const char *sRequestJson,
    xwork_tool_result *pResult
);
```

**parameter:**

- `pRuntime`: input parameters. It must be other than `NULL`, and the corresponding host service has been configured.
- `eKind`: input parameters. host service type, such as `XWORK_HOST_FILESYSTEM` or `XWORK_HOST_PROCESS`.
- `sOperationId`: input parameters. Must be a non-empty string, interpreted by the specific host service.
- `sRequestJson`: input parameters. Can be `NULL`, but should normally be a JSON request string.
- `pResult`: Output parameter. Must not be `NULL`. The function writes the tool results.

**Return value:**

- `XWORK_OK`: The host service call was successful.
- `XWORK_ERROR_INVALID_ARGUMENT`: Invalid parameter.
- `XWORK_ERROR_NOT_FOUND`: The corresponding host service is not configured or the operation does not exist.
- `XWORK_ERROR_EXTERNAL_FAILURE`: Host service or underlying xrt/xllm call failed.
- `XWORK_ERROR_CANCELLED`: Underlying execution observed cancellation.

**Resource ownership:**

`pResult` is owned by the caller; the result field pointer lifetime is determined by the host service contract. The runtime does not transfer `pUserData` ownership of the host service.

**Additional Note:**

- This function uses a contextless calling path.
- If a cancel token, run pointer or interrupt callback is required, `xwork_runtime_invoke_host_service_ex` should be used.
- If the runtime is bound to a replay engine, host service calls may be recorded or played back by the replay cassette.

**Example code:**

```c
#include "xwork.h"

int read_readme(xwork_runtime *runtime) {
    xwork_tool_result result;
    xwork_tool_result_init(&result);
    return xwork_runtime_invoke_host_service(
        runtime,
        XWORK_HOST_FILESYSTEM,
        XWORK_HOST_FILESYSTEM_READ_TEXT,
        "{\"path\":\"README.md\"}",
        &result
    ) == XWORK_OK ? 0 : 1;
}
```

**Related API:**

- `xwork_runtime_invoke_host_service_ex`
- `xwork_host_services_init`
- `xwork_local_host_configure_services`

### xwork_runtime_invoke_host_service_ex

Call the runtime configured host service with context.

**Function:**

You can use this function to pass run, cancel token and interrupt callback in the host service call to support cooperative cancellation of long-running file/process/terminal operations.

**Function prototype:**

```c
XWORK_API xwork_status xwork_runtime_invoke_host_service_ex(
    const xwork_runtime *pRuntime,
    xwork_host_service_kind eKind,
    const char *sOperationId,
    const char *sRequestJson,
    const xwork_host_invoke_context *pContext,
    xwork_tool_result *pResult
);
```

**parameter:**

- `pRuntime`: input parameters. Must not be `NULL`.
- `eKind`: input parameters. host service type.
- `sOperationId`: input parameters. Must be a non-empty string.
- `sRequestJson`: input parameters. Can be `NULL`, but should normally be a JSON request string.
- `pContext`: input parameters. Can be `NULL`; provides cancellation and interrupt information when not `NULL`.
- `pResult`: Output parameter. Must not be `NULL`.

**Return value:**

- `XWORK_OK`: The host service call was successful.
- `XWORK_ERROR_INVALID_ARGUMENT`: Invalid parameter.
- `XWORK_ERROR_NOT_FOUND`: The corresponding host service is not configured or the operation does not exist.
- `XWORK_ERROR_EXTERNAL_FAILURE`: The host service or underlying dependency failed.
- `XWORK_ERROR_CANCELLED`: Cancellation or interrupt in context was observed.

**Resource ownership:**

The context, request JSON, and result structures are all owned by the caller. The function does not take over ownership of the cancel token or user data.

**Additional Note:**

- If the host service provides `pfnInvokeEx`, the extension entry will be called first; otherwise, the basic entry will be returned.
- Long-running host services should call `xwork_host_invoke_context_should_cancel` during critical phases.

**Example code:**

```c
#include "xwork.h"

int invoke_with_context(
    xwork_runtime *runtime,
    const xwork_host_invoke_context *context
) {
    xwork_tool_result result;
    xwork_tool_result_init(&result);
    return xwork_runtime_invoke_host_service_ex(
        runtime,
        XWORK_HOST_PROCESS,
        XWORK_HOST_PROCESS_EXEC,
        "{\"command\":\"git status\"}",
        context,
        &result
    ) == XWORK_OK ? 0 : 1;
}
```

**Related API:**

- `xwork_runtime_invoke_host_service`
- `xwork_host_invoke_context_should_cancel`
- `xwork_tool_exec_context_should_cancel`

### xwork_tool_exec_context_should_cancel

Check if the tool execution context requested cancellation.

**Function:**

You can call this function at the critical stage of the custom tool executor to check the cancel token and interrupt callback uniformly.

**Function prototype:**

```c
XWORK_API bool xwork_tool_exec_context_should_cancel(
    const xwork_run *pRun,
    const xwork_tool_exec_context *pContext,
    const char *sPhase
);
```

**parameter:**

- `pRun`: input parameters. Can be `NULL`. Passed to interrupt callback, used to determine whether the current run should be interrupted.
- `pContext`: input parameters. Can be `NULL`; returns `false` if `NULL`.
- `sPhase`: input parameters. Can be `NULL`; used to describe the current inspection phase.

**Return value:**

- Returning `true` indicates that the tool should stop as soon as possible and return to `XWORK_ERROR_CANCELLED`.
- Returns `false` indicating that no cancellation is currently observed.

**Resource ownership:**

This function does not allocate resources and does not take over ownership of the cancel token or user data in the context.

**Additional Note:**

- The function checks the context for cancel token and interrupt callback.
- Tool executors should be checked before spawning, in long loops, and after external IO returns to avoid excessive cancellation delays.

**Example code:**

```c
#include "xwork.h"

static xwork_status long_tool(
    xwork_run *run,
    const xwork_tool_call *call,
    const xwork_tool_exec_context *context,
    xwork_tool_result *result,
    void *user_data
) {
    (void)call;
    (void)user_data;
    xwork_tool_result_init(result);
    if (xwork_tool_exec_context_should_cancel(run, context, "before_work")) {
        return XWORK_ERROR_CANCELLED;
    }
    result->sOutputText = "done";
    return XWORK_OK;
}
```

**Related API:**

- `xwork_runtime_invoke_host_service_ex`
- `xwork_host_invoke_context_should_cancel`
- `xwork_run_async_cancel`

## Error handling

- `XWORK_ERROR_INVALID_ARGUMENT`: The tool id, definition, runtime, operation, or result parameters are invalid.
- `XWORK_ERROR_ALREADY_EXISTS`: Register the same tool id repeatedly.
- `XWORK_ERROR_NOT_FOUND`: Find or execute a non-existent tool/host service.
- `XWORK_ERROR_CANCELLED`: Execution context observed cancellation.
- `XWORK_ERROR_EXTERNAL_FAILURE`: Host service or underlying xrt/xllm failed.

## Restore boundaries

Run snapshot can save the pending tool id, arguments, and approval status, but it will not save the callback stack, live host handle, or executor local variables. After recovery, you must re-register the same tool id and compatible host service.

## Thread boundaries

Tool registration should be completed before execution and serialized by the caller. The tool execution callback may be called concurrently by multiple agents or asynchronous paths. The callback itself must protect the shared `pUserData` and external resources.
