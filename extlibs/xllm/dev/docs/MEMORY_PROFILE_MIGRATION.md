# Memory Profile Migration And Rollback

This document defines how xllm should handle memory profile changes in a production host such as AI IDE / claw.

## Current Baseline

xllm already persists profile and schema identity:

- namespace-level `schema_version`.
- namespace-level `memory_profile_id`.
- namespace-level `memory_scheme`.
- record/chunk-level `memory_profile_id`, `chunk_profile_id`, `retrieval_profile_id`, `embed_profile_id`, `index_profile_id`, and `profile_version`.
- diagnostics and health checks expose stored/current profile mismatch.

The current safe default is strict: a namespace/profile mismatch must not be silently reused.

## Profile Change Classes

Treat profile changes by risk class:

- compatible config change: search weights, max hits, labels, context rendering, or host-only ranking preferences. No DB migration needed.
- retrieval-only change: lexical scoring constants, rank fusion, or debug output. No stored data rewrite needed, but eval baseline should be refreshed.
- chunking change: chunk size, overlap, language-aware chunker, or stable chunk id semantics. Requires re-chunk and reindex.
- embedder change: model id, dimension, normalization, asset identity, or embedding runtime. Requires re-embed and vector index rebuild.
- schema change: SQLite table/column/index changes. Requires schema migration with transaction and rollback plan.
- memory type metadata change: typed record metadata semantics. Requires compatibility mapping or host-visible migration note.

## Recommended Strategy

Use copy-forward migration rather than in-place destructive mutation for profile-incompatible changes.

1. Keep the old namespace readable.
2. Create a new namespace or DB file with the new `memory_profile_id`.
3. Re-ingest from source files/conversations/tasks when source material is still available.
4. If source material is not available, copy records as legacy text records and mark metadata with old profile identity.
5. Run health check and representative search/eval against the new namespace.
6. Atomically switch the host pointer from old namespace to new namespace.
7. Retain the old namespace until rollback window expires.

This avoids mixing chunks or embeddings generated by different profile assumptions.

## In-Place Migration Rules

In-place migration is acceptable only when all of the following are true:

- the change is schema-only or metadata-only.
- existing chunks and embeddings remain valid.
- the operation can run inside a SQLite transaction.
- health check runs after commit.
- the host has a backup or snapshot.

Do not in-place migrate when chunking, embedding dimension, embedding model, or stable chunk id semantics change.

## Rollback Rules

Rollback should be host-owned:

- Keep the old DB/namespace until the new one passes health and smoke/eval gates.
- For file-backed SQLite, copy or snapshot the DB together with WAL/SHM sidecars when relevant.
- Switch host config atomically so readers use either the old namespace or the new namespace, never both as the same profile.
- If migration fails before switch, discard the new namespace/DB and continue using the old one.
- If migration fails after switch, switch the host pointer back to the old namespace and run `xllm_memory_check_health`.

xllm should not hide a failed profile check by falling back to old data under a new profile id.

## Schema Migration Rules

Schema migration belongs in the SQLite store module:

- bump `XLLM__MEMORY_SQLITE_SCHEMA_VERSION`.
- make migration steps idempotent where possible.
- wrap destructive steps in `BEGIN IMMEDIATE` and rollback on failure.
- update namespace meta only after all schema changes complete.
- add health-check coverage for the new invariant.
- add a smoke that opens a pre-migration DB fixture or synthetic old layout when practical.

Current schema version is `1`. Future schema versions should document upgrade steps here or in a linked release note.

## Host Release Gate

Before a host upgrades a memory profile:

- Run current memory smoke subset.
- Run `memory-bench` and compare latency/DB size if retrieval behavior changed.
- Run fixed retrieval eval if chunk/embed/retrieval changed.
- Run `xllm_memory_check_health` on the migrated namespace.
- Verify delete/export flows still map records to source URI and typed metadata.
- Keep a rollback namespace/DB until real usage has passed the product-defined soak period.

## xllm Boundary

xllm owns:

- strict namespace/profile mismatch detection.
- profile metadata persistence.
- diagnostics and health check primitives.
- schema migration implementation when built-in SQLite schema changes.

host or xwork owns:

- deciding when to migrate.
- preserving source material.
- copy-forward orchestration.
- backup/snapshot and rollback.
- user-visible release notes when memories are rebuilt or unavailable during migration.
