## Module Role

Tool calling has two layers:

- **Model-generated tool call**: the response contains `XLLM_OUTPUT_TOOL_CALL`; the host reads and executes it manually.
- **Automatic xllm tool loop**: after you set an executor, `xllm_send_ex` or `xllm_session_chat_ex` can automatically execute client tools, append tool results to the request, and continue calling the model.

xllm only handles the protocol and loop. Real tool behavior, files, processes, terminals, permissions, approvals, and audit logs remain the responsibility of the host or xwork.

## Core Concepts

| Concept | Type | Description |
| --- | --- | --- |
| Tool definition | `xllm_tool_def` | Tells the model which tools exist, including name, description, and input schema. |
| Tool policy | `xllm_tool_policy` | Controls automatic, disabled, required, or named tool choice. |
| Tool call | `xllm_output_tool_call` | The model requests execution of a tool. |
| Execution request | `xllm_tool_exec_request` | Request passed from xllm to the host executor. |
| Execution result | `xllm_tool_exec_result` | Tool result returned by the host to xllm. |
| Sync executor | `xllm_tool_executor` | Executes directly and returns a result. |
| Async executor | `xllm_tool_executor_async` | Returns `xfuture *`; xllm waits and clones the result. |

## Tool Definition Types

### `xllm_tool_def`

| Field | Description |
| --- | --- |
| `sToolId` | Internal host tool ID. Automatic tool loop uses it to match tools. |
| `sWireName` | Tool name sent to the provider. Usually the function name seen by the model. |
| `sDescription` | Tool description shown to the model. |
| `eKind` | `XLLM_TOOL_CLIENT` or `XLLM_TOOL_PROVIDER`. |
| `tInputSchema` | Tool argument JSON schema, represented with `xvalue`. |
| `tVendorExtra` | Provider extension fields. |

### `xllm_tool_kind`

| Value | Description |
| --- | --- |
| `XLLM_TOOL_CLIENT` | Tool is executed by the host. Automatic tool loop only executes this kind. |
| `XLLM_TOOL_PROVIDER` | Tool is handled natively by the provider. xllm does not call the host executor. |

**Notes:**

- `sToolId` is for host-side identification. Keep it stable and namespaced, such as `xwork.workspace.inspect`.
- `sWireName` should satisfy the provider's function/tool name format requirements.
- The more accurate `tInputSchema` is, the easier it is for the model to generate executable arguments.

## Tool Choice Policy

### `xllm_tool_policy`

| Field | Description |
| --- | --- |
| `eMode` | Tool choice mode. |
| `sToolName` | Tool name specified when using `XLLM_TOOL_CHOICE_NAMED`. |
| `bAllowParallel` | Whether parallel tool calls are allowed. |

### `xllm_tool_choice_mode`

| Value | Description |
| --- | --- |
| `XLLM_TOOL_CHOICE_AUTO` | Let the model decide whether to call a tool. |
| `XLLM_TOOL_CHOICE_NONE` | Disable tool calls. |
| `XLLM_TOOL_CHOICE_REQUIRED` | Require the model to call a tool. |
| `XLLM_TOOL_CHOICE_NAMED` | Require the model to call a specific tool. |

**Notes:**

- Not every provider supports `required` or named tool forcing.
- `bAllowParallel=true` also requires provider and model support for parallel tool calls.
- If the provider does not support a policy, xllm should usually return `XLLM_ERROR_UNSUPPORTED_CAPABILITY`.

## Tool Execution Types

### `xllm_tool_exec_request`

| Field | Description |
| --- | --- |
| `sToolId` | Matched host tool ID. |
| `sWireName` | Wire/tool name. |
| `sCallId` | Tool call ID, used to associate tool results. |
| `sArgumentsJson` | JSON argument string generated by the model. |
| `tContinuation` | Provider continuation information. |
| `tVendorExtra` | Extension fields. |

**Ownership:**

These fields are valid during the executor call. Copy them if you need to save them asynchronously.

### `xllm_tool_exec_result`

| Field | Description |
| --- | --- |
| `pParts` / `iPartCount` | Tool-returned content, usually text or JSON parts. |
| `tVendorExtra` | Extension fields. |

**Ownership:**

The host executor fills `pResult`. After the call chain ends, release internal resources with `xllm_tool_exec_result_free()`.

### Executor typedef

```c
typedef int32 (*xllm_tool_execute_fn)(
    void *pCtx,
    const xllm_tool_exec_request *pRequest,
    xllm_tool_exec_result *pResult,
    xllm_error *pError
);

typedef xfuture *(*xllm_tool_execute_async_fn)(
    void *pCtx,
    const xllm_tool_exec_request *pRequest
);
```

**Return Value:**

- A sync executor returns `XRT_NET_OK` for tool success.
- A non-`XRT_NET_OK` value means tool failure; write the reason into `pError` when possible.
- The future returned by an async executor should provide an `xllm_tool_exec_result` or an error according to xrt future rules.

## Turn Tool APIs

### xllm_turn_add_tool

Adds one tool definition to the current turn.

**Prototype:**

```c
XLLM_API int xllm_turn_add_tool(xllm_turn *pTurn, const xllm_tool_def *pTool);
```

**Parameters:**

| Parameter | Direction | Can Be `NULL` | Description |
| --- | --- | --- | --- |
| `pTurn` | input/output | no | Initialized turn. |
| `pTool` | input | no | Tool definition. |

**Return Value:**

- `XRT_NET_OK`: added successfully.
- `XRT_NET_ERROR`: invalid parameter or clone failure.

**Resource Ownership:**

The turn clones the tool definition. The original `pTool` remains caller-owned.

**Notes:**

- If you do not add tools, the model usually will not receive a tool list.
- Tool definitions only apply to this turn. Whether the session keeps tool call results depends on session commit behavior.

**Example Code:**

```c
xllm_tool_def tool;
memset(&tool, 0, sizeof(tool));
tool.sToolId = "xwork.workspace.inspect";
tool.sWireName = "inspect_workspace";
tool.sDescription = "Inspect workspace state.";
tool.eKind = XLLM_TOOL_CLIENT;

xllm_turn_add_tool(&turn, &tool);
```

**Related APIs:**

- `xllm_turn_set_tool_choice`
- `xllm_session_set_tool_executor`

### xllm_turn_set_tool_choice

Sets the tool choice policy for the current turn.

**Prototype:**

```c
XLLM_API int xllm_turn_set_tool_choice(
    xllm_turn *pTurn,
    xllm_tool_choice_mode eMode,
    const char *sToolName,
    bool bAllowParallel
);
```

**Parameters:**

| Parameter | Direction | Can Be `NULL` | Description |
| --- | --- | --- | --- |
| `pTurn` | input/output | no | Initialized turn. |
| `eMode` | input | no | Tool choice mode. |
| `sToolName` | input | yes | Tool name in named mode. The function copies it. |
| `bAllowParallel` | input | no | Whether parallel tool calls are allowed. |

**Return Value:**

- `XRT_NET_OK`: set successfully.
- `XRT_NET_ERROR`: invalid parameter or copy failure.

**Resource Ownership:**

`sToolName` is copied into the turn and released by `xllm_turn_reset`.

**Notes:**

- `XLLM_TOOL_CHOICE_NAMED` usually needs `sToolName`.
- Unsupported provider tool choices fail during request validation or call execution.

**Example Code:**

```c
xllm_turn_set_tool_choice(&turn, XLLM_TOOL_CHOICE_AUTO, NULL, false);
```

**Related APIs:**

- `xllm_turn_add_tool`

## Executor Setup APIs

### xllm_set_tool_executor

Sets a synchronous tool executor on a lightweight `xllm` object.

**Prototype:**

```c
XLLM_API int xllm_set_tool_executor(xllm *pLlm, const xllm_tool_executor *pExecutor);
```

**Parameters:**

| Parameter | Direction | Can Be `NULL` | Description |
| --- | --- | --- | --- |
| `pLlm` | input/output | no | Object created by `xllm_create`. |
| `pExecutor` | input | yes | Executor. Passing `NULL` clears the executor. |

**Return Value:**

- `XRT_NET_OK`: set successfully.
- `XRT_NET_ERROR`: `pLlm` is `NULL`.

**Resource Ownership:**

xllm copies the executor structure, but does not take ownership of `pExecutor->pCtx`.

**Related APIs:**

- `xllm_send_ex`

Parameters, return values, and ownership are similar to `xllm_set_tool_executor`; the callback returns `xfuture *`.

**Prototype:**


**Parameters:**

| Parameter | Direction | Can Be `NULL` | Description |
| --- | --- | --- | --- |
| `pSession` | input/output | no | Session object. |
| `pExecutor` | input | yes | Executor. Passing `NULL` clears it. |

**Return Value:**

- `XRT_NET_OK`: set successfully.
- `XRT_NET_ERROR`: `pSession` is `NULL`.

**Resource Ownership:**

The session copies the executor structure and does not take ownership of `pCtx`.

**Notes:**

After setup, `xllm_session_chat_ex` attempts automatic execution when it sees client tool calls.

## Tool Result Cleanup

### xllm_tool_exec_result_free

Frees internal resources of a tool execution result.

**Prototype:**

```c
XLLM_API void xllm_tool_exec_result_free(xllm_tool_exec_result *pResult);
```

**Parameters:**

| Parameter | Direction | Can Be `NULL` | Description |
| --- | --- | --- | --- |
| `pResult` | input/output | yes | Tool execution result. |

**Return Value:**

None.

**Resource Ownership:**

Releases parts and extension data inside `pResult`, but not the outer structure.

## Automatic Tool Loop

Automatic tool loop flow:

1. The host adds `XLLM_TOOL_CLIENT` tool definitions to the turn.
2. The host sets an executor on `xllm` or `xllm_session`.
3. The host calls `xllm_send_ex` or `xllm_session_chat_ex`.
4. If the model returns `XLLM_STATUS_TOOL_CALL_REQUIRED`, xllm looks up the matching tool definition.
5. xllm calls the sync or async executor.
6. xllm appends the tool result as a tool message and continues the next model call.
7. The loop stops when the model returns a final response, the tool is unavailable, execution fails, or the maximum number of rounds is reached.

**Boundaries:**

- xllm does not perform permission approval.
- xllm does not parse business parameters; it passes through `sArgumentsJson`.
- xllm does not guarantee tool idempotency. The host should handle retries and side effects.

## Example Code

```c
static char *dup_text(const char *s)
{
    size_t n;
    char *out;

    if (!s) {
        return NULL;
    }
    n = strlen(s);
    out = (char *)xrtCalloc(n + 1u, sizeof(char));
    if (!out) {
        return NULL;
    }
    memcpy(out, s, n);
    return out;
}

static int32 inspect_workspace(
    void *ctx,
    const xllm_tool_exec_request *req,
    xllm_tool_exec_result *result,
    xllm_error *err
) {
    (void)ctx;
    (void)err;

    if (!req || !result || !req->sToolId) {
        return XRT_NET_ERROR;
    }

    result->pParts = (xllm_content_part *)xrtCalloc(1u, sizeof(xllm_content_part));
    if (!result->pParts) {
        return XRT_NET_ERROR;
    }
    result->iPartCount = 1u;
    result->pParts[0].eKind = XLLM_PART_TEXT;
    result->pParts[0].as.tSource.eKind = XLLM_SOURCE_INLINE_TEXT;
    result->pParts[0].as.tSource.sMimeType = dup_text("text/plain");
    result->pParts[0].as.tSource.as.sText = dup_text("workspace_status=clean");
    if (!result->pParts[0].as.tSource.sMimeType ||
        !result->pParts[0].as.tSource.as.sText) {
        xllm_tool_exec_result_free(result);
        return XRT_NET_ERROR;
    }
    return XRT_NET_OK;
}

xllm_tool_executor executor;
memset(&executor, 0, sizeof(executor));
executor.pfnExecute = inspect_workspace;
xllm_session_set_tool_executor(session, &executor);
```

## Common Mistakes

| Problem | Common Cause | Fix |
| --- | --- | --- |
| Model returns a tool call but xllm does not execute it automatically | Executor is not set, or the tool is `XLLM_TOOL_PROVIDER`. | Use a client tool and set an executor. |
| Automatic loop stops at `tool_unavailable` | Tool call name cannot match a tool definition in the turn. | Confirm `sToolId` / `sWireName` match the model output. |
| Memory leak after tool execution | Executor-filled result was not cleaned. | Use xllm automatic loop, or call `xllm_tool_exec_result_free` manually. |
| Provider rejects tool choice | Provider does not support required/named/parallel choices. | Use `AUTO` or fall back based on provider capability. |
| Tool execution has dangerous side effects | xllm does not perform permission control. | Add approval, sandboxing, and audit in the host/xwork layer. |
