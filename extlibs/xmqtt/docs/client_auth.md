# MQTT 5 enhanced authentication (developing)

Select `XMQTT_MODULE_XMQTT_CLIENT_AUTH` and use `xmqttClientConnectAuth` with an
explicit Authentication Method in CONNECT. The base factory retains its explicit
unsupported result for enhanced auth. MQTT 3.1.1 cannot use AUTH. The implementation
follows [OASIS MQTT 5 sections 3.15 and 4.12](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html).
Authentication Method/Data are protocol fields; this API intentionally delegates
the agreed algorithm, credential generation and server-proof validation to the
application. The offline example uses fixed assertion tokens and provides no
cryptographic authentication. TLS, reconnect and durable sessions remain pending.

## Application decisions

The network worker owns parsing and the protocol sequence. Existing `Notify`
signals a nonblocking mailbox; call `xmqttClientTakeAuth` to take a unique ticket,
move it to an application thread, then respond without blocking the network worker.
The immutable message is accessed through `xmqttAuthMessage`/`xmqttMessagePacket`.
Do not retain borrowed views beyond the message/ticket lifetime. MessageRetain
allows a proof/challenge to outlive Client/Engine independently.

| Phase | Application action |
|---|---|
| `CHALLENGE` | Send AUTH reason `0x18`, original method, algorithm-specific data with `xmqttAuthRespond`; or reject |
| `VERIFY_CONNECT` | Validate the successful CONNACK's final proof, then `xmqttAuthComplete(true)` or reject |
| `VERIFY_REAUTH` | Validate AUTH success's final proof, then accept or reject |

Every AUTH and successful CONNACK must include exactly the original method,
including an explicitly empty method. Initial authentication ends in CONNACK;
server AUTH-success cannot replace it. A server cannot initiate reauthentication.
Abbreviated AUTH-success without a method is structurally decodable but invalid
in this exchange. Request Problem Information applies to Reason String/User
properties, without forbidding Method/Data. A failed CONNACK can reject setup
at any point. No client AUTH-success packet is generated by local verification.

The shared Ready Future remains pending until the application accepts final
initial proof. Queued application sends remain gated. A broker can coalesce
CONNACK and PUBLISH: the bounded message queue quarantines these publications,
TakeMessage returns empty until verification, while ACKs/keepalive progress.
Initial rejection never exposes these queued messages. During earlier AUTH rounds,
CONNECT Keep Alive also progresses. Multiple PINGREQs may be sent while CONNACK
is pending; the server cannot send PINGRESP before successful CONNACK. Its response
budget therefore starts at CONNACK, while the original setup deadline still bounds
the whole exchange. A Server Keep Alive override uses the last control-output
time; final-proof computation does not suspend heartbeat processing. On successful readiness,
Negotiated.AuthMethod borrows the retained CONNACK, not erased startup storage.

`xmqttClientReauthenticateAsync` accepts one AUTH `0x19` exchange on an already
verified connection. Its independent typed result contains Status, sum of AUTH
bytes accepted by TCP, final owned message and retained cause. Ordinary traffic
continues using prior authentication. A pending reauthentication makes graceful
Disconnect overloaded; explicit abortive Close still works. The old exchange stays reserved until its result/producer are detached under the
client gate; a competing admission cannot replace a completing operation. Other
packet types retain their existing flow/identifier/alias rules. Frame-boundary arbitration
finishes partial PUBLISH/PUBREL/PING/receive-ACK/AUTH before starting another
packet. No retransmission, reconnect or credential replay is inferred.

Tickets retain the actual Client through their final release. Release every
taken ticket before physical WaitFor/Destroy. A ticket can be answered only once;
stale/duplicate decisions fail. Its identity cannot accidentally target a reused
Client address. Retaining just the message keeps no Client/Engine reference.
Release without responding leaves the finite decision timeout active. Multiple
producers may race a response/decision while borrowing a stable ticket owner;
exactly one can commit. The caller must prevent Release racing its own API calls.

## Bounds, cancellation and erasure

Defaults: 32 server challenges, 1 MiB aggregate received AUTH/final CONNACK and
submitted AUTH bytes, 5 seconds per local decision. CONNECT uses MaxSetupBytes.
The original SetupTimeout, or finite reauthentication Timeout from function entry,
also bounds the whole exchange; no round/notification restarts it. Admission checks local deadlines before
committing a response/final decision, even when the IO timer owner is delayed.
A late decision returns ERROR, closing with typed TIMEOUT and its owned cause. Even before
reauthentication wire admission, timeout/cancellation ends the connection. Future
cancellation wakes the owner; retained cancellation dispatches from a completed
reauthentication cannot close a later exchange, whose own token is sampled. Raw cancel tokens are sampled on progress/deadline.

There is one mailbox ticket and one current AUTH output. Tickets, retained
messages and reauth result boxes use MaxObjects/MaxObjectBytes through actual
retirement. The optional state/method snapshot and AUTH output/native tails use
MaxPrivateBytes. Ordinary request quota saturation cannot prevent a bounded auth
response. Normal OVERLOADED/CLOSED leaves caller error and output/ticket state
unchanged; failed wire/result/Future reservations roll back. Retained old tickets
remain charged rather than allowing an unbounded challenge history.

Local rejection has `XMQTT_STATUS_AUTHENTICATION`; initial/whole/decision timeouts,
Future cancellation, server DISCONNECT, malformed/protocol/resource failures keep
their distinct typed outcomes. First error wins. After initial verification,
local rejection attempts a client-legal minimal DISCONNECT `0x80`; `0x87` is a
server-only DISCONNECT reason. Partial AUTH or other partial frames force abort.
Diagnostic drain retains its original finite deadline and physical ownership.

Encoded AUTH wire is erased only after its last caller/native reference. AUTH and
CONNACK message wire is erased on last release; consumed input tails, old input
buffers at growth and final authenticated input storage are erased as well.
CONNECT wire retires on accepted CONNACK, before application proof computation,
and is erased after its final native reference. Caller buffers, TLS/native
queues, kernel copies and application algorithm state are outside this guarantee.

## Cost and evidence boundary

The optional leaf shares the existing client/worker/quota; it creates no shared
runtime. Existing public client config/info/results retain their layouts. With
this feature compiled, Client has one extra optional pointer; a base-factory
instance allocates no auth sidecar. Without the feature, the private pointer and
auth implementation are absent. Auth instances allocate one state/method snapshot.

Each incoming challenge copies one immutable packet including property views and
allocates one ticket, both quota-charged. Each response preflights and encodes one
owned wire snapshot; native gathers retain it rather than copying the payload
again in this layer. Each reauth adds one Future/Promise/cancel producer and one
typed result box. Gate/quota locks, reference operations, packet validation,
UTF-8/property walks, notifications, posts, secure erasure and native queue work
are real costs. No zero-overhead, zero-allocation or broker-comparator claim is
made.

The benchmark measures real loopback CONNECT plus repeated two-round reauth with
nonblocking fixture-token decisions in Notify and condition-signalled Future
waits. It reports throughput and P50/P99/max latency; optional XRT heap counters
cover allocations in both client and local peer. Pool hits still count as block
allocations; these are not libc malloc-call counts, total process RSS, or OS/kernel
allocation measurements. There is no deliberate 1 ms
polling delay in its measured decision path. It excludes cryptographic work,
external broker behaviour, admission contention and fixed-arrival overload;
therefore it is a focused regression workload, not complete production acceptance.

See the [runnable example](../examples/auth/README.md). Protocol/OOM/lifetime tests
live in `tests/test_client_auth.c` and also compile as a single-header program.
External enhanced-auth broker interoperability, algorithm integration and native
long-duration production acceptance remain to be established.

Reproduce the independent byte peer on Windows (replace `-lws2_32` with
`-pthread -lm` on Linux):

```text
gcc -std=c11 -O2 -Wall -Wextra -Werror -Iinclude -Iextlibs/xmqtt/include extlibs/xmqtt/tests/interop/single_auth_probe.c -lws2_32 -o out/auth_probe.exe
python extlibs/xmqtt/tests/interop/run_auth_wire.py --probe out/auth_probe.exe --output out/auth-wire.json
```

It exercises 23 literal-byte scenarios: initial and reauth method/sequence errors,
server-only direction, abbreviated success, refusal, EOF, decision/whole timeouts,
local proof rejection, delayed offloaded challenges/final proofs across Keep Alive,
Request Problem Information, one-byte writes and a coalesced
publication, final proof and post-auth publication observations.

Stage evidence: [2026-11-09 validation and cost report](../tests/results/client-auth-20261109.json).
